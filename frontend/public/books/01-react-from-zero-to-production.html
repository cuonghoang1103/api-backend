About this book

Most React tutorials teach you to type. This one is built to make you able to predict — to look at a component and know what React will do with it before you press save.

There is a large, strange gap in how React gets taught. The introductory material is genuinely good and gets you to a working counter in ten minutes. The advanced material — reconciliation, concurrent rendering, the compiler — is also good, and assumes you already have a working model of the whole system. Between those two lies the part where people actually get stuck: the months where your code runs, mostly, and you cannot say why.

That gap is what this book is for. It is not a tour of the API. It is an attempt to give you one accurate mental model early, and then spend twenty-five chapters showing that the same model explains everything else — why your list does not re-render, why your effect fires twice, why memoisation did nothing, why the value in your callback is stale.

Who should read this

You can write JavaScript. You have seen a for loop and written a function. You may have already built something small in React and found it worked without you fully understanding why. That last sentence describes most people who ship React professionally, and it is a fine place to start from.

You do not need TypeScript — chapter 11 teaches it. You do not need to have used a build tool — chapter A does that. You do not need a computer science degree. Chapter 0 §0.7 gives you an honest checklist of what you do need, with a self-test, so you can find your gaps before they trip you rather than after.

How this book is organised

Chapter 0 is context: what React is, who built it and why, what it is combined with, what is made from it, and how the machine actually works. Read it once; it makes every later chapter cheaper to understand.

Then sixteen numbered chapters, each mapping to one module of the React track in Code Lab. That pairing is the core method of this book:

The chapter is the worked example. The exercises are the problem. There is fifty years of evidence in instructional research that people learning something genuinely new learn faster from studying a fully worked solution than from being thrown at a blank editor — and then learn to transfer that knowledge only when the guidance is gradually removed. So each chapter walks you through the reasoning in full, then fades the support, then hands you ten graded exercises with no support at all. Read the chapter, then go and fail at the exercises. Both halves are load-bearing.

Around those sixteen there are eight lettered chapters, and they exist because the exercise track has gaps. Three come before chapter 1: you cannot practise React without a machine that runs it, and a surprising number of people stall on CSS rather than on React. Five come after, covering what you will unavoidably need on a real project that the track does not reach — routing, server state, accessibility, security and deployment.

Why chapter G exists

I audited the existing course material before writing this book. Across all sixteen modules, front-end security appeared zero times — no XSS, no dangerouslySetInnerHTML, no discussion of where a token may be stored. That is not unusual for React curricula and it is not acceptable, because the default way people render user-supplied HTML in React is also the way they create a cross-site scripting hole. Chapter G is short and you should not skip it.

About the code

Every code listing in this book was executed before it went in. Not "checked" — executed. The JavaScript ran on Node 22.22; React is 19.2; the JSX compiler output in §0.6 came out of a real build, not from memory. Where I claim two things differ, there is a program somewhere that printed the difference and I looked at it.

This matters more than it sounds. The most common defect in programming books is not a typo — it is a confident sentence about behaviour that changed three versions ago. §0.6 contains an example of exactly that, still repeated in current material. Where I am uncertain, I say so in the text rather than rounding up to confidence.

You can learn React without knowing any of this. You will learn it faster, and misunderstand less of it, if you know it first.

By the end of this chapter you will be able to

  • Explain why React is a library, not a framework, and what that costs you

0.1 The problem React was built to solve

In 2011, Facebook had a specific and worsening engineering problem, and it was not performance. It was that nobody could keep the screen and the data in agreement.

To see it, take one small feature: an unread message count. It appears in the page title, in the navigation bar, in a badge on the chat icon, and in the chat panel itself. Four places. Now the user reads a message. In the style of the time, your job is to remember all four and update each one by hand:

This works. It also has a defect that grows faster than the codebase does. Every new place that displays the count means editing every existing function that changes the count. With four display sites and three mutation paths that is twelve relationships to maintain; add a fifth site and a fourth path and it is twenty. Miss one — one branch, one early return, one error path — and the screen now lies to the user. It does not crash. It does not log. It just shows a number that is wrong, and you find out from a support ticket.

Jordan Walke, an engineer at Facebook, went at this from an unusual direction. Facebook's PHP codebase had a library called XHP, which let engineers write HTML-like markup directly inside PHP as composable components. It was pleasant to use. Its limitation was that it rendered on the server: every interaction meant a round trip.

The question that produced React was, roughly: what if the client could do that too — and what if, instead of describing the changes, you just re-described the whole screen every time and let the machine work out the changes?

The inversion

Stop writing "when this happens, change that." Start writing "for this data, the screen looks like this." Then re-run it whenever the data changes, and make the computer diff the two descriptions.

0.2 Who made it, and what happened next

Walke's prototype was called F-Bolt, then renamed FaxJS. It was deployed on Facebook's News Feed in 2011 and adopted by Instagram in 2012 — which mattered, because Instagram was a separate product proving the idea was not welded to Facebook's codebase.

It was open-sourced at JSConf US on 29 May 2013, and the reception was bad. The objection was JSX: putting markup inside JavaScript violated the separation-of-concerns orthodoxy that a decade of web development had been built on. The counter-argument — that markup and the logic driving it are one concern, and separating them by file type only makes it look otherwise — took years to win.

The distinction that saves you most pain

0.6 How React actually works

Four steps stand between the JSX you type and a pixel changing. Almost every "why did it do that?" in this book is answered by knowing which step you are in.

Step 1 · JSX is not HTML, and it is not magic

JSX is syntax sugar. A compiler rewrites it into ordinary function calls before the browser ever sees it. Here is a real compilation, produced by running the compiler rather than from memory:

A correction you will need

You will read, in a great deal of current material, that "JSX compiles to React.createElement." That has not been the default since React 17 (2020). The modern transform imports jsx / jsxs from react/jsx-runtime, which is why you no longer have to write import React from 'react' at the top of every file. For comparison, the old transform produced this:

classic transform — React 16 and earlierjavascript
const el = React.createElement("button", { className: "btn", onClick: handleClick }, "Add ", item.name);

Both produce the same thing. Knowing which one you are looking at tells you the age of the code — and of the advice.

Whichever transform ran, the result is the same and it is the important part: a plain JavaScript object.

Step 2 · Render — build the tree

React calls your component function. It returns elements; some of those have a function as their type, so React calls those too, and keeps going until everything is reduced to host elements — div, button, span. The result is a tree of plain objects describing the entire screen.

Note what this means and hold on to it, because chapters 1, 3 and 4 all depend on it: your component function runs again, top to bottom, on every render. It is not setup code. Every variable declared inside it is created anew each time.

Step 3 · Reconcile — find the difference

React now holds two trees: the one it just built, and the one from last time. It walks them together looking for differences, and it does so under two rules that explain a surprising amount of React's behaviour:

  • Different type at the same position ⇒ destroy and rebuild. A <div> replaced by a <section> means the old subtree is thrown away, along with its DOM nodes and its state.
  • Same type ⇒ keep the node, update only the changed props.

For lists there is no position to trust, because items get inserted and removed. That is what key is for: it tells React which item is which across renders. Chapter 2 shows exactly what breaks when you use an array index as a key, and it is worse than most people expect.

Step 4 · Commit — touch the DOM

Only now does React talk to the browser, and only about the differences it found. One text node changes, one class is added. The other 400 nodes on the page are not touched.

The part everyone gets backwards

"React is fast because of the virtual DOM" is not quite true, and believing it will mislead you in chapter 7. Diffing two trees is extra work — a hand-written DOM update is always faster in isolation. What the virtual DOM buys is that it is fast enough, automatically, without you maintaining Listing 0.1 by hand. React trades a little performance for a large amount of correctness. Once you see it as a correctness tool, its design stops seeming strange.

Two refinements you will meet later. Fiber (2017) restructured this so rendering can be paused, resumed and abandoned — which is what makes React 18's concurrent features possible. The React Compiler (1.0, 2025) analyses your components at build time and inserts memoisation you would otherwise write by hand. Chapter 7 covers both, after you can measure whether they helped.

Self-test

Six questions. Answer honestly before opening each — the point is to locate your gaps while they are cheap to fix.

1 · After const b = a where a is an array, how many arrays exist?

One. a and b are two names for the same array. b.push(1) changes what a sees. If this surprised you, §1.1 and §1.5 are the most valuable pages in this book for you.

2 · What does [1,2,3].map(n => n * 2) return, and what happens to the original?

[2,4,6], and the original is unchanged — map always builds a new array. If you were unsure, read §1.4 slowly.

3 · What is the difference between null and undefined?

undefined means "no value was ever set here"; null means "a value was deliberately set to nothing". APIs and databases send null. It matters because destructuring defaults fire on undefined only — §1.2 and §1.7.

4 · What does await do to the function it is written in?

It pauses that function until the promise settles, and returns control to the caller meanwhile. It does not block the page. If this is fuzzy, §1.9 and chapter C.

5 · In CSS, what does display: flex do to an element's children?

Lays them out along one axis, with justify-content controlling that axis and align-items the cross axis. If you cannot picture it, start at chapter B, not chapter 1.

6 · What does npm install actually do?

Reads package.json, downloads those packages and their dependencies into node_modules, and records exact resolved versions in package-lock.json. Chapter A.

How to read your score
  • All six — go straight to chapter 1.
  • Missed 5 or 6 — read chapters A and B first. You will save weeks.
  • Missed 1, 2, 3 or 4 — chapter 1 is written precisely for you. Read it twice and do the exercises.

0.8 How to read this book

  1. Read the chapter first, with the code in front of you. Type the listings out; do not paste them. Typing them is slow, and the slowness is where the noticing happens.
  2. Answer the checkpoints before opening them. Retrieving an answer from memory builds recall far better than recognising a correct one. Being wrong here is useful and free.
  3. Then do all ten exercises. This is not optional practice — it is the half of the method where the learning transfers. The chapter alone produces the feeling of understanding without the ability.
  4. When something breaks, ask which of the four steps in §0.6 you are in. Is the description wrong, or is React not noticing a change? Almost every React bug sorts into one of those two, and knowing which halves the search.

A.1 Node, and why not from the website

React tooling runs on Node. Installing it from nodejs.org works and then causes a problem six months later, when one project needs Node 20 and another needs 22. A version manager makes that a one-line change instead of a reinstall.

npm comes with Node and is fine. pnpm is faster and uses far less disk because it stores one copy of each package globally and links it — worth switching to once you have more than two projects.

A.2 Creating the project

Vite for learning React; Next.js (npx create-next-app@latest) when you need routing, server rendering and Server Components (chapters 10 and D). This book uses Vite until chapter 10 because it keeps the machinery visible.

The DOM, Events and the Event Loop

React abstracts the DOM. Abstractions leak, and this is the one that leaks at the worst moments.

C.1 The DOM, and React's relationship to it

The browser parses HTML into a tree of objects — the DOM. Changing a node changes the screen. Reading a measurement from it (getBoundingClientRect, offsetHeight) forces the browser to finish any pending layout work first, which is why doing it in a loop is slow.

React's contribution is that you stop doing this (§0.1). You describe the result; React works out the minimum set of DOM operations. So in a React application you touch the DOM directly in exactly three situations: measuring (§4.9), focusing, and handing a node to a library that owns its own rendering. All three go through useRef (§5.2).

C.2 Events bubble

A click on a button fires on the button, then its parent, then its parent, up to document. This is bubbling, and it is why event delegation works — one listener on a list can handle clicks on a thousand rows.

It is also the cause of a bug you will meet in your first week:

The menu closes immediately
<button onClick={() => setOpen(true)}>Menu</button>

useEffect(() => {
  const close = () => setOpen(false);
  document.addEventListener('click', close);
  return () => document.removeEventListener('click', close);
}, []);
The opening click bubbles up to document in the same tick and closes it again. The menu appears to do nothing.
Ask where the click landed

e.stopPropagation() fixes your component by breaking the page for everyone else's — analytics, a parent's row-click handler, another dropdown. Reach for it only when you know exactly what is above you, which in a component library you never do.

C.3 React's synthetic events

React wraps native events in a SyntheticEvent with the same API, normalised across browsers. Three practical differences:

  • e.target vs e.currentTarget. target is what was actually clicked — possibly an icon inside your button. currentTarget is the element the handler is attached to. In TypeScript, currentTarget is also the one that is correctly typed.
  • Passive listeners. React attaches touchstart, touchmove and wheel as passive for scroll performance, so e.preventDefault() in those handlers does nothing. Attach a non-passive native listener in an effect when you genuinely need to block scrolling.
  • Some events do not exist in React. resize, scroll on window, online/offline, and the storage event are window-level — add them yourself in an effect with cleanup (§4.2, Listing 4.2).

C.4 The event loop

JavaScript runs on one thread. Everything — your code, event handlers, React's rendering, the browser's layout and paint — takes turns on it. That single fact explains three things that otherwise seem unrelated.

  1. A long loop freezes the page. Sorting a million items blocks the one thread, so nothing renders, no click is handled, and the tab appears hung. This is what useTransition and useDeferredValue (§7.5) exist to work around, and why heavy work belongs in a Web Worker.
  2. await does not block the page. It suspends your function and returns the thread. When the promise settles, the rest of your function is queued as a microtask. Meanwhile clicks and rendering continue normally.
  3. Responses arrive out of order. Nothing guarantees that the first request queued is the first to resume — which is the entire content of §4.5's race condition, and now you know the mechanism underneath it.
One frame is 16.7 milliseconds

At 60Hz the browser wants to paint every 16.7ms. Any single task longer than that costs a dropped frame, which the user perceives as jank. It is the same 16ms threshold as §7.2's Profiler warning and §14.5's animation budget — three chapters, one number, one thread.

1.1 The one fact this whole chapter rests on

Here is the single sentence that makes the rest of this book cohere. Read it slowly, because almost every confusing thing React does is a consequence of it:

The fact

When something changes, React runs your component function again from the top, gets a fresh description of the UI, and compares it to the previous one to work out the smallest set of real DOM changes to make.

Two words in that sentence do the damage. The first is again: your function body is not setup code that runs once, it runs on every render, and every variable inside it is created fresh each time. The second is compares: React has to decide, quickly, whether a given piece of data changed.

That second word is where the language features come in. React cannot afford to walk through every object in your state comparing every field — on a large tree that work would cost more than the re-render it was meant to avoid. So it does the cheap thing instead. It compares references: is this the same object in memory as last time?

1.5 Spread and rest, and the copy that is not deep

... means two opposite things depending on which side of the = it appears. Spreading unpacks a value into a new one. Rest collects leftovers into a bag. The syntax is identical; only the position differs.

2.1 A component is a function that returns a description

That is the entire definition. A React component is a JavaScript function that takes one argument — an object of props — and returns a description of what should be on screen.

Two rules, both enforced by React and both worth understanding rather than memorising:

  • The name must start with a capital letter. This is not style. In JSX, <greeting /> compiles to the string "greeting", meaning an HTML element; <Greeting /> compiles to the variable Greeting. Lowercase your component and React looks for an HTML tag by that name, finds nothing, and renders nothing.
  • It must be pure. Same props in, same JSX out, no side effects on the way. Chapter 1 §1.10 argued this for reducers; it is the same argument, and §0.6 is the reason: React may call your function more than once, at a time of its choosing, and throw the result away.

Never put a raw number on the left of && in JSX. Coerce it to a boolean first — count > 0 &&, list.length > 0 &&, or Boolean(x) &&. An empty array's .length is 0, which is why {items.length && …} renders a lonely zero on exactly the empty state you were trying to hide.

The rules for keys
  • Use a stable id that comes with the data — a database id, a slug, a UUID.
  • Unique among siblings, not globally. Two different lists may both use key 1.
  • Never Math.random() or Date.now(). A key that changes every render tells React the item is brand new every time, so it destroys and rebuilds the DOM node — losing focus, scroll position and state on every keystroke.
  • Index is acceptable only if all three hold: the list never reorders, never has items inserted or removed except at the end, and the items have no state of their own. If you cannot promise all three today and after the next feature, do not use it.
  • The key goes on the outermost element returned by the map, not inside the component.
A use for the same mechanism, in reverse

Because a changed key means "this is a different thing", you can use it deliberately to reset a component: <ProfileForm key={userId} … /> throws away all the form's internal state whenever the user being edited changes. That is idiomatic, and much cleaner than an effect that clears fields.

3.1 Why a plain variable does not work

Start from the failure. Here is a counter written with an ordinary variable:

It fails for two separate reasons, and you need both:

  1. React does not know anything changed. Assigning to a local variable is invisible from outside the function, so nothing triggers a re-render (§0.6).
  2. Even if something did re-render, n would be 0 again. Recall §1.1: the function runs from the top every time, so let n = 0 runs again and wipes the value.

useState solves exactly these two problems and nothing else. It gives you a value that survives re-renders, and a setter that tells React to schedule one.

Where does the value actually live?

Not in your function — it cannot, per reason 2 above. React keeps it, in a slot attached to this component instance in the tree. Your function is handed a copy on the way in. That is the whole idea of §1.8's closures made concrete, and it is why the state of two <Counter /> elements is independent: two instances, two slots.

3.2 The rules of hooks, and the reason for them

Two rules, and every React codebase enforces them with a linter:

  1. Only call hooks at the top level — never inside a condition, loop, or nested function.
  2. Only call hooks from a component or another hook — never from a plain function.

Rule 1 looks arbitrary until you know how React stores the value. It does not use the name n — it cannot, your function has already been compiled and the name is gone. It uses call order. First useState in this component gets slot 0, second gets slot 1, and so on, every render, in the same order.

So the rule is not bureaucracy. It is the precondition that makes slot-by-position work at all. The fix is always the same shape — hooks unconditionally at the top, conditions after:

3.3 The value in this render is a snapshot

This is the single most disorienting fact about useState, and it is a direct consequence of §1.8. Calling the setter does not change the variable you are currently holding. It asks React for a new render, in which your function runs again and gets a new value.

n is a const captured by the closure that React created when it ran this render. Nothing can reassign it, because nothing is trying to — the next value arrives in a different closure, from the next render. The variable is not "not updated yet". It belongs to a render that has already finished.

The sentence to memorise

Each render has its own props, its own state, and its own event handlers. They are frozen together. Once you accept that, "why is my value stale?" answers itself: you are reading a variable from the render the handler was created in.

When the setter is handed a function, React puts it in a queue and, at render time, runs the queue in order over the pending value. That is why the functional form is immune to staleness: it never reads a captured variable at all.

The rule

If the next state depends on the current state, use the functional form. setN(c => c + 1), setItems(prev => [...prev, x]), setOpen(o => !o). If it does not — setName(e.target.value), setUser(fetched) — the direct form is fine and reads better. Exercise 8, "Fixing a Stale Scoreboard Under Batched Updates", is this rule and nothing else.

3.5 Batching, and what React 18 changed

In Figure 3.1, each handler called the setter three times — and each produced exactly one re-render. React collects the updates triggered by one piece of work and applies them together. Without that, a handler updating four pieces of state would paint four times and you would see it flicker.

Until React 17 this only worked inside React's own event handlers. Updates in a setTimeout, a fetch callback, or after an await fell outside and each caused its own render. React 18 made batching automatic — it applies everywhere:

3.7 Lazy initial state

The argument to useState is only used on the first render. But it is evaluated on every one, because that is how function arguments work — JavaScript computes the value before the call, and React discards it on renders 2, 3, 4…

Pass a function and React calls it only when it actually needs an initial value. Use this whenever computing the initial value costs something — parsing localStorage, seeding a board, building a large map. For useState(0) or useState('') it makes no difference and adds noise; do not bother.

3.8 What belongs in state

The most common cause of buggy React is not a wrong hook — it is too much state. Every extra piece is another thing that can fall out of step with the others.

Ask one question of each candidate: can I compute this from something I already have? If yes, it is not state.

3.9 Lifting state up

When two components need the same value, neither can own it. Move it to their nearest common parent and pass it back down — the value as a prop, the setter as a callback (§2.3).

An input whose value comes from state and whose changes go through a handler is called a controlled component. React owns the value; the DOM merely displays it. That is what lets you validate as the user types, format on the fly, and enforce a maximum length — and it is why exercise 2's character budget is possible at all.

The warning you will see

"A component is changing an uncontrolled input to be controlled." It means the value prop started as undefined and later became a string. Initialise with useState(''), never useState(), and never value={form.email} where email may be missing — value={form.email ?? ''} (§1.7).

Chapter 1 §1.10 had you write a pure reducer. useReducer is the hook that runs one. Reach for it when three signs appear together: several pieces of state that change as a unit, updates that depend on the previous value, and the same update logic scattered across many handlers.

Three things you get, and they are the reason to bother:

  • The logic is testable without React. cartReducer is a plain function — call it with a state and an action and assert on the result. No rendering, no DOM.
  • Every transition is in one place. To learn what can happen to the cart you read one function, not eleven handlers.
  • The reducer always receives the current state. It has the guarantee of §3.4's functional updater built in, for free.

4.3 The exact order

Guessing at this is the source of a lot of confusion, so here is the real sequence, printed by a component that logs each step. It rendered with id=1, updated to id=2, then unmounted:

  1. Effects run after the render is committed to the screen, not during it. This is why you cannot read a DOM measurement during render — the node is not there yet — and why §4.10 exists.
  2. On an update, cleanup runs before the new effect. React does not "update" an effect; it tears the old one down and sets a new one up. Every re-run is a full replacement.
  3. Cleanup runs on unmount too. Same function, same guarantee.
The mental model that makes effects easy

Stop thinking "on mount" and "on update". Think: for these dependency values, this connection should exist. When the values change, React disconnects the old one and connects a new one. Written that way, the cleanup is not an afterthought — it is half of the definition, and an effect without one is a definition with a hole in it.

4.4 The dependency array

The array is not a scheduling preference. It is a claim: "this effect uses these values and no others." Get the claim wrong in either direction and you get a distinct bug.

Too few — a stale closure
useEffect(() => {
  const id = setInterval(
    () => setN(n + 1), 1000
  );
  return () => clearInterval(id);
}, []);            // lies: it uses `n`
The effect captured n from the first render and never re-ran, so it sets 0+1 forever. The counter reaches 1 and stops. §1.8 and §3.4 predicted this exactly.
Remove the dependency instead
useEffect(() => {
  const id = setInterval(
    () => setN(c => c + 1), 1000
  );
  return () => clearInterval(id);
}, []);            // honest: uses no `n`
The functional updater reads nothing from the render, so the claim becomes true and the interval can safely live for the component's whole life.

This is the most important section in the chapter, and possibly in the book so far, because the bug is invisible in development, common in production, and shows one person another person's data.

5.1 A custom hook shares logic, never state

A custom hook is a function whose name begins with use and which calls other hooks. That is the entire specification. There is no registration, no base class, no API — the naming convention exists so the linter can apply §3.2's rules to it.

Now the point people get wrong, so here it is measured. Two components, one hook, click only the first:

Every call to a hook creates its own independent state, exactly as if you had written the useState line inline. This follows directly from §3.2: hooks are stored per component instance, by call order. A custom hook is inlined into whoever calls it.

If you want shared state

You need something outside the components: lift the state to a common parent (§3.9), use Context (chapter 6), or an external store (§5.9). A custom hook will never do it, no matter how it is written.

When to extract one

The honest test is not "is this reusable?" but "does this component contain machinery that is not about what it displays?" That last line is the entire character of useRef. It is a mutable box React hands back unchanged on every render. Writing to .current is invisible to React — which is a bug if the user should see the value, and exactly right if they should not.

  • Legitimate: a timer id, the previous value of a prop, a DOM node, a "have I already done this" flag, the latest version of a callback.
  • Not legitimate: anything rendered. If it appears in your JSX, it is state.

5.4 The latest-ref pattern

A real problem with a tidy solution. You want an event listener that calls a fresh handler, but you do not want to add and remove the listener on every render.

Re-subscribes constantly
useEffect(() => {
  window.addEventListener('resize', handler);
  return () => window
    .removeEventListener('resize', handler);
}, [handler]);
// handler is a new function each render,
// so this tears down and re-adds every time
Correct, and wasteful. With a scroll or mousemove listener it is also a performance problem.
Subscribe once, always current
const latest = useRef(handler);
useEffect(() => { latest.current = handler; });

useEffect(() => {
  const fn = e => latest.current(e);
  window.addEventListener('resize', fn);
  return () => window
    .removeEventListener('resize', fn);
}, []);            // honestly empty
The subscription reads the handler through a box. The box is stable; its contents are fresh. §4.4's dependency claim is now true.

The latest-ref pattern deliberately breaks the rule from §4.4 that dependencies must be honest — it is honest only because the ref makes the value invisible to the effect. That is fine for a subscription that should outlive renders, and wrong as a general way to silence the linter.

7.1 The cascade

One rule produces most React performance questions: when a component re-renders, all of its children re-render too — whether or not their props changed.

Before you reach for a fix, be clear about what a re-render costs. It is not a DOM update: React re-runs the function, builds new elements, diffs them, and — finding nothing different — touches the DOM not at all (§0.6). For a few dozen simple components that is well under a millisecond, which is why a re-render is not a bug.

It becomes a problem in three specific situations, and if you are not in one of them there is nothing to fix:

  1. The subtree is large — hundreds or thousands of nodes.
  2. A child does real work on each render — sorting, formatting dates, rendering a chart.
  3. The re-render happens very often — on every keystroke, on every mouse move, sixty times a second.

Exercise 1 asks you to trace a cascade before changing anything, which is the correct order and the one people skip.

7.2 Measure first

Guessing which component is slow is unreliable in a way that is easy to demonstrate and hard to accept: the component that looks heavy is usually cheap, and the cost is in something you would not have suspected.

memo wraps a component and skips the re-render when its props are shallowly equal to last time. Figure 7.1 showed it working. Now here is the version that ships in most codebases:

An inline arrow is a new function object on every render (§1.1). memo compares props with Object.is, sees a different function, and concludes the props changed. The component is now wrapped in machinery that costs a comparison and saves nothing — strictly worse than not having it.

The same trap catches object and array props: style={{ margin: 8 }}, items={[]}, config={{ … }}. All fresh references, all defeat memo.

7.4 Two fixes that need no memoisation

Before memoising, try changing the shape of the tree. Both of these are structural, permanent, and cannot go stale.

Move the state down

If a piece of state is used by one small part of a large component, the large component re-renders for it. Push the state into the small part and the cascade disappears:

State at the top
function Page() {
  const [q, setQ] = useState('');
  return (
    <>
      <input value={q}
        onChange={e => setQ(e.target.value)} />
      <HugeReport />      {/* repaints per keystroke */}
    </>
  );
}
Every character typed re-renders the entire report, which does not use q at all.
State beside its input
function SearchBox() {
  const [q, setQ] = useState('');
  return <input value={q}
    onChange={e => setQ(e.target.value)} />;
}

function Page() {
  return <><SearchBox /><HugeReport /></>;
}
Page no longer has state, so typing re-renders only SearchBox.

7.6 The React Compiler

React Compiler reached 1.0 in 2025. It analyses your components at build time and inserts memoisation automatically — the useMemo, useCallback and memo you would otherwise write by hand, placed correctly and kept in step with the code.

What that changes, in practice:

  • Write fewer of them. On a compiled codebase, hand memoisation is mostly redundant, and redundant memoisation is not free.

  • Measure before and after. The compiler is not magic; it removes a chore, not the need to profile.

8.2 The URL is state you already have

Filters, sort order, page number, the open tab — the instinct is useState. It is the wrong instinct, and the reason is not performance:

Filters in component state
const [category, setCategory] = useState('all');

Filters in the URL

Shareable, bookmarkable, survives refresh, and Back works — because the browser has been managing exactly this kind of state since 1993.
The test for where state belongs

"If I sent this URL to a colleague, should they see what I see?" Yes → the URL. No → component state. A product filter passes; a half-typed comment does not.

8.3 Guards that do not lose the destination

A guard is an ordinary component that either renders its children or redirects. The part people leave out is remembering where the user was trying to go:

8.5 Code splitting

8.6 The API client

Scattering fetch calls through components means the base URL, the auth header, error shape and refresh logic are all duplicated and all slightly different. One module fixes that.

Why it matters: a dashboard mounts and fires six requests at once. The token has expired, so all six come back 401. Without the shared promise, all six call the refresh endpoint simultaneously — and on a backend that rotates refresh tokens, five of those are now using a token the first one just invalidated, so the user is logged out. The ??= makes every caller after the first await the same in-flight promise.

Retry exactly once

If the retried request also returns 401, stop and sign the user out. A loop of refresh-and-retry against a genuinely dead session is an infinite loop that hammers your own API — the §1.9 warning, at a larger scale.

Chapter Twelve

Advanced State Management

Three good libraries with genuinely different philosophies. The skill is choosing, not learning all three.

By the end of this chapter you will be able to
  • Say when Context has stopped being the right shape, from symptoms rather than opinion
  • Write a Redux Toolkit slice, an async thunk, and an entity adapter
  • Write a Zustand store with selectors, persistence and DevTools
  • Model derived state as Jotai atoms, and use atom families
  • Choose between the three for a specific application, and defend the choice

12.1 When Context is no longer enough

Chapter 6 measured the limit precisely: any change to a context value re-renders every consumer, and memo cannot stop it. Splitting state from dispatch fixes the common case. Three symptoms say you have outgrown even that:

  1. Consumers want different slices at different rates. One widget updates per second, twenty do not, and all twenty repaint.
  2. Provider nesting has become a wall. Eight providers wrapped around <App />, each split into state and dispatch.
  3. You need state outside React. Read it from an event handler in a non-React module, or write to it from a WebSocket callback.

The common answer to all three is an external store: state that lives outside the component tree, which components subscribe to by slice. §5.8's useSyncExternalStore is the primitive; these libraries are what people build on top of it.

Check this first

Most "we need a state library" moments are actually server state in the wrong place (§0.4). If the thing you are trying to share is a cached copy of something your API owns — products, users, orders — no client store will make it pleasant. TanStack Query (chapter E) is the right tool, and reaching for Redux instead is how applications end up with three hundred lines of reducer that reimplement caching badly.

12.2 Redux Toolkit

Redux's reputation for ceremony comes from the pre-2019 era of hand-written action types and constants. Redux Toolkit is the official modern package and removes essentially all of it.

Choose Redux Toolkit when: the team is large, you want one enforced way to change state, the time-travel debugger will genuinely be used, or you have complex normalised data with relationships. Against: the most boilerplate of the three, and a store plus provider plus typed hooks before the first line of feature code.

12.3 Zustand

The opposite philosophy: a hook that is the store. No provider, no context, no actions module.

And the reason it exists — selector subscriptions, which is precisely what Context cannot do:

Choose Zustand when: you want a store today with almost no setup, you need to read or write state outside React, or per-slice subscriptions are the point. It is the default recommendation for most applications in 2026. Against: fewer guardrails — nothing stops five different shapes of store appearing across a large team.

12.4 Jotai

A third model: state as many tiny independent atoms, composed into derived atoms. It is React's useState generalised to be global.

Choose Jotai when: your state is naturally many small independent values with a lot of derivation between them, or you want per-entity state without inventing keys. Against: a genuinely different mental model, and atoms scattered across files can be harder to trace than one store object.

13.1 The problem every pattern here answers

A component starts with two props. A year later:

The name for this is prop explosion, and its cause is always the same: the component is trying to anticipate every use rather than letting callers assemble what they need. Every pattern in this chapter is a different way of handing composition back to the caller.

13.2 Compound components

Chapter 6 built an accordion this way. Here is the pattern stated generally: a parent owns state, children read it through context (§6.6), and the caller assembles the pieces.

Use it when the pieces have a natural hierarchy and callers will want to vary the arrangement: tabs, accordions, menus, dialogs, tables, form fields. Do not use it for a component with one job and no parts.

13.3 Polymorphic components

A button that is sometimes a link. The naive fix is isLink and then isExternal and then as-shaped chaos. The pattern is one prop that chooses the element:

Polymorphism is where accessibility quietly breaks

A <div> styled as a button is not a button. It is not focusable, Enter and Space do nothing, and a screen reader announces nothing. If as can produce a non-interactive element, you must add role="button", tabIndex={0} and keyboard handlers — or refuse the value. Prefer refusing: a real <button> or <a> gives you all of that for free, which is exercise 3's actual lesson. Chapter F goes further.

The division that has settled: hooks share behaviour, render props and children share rendering control. A hook cannot decide what a caller draws; a render prop cannot be composed with three others without nesting three levels deep.

The related structural pattern is container / presenter — one component fetches and computes, another takes plain props and renders. That is exercise 8, and its real payoff is testing: the presenter has no network, no context and no hooks, so it can be tested with nothing but props (chapter 9).

13.5 Controlled and uncontrolled, from one component

Most callers want a component that manages its own state. Some need to control it from outside. Supporting both is a small, well-defined pattern:

If value starts as undefined and later becomes a string, the component changes from uncontrolled to controlled mid-life and React warns about it (§3.9). Decide at mount and stay: useRef(isControlled) in development plus a warning if it ever differs is a kindness to whoever uses the component next.

14.6 Reduced motion is not optional

For people with vestibular disorders, large motion — parallax, sliding panels, scaling transitions — causes real nausea and dizziness. This is not a preference setting; it is an accessibility requirement, and the operating system already knows the answer.

Three questions before you animate anything
  1. What does this explain? Where something came from, that it was removed, that it is loading. If the answer is "it looks nice", cut it.
  2. How often will it be seen? A charming 600ms flourish becomes an obstacle the fortieth time. Interface motion belongs in the 150–250ms range.
  3. Does it survive reduced motion? If turning off movement breaks comprehension, the information was only in the movement — fix that first.

14.7 Checkpoint

Why can React not animate an element being removed on its own?

It unmounts the node immediately, so there is nothing left to animate. AnimatePresence keeps it mounted until the exit animation completes. See §14.3.

Almost certainly key={index}. Identity changes as the list re-orders, so Framer Motion cannot track an item from its old position to its new one. Use a stable id (§2.6). See §14.3.

Why use a motion value instead of state for a drag?

State would re-render on every pointer move — sixty times a second. A motion value lives outside the render cycle and writes straight to the DOM. See §14.4.

Why animate scale rather than width?

transform and opacity are handled by the compositor; width forces a full layout recalculation every frame. See §14.5.

What should useReducedMotion change, and what should it keep?

Remove movement — slides, parallax, large scale changes. Keep a short fade, so the user still perceives that something appeared. See §14.6.

Profile a production build

Development React is several times slower and StrictMode double-renders everything (§4.7). Numbers from a dev build tell you which component is relatively expensive; they never tell you whether it is a problem.

16.2 Three bugs and how they present

The state mutation

Symptom: the data is right in DevTools and wrong on screen, or a change appears late and in the wrong place. Cause: something was mutated instead of replaced — §3.6, measured there as a display showing 1 while the array held 2.

The memory leak

Symptom: a dashboard is fine for ten minutes and unusable after an hour. Cause: something subscribed and never unsubscribed — the cleanup that §4.7's double mount was designed to expose.

The request storm

Symptom: the network panel shows fifty requests where you expected one. Three usual causes, all covered earlier: an effect with a wrong dependency array firing repeatedly (§4.4); each row in a list fetching its own detail, the N+1 pattern; or requests running in series that should have been Promise.all (§10.4).

The fix for the second is almost always a batch endpoint or a shared cache — which is what chapter E's TanStack Query gives you by deduplicating identical in-flight requests automatically.

16.3 Error tracking

An error boundary (§8.4) stops a white page. It does not tell you the error happened. For that you need a reporter, and the difference between a useful report and a useless one is the context you attach.

  • (1) release is what lets you say "this started in v2.4.1", and what makes source maps resolve. Without it a stack trace is minified nonsense.
  • (2) Sample performance traces. Sending all of them from a busy site is expensive and tells you nothing more.
  • (3) Scrub before sending. URLs carry tokens, form bodies carry passwords, and an error report is a place data leaks into a third party without anyone deciding to send it.
  • (4) Identify by id. Enough to see how many people were affected and to correlate with a support ticket; not enough to be a privacy incident.

Without source maps the stack is a.b is not a function at chunk-4f2.js:1:88213. Upload them to the error tracker at build time — and make sure they are not deployed publicly, or you have published your entire source to anyone who opens the network tab.

A debugging order that works
  1. Reproduce it. A bug you cannot trigger on demand cannot be verified as fixed.

React protects you by default: everything interpolated into JSX is escaped.

The end of the book

Twenty-five chapters, one hundred and sixty graded exercises. If you have worked the exercises rather than only read the chapters, you can now build a React application, reason about why it behaves as it does, test it, secure it and ship it.

The single most useful habit to carry out of here is the one this book was written with: when you are not sure how something behaves, write six lines that print the answer. Every measured claim in these chapters — the index-key bug moving a tick to the wrong row, three setState calls incrementing once, a slow response showing another user's data — came from a program that took a few minutes to write. That habit is worth more than any pattern in the book.
