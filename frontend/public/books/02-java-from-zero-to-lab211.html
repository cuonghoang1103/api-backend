About this book

LAB211 does not fail people because Java is hard. It fails people because assignment 54 is twenty-five times longer than assignment 1, and nothing in between teaches you how to hold that much program in your head.

Look at the shape of the course. It opens with a 21-line exercise — read some numbers, add them up. It ends with a 500-line vehicle management system: abstract classes, interfaces, one collection holding several types, a menu loop, file persistence, and every input validated. Between those two points the line count grows by a factor of twenty-five, and the difficulty grows by considerably more than that.

Almost everyone can write assignment 1. Most people can write assignment 30. The wall is somewhere around assignment 44, and what fails there is never Java syntax — it is structure. A 500-line program written the way a 50-line program is written becomes unreadable to its own author in about two days.

So this book teaches two things at once. The language, from the beginning, assuming nothing. And, from chapter 8 onwards, the small number of structural ideas that make a large program stay manageable: objects, the four pillars, a validator that lives in one place, and a separation between what your program is and how it talks to the user.

Who should read this

Someone who has never written a line of code, and someone stuck on assignment 44, are both in the right place — they simply start at different chapters. Chapter 0 has a self-test that tells you which.

You do not need to have taken PRF192 or any prior course. You do not need to have installed anything yet; chapter 1 does that.

How this book is organised

Five parts, and the shape of them is the argument of the book:

  • Part 0 (ch. 0–1) — what LAB211 actually asks for, and getting Java running.
  • Part I (ch. 2–7) — the language: variables, input and output, decisions, loops, methods, arrays, strings. Enough to write the first thirty assignments.
  • Part II (ch. 8–13) — object-oriented programming, one pillar at a time, then all four working together. This is the longest part and the reason the book exists.
  • Part III (ch. 14–17) — collections, sorting and searching, files, exceptions.
  • Part IV (ch. 18–21) — validation, structuring a program with MVC, the menu loop, and a complete 500-line assignment written from an empty folder.

Every chapter ends with the assignments from the real course that it unlocks, linked to Code Lab. There are fifty-four of them; by the last chapter every one has been covered.

About the code

Every listing here was compiled and executed before it went in — on JDK 25, and checked against 17 and 21, which is what FPT University machines run. Where the book claims two things behave differently, a program printed the difference and I read the output. Where I show something failing, it really failed.

A word about copying

Solutions to these assignments are all over the internet. Copying one gets you a mark and leaves you unable to write assignment 45, then unable to answer a single question in an interview about the code with your name on it. The assignments are not the point; they are the measurement. This book is written to make you able to produce the solution, which is the only version of passing that is worth anything.

0.1 The shape of the course

LAB211 is fifty-four assignments, ordered by lines of code. That ordering is unusually honest, because line count turns out to be a good proxy for the thing that actually gets harder.

The jump that matters is between bands 3 and 4, and it is not a jump in Java. Assignment 47 is 150 lines you can hold in your head. Nothing in bands 1 to 3 teaches you how to do that, which is why the wall arrives so abruptly.

The honest summary

Bands 1–3 test whether you can write Java. Band 4 tests whether you can design a program. They are different skills, and only one of them is taught by doing more of band 2.

0.2 Reading a long-assignment brief

Here is the actual text of J1.L.P0013 — the 500-line vehicle management assignment, the last one in the course:

  1. "Classes, abstract classes, Interfaces" — you are being marked on OOP design, explicitly. Chapters 8–13.
  2. "Use only one collection" — two lists, one of cars and one of motorbikes, is a fail. One List<Vehicle> holding both is the whole point, and it only works because of polymorphism. Chapter 11.

Also worth noticing: the brief budgets 50 LOC per function. That is a hint about granularity. If your "add new vehicle" is 200 lines, you have put four jobs in one method.

"Use only one collection to store animals"

Animals. In the vehicle assignment. The brief was adapted from another one and the word survived. You will meet this in real briefs too, and the skill is the same: read for intent, implement what is clearly meant, and if genuinely ambiguous, ask — do not guess silently.

0.4 Where should you start?

Six questions. Answer honestly — the point is to find the right chapter, not to score well.

1 · What is the difference between int x = 5; and String s = "5";?

One holds a number the computer can do arithmetic with; the other holds text. 5 + 5 is 10; "5" + "5" is "55". If that is new, start at chapter 2.

2 · What does scanner.nextInt() leave behind, and why does it break the next nextLine()?

It reads the number and leaves the newline in the buffer, so the following nextLine() returns an empty string instantly. It is the single most common bug in the first thirty assignments. If this is new, start at chapter 3.

3 · Write the signature of a method that takes an array of int and returns the largest.

public static int max(int[] a). If you had to think hard, read chapters 5 and 6.

4 · What is the difference between a class and an object?

A class is the description; an object is one thing made from it. Car is a class; the specific Civic with id C01 is an object. If that is fuzzy, start at chapter 8 — and this is where most people who are stuck actually are.

5 · Why can one List<Vehicle> hold both a Car and a Motorbike?

Because both are vehicles — and calling describe() on the list runs each object's own version. That is polymorphism, and it is the idea the whole course is built towards. If you cannot explain it, chapters 10 and 11 are the most valuable in the book for you.

6 · Your "add new vehicle" method is 180 lines. What is wrong?

It is doing several jobs: prompting, validating, constructing, storing, reporting. Each should be separate — chapter 19. If your code looks like this, go straight to chapters 18 and 19; you already know enough Java.

Reading your score
  • Struggled with 1–3 — start at chapter 2 and read straight through. Do not skip to OOP; it will not stick.
  • Fine on 1–3, stuck on 4–5 — you can write Java and cannot yet design. Part II is why this book exists. Start at chapter 8.
  • Fine on 1–5, recognised 6 — chapters 18–21, then go and finish the long assignments.

0.5 How to use the assignments

  1. Read the brief twice before writing anything. The second reading is for the requirements hiding in prose, as in §0.2.
  2. Write the class diagram on paper first for anything over 100 lines. Ten minutes there saves an evening.
  3. Get one function working end to end before starting the second. A program that does one thing correctly is worth more than five half-built functions.
  4. Test the ugly input. Empty string, letters where a number goes, a negative price, an id that does not exist. That is what the marker will type.
  5. Type the code. Copying a solution produces a mark and no ability. The assignments are the measurement, not the point.

None of these produces an error. All three produce a wrong answer, which is worse.

Two rules from Figure 2.1

Money is never a double. Store đồng as long (they are whole numbers anyway), or use BigDecimal if you need fractions of a unit. A price of 1,200,000,000₫ also overflows an int — several LAB211 briefs use prices in that range.

2.4 Converting between types

2.5 Primitive or reference

The distinction that explains chapter 8, so it is worth a paragraph here.

A primitive variable holds the value itself. An object variable holds a reference — the location of the value. Everything that is not one of the eight primitives is a reference: String, arrays, Scanner, your own classes.

Each primitive has a matching object type — int/Integer, double/Double. You need them because collections hold objects only: List<int> is illegal, List<Integer> is not (chapter 14). Java converts between them automatically, so this rarely intrudes.

2.6 Checkpoint

What does 7 / 2 evaluate to, and why?

3. Both operands are int, so the result is an int and the fraction is discarded. Make one side a double. See Figure 2.1.

A total of vehicle prices comes out negative. What happened?

int overflow — measured: MAX_VALUE + 1 is -2147483648, silently. Prices near a billion đồng need long. See Figure 2.1.

Why is double wrong for money?

It cannot represent 0.1 exactly. Measured: adding 0.1 ten times gives 0.9999999999999999, and == 1.0 is false. Use long đồng or BigDecimal. See §2.3.

int[] y = x; y[0] = 99; — what is x[0]?

99. Arrays are references; the assignment copied the location, not the contents. See §2.5.

2.7 Summary

  • Every variable has a declared type. final for anything that must not change.
  • int, double, boolean cover most of it; long for prices in đồng.
  • Integer division truncates, overflow wraps, and double arithmetic is inexact — all silently.
  • Widening is automatic; narrowing needs a cast and truncates.
  • Primitives hold values; everything else holds a reference.

3.1 Scanner

3.2 The trap

This costs more LAB211 hours than any other single thing, and it looks like the program is skipping a question.

The bug
System.out.print("Quantity: ");
int qty = sc.nextInt();

System.out.print("Name: ");
String name = sc.nextLine();   // never waits
                               // name is ""
The prompt appears and the program moves straight past it. It looks like the program ignored you.
The fix — use one method
System.out.print("Quantity: ");
int qty = Integer.parseInt(sc.nextLine());

System.out.print("Name: ");
String name = sc.nextLine();   // works
nextLine() consumes the newline as part of reading. Never mix it with nextInt.
The rule for the whole course

Use nextLine() and nothing else. Parse numbers yourself with Integer.parseInt / Double.parseDouble. You gain two things: the trap disappears from every program you write, and you can catch NumberFormatException and re-prompt (chapter 18) instead of crashing on abc — which nextInt() cannot do gracefully.

3.3 printf, and the marking scheme

Long-assignment briefs specify a table layout, and the marker compares your output to it. printf is how you hit it exactly.

Use %n, not \n

%n emits the platform's line separator; \n always emits a single character. On Windows the difference shows up when your output is compared byte-for-byte, which is what an automated marker does.

3.4 Checkpoint

Your program prints "Name:" and immediately moves on. Why?

A previous nextInt() left the newline in the buffer and the nextLine() consumed it, returning "". Measured in Figure 3.1. Use nextLine() everywhere and parse yourself. See §3.2.

Why prefer Integer.parseInt(sc.nextLine()) to sc.nextInt()?

It removes the newline trap, and it lets you catch NumberFormatException and re-prompt instead of crashing on non-numeric input. See §3.2 and chapter 18.

What does the minus in %-28s do?

Left-aligns within a 28-character field. Without it the text is right-aligned. See §3.3.

Where should the table format string live?

In the model's toString() and the view — one place, not repeated at every listing. See Figure 3.2 and §19.2.

3.5 Summary

  • One Scanner for the whole program.
  • nextLine() only. Parse numbers yourself — the trap disappears and bad input becomes catchable.
  • printf with %-5s, %,14.0f, %n hits the required layout exactly.
  • Formatting rounds the display, never the value.

4.1 if, and the traps in the condition

TrapWrongRight

4.4 Checkpoint

Which loop for a menu, and why?

do-while. The menu must be shown at least once before the user can choose to quit; a while would test the condition first. See §4.2.

if (v != null && v.getId().equals(x)) — why is the order load-bearing?

&& short-circuits: if the left side is false the right never runs, so getId() is never called on null. Reversed, it throws. See §4.1.

for (int i = 0; i <= arr.length; i++) throws. Why?

Valid indexes are 0 to length - 1. <= runs one iteration too many. Use <. See §4.3.

Why prefer case 1 -> … to case 1:?

No break needed and no fall-through, which removes the classic switch bug entirely. See Listing 4.2.

4.5 Summary

  • Arrow switch — no break, no fall-through.
  • for with an index; while may run zero times; do-while for menus; enhanced for to visit everything.
  • Off-by-one, infinite loop, stray semicolon, scope — four bugs, and you will meet all four.

Chapter Five · Part I

Methods

A method is a named piece of program. Naming things is how a 500-line assignment becomes twelve things you can think about one at a time.

By the end of this chapter you will be able to

  • Explain what static means and why main has it

5.1 The anatomy

void means the method returns nothing — it exists for its effect, such as printing. Everything else must return the declared type on every path, and the compiler checks that.

5.2 Overloading

Several methods, same name, different parameters. The compiler picks by the arguments you pass.

The return type is not part of the signature

int f(int x) and double f(int x) do not overload — they collide, and the file does not compile. The parameters must differ.

5.4 When a method is too long

There is no rule about line counts, but there is a reliable test.

The one-sentence test

Describe what the method does in one sentence with no "and". If you need an "and", it is doing two things and wants to be two methods.

"Adds a vehicle to the collection" — fine. "Prompts for the details and validates them and checks for a duplicate id and adds it and prints a message" — that is Listing 19.1, and it is five methods.

Three more signs, all cheap to notice:

  • It does not fit on a screen. Not a law, but a reliable warning. The brief's 50-LOC-per-function budget (§0.2) is a hint in the same direction.
  • You need a comment to explain a section. That comment is a method name asking to exist.
  • You cannot name it without "and", "then" or "Helper". Naming difficulty is a design signal.

5.5 Checkpoint

"Non-static method cannot be referenced from a static context." What happened?

You called an instance method from main without an object. Either make the method static, or create an object and call it on that. See §5.1.

Overloading vs overriding, in one line each.

Overloading: same name, different parameters, same class, chosen at compile time. Overriding: same signature, subclass, chosen at runtime by the object. See §5.2 and §11.1.

A method sets a[0] = 99 on an array parameter. Does the caller see it?

Yes — it has the address, so it changes the same array. But assigning a = new int[]{…} would not be visible: that only changes the local copy of the reference. See §5.3.

Your average method returns 3 instead of 3.5. Why?

sum / count with two ints is integer division. Cast one side: (double) sum / count. See §2.3 and Listing 5.1.

5.6 Summary

  • Access, static, return type, name, parameters. void for effect-only methods.
  • static belongs to the class; instance methods need an object. That is why main is static.
  • Overloading differs by parameters and is resolved at compile time; the return type is not part of it.
  • A method can change an object's contents, never which object the caller points at.
  • One sentence, no "and". Otherwise it is two methods.

8.1 The problem objects solve

Assignment 47 asks you to manage employees. Without objects, an employee is several parallel arrays:

The insight of object-oriented programming is that those four values are not four things — they are one thing with four properties. A class describes that thing; an object is one of them.

Class and object, once and for all

A class is the description. It is written once and holds no data. Employee is a class.

An object is one thing made from that description, with its own values. The specific employee with id E001 is an object. You can make a thousand from one class, and each has its own fields.

The usual analogy is a blueprint and a house. A better one for programming: a form and a filled-in form. The blank form is the class; each completed one is an object.

8.2 Writing one

this means "the object this method was called on". You need it when a parameter has the same name as a field, which in constructors is nearly always — and using the same name is good practice, because it documents which field the parameter fills.

8.3 What new actually does

Worth knowing precisely, because it explains a whole family of confusing behaviour later.

  1. Space is reserved on the heap for the object's fields.
  2. Fields get default values — 0, 0.0, false, null.
  3. The constructor runs and sets them properly.
  4. The address of that space is returned and stored in your variable.

Step 4 is the important one. Employee e1 does not hold an employee. It holds a reference — the location of one.

8.4 toString and equals

Every class inherits from Object, which gives it a few methods with useless defaults. Two are worth replacing in every LAB211 class.

The rule

Use .equals() for objects, == only for primitives (int, double, char, boolean). Every "search by id" in this course compares strings, and every one of them must use equals — or better, equalsIgnoreCase, since the marker will type e001.

8.5 Checkpoint

A class holds no data. What does?

The object. The class is the description written once; each object made with new has its own copy of the fields. See §8.1.

Why does public void Employee(...) break your program?

A constructor has no return type. Adding void makes it an ordinary method that happens to share the class's name, so your fields are never initialised. See §8.2.

99. The assignment copied the reference, so both names point at one object. See §8.3.

Printing an object shows Employee@6d06d69c. Why, and what fixes it?

That is Object's default toString — class name and hash. Override toString(). See §8.4.

Your search by id works in testing and fails when marked. Likely cause?

== on strings. It happens to be true for literals and false for strings built at runtime, which is what reading from a file or a Scanner produces. Use equalsIgnoreCase. See Figure 8.1.

8.6 Summary

  • A class is a description; an object is one thing made from it. Parallel arrays are the problem objects solve.
  • Fields, a constructor (no return type), and methods. this distinguishes a field from a parameter of the same name.
  • new allocates on the heap and returns a reference. Assigning copies the reference, not the object.
  • Override toString() in every model class — the marking scheme's output format lives there.
  • == compares references; .equals() compares content. Override equals and hashCode together.

Chapter Nine · Pillar 1 of 4

Encapsulation

Hide the data; expose the operations. The payoff is that a rule written once cannot be broken from anywhere else in the program.

By the end of this chapter you will be able to
  • State what encapsulation is and what it buys, in one sentence each
  • Choose an access modifier deliberately
  • Write setters that enforce a rule, and know when not to write a setter at all

9.1 The demonstration

Two versions of the same class. Only the access modifiers differ.

public fields
class Product {
    public String name;
    public double price;
}

Product p = new Product();
p.price = -999;
Measured: accepted, silently. The object is now in a state that should be impossible, and the bug surfaces later — in a total, on an invoice, in front of a customer.
private + setter
class Product {
    private String name;
    private double price;

    public void setPrice(double p) {
        if (p < 0) throw new
          IllegalArgumentException("price<0");
        this.price = p;
    }
}
Measured: price<0 thrown at the moment of the mistake, at the line that made it.

Figure 9.1 Real output from JDK 25. Both programs are correct Java; only one is a correct program.

Encapsulation, in two sentences

What: keep fields private and let the outside world touch them only through methods you wrote.

Why: so a rule about the data is enforced in one place that every change must pass through, instead of being everyone's responsibility everywhere.

9.2 The word that matters: invariant

An invariant is something that must be true about an object for its whole life. "Price is never negative." "Id is never null." "The list of items never contains a null." "Quantity is at least one."

Without encapsulation, an invariant is a hope. Every line of code in the program is free to break it, so keeping it true means checking everywhere — and you will miss one.

With encapsulation, an invariant is a guarantee. There is exactly one door into the field, and the check stands in it. This is the whole of the pillar; everything else is mechanics.

The rule for LAB211

Every field private. Every method public unless it is a helper. Then relax it only where you can say why. Markers look for this, and more importantly it is what makes the 500-line assignment stay under control.

9.4 Getters and setters that earn their place

A setter that only assigns is a public field with extra typing. It is not wrong, but it is not encapsulation either — the value comes from the check inside.

Three cases where the answer is to write less:

  • No setter at all. An id should never change after creation. Make the field private final, set it in the constructor, and give it only a getter. The compiler then enforces it.
  • A verb instead of a setter. account.deposit(500) says what is happening and can check the rules; account.setBalance(account.getBalance() + 500) makes the caller responsible for arithmetic on your data.
  • A defensive copy. Returning your internal List hands the caller the ability to clear it. Return new ArrayList<>(items) or Collections.unmodifiableList(items).

9.5 Checkpoint

What does encapsulation buy you, in one sentence?

A rule about the data is enforced in one place that every change must pass through — so it is a guarantee rather than a hope. See §9.2.

Your setter validates but objects still end up invalid. Why?

The constructor assigned the field directly instead of calling the setter. Route it through setPrice(price). See Listing 9.1.

Every field is private and a caller still emptied your list. How?

The getter returned the internal list itself. Return a copy or an unmodifiable view. See Listing 9.3.

When should a field have no setter?

When it must never change after creation — an id, for instance. Make it private final, set it in the constructor, expose only a getter. See §9.4.

9.6 Summary

  • Encapsulation: fields private, access through methods you control.
  • The real product is the invariant — something guaranteed true about the object for its whole life.
  • The constructor must go through the setters, or objects can be born invalid.
  • A setter that only assigns is not encapsulation. The check is the point.
  • Prefer final with no setter, verbs over setters, and defensive copies for collections.

10.2 Overriding, and the annotation that saves you

Overriding is replacing an inherited method with your own. The signature must match exactly, and this is where a silent bug lives:

Overriding is not overloading

Overriding: same signature, in a subclass, replacing behaviour. Overloading: same name, different parameters, in the same class. They are unrelated, and the exam asks the difference.

10.3 When inheritance is wrong

Inheritance is the most over-used idea in object-oriented programming, and the test is one question: can you say "a Car is a Vehicle" and have it be true in every situation?

Two traps in LAB211 assignments specifically

Do not inherit to share code. If Report extends Employee because you wanted getName(), you have said a report is an employee. It is not, and the design will fight you at the next feature.

Do not build deep hierarchies. Vehicle → LandVehicle → MotorVehicle → Car → SportsCar is impressive and unmaintainable. Two levels is almost always enough; the briefs never need three.

10.4 Checkpoint

Why must super(...) be the first statement in a constructor?

The parent part of the object must be initialised before the subclass touches anything — otherwise you could read fields that do not exist yet. See Listing 10.2.

You misspell an overriding method. What happens without @Override?

It compiles as a new, unrelated method; the parent's version keeps running and your output is silently wrong. With @Override it is a compile error. See Listing 10.3.

Overriding vs overloading?

Overriding: same signature, in a subclass, replaces behaviour, resolved at runtime. Overloading: same name, different parameters, same class, resolved at compile time. See §10.2.

Should Car extend Engine?

No. A car has an engine — that is a field. Apply the is-a test before every extends. See §10.3.

10.5 Summary

  • extends shares the common part once; super(...) calls the parent constructor and must come first.
  • super.method() calls the parent's version of a method you are overriding.
  • Always write @Override. It turns a silent typo into a compile error.
  • Apply the is-a test. "Has-a" is a field — composition, not inheritance.
  • Two levels of hierarchy is enough for every assignment in this course.

11.1 One sentence, then the proof

Polymorphism

A variable declared as the parent type can hold any subtype, and calling a method on it runs that object's version — decided when the program runs, not when it compiles.

11.2 Why the brief demands one collection

Without polymorphism you would need one list per type, and every operation would double:

Two collections
List<Car> cars = new ArrayList<>();

// show all:
for (Car c : cars)  System.out.println(c);
for (Motorbike m : bikes) System.out.println(m);

// sort by price? Twice, then merge.
// search by id?  Twice.
// add a Truck?   A third list, and
//                every method again.
This is the design the brief forbids, and the forbidding is a kindness.
One collection
List<Vehicle> showroom = new ArrayList<>();
showroom.add(new Car(...));
showroom.add(new Motorbike(...));

    System.out.println(v);        // each runs its own

showroom.sort(Comparator
    .comparingDouble(Vehicle::getPrice)
    .reversed());                 // sorts both types

// Add a Truck? One new class. Nothing else changes.

11.3 The if/else chain that should not exist

Here is the single most reliable sign that polymorphism has been missed:

Type-checking by hand
for (Vehicle v : showroom) {
    if (v instanceof Car) {
        Car c = (Car) v;

The rule to carry into every long assignment

If you are testing an object's type to decide what to do, the behaviour belongs on the object. Move it into a method, override it per subclass, and delete the chain. Markers notice this, and so does the version of you who has to add a feature next week.

11.5 Checkpoint

State polymorphism in one sentence.

Why does the brief say "use only one collection"?

Because with polymorphism one List<Vehicle> handles every type — one loop to display, one sort, one search — and adding a type changes none of it. Separate lists double every operation. See §11.2.

12.1 The problem with a plain parent

In chapter 10, Vehicle was an ordinary class. Two things are wrong with that.

First, new Vehicle(...) is legal — and meaningless. A vehicle that is neither a car nor a motorbike is not a thing in the showroom. Second, nothing forces a subclass to provide its own describe(); forget it and you silently get the generic one.

abstract fixes both.

Notice what toString() does. It calls describe(), which does not exist yet — and that is fine, because by the time any object exists it is a Car or a Motorbike and the call resolves to theirs (chapter 11). An abstract class can write logic in terms of methods its subclasses will supply. That is the pillar in one line.

12.2 Interfaces

An interface is a list of methods with no implementation and no fields — a contract. "Whoever implements me can do these things."

"Is this a kind of thing, or something a thing can do?"

A Car is a Vehicle → abstract class. A Motorbike can make a sound; so could a doorbell, which is not a vehicle at all → interface. If the answer names a noun, abstract class. If it names a verb, interface.

12.4 Checkpoint

What two things does abstract guarantee?

The class cannot be instantiated, and every subclass must implement each abstract method — both enforced by the compiler. See §12.1.

How can toString() call describe() when describe() has no body?

Because every actual object is a concrete subclass, so the call resolves to that subclass's version at runtime (chapter 11). An abstract class can be written in terms of what its subclasses will supply. See §12.1.

Abstract class or interface for "can make a sound"?

Interface — it is a capability, not a kind, and a doorbell could have it too. Noun → abstract class; verb → interface. See §12.2.

Why can a class implement many interfaces but extend only one class?

An interface carries no state or constructor, so combining several is unambiguous. Two parent classes could both define the same field, which is the ambiguity Java avoids. See §12.2.

12.5 Summary

  • abstract means "cannot be created directly", and an abstract method means "every subclass must supply this".
  • An abstract class can hold state, a constructor and shared logic written in terms of methods subclasses will provide.
  • An interface is a contract with no state. One extends, many implements.
  • Noun → abstract class. Verb → interface.
  • Comparable and Comparator are interfaces you implement to get sorting for free.

Exceptions

Something goes wrong. The question is not whether to handle it, but where — and the wrong answer is the empty catch block.

By the end of this chapter you will be able to

  • Decide whether to catch here or let it propagate

17.1 Two kinds

CheckedUnchecked (Runtime)
ExamplesIOException, FileNotFoundExceptionNullPointerException, NumberFormatException, ArrayIndexOutOfBounds
CompilerForces you to catch or declareSays nothing
MeansSomething outside your program failedUsually a bug in your program
ResponseHandle it — the disk is genuinely fullFix the code, or validate the input

That last row is the useful distinction. A missing file is a fact about the world; a NullPointerException is a fact about your code. Wrapping the second in a try/catch hides a defect instead of removing it.

17.2 The empty catch

The worst three lines in Java
try {
    save(items);
} catch (IOException e) {
    // ignore
}
The save failed. Nobody was told. The user closes the program believing their work is on disk. This is the single most damaging habit in the course.
Say something true
try {
    save(items);
} catch (IOException e) {
    view.message("Could not save: "
        + e.getMessage()
        + ". Your changes are not on disk.");
}
The user knows. They can retry, or copy the data out. The program is still running.
Three rules
  1. Never swallow an exception silently. If you truly cannot act on it, at minimum print it.
  2. Catch the specific type, not Exception — catch (Exception e) also catches the NullPointerException from your own bug and disguises it as a file problem.
  3. Catch where you can do something about it. A method deep in the model cannot show a message; it should throw and let the layer that owns the screen decide (§19.1).

Which exception to throw, for the cases this course produces:

  • IllegalArgumentException — a parameter is wrong. The common one.
  • IllegalStateException — the object is not in a state where this makes sense (checking out an empty cart).

Checked (compiler-enforced) means something outside your program failed. Unchecked usually means a bug in your code. Handle the first; fix the second. See §17.1.

Two things: it swallows the failure silently, and it catches your own bugs too, disguising a NullPointerException as an expected error. See §17.2.

18.5 Checkpoint

Why does the whole Validator use nextLine() and never nextInt()?

nextInt() leaves the newline in the buffer and the next nextLine() returns empty. Reading lines and parsing them yourself removes the trap from the entire program. See §18.2.

Different threats: the validator guards against a person mistyping; the invariant guards against any code — including code you write later — creating an invalid object. See §18.4.

  • nextLine() everywhere, parse yourself — the newline trap disappears.
  • Regex for shape, then a parse or range check for meaning. Double every backslash.
  • Validator protects the user; the invariant protects the data. Keep both.
