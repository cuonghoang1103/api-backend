About this book

JavaScript is the only language most people learn by accident. This book is the version where you learn it on purpose.

Almost nobody sets out to learn JavaScript. They set out to make a button work, and JavaScript is what was lying around. So the language gets absorbed in fragments — a fetch from Stack Overflow, an async copied from a tutorial, a this that behaves oddly and gets worked around rather than understood.

That produces a particular kind of developer: fluent, productive, and quietly uncertain. The code works. Why it works is a slightly different question, and the gap shows up the day something behaves in a way the fragments do not explain.

This book closes that gap by going in the other direction — from the mechanisms outward. What a variable binding actually is. When code runs and in what order. What this is bound to and by what rule. Why 0 == "" is true. Those are not trivia; they are the four or five facts that make every surprising behaviour predictable.

Who should read this

Someone who has written JavaScript and would like to stop guessing. If you have never programmed at all, chapters 1 and 2 assume nothing — but they move quickly, and a slower first course would serve you better.

If you are heading for React, read chapters 1 to 6 first. Volume 1 of this series opens by saying that React is mostly consequences of JavaScript's reference semantics; this is that material at full length.

How this book is organised

Chapter 0 places JavaScript — where it came from, why it has three module systems, and what "the platform" now means. Then sixteen chapters, each mapping to one module of the JavaScript track in Code Lab, ending with that module's ten graded exercises.

The method is the same throughout: the chapter is the worked example, the exercises are the problem. Read, then go and fail at them.

About the code

Every listing ran on Node 22 before it went in. Where the book says two things differ, a program printed the difference. Several claims that "everyone knows" turn out to be stale or half-right once actually tested, and those are marked.

Chapter Zero · Orientation

What JavaScript Is, and How It Got This Way

Most of JavaScript's oddities are history rather than design. Knowing which is which tells you what to learn and what to route around.

By the end of this chapter you will be able to
  • Explain why the language has the quirks it has, and which are permanent
  • Distinguish JavaScript, ECMAScript, the DOM and Node
  • Say why there are two module systems and which to use
  • Read a compatibility table and decide whether you can use a feature

0.1 Ten days

In May 1995 Brendan Eich was given roughly ten days at Netscape to produce a scripting language for the browser. The brief was contradictory by design: it had to look like Java for marketing reasons, behave like Scheme for the engineers, and be simple enough for people writing four lines in a web page.

What shipped was called Mocha, then LiveScript, then — for reasons entirely of marketing — JavaScript. It has approximately nothing to do with Java.

Three decisions from that fortnight are still with you every day:

  • Automatic type coercion. Beginners should not see type errors, so the language converts silently. That is why 0 == "" is true (§1.5).
  • Prototypal inheritance. Objects inherit from objects rather than from classes. class arrived in 2015 as syntax over the same machinery (§8.1).
  • Single-threaded with an event loop. A browser script must never freeze the page, so nothing blocks and everything is a callback (§5.1).
The one thing that could never be fixed

Backward compatibility is absolute. Fixing == would break a fraction of the web, and the web does not get recompiled. So the language only ever grows: === was added beside ==, let beside var, modules beside scripts. Nothing is ever removed, which is why the language is large and why "the old way still works" is always true and rarely the answer.

0.2 Four words that get confused

TermIsGives you
ECMAScriptThe language specificationlet, functions, Promise, Array
JavaScriptThe common name for implementations of itThe same
The DOMA browser API, not part of the languagedocument, querySelector, events
NodeThe language outside a browserfs, process, require

The distinction is practical. Array.prototype.map works everywhere because it is the language. document.querySelector throws in Node because there is no document. fs.readFile does not exist in a browser because a web page may not read your disk.

Versions are named by year — ES2015 (also called ES6, the large one), then ES2016 through ES2024, each small. In practice nobody says "ES2021"; they say "does it have at() yet", and check caniuse or MDN's compatibility table.

0.3 Why there are two module systems

The language shipped with no way to split a program into files. For fifteen years the answer was to concatenate scripts and hope the global namespace held. Node solved it in 2009 with CommonJS — require() and module.exports. The standard arrived six years later as ES Modules — import and export.

CommonJSES Modules

LoadingSynchronous, at runtimeStatic, analysed before running
EnablesDynamic pathsTree shaking, top-level await
UseOlder Node codeEverything new

Use ES Modules. In Node that means "type": "module" in package.json, or a .mjs extension. Chapter 11 covers the failure modes, of which there are more than there should be.

0.4 Where it runs now

  • Browsers — the original home, now with a platform around it (chapter 10).
  • Servers — Node, and now Deno and Bun. Node remains the default.
  • Mobile and desktop — React Native, Electron.
  • Build tooling — increasingly written in Rust or Go, and still driven from JavaScript.

One consequence worth internalising early: the same language runs in places with completely different capabilities. Code that assumes window breaks on a server; code that assumes process.env breaks in a browser. Chapter 11 is largely about that boundary, and volume 1's chapter 10 is the React-specific version of it.

The rule

Chapter Two · Part I

Control Flow and Functions

Functions are the language's one big idea. Closures and this are the two things about them that people never quite pin down — so this chapter pins them down.

By the end of this chapter you will be able to
  • Write functions in all four forms and say which to use
  • Explain a closure well enough to build private state with one
  • Determine what this is bound to, by rule rather than by guess
  • Say why arrow functions are the default in modern code

2.1 Four forms

2.2 Closures

A closure is a function that remembers the variables it was created beside, even after the surrounding function has returned. It is not an advanced topic — it is how every callback, every hook and every module in JavaScript works.

A closure captures the variable, not a snapshot

The classic demonstration: a loop with var shares one binding across all iterations, so every callback sees the final value. With let, each iteration gets its own binding and the callbacks see 0, 1, 2. That is the single most useful practical difference between the two, and another reason §1.1 says never var.

2.3 this, by rule

this is not decided by where a function is written. It is decided by how it is called, and there are exactly four rules, checked in order.

Called asthis is
new Fn()The newly created object
fn.call(x) / .apply / .bindx
obj.fn()obj
fn()undefined in modules and strict mode
An arrow function ignores all four — it uses the this of wherever it was written
The practical consequence

Arrow functions do not have this problem, which is why modern JavaScript uses them almost everywhere. Reach for a regular function only when you want the caller to supply this: a method in a class, or an object literal's method shorthand.

4.2 Events, and delegation

An event fires on the element, then on its parent, then its parent, up to document. That is bubbling, and it is what makes one listener able to serve a thousand rows.

PropertyIs
e.targetWhat was actually clicked — possibly an icon inside your button
e.currentTargetThe element the listener is attached to
e.preventDefault()Stop the browser's default — form submit, link navigation
e.stopPropagation()Stop bubbling. Use sparingly; it breaks other people's listeners.
Two traps in one

The handler fires twice. Almost always addEventListener ran twice — a setup function called on every render, or a script included twice.

The handler will not go away. removeEventListener compares by identity, so an inline arrow can never be removed — it is a different function each time. Keep a reference, or pass { signal } from an AbortController and call abort().

the modern way to unsubscribe everythingjs
const ac = new AbortController();
el.addEventListener("click", onClick, { signal: ac.signal });
window.addEventListener("resize", onResize, { signal: ac.signal });
ac.abort();          // removes BOTH, whatever they were

4.3 A widget that works for everyone

The habit that makes DOM code manageable

Keep the state in a variable and re-render from it. Reading the current state out of the DOM — counting elements with a class, parsing text back into a number — works until two things disagree. One source of truth, one render function. That idea, taken to its conclusion, is React.

4.4 Checkpoint

New rows do not respond to clicks. Why?

Listeners were attached per row, at load, and the new rows were added afterwards. Delegate from a stable parent instead. See Listing 4.3.

removeEventListener does nothing. Why?

It compares functions by identity and you passed a new inline arrow. Keep a reference, or use an AbortController signal. See §4.2.

e.target versus e.currentTarget?

target is what was clicked — possibly a child. currentTarget is where the listener lives. In delegation you want e.target.closest(...). See §4.2.

Why textContent rather than innerHTML for user data?

innerHTML parses and executes markup — that is a cross-site scripting hole. See §4.1 and chapter 12.

4.5 Summary

  • Build off-screen with a fragment and write to the DOM once.

  • removeEventListener matches by identity; an AbortController signal removes everything at once.
  • Real buttons, ARIA state, keyboard handlers.

Chapter Five · Part III

Asynchronous JavaScript

One thread, an event loop, and four combinators. This chapter is the one that most changes how you read other people's code.

By the end of this chapter you will be able to
  • Predict the order in which asynchronous code runs
  • Write async/await and know exactly where the function pauses
  • Choose between the four Promise combinators
  • Run work in parallel rather than accidentally in series
  • Recognise the forEach + async trap

5.1 The event loop

JavaScript runs on one thread. Everything — your code, event handlers, rendering — takes turns on it. Asynchronous work does not run in parallel; it runs later.

Two consequences worth carrying: a long synchronous loop freezes the page, because nothing else can run on the one thread; and await does not block the page — it suspends your function and gives the thread back.

5.2 Promises, and async/await

Three facts about async functions that remove most confusion:

  • An async function always returns a promise, whatever you return inside it.
  • await pauses that function and returns control to the caller. Nothing else stops.
  • A rejected promise with no catch anywhere is an unhandled rejection — in Node it will crash the process.

7.4 Writing the tests

What to assert on

Assert on what the function returns and what it calls, never on how it computed it. A test that reads a private field or counts internal loop iterations breaks on every refactor, which trains the team to delete tests rather than fix code.

7.5 Checkpoint

Why copy the handler set before iterating in emit?

A handler may unsubscribe itself — or another — during the emit, which would mutate the set you are iterating. See Listing 7.1.

Why should a retry wrapper not retry a 400?

A client error will fail identically every time; retrying only delays the user's error message. Retry 5xx and network failures. See Listing 7.2.

What is the difference between retry and a circuit breaker?

Retry handles a blip in one call. A circuit breaker stops calling at all once a service is clearly down, so a hundred clients do not keep it down. See Listing 7.3.

What makes a function easy to test?

Being pure — inputs in, value out, no I/O. Push side effects to the edges. See Figure 7.1.

  • An emitter needs a copy before iterating and a try around each handler.
  • Retry with backoff and jitter, only for retryable errors; a circuit breaker for a service that is down.
  • Testability is a design property: pure decisions, effects at the edges.
  • Assert on return values and call counts; control time with fake timers.

8.1 The prototype chain

JavaScript has no classes underneath. Every object has a hidden link to another object — its prototype — and a property lookup walks that chain until it finds the name or runs out.

Two practical consequences. obj.hasOwnProperty(k) distinguishes a property on the object from one inherited — and Object.hasOwn(obj, k) is the modern spelling. And assigning to __proto__ or to Object.prototype from parsed JSON is prototype pollution, a real vulnerability (chapter 12).

  • Resolves every import into one dependency graph.
  • Transforms — JSX, TypeScript, newer syntax down to what you target.

15.1 The problem, stated honestly

Micro-frontends solve an organisational problem, not a technical one: several teams cannot ship independently because they share one build and one deploy. If you do not have that problem, you do not have this solution.

You getYou pay
Independent deploys per teamDuplicate dependencies across bundles
Teams can choose their own stackA visually inconsistent product
A failure is contained to one areaMuch harder end-to-end debugging
Incremental migration off a legacy appVersion skew between shared contracts
The honest default

Under about four teams, do not. A monolith with clear module boundaries — volume 1's chapter 13 folder structure, dependency rules enforced by lint — gives most of the benefit and none of the cost. Micro-frontends are a way of buying autonomy with complexity, and the exchange rate is poor at small scale.

15.2 Three ways to compose

ApproachHowGood / bad
Route-levelA reverse proxy sends /shop/* to one app, /admin/* to anotherSimplest by far; full page load between areas
Build-timeEach team publishes an npm package; one app composes themBest performance; no independent deploy

Route-level composition covers a surprising share of real cases and needs nothing but a proxy config. Try it first.

15.3 Boundaries and contracts

  • Split by domain, never by layer. "Checkout" is a boundary; "all the components" is not.
  • Communicate through explicit contracts — custom events, a URL, a small shared store with a versioned shape. Never by reaching into another app's internals.
  • Share design tokens, not components, unless you are willing to version and deploy the component library like a public package.
  • One team owns the shell — routing, auth, layout, error boundaries.
  • Contract-test the seams. The integration bug you will actually hit is a payload shape changing, and only a contract test catches it before production.

An organisational one — teams that cannot deploy independently. Not a technical one. See §15.1.

Route-level, via a proxy. It needs no build machinery and covers many real cases. See §15.2.

  • Route-level, build-time, runtime — in increasing order of power and cost.

A warning nobody reads is not a check

If a step can fail without failing the build, it will be ignored within a fortnight. Bundle budgets, coverage thresholds and audit failures should break the pipeline or not be there at all.

16.3 Deploying

  • Build once, promote the artefact. Rebuilding per environment means the thing you tested is not the thing you shipped.
  • Cache correctly: hashed assets immutable for a year; HTML never cached. Getting either backwards is a classic outage.
  • Roll back faster than you fix. The previous build should be one command away, always.
  • Feature-flag risky changes so shipping and releasing are separate decisions.
  • Handle the stale tab. After a deploy the old chunk filenames vanish; a lazy import in an open tab 404s. Catch it in a boundary and reload (volume 1 §8.5).

16.4 Checkpoint

Why so few end-to-end tests?

They are slow, flaky and expensive to maintain. Keep them for the flows that make money. See §16.1.

Why is the lint step before the test step?

Cheapest first: a lint error should fail in twenty seconds, not after a browser suite. See Listing 16.2.

Why "build once, promote"?

Rebuilding per environment means production is running a different artefact from the one that passed the tests. See §16.3.

What breaks in an open tab after a deploy?

  • Roughly 70/20/10 unit, integration, end-to-end. Query by role, not by class.
  • Cheap checks first; anything that can be ignored will be.
  • Build once and promote; cache assets forever and HTML never; roll back in one command.
  • Watch errors by release, real-user vitals, bundle size and external uptime.
The end of the book

Seventeen chapters, one hundred and sixty exercises. The habit worth keeping is the one this book was written with: when you are unsure how something behaves, write six lines that print the answer. Every measured claim here — that forEach silently discards a promise, that spread shares nested objects, that removing a listener by a new arrow does nothing — came from a program that took two minutes to write.
