About this book

TypeScript is usually learned as a tax — annotations added to JavaScript to stop a linter complaining. This book treats it as what it is: a tool that can make entire categories of bug impossible to write.

Almost everyone arrives at TypeScript the same way. A project already uses it, so you add : string where the red squiggles are, discover any and as, and get productive. The code compiles. Nothing about it is safer than the JavaScript it replaced.

The gap between that and the thing TypeScript can actually do is large, and it is not about knowing more syntax. It is about a handful of ideas: that types describe what you already know and validation establishes what you do not; that a union with a discriminant makes an unhandled case a build error; that narrowing is a thing the compiler does statement by statement and you can steer it. Those ideas are worth more than every utility type in chapter 5.

Who should read this

Someone who writes JavaScript comfortably and writes TypeScript uncertainly. You should be at ease with objects, closures, promises and modules — Volume 3 of this series is that material if you are not. No experience of Java, C# or any other typed language is assumed; if you have it, §2.4 will explain why the rules feel wrong for a week.

Chapter Zero · Orientation

What TypeScript Is, and What It Is Not

TypeScript is a type checker that runs before your program does, and then gets out of the way entirely. Almost every confusion about it comes from expecting it to still be there at runtime.

By the end of this chapter you will be able to
  • Say precisely what TypeScript adds to JavaScript, and what it does not
  • Explain why as is a promise you make to the compiler, not a check
  • Describe what happened to the compiler in version 7, and why it matters
  • Read a tsconfig.json and predict how strict the project is

0.1 A type checker, not a language

The single most useful sentence about TypeScript: it is JavaScript plus annotations, minus the annotations. You write types, a compiler reads them, and then it deletes them. What runs is JavaScript — the same JavaScript you would have written, with the type text stripped out.

That has three consequences that catch everybody at least once.

If you believe…What actually happens
"The types protect me at runtime"They do not exist at runtime. A JSON response with the wrong shape sails straight through (§0.4, chapter 13).
"as User checks that it is a User"as tells the compiler to stop arguing. It checks nothing.
"TypeScript makes my code slower"It compiles away to nothing. There is no runtime cost, only a build step.

0.2 Where it came from

Anders Hejlsberg — who had already designed Turbo Pascal, Delphi and C# — started TypeScript at Microsoft in 2010 and released it publicly in October 2012. The problem it was built for was concrete: Microsoft was writing large applications (Office Online, later VS Code) in a language with no way to describe the shape of anything.

Two design decisions from the beginning explain almost all of its character:

  • It is a superset. Every valid JavaScript file is a valid TypeScript file. That is why you can rename .js to .ts and adopt it a file at a time (chapter 14) — and also why the type system has to model some deeply strange JavaScript behaviour.
  • The type system is structural, not nominal. Two types match if their shapes match, regardless of name or declaration. Java and C# ask "does it declare that it implements this interface?"; TypeScript asks "does it have the right properties?" (§2.4).
Not a Microsoft-only story any more

TypeScript is now the default for almost every serious JavaScript project: Angular requires it, React and Vue ship types, Node has run .ts files natively since 22.6 with --experimental-strip-types, and Deno and Bun execute TypeScript directly. The "should we use TypeScript" argument is largely over; what remains is how strictly.

0.3 What happened in version 7

For twelve years tsc was written in TypeScript and ran on Node. In 2025 Microsoft rewrote the compiler in Go — a native binary, with real parallelism. That shipped as TypeScript 7, and it is what this book uses.

The rewrite is invisible in your source code and very visible in your terminal. Here is the same project, 1,501 files and 15,000 lines, type-checked by both compilers on the same 12-core machine:

Where the compiler now lives

Installing typescript pulls a small wrapper (3.6 MB) plus a platform-specific native binary — on this machine @typescript/typescript-linux-x64, 27 MB. If your CI caches node_modules by platform, that is a new thing to be aware of. Your tsconfig.json, your editor and your npx tsc command are otherwise unchanged.

One default that changed, and it will bite you

tsc --init in version 7 now writes noUncheckedIndexedAccess: true and exactOptionalPropertyTypes: true. Both are correct and both reject code that older projects are full of. §A.3 explains each one; if a fresh project suddenly errors on arr[0].name, that is why.

0.4 The seam between compile time and run time

Here is the mistake, written out, because everyone makes it once and it is better to make it on this page:

The fix is not a better type. It is a runtime check at the boundary, whose result the compiler can then trust — that is what chapter 13 is about, and why Zod exists.

The rule worth writing on a sticky note

Types describe what you already know. Validation establishes what you do not. Anything crossing your program’s boundary — HTTP, files, localStorage, environment variables, user input — is unknown until checked. Inside the boundary, types are enough.

Checkpoint

Why does as User not protect you from a malformed API response?

Because as is an assertion, not a check — it changes what the compiler believes, and emits no code at all. At runtime nothing inspects the object. The only thing that can protect you is a runtime validator whose success narrows the type (chapter 13).

Your colleague says "TypeScript slows the app down." What is wrong with that?

Types are erased at compile time; the shipped JavaScript is identical to what you would have written by hand. There is a build cost, which version 7 cut by roughly 4× (§0.3), and zero runtime cost. The only exceptions are features that emit code — enum (§2.6) and decorators (chapter 8).

What does "structural typing" mean in one sentence?

A value is accepted wherever its shape fits, no matter what it was declared as or whether it names the interface. An object literal with id and name is a User without ever mentioning User (§2.4).

Chapter A · Supplement

The Compiler and tsconfig.json

Nothing about TypeScript feels arbitrary once you know which flags are on. Most "why is TypeScript complaining" questions are really "which of these twenty-three options is this".

By the end of this chapter you will be able to
  • Write a tsconfig.json from scratch and explain every line
  • Say what strict actually turns on — all eight of them
  • Choose module and moduleResolution without guessing
  • Read a compiler error code and know where to look

A.1 What tsc --init gives you now

Run it in an empty directory and read what comes out. In version 7 the generated file is short and opinionated — that is a deliberate change, and it is stricter than most existing projects.

There is no such file as "the default tsconfig"

With no tsconfig.json at all, tsc runs with strict: false — which means noImplicitAny off, strictNullChecks off, and a type system that will accept almost anything. That is the mode most tutorials are written in, and it is why their examples do not reproduce for you. Always have a config file.

Tony Hoare called the null reference his "billion-dollar mistake". strictNullChecks is the flag that fixes it: string means a string, and if it might be absent you write string | null and the compiler forces you to handle it. If you adopt exactly one strict flag in a legacy codebase (chapter 14), adopt this one — and expect it to find real bugs immediately.

A.3 The two new defaults that break old code

Adopting these in an existing project

Both flags will produce hundreds of errors on a codebase written without them. That is not a reason to leave them off; it is a reason to turn them on one directory at a time. Chapter 14 covers the mechanics — the short version is a second tsconfig.strict.json that includes only the migrated folders.

The extension rule that catches everyone

Under nodenext, an import of a local file must carry the runtime extension: import { x } from "./util.js" — even though the file on disk is util.ts. It looks wrong and it is correct: the specifier describes the file that will exist after compiling. Under moduleResolution: bundler you write "./util" and the bundler figures it out.

Checkpoint

A colleague sets "strict": false to clear an error. What did they just switch off?

Eight flags, not one — including strictNullChecks and noImplicitAny, the two that carry most of the value. If a single rule is in the way, disable that single rule ("strictPropertyInitialization": false) and leave the other seven on.

Why does import { x } from "./util.js" point at a file that does not exist?

It will exist. Under moduleResolution: nodenext the specifier describes the emitted JavaScript, not the source, because Node resolves the specifier at runtime and Node never sees your .ts. Under bundler resolution you omit the extension instead.

What is the difference between nickname?: string and nickname?: string | undefined?

With exactOptionalPropertyTypes on, the first means the key may be absent, and writing { nickname: undefined } is an error; the second means the key may be absent or present holding undefined. Without the flag they are identical. The distinction matters for in checks, Object.keys, and JSON round-trips.

Chapter B · Supplement

Narrowing and Control-Flow Analysis

The compiler tracks what a variable can be, statement by statement. Learning to read that tracking is the difference between fighting TypeScript and steering it.

By the end of this chapter you will be able to
  • Name the six narrowing constructs and when each applies
  • Explain why typeof x === "object" does not exclude null
  • Write a type predicate and an assertion function, and say when to use which
  • Diagnose narrowing that silently disappears inside a callback

B.1 The idea: a type per position, not per variable

Most typed languages give a variable one type for its whole life. TypeScript gives it a type at every point in the program, and recomputes it after every branch. This is control-flow analysis, and it is the single feature that makes union types practical.

The falsy trap, restated for TypeScript

if (count) narrows away undefined — and also 0. if (name) narrows away undefined — and also "". When the value is a number or a string, write the check you mean: if (count !== undefined). This is the same bug as Volume 3 §1.6, now with a compiler that will not warn you because your code is, strictly speaking, type-correct.

B.3 Type predicates and assertion functions

Narrowing stops at the function boundary: the compiler cannot see inside a helper. Two syntaxes let you teach it what your helper proved.

Both are promises, and both can lie

a is Cat and asserts v is string are unchecked. If the body returns true for a dog, the compiler believes you and your program breaks later, somewhere else. Keep predicate bodies to one obvious line, and prefer a discriminated union that needs no predicate at all.

B.4 Discriminated unions — the pattern to reach for first

A union whose members share a literal-typed field is the one shape TypeScript narrows perfectly, with no helper functions and no casts.

B.5 When narrowing silently disappears

Narrowing is lost when…Fix
The value is a mutable property (this.x, obj.x)Copy to a const first: const v = this.value;
You are inside a callback or closureSame — narrow the local copy
The variable is let and reassigned in a loopUse const, or re-check inside the loop
You called any function in betweenOnly for properties; locals survive calls

Table B.2 The universal fix is one line: assign to a const, then narrow the const. A const cannot change, so the compiler will trust the guard anywhere.

Checkpoint

Why does if (typeof x === "object") not give you an object?

Because typeof null === "object" — a bug in the first JavaScript implementation that backward compatibility has frozen forever. The branch still contains null, and arrays too. Use Array.isArray(x), or x !== null && typeof x === "object".

When would you write asserts v is string rather than v is string?

When the caller should stop rather than branch — validating a function argument, or a boundary check that has no sensible fallback. A predicate (v is string) returns a boolean you use in an if; an assertion throws and narrows everything after the call site.

Your guard works, then stops working when you move the code into a .forEach. Why?

Because the narrowed value is a mutable property, and the callback may run after the property changes. Copy it into a const outside the callback and narrow that — a const cannot be reassigned, so the narrowing survives.

Chapter C · Supplement

Types You Did Not Write

Most of the types in your project came from somewhere else. Knowing where they live, when they lie, and how to bend them is a large part of working in a real codebase.

By the end of this chapter you will be able to
  • Explain where a package’s types come from and in what order they are found
  • Fix TS7016 three different ways and pick the right one
  • Write a .d.ts for an untyped library

C.1 Three places types can come from

The compiler looks in that order. If all three miss, you get the error every TypeScript developer has seen:

Why @types is a separate package

Because the library is JavaScript and its author never wrote types. DefinitelyTyped is a single enormous GitHub repository where volunteers maintain declarations for thousands of packages, published automatically as @types/name. It is why npm i -D @types/lodash works for a library that has never heard of TypeScript.

C.2 Writing your own declaration

When there is no @types package, you write one. It does not have to be complete — it has to cover what you actually call.

Where the file goes

Anywhere your tsconfig.json includes — conventionally types/ or src/types/. Declaration files are not imported; the compiler picks up every .d.ts in the program. If yours seems to be ignored, it is almost always outside include.

C.3 Augmenting types you do not own

You attach req.user in an Express middleware and TypeScript says Property ‘user’ does not exist on type ‘Request’. You cannot edit @types/express. You can add to it.

The one-character bug in this file

Delete the import "express"; line and the file stops being a module. declare module "express" then means “declare a new ambient module called express” and replaces the real types instead of extending them — every Express type in your project quietly becomes wrong. If augmentation seems to destroy the types it was meant to extend, this is why.

C.4 When the types are wrong

Third-party types are code, and code has bugs. Options, in the order you should try them:

SituationDo this
A property exists at runtime but not in the typesAugment (§C.3). Open a PR upstream too.
The type is too wide (any, object)Narrow at your boundary with a validator (chapter 13).
The type is too narrow and rejects valid inputas — with a comment naming the upstream issue.
@types lags the library by a major versionPin the library, or write a local override.
A .d.ts in node_modules fails to compileskipLibCheck: true — this is exactly what it is for.
as is a comment with teeth

Every as in a codebase should carry a reason. value as User tells the next reader nothing; // @types/foo#812 — opts is typed string, accepts RegExp at runtime above it tells them everything, including when it can be deleted.

Checkpoint

What are the three ways to fix TS7016, and which do you try first?

1. npm i -D @types/name — try first, works most of the time. 2. Write a small .d.ts covering the functions you actually call. 3. declare module "name"; to make it any — fastest and least safe, so leave a comment.

Why does module augmentation need an import at the top of the file?

Because a .d.ts with no top-level import or export is a global script, and inside one, declare module "x" declares a brand-new ambient module that shadows the real one. One import makes the file a module, and then declare module means “merge into” instead of “replace”.

Why does this book keep saying unknown where you might write any?

any switches the checker off for that value and everything derived from it — the errors reappear ten files away. unknown keeps the checker on and simply refuses every operation until you narrow. It is any with the safety catch still engaged.

1.1 A project in four commands

Node can now run TypeScript by itself

1.5 Literal types and as const

as const vs satisfies

as const makes everything as narrow and readonly as possible. satisfies (§3.6) checks a value against a type without widening it. They solve adjacent problems and are frequently used together: {...} as const satisfies Config.

Checkpoint

Why is let x: string = "hi" considered noise?

Because inference already produces string, so the annotation adds nothing and now has to be maintained. Annotate inputs — function parameters, exported signatures, empty containers (const xs: User[] = []) — and let outputs infer.

Your API helper returns any. Why is that worse than returning unknown?

any disables checking for every value derived from it, so a typo like user.nmae compiles fine and fails in production. unknown forces one narrowing at the call site and keeps every downstream type real.

req(opts) fails but req({ method: "GET" }) works. Why?

Passing the literal directly gives TypeScript no reason to widen — it checks it against the parameter type immediately. Storing it in a const first widens method to string, because the object is mutable and someone could assign to it later. as const or satisfies fixes it.

2.1 Arrays and readonly arrays

Use readonly on parameters, almost always

function total(items: readonly Item[]) documents that the function will not mutate its argument, and the compiler enforces it. Callers can still pass a normal array — string[] is assignable to readonly string[], just not the reverse. It costs one word and prevents a whole class of surprising bug.

2.2 Tuples: position carries meaning

When a tuple is the wrong tool

If you find yourself writing const name = row[3], the tuple has too many elements — use an object. Tuples are right for exactly two situations: pairs where position is obvious (coordinates, key/value), and returning two things from a function where the caller destructures immediately (React’s useState is the famous example).

2.4 Structural typing

Why the same object is accepted one way and rejected the other

Because a variable might legitimately be a wider object used in several places, while a literal written at the call site is almost certainly a typo. It is a deliberate special case, and knowing it exists saves an afternoon.

2.5 Union and intersection

Intersections of primitives are never

string & number is a type with no possible value, which TypeScript calls never. If a type resolves to never unexpectedly, an intersection somewhere has contradicted itself — usually two interfaces declaring the same property with different types.

Checkpoint

Give two concrete reasons to prefer a string-literal union over a numeric enum.

1. It emits no runtime code, while an enum emits an object with a reverse mapping. 2. The values are self-describing in logs and JSON — "admin" rather than 0 — and it narrows in switch without importing anything.

Why is greet(dog) allowed but greet({ name: "Miu", legs: 4 }) not?

Structural typing accepts dog because its shape includes everything Named requires. The object literal triggers excess property checking, which rejects properties the target type cannot possibly use — on the assumption that a property written at the call site and never read is a mistake.

When is a tuple better than an object?

When there are exactly two or three elements, position is unambiguous, and the caller destructures immediately — const [value, setValue] = useState(). Once you need row[3], the meaning has stopped being obvious and an object is clearer.

3.1 Signatures

Return types: annotate exported functions

Inference gets the return type right almost always. Annotate it anyway on anything exported: it turns a change in the body from a silent ripple through your callers into one error at the source. Inside a module, let it infer.

3.2 Optional, default, rest — and the difference that catches people

3.3 The rule that looks backwards

You write an event handler that needs more information than the handler type provides. TypeScript rejects it, and the reason is worth understanding once, properly.

Parameters are contravariant. Returns are covariant.

A function is substitutable for another if it demands less and provides more. So parameters may be wider than required and return types may be narrower. This is enforced by strictFunctionTypes (§A.2) — and note that method syntax in an interface is deliberately exempt, for backward compatibility with the DOM. That exemption is a known hole, not a feature.

3.4 Overloads

Prefer a generic or a union first

Overloads are unchecked against the implementation: TypeScript does not verify that parse(v: string): string[] actually returns strings. A generic (chapter 4) or a union return is checked. Reach for overloads only when the return type genuinely varies by input type and no generic expresses it.

3.5 Interfaces in anger

3.6 satisfies

Added in TypeScript 4.9, and it solves a problem that used to have no clean answer: check this value against a type, but keep the narrow type you inferred.

A rule of thumb for the three

Annotation (: T) — when you want the value treated as T and nothing more. satisfies — when you want it checked against T but used at its real, narrower type. as — when you are overriding the compiler and taking responsibility. Reach for them in that order.

Checkpoint

Why is a handler that takes a more detailed event rejected?

Because the caller only promised to supply the declared parameter type. Your function would read a property that may not be there. Parameters are contravariant: a substitute may accept more kinds of input, never fewer.

When would you deliberately write b: number | undefined instead of b?: number?

When forgetting the argument should be an error. ? lets a caller omit it silently; the union forces them to write undefined, which means they thought about it. Useful for options objects assembled programmatically, where a missing key is usually a bug.

What does satisfies do that an annotation cannot?

It validates the value against a type without widening it. The annotation replaces the inferred type with the declared one, losing literal types and precise property types; satisfies checks and then leaves the inferred type alone.

This is how Exclude works

type Exclude<T, U> = T extends U ? never : T. Because it distributes, each member of the union is tested separately, and the ones that match become never — which vanishes from a union. Four words of syntax, and it is the whole implementation.

5.5 Building DeepReadonly

Where recursion stops being free

Recursive conditional types are limited to about 100 levels — deeper and you get TS2589: Type instantiation is excessively deep. In practice you hit it not with deep data but with recursive string types (parsing a path like "a.b.c.d"). If it happens, add an explicit depth counter as a tuple type parameter and stop at 10.

5.6 Template literal types

The combinatorial trap

Ten methods × fifty paths × five locales is 2,500 union members, and the compiler will build every one. Union sizes in the tens of thousands make your editor slow and eventually error with TS2590. Template literal types are for small, closed sets — HTTP methods, CSS properties, event names — not for modelling every possible string.

Checkpoint

Why does Distributed<string | number> give a union but NoDist does not?

Because a naked type parameter on the left of extends distributes: the conditional is applied to each union member and the results are unioned. Wrapping both sides in a tuple — [T] extends [string] — makes the check apply to the union as a whole.

In DeepReadonly, why is the array case tested before the object case?

Because an array is an object, so T extends object would match arrays first and map over their numeric keys and methods instead of their elements. Conditional types are checked in order, so the more specific case must come first.

Your build gets slow after adding template literal types. What happened?

You almost certainly multiplied two large unions. The compiler materialises every combination, so 10 × 50 is 500 members and grows fast. Narrow one of the unions, or replace the template with a plain string plus a runtime check at the boundary.

TypeScript gives JavaScript classes the vocabulary of a typed OO language. One of those words — private — does less than it looks like it does.

6.1 The shape of a class

UseWhen
interfaceA contract with no shared code. Many can be implemented at once.
abstract classA contract plus shared implementation or state. Only one can be extended.
A plain classNo contract needed yet. Add one when a second implementation appears.

6.2 private is a suggestion. # is not.

Which to use

Use # when the value must genuinely not be reachable — credentials, internal state a library consumer could corrupt, anything where “someone will find a way” is a real risk. Use private for ordinary encapsulation inside your own codebase, where the compiler is a sufficient referee and the friendlier syntax is worth it. Note that # fields are invisible to JSON.stringify, Object.keys and most test spies — which is the point, and occasionally an annoyance.

6.3 Inheritance, and the method that silently does nothing

The flag that catches it

noImplicitOverride (§A.5) requires the override keyword on any method that replaces a parent method. Then override gret() is an error, because there is nothing called gret to override. It is not in strict; turn it on in any project with a class hierarchy.

The test, stated precisely

Inherit when the subclass is the parent in every context the parent is used — anywhere a Shape is accepted, a Circle must work, with no caller checking which it got. That is the Liskov substitution principle, and the moment a caller writes if (x instanceof Circle) the hierarchy has already failed it. Otherwise, compose.

6.4 Statics, this, and factories

this in a callback still loses its binding

Types do not fix runtime this. setTimeout(this.tick, 100) still calls tick with this === undefined. Bind it, or declare it as an arrow-function property: tick = () => {...}. Turning on noImplicitThis (part of strict) catches the cases the compiler can see, but not this one.

6.5 Implementing several interfaces

implements checks; it does not add

implements is a compile-time assertion that the class has the right shape. It does not give the class any members, and it does not change the emitted code — because TypeScript is structural (§2.4), a class with the right shape satisfies the interface whether or not it says implements. Writing it anyway moves the error from the call site to the class, which is where you want it.

Checkpoint

Your colleague stores an API key in a private field. What do you tell them?

That private is erased at compile time — the field is an ordinary public property in the shipped JavaScript, readable with (obj as any).key or from the browser console. Use #key, which is enforced by the runtime. Better still, do not put the key in the client at all.

A method override stops working after a rename. How could the compiler have caught it?

noImplicitOverride. It requires the override keyword on replacing methods, so a typo becomes “this member cannot have an override modifier because it is not declared in the base class” instead of a silent second method.

When is abstract class right and interface wrong?

When there is shared implementation or state — describe() in Listing 6.1 calls the abstract area() and every subclass gets it free. An interface has no bodies and no fields, so that method would have to be copied into every implementation.

7.1 Type-only imports

verbatimModuleSyntax makes this compulsory

With that option on (a default in tsc --init — §A.1), the compiler no longer guesses which imports were types and drops them. What you write is what you get, so an import you use only as a type must be marked type. This is stricter and much more predictable: no more “my import disappeared” and no more accidental circular runtime imports.

The bug this prevents

Importing a class purely for its type, in a project with side-effecting modules, used to keep the runtime import alive and could create an import cycle that crashed at startup — a failure with no connection to the line that caused it. import type makes the dependency provably compile-time.

Turn on declarationMap too

declaration: true gives consumers types. declarationMap: true gives them go-to-definition that lands in your source instead of the generated .d.ts. In a monorepo this is the difference between navigating your own code and staring at signatures. Both are defaults in tsc --init now.

7.4 Publishing types that actually resolve

Verify it before publishing

Run npx @arethetypeswrong/cli --pack . in the package directory. It resolves your package the way every real consumer configuration would — ESM, CJS, node10, bundler — and names each one that fails. It catches the exports ordering bug above, missing .d.cts files, and the “masquerading as ESM” problem, none of which your own build will ever notice.

7.5 Barrel files, and their cost

Why a barrel slows everything down

Importing one symbol from a barrel makes the compiler load and check every module the barrel re-exports, and at runtime a bundler must prove each one is side-effect-free before it can drop it. In a large repo this shows up as slow editor response and bundles containing modules you never used. Export a barrel at your package boundary; inside the package, import the specific file. Add "sideEffects": false to package.json so bundlers are allowed to shake the rest.

Checkpoint

Why mark an import type when the compiler could work it out?

Because with verbatimModuleSyntax it no longer works it out — and that is an improvement. The emitted imports become exactly what you wrote, so a type-only dependency can never create a runtime import cycle or drag a module into the bundle.

Why does namespace behave like enum?

Both are the two TypeScript-era constructs that emit runtime code rather than being erased — an IIFE building an object. Both predate the JavaScript features that replaced them (modules and union types), and both break single-file transpilers under isolatedModules.

Consumers of your package get any for everything. Where do you look?

At exports in package.json: the "types" condition must come before "import" and "require", because conditions match in order. Then run @arethetypeswrong/cli, which reproduces every consumer resolution mode and names the broken one.

The Compiler API

The compiler is a library. You can parse a file, ask what type an expression has, and build tools that know what your code means rather than what it looks like.

9.1 Which version to install

The API is not in TypeScript 7 yet

This is the one place in the book where you should not use version 7. The Go rewrite (§0.3) has not yet shipped a stable JavaScript API. require("typescript") in 7.0.2 resolves to a module exporting exactly two things — version and versionMajorMinor. The real surface lives behind typescript/unstable/sync, typescript/unstable/ast and friends, and the word in the path is meant literally.

So: npm i -D typescript@5.9.3 for compiler-API work. Everything in this chapter runs on it, the API is stable, and every tool in the ecosystem — ESLint, ts-morph, API Extractor — is still built on it. Watch typescript/unstable for when this stops being true.

9.2 Parsing: source text to AST

forEachChild versus getChildren

forEachChild visits semantic children and skips punctuation. getChildren visits every token including commas, braces and keywords — which you want for a formatter and never want for analysis. Using the wrong one is the second most common bug in a first compiler-API script.

9.3 The type checker

Set lib explicitly, or you get the DOM

Leave lib out and the default includes lib.dom.d.ts, which declares globals like name, length, event and status. A top-level const name = ... in the analysed file then reports TS2451: Cannot redeclare block-scoped variable — an error that has nothing to do with the code being analysed. Ask for the libs you mean.

Chapter Twelve · Part V

Functional Patterns

Not a conversion attempt. Three or four ideas from functional programming are worth adopting in ordinary TypeScript, and the type system makes them cheap.

By the end of this chapter you will be able to
  • Model failure as a value with Result instead of exceptions
  • Compose functions with a typed pipe
  • Explain currying and when it helps
  • Say why full monad stacks rarely survive contact with a team

12.1 Result: errors that the compiler can see

An exception is invisible in a type. function parse(s: string): number says nothing about the fact that it throws. A Result puts the failure in the return type, where the compiler can force you to handle it.

Where to draw the line

Use Result for expected failures: validation, parsing, a lookup that may miss, an HTTP call that may 404. Keep exceptions for bugs and catastrophes: a null where the type said there is none, out of memory. If every function returns a Result, you have rebuilt checked exceptions, and Java already ran that experiment.

12.2 pipe, and why it needs overloads

Before you install a library for this

Native chaining already composes: arr.filter(...).map(...).reduce(...). pipe earns its place when the steps are named functions defined elsewhere and you want them in reading order. If your pipeline is three inline arrows, a couple of intermediate consts are clearer and debuggable line by line.

12.3 Currying

Currying versus an options object

Curry when the early arguments are fixed for a whole subsystem and the last one varies per call — a logger bound to a module name, a formatter bound to a locale, a fetcher bound to a base URL. For everything else, one call with an options object is easier to read and easier to extend, because adding a parameter does not change the shape of every call site.

12.4 Immutability, in practice

Structural sharing without a library

{ ...state, count: state.count + 1 } and [...xs, x] cover most updates and are what React, Redux and Zustand expect. Reach for Immer only when the update is deeply nested — five levels of spread is where the spread operator stops being readable and starts being a bug factory.

12.5 Where this stops being worth it

PatternVerdict in ordinary TypeScript
Result / EitherAdopt. Twenty lines, and errors become visible in types

pipeAdopt for named-function pipelines
CurryingAdopt narrowly (§12.3)
Functors, applicatives, monad transformersRarely. The type signatures outgrow the team before the benefits arrive
Phantom types / branded typesAdopt for units and ids — see below

Checkpoint

What does Result give you that throw does not?

Visibility. An exception is absent from the signature, so nothing forces a caller to handle it and nothing tells them it exists. A Result return type cannot be unwrapped without checking ok, so the compiler enforces exactly what a code review would have to catch by eye.

Why does pipe need one overload per number of arguments?

Because each arity threads a different chain of type variables — A→B, then A→B→C, and so on. A single rest-parameter signature can only say unknown for the intermediate types, which loses the final type. Variadic tuple types can express it, but the overloads produce far better errors.

Why are branded types worth it when full FP usually is not?

Because the cost is three lines and no runtime, and the payoff is a real bug class eliminated — passing a user id where an order id belongs, or metres where seconds belong. Monad stacks, by contrast, cost the whole team a new vocabulary before anything gets safer.

Coercion is a loaded gun

The rule for the whole migration

Every commit must be releasable. A migration that lives on a branch for six weeks will lose a race with the product roadmap. Convert leaves first — files with no imports of your own code — because their types are decided by the standard library, not by files you have not converted yet.

Turn it off and use // @ts-check as the first line of individual files instead. Then the count is whatever you choose to take on this week, and each file that gets the comment is a file that stays checked. The reverse escape hatch is // @ts-nocheck, for the one file that is not worth it yet.

15.5 Codemods for the mechanical part

What a codemod must not decide

Codemods are good at syntax and bad at meaning. Rewriting require to import is mechanical. Deciding whether a parameter is string or string | null is a judgement about the program, and a codemod that guesses will insert a hundred confident lies that all type-check. Automate the shape; type the meaning by hand.

The error-count ratchet

Record the current error count in a file. CI fails if the number goes up, and prints a reminder to lower the number when it goes down. It costs about fifteen lines of shell and it is the only mechanism in this chapter that keeps working after everyone loses interest in the migration.

Checkpoint

Why start with allowJs and JSDoc rather than renaming files?

Because steps 1–3 change no filenames, so every commit is small, reviewable and shippable, and the team keeps delivering features throughout. Renaming first produces one enormous pull request that conflicts with everything and ships late or never.

What can JSDoc types not express?

Conditional and mapped types, and the more advanced generic constructions of chapter 5. Nearly everything else — parameters, returns, generics via @template, unions, satisfies, imported types — has a JSDoc form and is checked identically.

Why does strictNullChecks come before noUncheckedIndexedAccess?

Because noUncheckedIndexedAccess produces far more errors, and a large share of them are already fixed once strictNullChecks has forced proper handling of absent values. Doing it in the other order means fighting the same code twice.

Chapter Sixteen · Part VII

Language Service Plugins

Everything your editor knows about TypeScript comes from one object. A plugin wraps it, and adds completions, diagnostics and quick fixes that understand your project specifically.

By the end of this chapter you will be able to
  • Explain what the language service is and how the editor uses it
  • Drive it directly to get quick info, completions and diagnostics
  • Write a plugin that adds a diagnostic
  • Say why a plugin must never be slow

16.1 What the editor is actually talking to

VS Code does not parse your TypeScript. It runs tsserver — the compiler in a long-lived process — and asks it questions over a JSON protocol. Every hover, every red squiggle, every rename is a call to a LanguageService object.

Why it is a service and not a compiler run

The service is incremental. It keeps a program alive and re-uses every unchanged source file between keystrokes, so answering a hover costs milliseconds rather than the seconds a full createProgram takes (§9.5). A plugin lives inside that loop, which is why §16.4 matters.

16.4 Plugins run between keystrokes

The performance budget

Your plugin runs on every diagnostic pass, which is roughly every time the user stops typing. A hundred milliseconds of work makes the editor feel broken, and users will blame TypeScript rather than your plugin. Three rules: never call getProgram() more than once per invocation; never walk the AST when a regex over the text will do; cache anything derived from a file against its version and throw the cache away when the version changes.

Checkpoint

What does the proxy in Listing 16.4 do, and what breaks without the loop?

It forwards every language service method to the real implementation so the editor keeps working, and lets you override just one. Without the loop, proxy has only the methods you defined — so completions, hovers, go-to-definition and rename all silently stop working in that project.

Your plugin has no effect in VS Code. What is the most likely cause?

VS Code is running its own bundled TypeScript, which does not load workspace plugins. Run TypeScript: Select TypeScript Version → Use Workspace Version. Second most likely: the plugin package name in plugins does not resolve from the project directory.

Why does a plugin have a much tighter performance budget than a lint rule?

Because a lint rule runs on save or in CI, while a plugin runs between keystrokes inside the editor’s incremental loop. A hundred milliseconds is invisible in CI and is a visibly laggy editor here — and the user will experience it as TypeScript being slow.
