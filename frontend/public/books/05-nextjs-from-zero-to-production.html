About this book

Next.js is not hard because there is a lot of it. It is hard because your application now runs on two machines, and almost every confusing error is really a question about which one a particular function is on.

That is the thesis of this book, and it is why chapter A comes before chapter 1. Once the boundary is clear — what "use client" actually marks, what can cross it, what happens to a secret that ends up on the wrong side — the rest of the framework stops feeling arbitrary. Caching, streaming, Server Actions and partial prerendering are all consequences of that one split.

The second reason it is hard is that the framework has changed a great deal, publicly, in a short time — and the internet still contains every previous version of the advice. An article from 2024 will tell you fetch is cached by default. It was. It is not. This book is written entirely against Next.js 16.3.2, and where a widely repeated claim is now false, it says so and shows the current behaviour instead.

Who should read this

Someone who knows React and wants to build a real application with it. You should be comfortable with components, props, state and effects — Volume 1 of this series is that material — and reasonably fluent in TypeScript (Volume 4). Everything else is explained here.

How this book is organised

Chapter 0 places the framework and teaches you to read a build. Then three lettered supplements — the boundary, upgrading, and Turbopack — which the Code Lab track does not cover and every real project needs. Then chapters 1–16, mapping one-to-one onto the sixteen modules of the Next.js track in Code Lab, each ending with that module’s ten graded exercises.

Read chapter A before chapter 3. It is the one that makes everything after it make sense.

About the code

A single application was built alongside this book: routes, a route handler set, a Server Action, a cached function, parallel and intercepting routes, a proxy, and a test suite. Every next build table, every curl transcript, every error message and every measurement is that application’s real output. When the book says a build fails, the build failed; the message is pasted, not paraphrased.

Three things in version 16 that break older writing

1. params and searchParams are promises — every pre-2025 example is wrong (§0.3). 2. Caching is off by default and opted into with "use cache", the reverse of versions 13 and 14 (chapter 10). 3. middleware.ts is now proxy.ts, and Turbopack is the default bundler (§C).

Chapter Zero · Orientation

What Next.js Is, and What Changed

A React framework that decided where your code runs. Almost every difficulty with it is really a question about which side of the network your function is on.

By the end of this chapter you will be able to
  • Explain what Next.js adds to React, and what it takes away
  • Say what the App Router changed and why the Pages Router still exists
  • Name the three things in version 16 that invalidate older tutorials
  • Read a next build route table

0.1 React with the deployment decided

React renders components. It has nothing to say about routing, data fetching, bundling, or which machine any of it happens on. For a long time you assembled those yourself — React Router, Webpack, an Express server, a CDN — and every team assembled them slightly differently.

Next.js is the assembly, made by the React team’s closest collaborators and now, in practice, the reference implementation of React’s server features. What you get:

Next.js gives youYou would otherwise wire up
Routing from the filesystemReact Router, by hand
Server rendering and streamingA custom Node server
Server ComponentsNothing — they do not work without a framework
Bundling, code splitting, minificationWebpack or Vite, configured
Image, font and script optimisationThree more libraries
Caching with tags and revalidationA cache layer and an invalidation story
And what it takes away

Control. Next.js has strong opinions about file layout, about where data fetching belongs, and increasingly about caching. When those opinions match your application it removes months of work; when they do not, you fight the framework. The honest guidance: if you are building something with pages, a CMS, auth and SEO, this is close to the best tool available. If you are building a canvas editor or a desktop-like single-page app, Vite plus React Router (Volume 1, chapter D) is less framework for the same result.

0.2 A short history, because it explains the confusion

Why every tutorial disagrees with every other

There are two complete, coexisting ways to build a Next.js app — the pages/ directory and the app/ directory — and they have different data-fetching APIs, different caching, and different mental models. An article that opens with getServerSideProps is Pages Router; one that opens with an async function Page() is App Router. Both still work in version 16. This book is entirely App Router, with §B covering what to do if you have a Pages Router codebase.

0.3 Three things version 16 changed under the tutorials

1 · params is a promise

Since version 15, params and searchParams are promises and must be awaited. Every pre-2025 example destructures them synchronously and will not compile:

export default async function Post({ params }: { params: Promise<{ slug: string }> }) { const { slug } = await params; }

This was done so a page can start streaming before the router has finished resolving dynamic segments — the cost is one await and a great deal of stale documentation.

2 · Caching is opt-in now, and then opt-in again

Next 13 and 14 cached fetch by default, which surprised everyone by serving stale data. Version 15 reversed it: fetch, route handlers and client navigations are uncached unless you say otherwise. Version 16 adds Cache Components — "use cache" plus cacheLife — as the explicit replacement (chapter 10). If an article says “Next caches your fetches automatically”, it is describing version 14.

3 · Turbopack is the default bundler

next dev and next build both use Turbopack in version 16; Webpack is opt-out. Custom webpack: configuration in next.config.js is the single most common upgrade blocker (§C).

One React idea you must have straight

A component is a function that returns a description of UI. Next.js runs some of those functions on a server and some in a browser, and the entire difficulty of this book is knowing which. If that sentence is not yet solid, read Volume 1 chapter 2 before chapter 3 here.

Checkpoint

You find a tutorial using getServerSideProps. Is it wrong?

No — it is Pages Router, which still works in version 16. It is simply a different framework inside the same package, with different data fetching and different caching. Do not mix its advice with App Router code; the two do not share APIs.

A route you expected to be static shows as ƒ in the build output. What happened?

Something in it read a request-time value — cookies(), headers(), searchParams, or an uncached fetch with no-store. One such call anywhere in the tree makes the whole route dynamic. Chapter 10 covers finding the offender and isolating it behind a Suspense boundary.

Why did params become a promise?

So rendering can begin before dynamic route segments are resolved, which is what makes partial prerendering possible. The practical consequence is that every page reading params must be async and await it, and that most published examples predate the change.

Chapter A · Supplement

The Boundary

One idea explains most Next.js confusion: your application is split across two machines, and the split is drawn by a string literal at the top of a file.

By the end of this chapter you will be able to
  • Say which of your components run on the server and which run in the browser
  • Explain what "use client" actually marks
  • Predict what crosses the boundary and what cannot
  • Use server-only to make a leak a build error

A.1 Two runtimes, one codebase

In a plain React app every component runs in the browser. In Next.js App Router, every component is a Server Component by default — it runs on the server, once, and what reaches the browser is the result, not the code.

Server ComponentClient Component
Marked bynothing — the default"use client" at the top of the file
RunsOn the server, during the request or the buildIn the browser, and once on the server for the initial HTML
Canawait a database query, read env vars, read filesUse useState, useEffect, event handlers, browser APIs
CannotUse hooks or event handlersTouch a database, read secrets, use fs
Ships to the browserNo JavaScript at allIts code, plus its imports

Table A.1 The last row is the reason the whole design exists: a Server Component that renders a 300 kB Markdown library ships zero kilobytes of it.

A.2 What "use client" really marks

It is a boundary, not a label

"use client" does not mean “this component runs in the browser”. It means “from here down, everything is client code”. Every module this file imports — and everything those import — becomes part of the client bundle, whether or not it says "use client" itself. One directive at the top of a barrel file can move your entire application into the browser.

Push the directive down, not up

The instinct when something needs useState is to put "use client" at the top of the page. The correct move is to extract the interactive part into its own file and mark that. A page that is a Client Component cannot await anything and has just pulled every one of its imports into the bundle.

A.3 What can cross

Props passed from a Server Component to a Client Component are serialised — turned into a stream, sent over the network, and rebuilt in the browser. So the rule is simple and unforgiving:

CrossesDoes not cross
Strings, numbers, booleans, nullFunctions (except Server Actions)
Plain objects and arraysClass instances — a Date survives, a User class does not
Date, Map, Set, BigIntSymbols, Error objects
Promises — the client can use() themAnything with a closure over server state
JSX elementsReact elements holding non-serialisable props

Table A.2 Passing a function down produces “Functions cannot be passed directly to Client Components”. The exception is a Server Action (chapter 13), which crosses as a reference the browser can call.

The ORM trap

Prisma, Drizzle and most ORMs return objects that look plain and are not — Decimal, Buffer, sometimes class instances. Passing a query result straight into a Client Component throws at render time with a message about serialisation. Map to a plain shape at the boundary; it also stops your database schema from becoming your component API.

A.4 Making a leak a build error

Install it in every project, on day one

npm i server-only, then one import at the top of every module that touches a database, a secret, or the filesystem. There is a matching client-only for modules that must not run on the server (anything touching window at module scope). Two packages, four lines, and a class of security bug becomes impossible.

A.5 Where the environment variables go

NameVisible toUse for
DATABASE_URLServer onlyEverything secret
NEXT_PUBLIC_SITE_URLThe browser — inlined into the bundleOnly what is genuinely public

Table A.3 The NEXT_PUBLIC_ prefix is not a hint, it is a switch: the value is substituted into the client JavaScript at build time and is readable by anyone.

Two consequences people learn the hard way

1. A NEXT_PUBLIC_ variable is baked in at build time, so changing it in your host’s dashboard does nothing until you rebuild. 2. Anything you accidentally prefix is public forever — it is in every copy of the bundle already served. Rotate the secret; do not just rename the variable.

Checkpoint

Adding "use client" to one file made your bundle much larger. Why?

Because it marks a boundary, not a component: every module reachable from that file becomes client code. If the file imports a barrel (@/components) or a heavy utility, all of it is now bundled. Move the directive down to the smallest file that genuinely needs interactivity.

Passing a Prisma result into a Client Component throws. What is the fix?

Map it to a plain object at the boundary — { id, name, price: price.toString() }. ORM results contain non-serialisable values (Decimal, Buffer, class instances) that cannot cross. The mapping also stops your database schema from leaking into your component props.

What does server-only buy you that code review does not?

Certainty. It turns “someone might import the database module into a client component” into a build failure, with an import trace naming the exact path. Review catches it sometimes; the build catches it every time, including the transitive cases nobody would spot.

Chapter B · Supplement

Upgrading, and the Two Routers

Most Next.js codebases in the world are not on the current version. This chapter is the route from wherever you are to version 16, without a rewrite.

By the end of this chapter you will be able to
  • Decide whether to migrate from Pages Router at all
  • Run the codemods and know what they cannot fix
  • Handle the breaking changes in 15 and 16 in order
  • Run both routers side by side while you migrate

B.1 First: should you migrate?

SituationRecommendation
Pages Router, working, no new features plannedStay. It is still supported and receives fixes
Pages Router, actively growingMigrate route by route (§B.4)
App Router on 13 or 14Upgrade. The caching defaults alone are worth it
App Router on 15Straightforward — §B.3
New projectApp Router, version 16, no question
The honest cost of a Pages → App migration

It is not a syntax change. getServerSideProps has no equivalent — the data fetching moves into the component. _app.tsx and _document.tsx become layout.tsx. Any library that assumed it ran in the browser needs a "use client" boundary (§A.2). For a large app, budget weeks, not days — and do it incrementally, because both routers run in the same application.

The React 19 peer-dependency wall

The most common thing that actually blocks a version 16 upgrade is not Next.js — it is a UI library still declaring "react": "^18". Check with npm ls react before starting. If a library is unmaintained, that is a decision to make now rather than halfway through.

B.5 A worked upgrade checklist

The order that keeps every commit shippable

1. npm ls react — resolve peer conflicts first. 2. Upgrade one major version. 3. Run the offered codemods; commit them alone, with no manual edits mixed in. 4. next build and fix type errors. 5. Run the app and click through the ten most important routes. 6. Compare the build’s route table with the previous one — routes that changed from ○ to ƒ are your caching regressions. 7. Add caching back deliberately. 8. Only then start the next major version.

Step 6 is the one people skip

Save the route table from next build before upgrading. After the upgrade, diff them. A route that silently became dynamic will not fail any test, will not appear in any error log, and will quietly multiply your server bill. The build output is the only place it shows.

Checkpoint

Should a working Pages Router app be migrated?

Not necessarily. It is still supported, and the migration is a real project — data fetching moves into components, layouts change shape, and client-only libraries need boundaries. Migrate if the app is actively growing and you want Server Components; otherwise upgrade the version and stay.

You ran every codemod and the site is correct but slower. What happened?

Version 15 stopped caching fetch by default. Requests that were silently cached now hit the origin every time. No codemod can decide which ones should be cached — that is a judgement about your data, and chapter 10 is how to express it.

Why compare the route tables before and after an upgrade?

Because a route changing from ○ Static to ƒ Dynamic is a large performance and cost regression that produces no error, no failing test and no log line. The build output is the only place it is visible.

Chapter C · Supplement

Turbopack and the Build

The bundler changed. Most projects notice nothing; the ones that notice are the ones with a custom Webpack configuration, and this is what to do about it.

By the end of this chapter you will be able to
  • Say what Turbopack is and why it replaced Webpack
  • Measure the difference on your own project
  • Port the three most common Webpack customisations
  • Fall back safely when something genuinely will not port

C.1 What changed

Turbopack is a bundler written in Rust by the Next.js team, incremental by design: it caches at the level of individual functions, so a change to one file re-does only the work that file affected. In version 16 it is the default for both next dev and next build.

Where you actually feel it

Not the production build, which happens on CI while you do something else. It is the dev server: cold start and the delay between saving a file and seeing the page update. On a large App Router codebase that is the difference between a few hundred milliseconds and several seconds, several hundred times a day.

C.2 Porting a Webpack config

Prefer deleting the customisation

A large share of Webpack config in Next.js projects is either obsolete (path aliases, which tsconfig.json paths now handles) or working around something the framework has since absorbed. Before porting a rule, check whether it is still needed at all — the fastest migration is the one where you delete four of the five entries.

C.3 Analysing what you shipped

What to look for, in order

1. A dependency you did not expect in a client bundle at all — almost always a "use client" file importing a barrel (§A.2). 2. Two copies of the same library at different versions — npm ls name will show which dependency pinned the second. 3. A date or icon library imported wholesale rather than per-symbol. Those three account for most of the bloat in most applications.

C.4 When it will not port

SymptomLikely cause

A custom plugin mutates the compilationNo equivalent by design; rethink the approach
“Module not found” only under TurbopackA dependency relying on Webpack-specific resolution — usually fixed by an explicit resolveAlias
Builds fine, breaks at runtimeA Node builtin polyfilled by Webpack and not by Turbopack — shim it explicitly
Report it

Turbopack’s remaining gaps are tracked publicly and closed quickly, and a reproduction from a real project is genuinely useful. next info prints the environment block that a good issue needs.

Checkpoint

Where does Turbopack actually save you time?

In the dev server. Production builds run on CI while you do something else; the rebuild after every file save happens hundreds of times a day and is where an incremental Rust bundler changes how the work feels. The cold-build ratio (2.3× here) understates it.

Your next.config.js has a webpack: function. What do you do first?

Read each entry and ask whether it is still needed — path aliases now live in tsconfig.json, and several old workarounds have been absorbed by the framework. Port what remains to turbopack.resolveAlias and turbopack.rules, and use --webpack as a temporary fallback if one entry genuinely has no equivalent.

A dependency appears twice in your bundle. How do you find out why?

npm ls name shows the whole dependency tree for that package and which parent pinned each version. The fix is usually a version alignment or an overrides entry — not a bundler setting.

1.1 A project

Fix the generated tsconfig before you write anything

create-next-app writes "strict": false. That switches off strictNullChecks and noImplicitAny — the two flags carrying most of TypeScript’s value (Volume 4, §A.2). Set it to true on day one, while the fix is four errors instead of four hundred.

Checkpoint

Why is "strict": false in the generated tsconfig worth fixing immediately?

Because it disables strictNullChecks and noImplicitAny, so nothing warns you about the undefined that will crash the page. Fixing it on day one costs a handful of errors; fixing it a year later costs hundreds, and by then the team has learned to work without it.

What is the practical difference between layout.tsx and template.tsx?

A layout persists across navigations — its state and DOM survive, which is why a sidebar keeps its scroll position. A template remounts every time, which you want for an enter animation or an effect that must run per navigation. Default to layout.

What does putting "use client" in the root layout do?

Makes the entire application a client bundle, because the directive marks a boundary and everything below it inherits (§A.2). You lose Server Components, direct data access, and the bundle-size benefit all at once. The root layout should stay a Server Component permanently.

3.2 What actually reaches the browser

Not HTML, and not your code

A Server Component is rendered on the server into the RSC payload — a compact stream describing the resulting element tree, plus references to the Client Components that need hydrating. The browser gets HTML for the first paint and that payload, which lets React reconcile without re-running your server code. On a client navigation only the payload is fetched, which is why moving between routes does not reload the shell.

Two consequences worth internalising

1. Anything a Server Component closes over stays on the server, so a large parsing library used only during render costs zero kilobytes. 2. Props passed down to a Client Component do cross, serialised, and appear in the payload — so a Server Component that fetches a 2 MB object and passes it to a small client widget has sent 2 MB to the browser. §A.3.

3.3 Waterfalls, and how to not have them

When you truly cannot parallelise

Do not block the page on it. Render the part you have, put the slow part behind its own Suspense boundary, and let it stream in (chapter 11). The user sees the page immediately and the slow section fills in — which is better than either waterfall.

3.4 Where to put the data access

Deduplication is automatic for fetch, and not for anything else

React deduplicates identical fetch calls within a single render pass, so three components calling fetch("/api/user") produce one request. A database call is not deduplicated. Wrap it in React’s cache() if several components need the same row in one render:

export const getUser = cache(async (id: string) => db.user.findUnique({ where: { id } }));

The composition trick that keeps the boundary small

A Client Component may render a Server Component passed to it as children. So a client <Tabs> can wrap server-rendered panels: the interactivity is client, the content stays server. What it cannot do is import a Server Component — that pulls it into the client bundle. Pass it as a prop instead.

Checkpoint

Why is a Server Component that renders a 300 kB library free?

Because the library runs during the server render and never reaches the browser. Only the output — the element tree — is sent. A Markdown renderer, a syntax highlighter or a date library used purely to produce HTML costs zero client kilobytes.

Two awaits in a row, on independent data. What is wrong and what is the fix?

They run sequentially, so the page takes the sum of both. await Promise.all([a(), b()]) starts both immediately. Only chain awaits when the second call genuinely needs the first result — and if it does, consider streaming instead of blocking (chapter 11).

Can a Client Component render a Server Component?

Yes, if it receives it as children or another prop — the server rendered it, the client just places it. It cannot import one, because an import from a "use client" module makes the target client code (§A.2). “Pass, do not import” is the rule.

Why runtime CSS-in-JS is awkward here

It generates styles while components render — in the browser. A Server Component never runs in the browser, so there is no render pass to hook into, and styles arrive after the HTML: a flash of unstyled content. The workarounds all amount to marking the styled tree "use client", which surrenders the benefit of Server Components. If you are starting today, choose from rows 1–3 or 5.

5.2 CSS Modules and Tailwind

Tailwind, honestly

It suits this architecture unusually well: no runtime, no boundary problems, and the styles for a component travel with its markup, which matters when the markup might be server-rendered on one machine and hydrated on another. The cost is markup that reads like configuration. That is a genuine trade, not a flaw — decide it once, as a team, and stop relitigating it.

5.3 Fonts, without layout shift

The size-adjusted fallback is the important part

Cumulative Layout Shift from web fonts happens because the fallback has different metrics from the real face, so text reflows on swap. next/font computes size-adjust, ascent-override and friends for the specific font and emits a matching @font-face fallback. It is several hours of manual work that you get from one import.

7.2 Where the check goes

Why notFound() rather than a 403

A 403 confirms the record exists. Over enough requests that is an enumeration oracle: an attacker learns which ids are real. Returning 404 for “does not exist” and “not yours” alike tells them nothing.

7.3 The database connection

Serverless is the other half of this problem

On a serverless platform each concurrent request may be its own instance with its own pool, so a hundred concurrent requests can mean a hundred connections against a database that allows twenty. Use a pooler — PgBouncer, Prisma Accelerate, Neon’s or Supabase’s built-in pooler — or deploy to a long-lived Node server (chapter 8). Images without width/height (or fill with a sized container), and fonts loaded without a metric-matched fallback. next/image and next/font (chapter 5) address both, and between them account for most CLS on a typical page.

Distance to the database. Locally it is on the same machine; deployed it may be a continent away, and every query in a waterfall pays that round trip. Co-locate them, cut the number of queries, or cache — in that order of effect.

9.2 Intercepting routes

What it buys you

Click a product from the grid and it opens in a modal, with the URL updated to /shop/item/1. 9.3 default.tsx

The file that fixes the refresh

Slots are matched independently. On a client navigation Next.js remembers what each slot was showing; on a full page load it does not, and any slot with no match for the current URL renders default.tsx. Without one, the route 404s. Symptom: a dashboard that works while clicking around and breaks on refresh. Add default.tsx returning null to every slot that is not always present.

9.5 When not to

The honest guidance

Parallel and intercepting routes are the most complex feature in the App Router and the one most often used because it is interesting rather than because it is needed. A modal that does not need its own URL is a useState and a <dialog> — ten lines, no new concepts, and everyone on the team can read it. Reach for interception when the modal genuinely must be linkable and shareable: a photo in a gallery, a product detail, a shared document. That is a real requirement and this is the right tool for it. “It would be neat” is not.

Checkpoint

What does (.) in a folder name mean?

Intercept a route at the same level. (..) is one level up, (..)(..) two, (...) from the app root. The interception applies only to client-side navigation from within the app; a direct load or refresh gets the real route.

Your parallel-route dashboard works while clicking and 404s on refresh. Why?

A slot has no match for the current URL on a fresh load, and there is no default.tsx for it. On client navigation Next.js remembers the previous slot state; on a full load it has nothing to remember. Add default.tsx returning null.

The build says data was accessed outside a Suspense boundary. Which of the three fixes do you pick?

[stream] unless you have a reason not to — wrap the data access in Suspense so the shell still prerenders. Use [cache] when the data is shared and may be stale, and [block] only when the page is worthless without per-request data.

Chapter Eleven · Part IV

Streaming and Progressive Rendering

Send the page before the data is ready. One React feature — Suspense — and the framework does the rest.

By the end of this chapter you will be able to
  • Stream a page in parts instead of waiting for the slowest query
  • Choose between loading.tsx and an explicit boundary
  • Explain partial prerendering in terms of the build output
  • Avoid the two ways streaming makes things worse

11.1 The idea

What is actually on the wire

One HTTP response, chunked. The shell arrives with the fallbacks in place, then each resolved boundary arrives as a further chunk containing the real markup and an inline script that swaps it in. It works without client-side JavaScript for the initial render, and it works with the browser’s ordinary streaming HTML parser — no framework magic in the browser.

11.2 loading.tsx

UseWhen
loading.tsxThe whole route is slow and there is nothing useful to show first
Explicit <Suspense>Part of the page is fast — show it
BothA route-level fallback plus finer boundaries inside

Table 11.1 An explicit boundary is almost always better: loading.tsx replaces the entire page with a skeleton even though the header, nav and title were ready immediately.

Design the fallback to match

A skeleton whose shape differs from the real content produces a layout shift when it swaps — you optimised the perceived speed and damaged the CLS score. Give the skeleton the same box dimensions as the content it stands in for. A spinner of unknown size is the worst option available.

11.3 Partial prerendering

The build output tells you which routes are doing this. ◐ means a route has a static shell prerendered at build time and dynamic holes filled per request.

The rule to take away

A Suspense boundary is the line between what can be prerendered and what cannot. Move the boundary inward — as close to the dynamic data as possible — and more of your page becomes free. This is why chapter 10’s advice about the personalised corner works.

11.4 The two ways streaming makes things worse

1 · A boundary too high up

Wrapping the whole page in one Suspense is the same as not streaming: the user sees a skeleton until the slowest query finishes. The value is entirely in how much stays outside the boundary.

2 · Too many boundaries

Twenty independent boundaries produce twenty separate content swaps at unpredictable times. The page visibly assembles itself in front of the reader, which measures well and feels chaotic. Group related content into one boundary; three or four per page is usually the right order.

The buffering one costs people days

nginx buffers proxied responses by default, so the whole streamed response is collected before anything is sent — streaming works perfectly in development and does nothing in production. proxy_buffering off; for the Next.js location block. Some CDN configurations do the same.

Checkpoint

Why is the page component in Listing 11.2 not async?

Because it no longer awaits anything itself — each child fetches its own data and suspends. If the page awaited first, nothing below could stream: the response cannot start until the page function returns.

When is loading.tsx the wrong choice?

When part of the page is fast. loading.tsx replaces the whole route with a skeleton, so a header and nav that were ready immediately are hidden until the slowest query finishes. Put explicit boundaries around the slow parts instead.

Streaming works in development and not in production. Where do you look?

At whatever sits in front of the app. nginx buffers proxied responses by default (proxy_buffering off;), and some CDN configurations do the same. The application is fine; something downstream is collecting the whole response before forwarding it.

Proxy, Middleware and the Edge

Code that runs before every request. In version 16 the file is called proxy.ts, it runs in a restricted runtime, and the main skill is knowing what does not belong in it.

By the end of this chapter you will be able to
  • Write a proxy that rewrites, redirects and sets headers
  • Match only the requests you mean to
  • Say what the Edge runtime cannot do
  • Decide what belongs here and what belongs in the data layer

12.1 The file, and the rename

Why the rename

“Middleware” suggested an Express-style chain where you do work, call the database, and hand off. It is not that: it runs at the network edge, before routing, in a restricted runtime, and it is meant to route and rewrite. proxy describes the job accurately, and the rename is mostly an attempt to stop people putting authorisation logic in it.

12.2 The matcher

They must be static strings — you cannot build one from a variable or an environment value. If you need a runtime decision, match broadly and branch inside the function.

12.3 What it can and cannot do

Table 12.1 The Edge runtime is a Web-standard environment, not Node. fetch, crypto.subtle, URL and Request are available; pg and fs are not.

12.4 What does not belong here

Not authorisation

A proxy sees the request. It cannot cheaply check that a session is valid, not revoked, and permitted to read this record — that needs a database, which it cannot reach. A cookie-presence check in the proxy is a convenience redirect that improves the experience of signed-out users. The security boundary is in the data layer (§7.2), where the query happens and cannot be bypassed.

Not heavy work

It runs before every matched request, so its latency is added to your TTFB across the whole site. A ten-millisecond token verification is fine. A network call to an auth service is not — do it once, in the data layer, cached per request with React’s cache().

12.5 Per-route runtimes

“Edge” is not automatically faster

It cuts the network distance to the user. If the handler then queries a database in one region, you have moved the compute away from the data and added a round trip. Edge wins for responses that need no origin data — geolocation, redirects, feature flags, signed URLs. For anything database-backed, being close to the database usually wins.

Checkpoint

Why is a session check in the proxy not your security boundary?

Because it can only see the request. It cannot check that the session is unrevoked or that this user may read this record — that requires a database it cannot reach from the Edge runtime. Treat it as a redirect for convenience and put the real check in the data layer.

What happens if you omit matcher?

The proxy runs on every request, including every static asset, image and font — adding latency to hundreds of requests per page for no benefit. Always exclude _next/static, _next/image and your image extensions.

Is moving an API route to the Edge runtime an optimisation?

Only if it needs no origin data. Edge reduces distance to the user; if the handler then queries a database in one region, you have increased the distance to the data. Geolocation, redirects and feature flags win at the edge; database-backed endpoints usually do not.

13.2 The security property nobody expects

An action is a public HTTP endpoint

The form is a convenience for your users; it is not a gate. Every action must authenticate and authorise on its own, and validate every input — exactly as if it were a public API, because it is one.

The test for a shared package

Could it be published to npm and used by a stranger? If yes, it is a real package with a real boundary. If it only makes sense because of what one of your apps happens to do, it is a folder in that app that has been given a package.json.

Checkpoint

Why point a shared package’s exports at TypeScript source rather than a built dist/?

Because Next.js compiles it anyway, so a build step adds a watch process, a stale-output failure mode, and a source-map indirection for nothing. Source exports mean editing a shared component updates the app instantly, exactly like editing a local file.

Why per-file exports instead of an index barrel?

Because importing one symbol from a barrel pulls the whole package into the module graph — and if any file in it carries "use client", into the client bundle. Per-file exports keep the graph proportional to what you actually used.

Your app “feels big”. Is that a reason to split it into packages?

No. Package boundaries solve sharing between deployable units. A single application that is hard to navigate has a module-boundary problem — solve it with folders, lint rules on import paths, and a data layer, all of which are cheaper than workspace tooling.

16.2 Web Vitals from real users

Report percentiles, not averages

An average LCP of 2.1 s can hide a p75 of 4 s and a p95 of 9 s. Core Web Vitals are assessed at the 75th percentile, and a mean is arithmetic that conceals the users having a bad time. Store the raw values and aggregate at read time.

MetricBad because
LCP > 2.5 sThe main content is slow to appear
INP > 200 msThe page does not respond to taps

16.3 Tracing

What a trace shows that a metric cannot

A metric says the page took 1.8 s. A trace shows 1.2 s of it was three sequential database queries that could have been one Promise.all (§3.3) — and shows it as a staircase, which is unmistakable once you have seen it.

16.4 Errors

Why the message is useless in production

Next.js replaces server error messages with a generic string before they reach the browser, to avoid leaking internals, and gives you a digest hash instead. The real message is only in your server logs. If you only capture errors client-side, every production server error is an anonymous digest — instrument the server too.

16.5 Finding a regression

The order that works

1. Which metric moved, and at which percentile? 2. Which routes? If all of them, look at the server or the shared layout; if one, look at that route. 3. TTFB or paint? TTFB is server work — chapters 3 and 10. Paint is bundle size or images — §C.3 and chapter 5. 4. Diff the next build route table against the last deploy: a route that changed from ○ to ƒ is your answer more often than anything else. 5. Only now open a trace.

SymptomMost likely
Everything slower after a deployA route went dynamic, or caching was lost (chapter 10)
One route slowA waterfall or an uncached query (§3.3)
Slow only at peakConnection pool exhaustion (§7.3)
INP got worse, LCP did notMore client JavaScript shipped
CLS appearedAn image or font without reserved space (chapter 5)
Errors spiking with no code changeA dependency of yours is failing — check its own status
Save the route table with every release

Commit the output of next build, or store it as a CI artefact. It is a few kilobytes and it is the single most useful artefact you can have when a deploy makes the site slower — because it makes an invisible change (static → dynamic) into a line in a diff.

Checkpoint

Why is a Lighthouse score not enough?

It is a lab measurement on one machine and one connection. Real users are on slower devices and worse networks, and Core Web Vitals are assessed at the 75th percentile of real traffic. Lighthouse tells you what is possible; field data tells you what is happening.

A production error shows only a digest and no message. Where is the message?

In your server logs. Next.js strips server error messages before they reach the browser to avoid leaking internals, leaving a digest hash to correlate with. Instrument the server side, and show the digest to the user so support can quote it.

The site got slower after a deploy with no obvious cause. What do you check first?

The next build route table, diffed against the previous release. A route changing from ○ to ƒ is a large regression that produces no error and no failing test — and it is the most common cause of exactly this symptom.
