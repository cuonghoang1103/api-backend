About this book

Most SQL is learned by copying a query that worked and changing the table name. This book is the other way round: from what the database is doing, outward to what you should write.

PostgreSQL rewards that direction unusually well, because almost nothing about it is arbitrary. VACUUM exists because of MVCC. NOT IN loses rows because of three-valued logic. A LEFT JOIN becomes an inner join because NULL comparisons are not true. Each of those is a five-minute explanation that permanently removes a class of bug — and each of them is demonstrated here with output you can reproduce.

The rule for the whole book: every listing was executed before it was printed. The plans are real plans from a real 500,000-row table on the machine this was written on. The error messages are pasted, not paraphrased. Where a measurement did not support the claim it was supposed to illustrate — and that happened more than once — the claim was changed, not the measurement.

Who should read this

Someone who writes SQL and would like to stop guessing about what happens after they press enter. Chapters 1–7 assume nothing beyond a terminal. From chapter 10 onward the material is what a backend engineer needs and rarely gets taught: plans, locks, isolation, replication and the settings that decide whether a Tuesday is quiet.

How this book is organised

Chapter 0 places the database. Then three lettered supplements — modelling, reading EXPLAIN, and connecting from an application — which the Code Lab track does not cover and every real project needs. Then chapters 1–21, mapping one-to-one onto the twenty-one modules of the PostgreSQL track in Code Lab, each ending with that module’s ten graded exercises.

Read supplement B early — probably after chapter 6. Everything in the second half of the book is easier once you can read a plan.

About the cluster

A throwaway cluster created with initdb into a directory, running PostgreSQL 18.3 with PostGIS 3.6.4. The sample schema is four tables — authors, books, sales and half a million events — and it is created from a seed script before every rebuild of this book, so every number here is reproducible rather than remembered.

Three things in this book that are newer than most tutorials

1. Since PostgreSQL 12 a CTE is inlined, not an optimisation fence — the “CTEs are slow” advice expired in 2019 (§7.2). 2. COPY … ON_ERROR IGNORE arrived in 17 and changes how bulk loads handle bad rows (§18.3). 3. uuidv7() is built in as of 18, and it is not the same trade-off as v4 (§2.4).

Chapter Zero · Orientation

What PostgreSQL Is, and Why It Won

A relational database that spent thirty years being the careful option, and is now the default one. This chapter is what that means for the code you write.

By the end of this chapter you will be able to
  • Say what PostgreSQL guarantees and what it does not
  • Explain MVCC in one paragraph, and why VACUUM exists
  • Choose between PostgreSQL and the alternatives with a real reason
  • Read a version number and know what you are missing

0.1 Thirty years, and no owner

POSTGRES began at Berkeley in 1986 as Michael Stonebraker’s successor to Ingres. SQL support arrived in 1995 and the name became PostgreSQL a year later. It has never had a commercial owner: development is done by a global group under a permissive licence, and there is no paid edition with the good features in it.

That last point matters more than it sounds. There is no “PostgreSQL Enterprise”. Partitioning, replication, row-level security, full-text search, JSON, window functions — all of it is in the free database that ships in every Linux distribution.

Version numbers, briefly

Before version 10 it was 9.6.24 — two numbers for the major version. Since 10 it is one: 18.3 means major 18, patch 3. A major version is supported for five years; upgrading between majors needs pg_upgrade or a dump/restore, while patches are drop-in. If you are on 12 or older, you are running something out of support.

0.2 What it actually guarantees

PropertyMeansCosts
AtomicityA transaction happens completely or not at allAlmost nothing
ConsistencyConstraints hold at every commitConstraint checking
IsolationConcurrent transactions do not see each other’s partial workLocking and MVCC bookkeeping
DurabilityA committed transaction survives power lossAn fsync per commit

Table 0.1 The fourth is the one people disable to make benchmarks look good, and the one whose absence you discover during an outage.

What it does not give you

Horizontal write scaling. One PostgreSQL cluster has one primary that accepts writes. You can add read replicas, shard at the application layer, or use Citus — but there is no configuration flag that turns it into a distributed database. If you genuinely need multi-master writes across regions, that is a different product and a much harder set of trade-offs. Almost nobody needs it as early as they think.

0.3 MVCC, and why VACUUM exists

PostgreSQL never overwrites a row in place. An UPDATE writes a new version of the row and marks the old one as dead as of a particular transaction id. A reader looking at the table sees whichever version was current when its transaction started.

This is multi-version concurrency control, and it buys one enormous thing: readers never block writers, and writers never block readers. A long-running report does not stop anyone from updating the rows it is reading.

The cost, and the tool

Dead row versions accumulate. VACUUM reclaims them; autovacuum runs it for you in the background. Two consequences worth knowing on day one: a table that is updated heavily can grow far larger than its live data (bloat), and a very long-running transaction prevents vacuuming of everything newer than it, because those dead rows might still be visible to it. Most mysterious PostgreSQL disk-space problems are one of those two.

Table 0.2 The MongoDB row is the one that costs teams the most: JSONB (chapter 11) gives you schemaless documents inside a relational database, so the choice is rarely either/or.

The argument that actually settles it

PostgreSQL is boring in the good way. It is in every cloud as a managed service, every ORM supports it first, every hosting platform offers it, and the failure modes are documented by thirty years of people hitting them. Choosing it is rarely the interesting decision on a project, and that is the point.

Checkpoint

Why does PostgreSQL need VACUUM when other databases do not?

Because it never overwrites rows — an UPDATE writes a new version and marks the old one dead, which is what lets readers and writers avoid blocking each other. The dead versions have to be reclaimed, and that is what VACUUM does. It is the visible cost of MVCC.

A colleague wants MongoDB because the data is “document-shaped”. What is the counter-argument?

JSONB (chapter 11) stores and indexes documents inside PostgreSQL, with the same GIN indexes and containment operators — and you keep joins, transactions, constraints and ad-hoc SQL for the parts of the data that are relational. The choice is not either/or, and almost all data turns out to have relationships eventually.

What does PostgreSQL not do?

Scale writes horizontally. One cluster has one primary. Read replicas, application-level sharding and Citus exist, but there is no flag that makes it multi-master. Plan around one primary and you will be fine far longer than you expect.

Chapter A · Supplement

Data Modelling

The decisions that are cheap now and expensive later. Everything else in this book can be changed on a Tuesday afternoon; these cannot.

By the end of this chapter you will be able to
  • Normalise far enough and no further
  • Model a many-to-many relationship and its attributes
  • Choose how to represent state, history and soft deletion
  • Recognise the four schemas that always go wrong

A.1 Normalisation, briefly and practically

FormRuleIn practice
1NFNo repeating groups in a columnNo tags as a comma-separated string
2NFNo partial dependency on a composite keyRare once you use surrogate keys
3NFNo column depending on another non-key columnAim here
BCNF+Stricter stillAlmost never worth the extra joins

Table A.1 “Third normal form unless measured otherwise” is a defensible default for the whole of your career.

When to denormalise, and how to keep it honest

Denormalise when a join is measurably too slow and you have the plan to prove it. Then make the redundant value impossible to get wrong: a GENERATED ALWAYS AS … STORED column, a trigger (chapter 13), or a materialized view (§14.2). A denormalised column maintained by application code is a copy that will diverge, and you will find out from a customer.

A.2 Relationships

The column order in a composite primary key matters

PRIMARY KEY (book_id, tag_id) creates an index that serves “tags of this book” and not “books with this tag” (§10.3). If you need both directions, add a second index on (tag_id, book_id) — it is the same rule as any composite index, and it is routinely forgotten on join tables.

A.3 State, history and deletion

RequirementModel
Current state onlyA status column
State plus when it changedstatus + status_changed_at
Full historyA separate *_event table, append-only
“What did this look like on 1 June?”Temporal: valid_during tstzrange + EXCLUDE (§12.2)

Why deleted_at beats is_deleted

It answers “when” for free, and a partial index — CREATE INDEX … WHERE deleted_at IS NULL — indexes only the live rows, which is usually the vast majority of your queries and a fraction of the table.

The cost of soft deletion, stated plainly

Every query must remember the filter. Forget it once and deleted rows appear in a report, an export, or someone else’s dashboard. Unique constraints stop working as intended — a “deleted” row still occupies the email address. And the table grows forever. If you adopt it, put the filter in a view that the application queries instead of the table, or use row-level security (§15.3), so forgetting is not possible.

A.4 Four schemas that always go wrong

Anti-patternWhy it failsInstead
EAV — entity/attribute/valueNo types, no constraints, unreadable queriesColumns for what you know, JSONB for what you do not (§11.5)
One table with a type column and 40 nullable fieldsNothing can be NOT NULLSeparate tables, or a shared table plus per-type detail tables
Comma-separated ids in a columnNo foreign keys, no index, string parsingA join table (§A.2)
A settings table with one rowNothing stops a second row appearingCHECK (id = 1), or per-key rows with a unique key

Table A.2 Each of these starts as a reasonable shortcut on a small feature and becomes structural once three other things depend on it.

The EAV exception

User-defined custom fields, where the set genuinely cannot be known in advance, is the one legitimate case — and today the answer is a jsonb column with a GIN index, not three tables. You get indexing, types within the document, and queries a human can read.

A.5 Naming

ConventionExampleWhy
snake_casecreated_atUnquoted identifiers fold to lower case anyway
Singular table namesbook, not booksConsistent with the type it holds; ends the argument
<table>_id for foreign keysauthor_idMakes USING (author_id) possible

The one that is not a matter of taste

Never use quoted mixed-case identifiers. CREATE TABLE "Book" forces every reference to be quoted forever, and one unquoted book in a script fails with “relation does not exist” on a table that is plainly there. Unquoted identifiers fold to lower case; lower case them yourself and the problem never exists.

Checkpoint

When does a join table become an entity?

When the relationship has its own attributes — when it started, who approved it, what price was agreed. Then it needs its own surrogate key and its own timestamps, with a UNIQUE constraint preserving the pairing rule.

Why is deleted_at better than is_deleted?

It records when at no extra cost, and it enables a partial index on WHERE deleted_at IS NULL that covers only live rows. But both share the real cost: every query must remember the filter — put it in a view or an RLS policy rather than in every call site.

A colleague proposes an entity-attribute-value table for flexible product fields. What do you suggest?

A jsonb column with a GIN index. You keep types within the document, get indexed containment queries, and the SQL stays readable — where EAV gives you no types, no constraints, and a self-join per attribute.

Two habits worth more than any single fix

Save the plan before you change anything, so you can prove the change helped rather than believing it did. And use a visualiser — paste the JSON into explain.dalibo.com or pgMustard; a forty-node plan is genuinely hard to read as text, and the tools highlight the node that dominates.

Checkpoint

A node reports rows=1 loops=200000. How many rows did it produce?

200,000 — the rows figure is per loop. The same applies to the timing. Missing the multiplication is the most common misreading of a plan, and it hides exactly the nested loops that are killing the query.

The estimate says 100 rows, the actual is 400,000. What is the likely cause and cure?

Either stale statistics — run ANALYZE — or correlated conditions the planner assumes are independent. For the second, CREATE STATISTICS … (dependencies) ON a, b FROM t teaches it the correlation. A 1000× miss is almost always the reason a plan is bad.

Why is BUFFERS the number to compare between runs?

Because pages read is the actual work, and it is stable across machines and cache states. Milliseconds depend on what else was running and what was already cached; a query touching 6,000 buffers will touch 6,000 buffers in production too.

Table C.1 require is the common setting and it is not enough: it encrypts to whoever answered, without checking who that was.

C.2 Pool sizing

The formula, and why it is smaller than you think

Start from connections ≈ (cores × 2) + effective_spindle_count. On an 8-core server with SSD that is about 17, not 200. Throughput falls beyond that point: each connection is a process (§16.4), and more processes than cores means context switching rather than work. If you need more concurrency than that, you need a pooler and a queue, not more connections.

SettingMeaningA starting point
max / pool sizeConnections this instance may openSee above, divided by instance count
connectionTimeoutWait for a free connection2–5 s — fail fast
idleTimeoutClose an unused connection10 min
maxLifetimeRecycle a connection30 min — survives failovers and DNS changes
statement_timeoutServer-side capPer role (§16.5)
The arithmetic people forget

Ten application instances × a pool of 20 = 200 connections, and the database sees the total, not the per-instance number. Autoscaling makes this worse in exactly the moment you least want it: traffic rises, instances multiply, and the database runs out of connections precisely at peak. Size the pool by dividing the cluster’s budget by the maximum instance count, and put PgBouncer in front.

C.3 ORMs

Table C.2 The healthy pattern is an ORM for the 90% that is CRUD and hand-written SQL for the 10% that is not. Every mature codebase converges on this; the argument is only about where the line is.

The N+1 query problem

Fetch 100 books, then read book.author.name in a loop: 1 query plus 100. It is invisible in development with ten rows and fatal in production. Every ORM has an eager-loading directive (include, joinedload, with) — the difficulty is noticing. Log query counts per request in development and fail the test suite above a threshold; that turns a lurking bug into a build failure.

Prepared statements and PgBouncer

Most drivers use server-side prepared statements, which do not survive transaction-mode pooling (§16.4). Symptoms are bizarre: “prepared statement s1 already exists”, or errors that look like corruption. The fix is a driver flag — statement_cache_size=0, prepareThreshold=0, ?pgbouncer=true, depending on the stack. Know which one your driver uses before you introduce a pooler.

The expand–contract pattern

Renaming a column with zero downtime takes three deploys. 1. Add the new column and write to both. 2. Backfill in batches; switch reads to the new column. 3. Stop writing the old one and drop it. Any attempt to do it in one deploy means a window where the running code and the schema disagree — which is an outage, not a race you can win.

The one-line health check

SELECT 1 proves the connection is alive and proves nothing else. A better probe is a real read from a real table with a short statement_timeout: it exercises the pool, the schema and the disk. A cluster whose health check passes while every query times out is a well-known way to keep a broken instance in the load balancer.

Checkpoint

Ten instances each with a pool of 20. What have you configured?

200 connections. The database sees the total. On an 8-core server the useful number of active connections is closer to 17, so this is roughly twelve times too many — and autoscaling makes it worse exactly at peak. Divide the cluster budget by the maximum instance count, and use PgBouncer.

Why is sslmode=require not enough?

It encrypts the connection but does not verify the server’s certificate, so anything that answers on that address gets an encrypted channel with your credentials. verify-full checks the chain and the hostname.

How do you rename a column with no downtime?

Expand and contract, over three deploys: add the new column and write to both; backfill and move reads; then stop writing the old one and drop it. A single-deploy rename guarantees a window where the running code and the schema disagree.

1.4 Reading an error

Errors have codes

Every error carries a five-character SQLSTATE: 23505 unique violation, 23503 foreign key violation, 23514 check violation, 40001 serialization failure, 40P01 deadlock. Application code should branch on the code, never on the message text — the text is localised and changes between versions.

Checkpoint

Why can you not join two tables in two different databases?

Because a database is the isolation boundary — a connection is to one database and the planner only sees that one. If two things must be joined they belong in one database, in separate schemas. (postgres_fdw can bridge two databases, but it is a network hop, not a join.)

Why does WHERE deleted_at = NULL return no rows?

Because any comparison with NULL yields NULL, not true, and WHERE keeps only rows where the condition is true. Use IS NULL. Set \pset null so you can at least see nulls in output.

Your application shows users the raw database error text. What should it do instead?

Branch on the five-character SQLSTATE — 23505 for a duplicate, 23503 for a missing parent — and show its own message. Error text is localised and changes between versions; the code does not. Naming your constraints makes the mapping obvious.

The lock is the thing to think about, not the duration

ALTER TABLE takes ACCESS EXCLUSIVE, which blocks everything including SELECT. And it queues: while it waits for a slow query to finish, every subsequent query queues behind it. A migration that would take two seconds can stop the site for a minute because one report was running. Always set lock_timeout in migrations and retry.

Checkpoint

Why is varchar(255) not better than text?

Because in PostgreSQL they are the same type internally with the same performance; the length is just a constraint. If you genuinely need a limit, text CHECK (length(x) <= 255) says so explicitly and can be changed without rewriting. 255 itself is a MySQL row-format artefact.

Why timestamptz rather than timestamp?

Because timestamptz stores an absolute instant and renders it in the session’s zone, so two servers agree on what a value means. timestamp stores wall-clock digits with no zone — the same value means different moments depending on who reads it.

Your migration takes ACCESS EXCLUSIVE for two seconds and the site stops for a minute. Why?

Because the lock request queues behind a running query, and every query that arrives after it queues behind the lock request. Set lock_timeout so the migration fails fast and retries, rather than holding the queue open.

3.2 Sorting

Sorting text is locale-dependent

The order of ‘a’, ‘B’ and ‘á’ depends on the collation. This cluster was initialised with --locale=C, which sorts by byte value — fast, stable across systems, and wrong for human names. A real application usually wants ICU collation, and should be aware that a glibc upgrade can change sort order and silently corrupt text indexes. Set collation deliberately at initdb time; changing it later means reindexing.

3.3 Pagination

The bug OFFSET has and keyset does not

With OFFSET, if a row is inserted while the user is reading page 1, everything shifts and page 2 repeats a row the user already saw. If a row is deleted, page 2 skips one. Keyset pagination is immune, because it anchors on a value rather than a count.

Why can you use a select alias in ORDER BY but not in WHERE?

Because of the evaluation order: WHERE runs second and SELECT fifth, so the alias does not exist yet. ORDER BY runs sixth — after SELECT — so it does. Table 3.1.

What is wrong with ORDER BY created_at DESC LIMIT 20 OFFSET 40?

Two things. It is not deterministic unless created_at is unique — add , id DESC. And OFFSET reads and discards 40 rows, growing linearly with page depth, while rows inserted between page loads shift the window and duplicate or skip results.

A column of concatenated names came out all null. What happened?

|| with a null operand yields null, so one missing middle name blanked the whole value. Use concat(), which treats null as empty, or coalesce each part.

Why does WHERE status <> ‘done’ miss rows?

Because rows where status is NULL produce null <> ‘done’ = null, which is not true, so they are filtered out. Use status IS DISTINCT FROM ‘done’, or make the column NOT NULL.

Why prefer NOT EXISTS over NOT IN?

Because a single NULL anywhere in the NOT IN list makes the whole predicate null and the query returns nothing — silently, with no error. NOT EXISTS is null-safe, and usually plans better because it can stop at the first match.

Escaping of LIKE metacharacters in user input. Parameterisation prevents SQL injection but not pattern injection — escape %, _ and \ before building the pattern, and consider full-text or trigram search (chapter 12) rather than %…%.

The empty-set difference that bites

Over zero rows, count returns 0 and sum returns null. So a dashboard that shows “total revenue” renders blank rather than zero on a quiet day. coalesce(sum(x), 0), always.

In a rollup, the extra rows have NULL in the rolled-up column — indistinguishable from a genuine null in the data. GROUPING(channel) returns 1 for a subtotal row and 0 for a real one. Use it rather than guessing.

Checkpoint

Your revenue dashboard shows blank instead of 0 on a day with no sales. Why?

sum() over zero rows returns NULL, not 0 — only count() returns 0. Wrap it: coalesce(sum(x), 0).

What is the difference between count(*) and count(email)?

count(*) counts rows; count(email) counts rows where email is not null. Every aggregate ignores nulls, so avg(score) is the average of the scores that exist — which is often right and occasionally very wrong.

When does a condition belong in HAVING rather than WHERE?

Only when it refers to an aggregate — HAVING count(*) > 5. A plain row condition in HAVING gives the same answer but makes the database group rows it is about to discard. WHERE runs second, HAVING fourth (Table 3.1).

The rule

In an outer join, conditions on the outer table belong in ON, not WHERE. The only exception is a deliberate anti-join: LEFT JOIN … WHERE b.id IS NULL means “rows with no match”, and is a perfectly good idiom.

Checkpoint

Your LEFT JOIN stopped returning unmatched rows after you added a filter. What happened?

The filter went in WHERE. Unmatched rows have nulls on the right side, and any comparison with null is null, so WHERE discards them — turning the outer join into an inner one. Move the condition into ON.

Why count(b.id) rather than count(*) after a LEFT JOIN?

Because an unmatched left row still produces one output row, so count(*) reports 1 for something with zero matches. count(b.id) counts non-null values and correctly reports 0.

When is LATERAL better than a window function?

For top-N-per-group on a large table. A window function ranks every row and then discards all but N; LATERAL with ORDER BY … LIMIT N and an index stops after N rows per group. Same answer, very different amount of work.

Chapter Seven · Part III

Subqueries, CTEs and Set Operations

Ways to build a query out of smaller queries. One of them changed behaviour in PostgreSQL 12, and code written before that still assumes the old rules.

By the end of this chapter you will be able to
  • Choose between a subquery, a CTE and a join
  • Say what changed about CTE materialisation in version 12
  • Write a recursive CTE and stop it running away
  • Use UNION, INTERSECT and EXCEPT correctly

7.1 Three shapes of subquery

“Runs per row” is conceptual, not literal

The planner routinely rewrites a correlated EXISTS into a semi-join and evaluates it once. Do not contort a query to avoid correlation — write what is clear, then read the plan (supplement B). The exception is a correlated scalar subquery in the select list over a large result, which genuinely can execute per row.

7.2 CTEs, and what changed in version 12

The optimisation fence, and its removal

Before PostgreSQL 12, a CTE was always materialised — computed in full, then used. That made it an optimisation fence: predicates from the outer query could not be pushed into it, so a CTE over a huge table computed the whole thing before filtering. From 12 onward, a CTE used once and not recursive is inlined by default, and the planner optimises across the boundary.

You can still force either: WITH x AS MATERIALIZED (…) or AS NOT MATERIALIZED (…). Advice written before 2019 says “CTEs are slow”; that advice expired.

7.3 Recursive CTEs

Two ways it runs away

1. No termination condition — it loops until the disk fills. 2. A cycle in the data: A is B’s parent and B is A’s. PostgreSQL 14 added CYCLE id SET is_cycle USING path, which detects it for you; before that, carry an array of visited ids and check NOT id = ANY(path). Always add a depth limit as well — it costs nothing and it is the difference between a bug and an outage.

The requirements people forget

Both sides must have the same number of columns with compatible types, and the column names come from the first branch. ORDER BY applies to the whole result and goes at the end — putting it in a branch is either an error or silently meaningless.

7.5 Data-modifying CTEs

The snapshot rule that surprises everyone

All parts of a data-modifying CTE see the same snapshot — the state at statement start. So a CTE that inserts rows and a main query that selects from the same table will not see those rows. Sub-statements cannot see each other’s effects; they can only see each other’s RETURNING output. If you need to read what you just wrote, you need two statements.

Checkpoint

Someone says “never use CTEs, they are an optimisation fence”. Are they right?

Not since PostgreSQL 12. A non-recursive CTE referenced once is now inlined and optimised across, so it costs nothing. You can still force the old behaviour with AS MATERIALIZED when you want it — for an expensive CTE used several times, or one with side effects.

What stops a recursive CTE from running forever?

The recursive term returning zero rows. That means the WHERE in the recursive branch is the termination condition, not a filter. Add a depth bound always, and cycle detection (CYCLE … SET … USING …, PG 14+) whenever the data could contain one.

Your data-modifying CTE inserts rows and the main query does not see them. Why?

Because every part of the statement sees the same snapshot, taken at statement start. Sub-statements can only observe each other through RETURNING. To read what you just wrote, use a second statement in the same transaction.

Why SELECT then INSERT is wrong

Between the select and the insert, another transaction can insert the same row. You then get a unique violation — or, worse, no constraint exists and you get a duplicate. ON CONFLICT is a single atomic statement and has no window. This is not a rare race; on a busy endpoint it happens constantly.

Checkpoint

Why is SELECT then INSERT not a safe upsert?

Because another transaction can insert between the two statements, so you get a unique violation or a duplicate. INSERT … ON CONFLICT is one atomic statement with no window, and it needs a real unique constraint to detect the conflict against.

Your script hits one error and then every later statement fails. Why?

PostgreSQL aborts the whole transaction on a failed statement; everything after it returns “current transaction is aborted” until you roll back. Use a SAVEPOINT before a statement you expect might fail, and ROLLBACK TO it to carry on.

Why is holding a transaction open across an HTTP call so damaging?

It holds locks and, more importantly, holds a snapshot — so VACUUM cannot reclaim any row version newer than the transaction start, anywhere in the database. A few seconds is bad; a stuck connection can bloat the whole cluster. Set idle_in_transaction_session_timeout.

9.1 The idea

The default frame is the source of most surprises

With an ORDER BY and no explicit frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — which for a running total is what you want, but note it is RANGE, so all rows with the same order value are included at once. If two sales share a date, both jump into the running total together. Write ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW when you mean row-by-row.

When would you use a window function instead of GROUP BY?

When you need the aggregate and the individual rows — each sale with its share of the book’s total, each employee with their department average, each row with a running total. GROUP BY collapses; a window does not.

rank versus dense_rank versus row_number?

They are identical without ties. With a tie: row_number assigns distinct numbers arbitrarily; rank gives equal ranks then skips (1,1,3); dense_rank gives equal ranks and continues (1,1,2).

The rule for column order

Equality columns first, then the range or sort column. An index on (user_id, kind, at) serves WHERE user_id = ? AND kind = ? ORDER BY at perfectly, and also WHERE user_id = ? alone. 10.5 The cost of an index

Every index makes writes slower

An INSERT updates every index on the table; an UPDATE updates every index whose columns changed (and, if the new row does not fit on the same page, all of them). Five indexes on a hot table is a real write cost. Add indexes for queries you actually run, measure, and delete the ones nothing uses.

CREATE INDEX CONCURRENTLY, in production

A plain CREATE INDEX holds a lock that blocks writes for the whole build. CONCURRENTLY does not, at the cost of two table passes and the possibility of leaving an INVALID index if it fails — check \d afterwards and drop and retry if so. It cannot run inside a transaction, which means most migration frameworks need to be told about it explicitly.

Checkpoint

Why look at Buffers rather than the timing in a plan?

Because timing depends on cache state and machine load, while buffer counts are the actual work done — pages read. A query that touches 6,173 buffers will touch 6,173 buffers on production too; its millisecond figure will not transfer. Always EXPLAIN (ANALYZE, BUFFERS).

You have an index on (user_id, kind). Does it help WHERE kind = ‘click’?

Barely — a B-tree is ordered by the leftmost column first, so with no constraint on user_id it cannot seek. The planner may still do a full index scan if the index is much narrower than the table, but that is not what you built it for. Reorder, or add a second index.

Your query returns 60% of the table and ignores the index. Is that a bug?

No — it is correct. Reading 60% of the rows via an index means 60% of the pages in random order plus the index itself; a sequential scan reads them in order, faster. The planner switching to a seq scan at high selectivity is it doing its job.

The default GIN opclass supports @>, ?, ?| and ?&. If you only ever use containment, USING gin (payload jsonb_path_ops) builds a much smaller and faster index by hashing whole paths instead of storing every key separately. Check which operators your queries actually use before choosing.

The whole document is rewritten

Checkpoint

When would you choose json over jsonb?

Only when you must reproduce the exact bytes — a signed webhook body, an audit copy of a request. jsonb normalises key order, whitespace and duplicate keys, which breaks a signature check. Everywhere else, jsonb: it is the one that can be indexed.

meta -> ‘pages’ = 304 does not work. Why?

-> returns jsonb, and you are comparing it to an integer. Use ->> to get text and cast: (meta ->> ‘pages’)::int = 304. One arrow JSON, two arrows text.

A field inside a JSONB column is updated on every request. What should change?

Make it a real column. Updating one key rewrites the entire row — MVCC has no partial update — so a frequently-changed field inside a large document causes constant bloat and index churn. Columns are for things that change and are queried; JSONB is for the rest.

12.1 Arrays

When an array is the wrong choice

If the elements need their own attributes, constraints, or foreign keys, you want a table. Tags on a book are a good array: they are strings, order barely matters, and nothing references them. “The ids of this order’s line items” is a bad array: you cannot foreign-key into it, cannot join efficiently, and cannot store a quantity alongside.

12.2 Range types

This is the most underused feature in PostgreSQL

Room bookings, employee shifts, price validity periods, subscription terms, seat reservations — anything where two records must not overlap. It is a one-line constraint backed by a GiST index, and it is correct under concurrency in a way that application code cannot be.

When is an array column the wrong model?

When the elements need attributes, constraints or foreign keys. Tags are fine — strings with no identity. Line items are not: you cannot foreign-key into an array, cannot store a quantity beside each element, and cannot join efficiently.

Marking something IMMUTABLE when it is not

Is a lie the planner believes. A function that reads a table and claims to be immutable will be called once and its result cached into a plan or an index — and then silently return stale values forever. The classic case is a date function that depends on the session timezone: it is STABLE, not IMMUTABLE, and an index built on it will be wrong for anyone in another zone.

They are invisible. A developer reads the UPDATE, sees nothing about updated_at, and cannot explain the value. They fire in alphabetical order by name when several exist. Database code is hard to version (it lives in migrations, not files), hard to test (no unit test framework you already use), hard to debug (RAISE NOTICE is the debugger), and invisible in a stack trace. None of that makes it wrong — it makes it expensive. Spend it where the guarantee is worth it.

Checkpoint

Why prefer language sql over plpgsql when both work?

Because a single-statement SQL function can be inlined into the calling query and optimised with it. A PL/pgSQL function is a black box the planner must call, so it cannot push predicates through it or use indexes on the far side.

What goes wrong if you mark a table-reading function IMMUTABLE?

The planner folds it at plan time and may cache its result — including into an index. The function then returns a value that was correct once and is now permanently stale, with no error. A function that reads tables is STABLE at best.

When is a trigger the right tool?

When the invariant must hold no matter which client writes — updated_at, an audit row, a maintained counter. Not for business logic: triggers are invisible at the call site, fire in name order, run inside your transaction, and are the last place anyone looks.

Views, Materialized Views and Partitioning

Three ways to reshape what a query sees: a saved query, a saved result, and a table split into many.

By the end of this chapter you will be able to

  • Refresh a materialized view without blocking readers

14.1 Views

What views are actually for

Naming a join you write constantly; presenting a stable interface while the underlying tables change; and, with column privileges, exposing part of a table to a role that cannot see all of it (chapter 15). What they are not for is performance — a view is not cached.

Views nested three deep

A view on a view on a view produces a plan the size of a house and a query nobody can debug. The planner usually copes; the human does not. Two levels is a reasonable limit.

14.2 Materialized views

ViewMaterialized view

Table 14.1 The decision is entirely about staleness: if the answer may be an hour old, a materialized view turns a ten-second aggregate into a millisecond lookup.

Nothing refreshes it for you

There is no automatic refresh. Use pg_cron, an application scheduler, or a trigger on the source table (rarely a good idea — it makes every write pay for the rebuild). And decide what happens if a refresh fails: a materialized view silently serving three-day-old numbers is worse than an error.

14.3 Partitioning

Partition byWhen

The real reason to partition is not speed

It is maintenance. Dropping last year’s data becomes DROP TABLE — instant, no bloat — instead of a DELETE of a hundred million rows followed by a vacuum that takes a day. Indexes are per-partition, so they are smaller and rebuild faster. Query speed usually improves too, but if that is your only motivation an index is cheaper.

The rule of thumb

Partition when the table is large enough that maintenance is the problem — vacuum time, index rebuild time, deleting old data — and when almost every query filters on the partition key. If you are partitioning a 2 GB table to make a query faster, add an index instead.

Checkpoint

Does a view make a slow query faster?

No. A view is expanded into the calling query at plan time and stores nothing. It makes the query shorter to write. A materialized view stores the result and does make it faster — at the cost of staleness.

Why does REFRESH MATERIALIZED VIEW CONCURRENTLY need a unique index?

Because it computes the new contents and then applies the difference row by row, which requires a way to match old rows to new ones. Without the unique index it can only replace the whole thing, which needs an ACCESS EXCLUSIVE lock for the duration.

What do you actually gain from partitioning?

Mostly maintenance: dropping old data becomes DROP TABLE, vacuum and index rebuilds work on small pieces, and queries that filter on the key prune away most of the data. If your motivation is only query speed on a table under about 100 GB, an index is simpler and usually enough.

15.2 The public role

Every role is a member of public

Two things that switch RLS off entirely

1. The table owner bypasses RLS unless you also run ALTER TABLE … FORCE ROW LEVEL SECURITY. If your application connects as the owner — and most do — your policies do nothing. 2. 15.4 RLS and connection pooling

The problem

SET app.tenant_id is a session setting. With a pooler in transaction mode, the next request may get the same connection with the previous tenant’s value still set — a cross-tenant data leak of the worst kind. Use SET LOCAL inside the transaction, which reverts at commit, and set it as the first statement of every transaction.

The performance note

An RLS policy is a predicate the planner ANDs in. Make sure the column it references is indexed — a policy on tenant_id with no index on tenant_id turns every query into a full scan, and the plan will not obviously explain why.

Checkpoint

You granted SELECT and the role still gets “permission denied”. What is missing?

Almost certainly GRANT USAGE ON SCHEMA. Table privileges do nothing without schema usage, and the error names the schema rather than the table, which makes it look unrelated.

Your RLS policies have no effect. Why?

Most likely the application connects as the table owner, who bypasses RLS unless you add ALTER TABLE … FORCE ROW LEVEL SECURITY. Also check the role is not a superuser and does not have BYPASSRLS.

Why is SET rather than SET LOCAL dangerous with a pooler?

Because SET persists for the session, and a transaction-mode pooler hands the same session to the next request — which may belong to a different tenant. SET LOCAL reverts at commit, so a leaked value is impossible.

16.4 Connections and pooling

Each connection is a process

PostgreSQL forks a backend process per connection, each with its own memory. A thousand connections is a thousand processes competing for CPU, and throughput falls well before that. The right number of active connections is roughly cores × 2 plus a bit; everything else should queue in a pooler.

What transaction-mode pooling breaks

Session state does not survive between transactions: SET (use SET LOCAL — §15.4), server-side prepared statements, advisory locks held across transactions, LISTEN/NOTIFY, and temporary tables. Most ORMs need a flag to disable server-side prepared statements when behind PgBouncer, and forgetting it produces errors that look like corruption.

16.5 The timeouts

Why lock_timeout is the important one for migrations

A migration waiting for ACCESS EXCLUSIVE queues every subsequent query behind it (§2.5). With lock_timeout = ‘3s’ the migration fails fast and can be retried, instead of taking the site down while it waits. Set it in the migration itself, not just on the role.

Checkpoint

Why is random_page_cost = 4 wrong on modern hardware?

It encodes the assumption that a random read costs four times a sequential one, which was true for spinning disks. On SSD the ratio is close to 1, so the default makes the planner avoid index scans that would be faster. 1.1 is the usual setting.

Is raising work_mem to 1 GB a good idea?

Almost never. It is per sort node, per connection — a query with three sorts across two hundred connections could ask for 600 GB. Keep the global value modest and raise it with SET LOCAL for the specific report that needs it.

Your app behind PgBouncer starts throwing prepared-statement errors. Why?

Transaction-mode pooling gives each transaction a different backend, so server-side prepared statements from a previous transaction are gone. Disable them in the driver (or use PgBouncer’s prepared-statement support). The same class of problem hits SET, advisory locks and temp tables.

Concurrency, Locking and Isolation

19.1 Isolation levels

Table 19.1 PostgreSQL has no true READ UNCOMMITTED: asking for it gives you Read Committed, because MVCC makes dirty reads impossible.

“Serializable” here means what it says

PostgreSQL implements Serializable Snapshot Isolation: it detects dependency cycles between concurrent transactions and aborts one with SQLSTATE 40001. The guarantee is genuine — any successful set of transactions is equivalent to some serial order. The price is that your application must retry on 40001. Code that does not retry will fail under load in a way that testing on one connection never reveals.

19.4 Deadlocks

The prevention that always works

Acquire locks in a consistent order. If every transaction touches accounts in ascending id order, the cycle cannot form. In application code that means sorting your ids before the loop — one line, and the class of bug is gone.

Also helpsWhy
Shorter transactionsLess overlap, less chance to interleave

The log line to look for

A deadlock writes a full report to the server log naming both processes and both statements. It is one of the most useful log entries PostgreSQL produces — and it is only in the server log, so if you have never read that file, you have been throwing this information away.

19.5 Retrying, properly

Not every error is retryable

40001 and 40P01 are transient and should be retried. 23505 (unique violation) usually means the work is already done — check before retrying blindly. A CHECK violation is a bug and retrying will fail identically. Retry on the codes you have decided are transient, never on “any error”.

Checkpoint

Two users buy the last item and both succeed. What is the minimal fix?

UPDATE item SET stock = stock - 1 WHERE id = ? AND stock > 0. The database reads and writes atomically under a row lock, and the guard makes an oversell update zero rows, which the application can detect. No explicit locking, no isolation change.

What must you add before switching to SERIALIZABLE?

A retry loop on SQLSTATE 40001, with jitter, that re-runs the whole transaction. Serializable works by aborting transactions that would violate serial order; without retries you have converted a correctness problem into an availability problem.

How do you prevent deadlocks rather than react to them?

Take locks in a consistent order — sort the ids before the loop, so no cycle can form. Shorter transactions and locking everything up front in order help too. And retry on 40P01: a deadlock is expected under concurrency, not exceptional.

pg_dump is consistent, and it is not free

It takes a snapshot, so the dump is a consistent point in time even while the database is being written to. But that snapshot is a long-running transaction — so for its whole duration, vacuum cannot clean anything newer (§0.3). Dumping a large busy database at peak is a real cause of bloat. 20.2 WAL, and what makes recovery possible

Use a tool, not a cp

pgBackRest or Barman handle compression, parallelism, retention, encryption, and — critically — verify the archive. A hand-rolled archive_command that silently fails leaves you with a base backup and no way to bring it forward, which you discover on the worst day. Both tools also make restore a single command with a target time.

The trade-off nobody explains up front

hot_standby_feedback = on stops the primary from vacuuming rows a long query on the replica still needs — which prevents query cancellations on the replica and causes bloat on the primary. Off, the replica runs a long report and gets ERROR: canceling statement due to conflict with recovery. There is no setting that avoids both; you are choosing which problem to have.

20.4 Point-in-time recovery

The number that decides your architecture

RPO — how much data may you lose? RTO — how long may recovery take? A nightly pg_dump is an RPO of 24 hours. WAL archiving every 60 seconds is an RPO of 60 seconds. A synchronous replica is an RPO of zero, at the cost of every commit waiting for the replica. Write both numbers down before choosing tooling; almost every argument about backups is really a disagreement about these.

20.5 Testing the restore

The only rule in this chapter that matters

A backup that has not been restored is a hypothesis. Restore into a scratch cluster on a schedule — monthly at worst — and check the row counts. The failure modes are mundane and fatal: the archive was full and archive_command was silently failing; the dump excluded a schema; nobody had the encryption key; pg_dump was there but roles were not, because that needs pg_dumpall.

Why keep both logical and physical backups?

Physical gives you fast whole-cluster recovery and point-in-time restore; logical gives you a single table, a single database, or a copy that restores onto a different major version or platform. What does point-in-time recovery need that a nightly dump does not?

A base backup plus continuously archived WAL. The dump is a single instant; WAL lets you replay forward to any moment after the base backup, which is what turns “we lost a day” into “we lost 40 seconds”.

What is the risk of hot_standby_feedback = on?

Bloat on the primary: it stops vacuuming rows that a long-running query on the replica might still need. With it off, that replica query gets cancelled instead. You are choosing which failure to accept, not avoiding both.
