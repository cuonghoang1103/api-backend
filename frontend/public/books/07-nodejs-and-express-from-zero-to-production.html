About this book

Node is a small runtime with one thread and an enormous ecosystem. Almost everything that goes wrong with it is a consequence of that first fact, and almost everything that goes wrong around it is a consequence of the second.

So this book spends its first chapter on the event loop and its second on the standard library, before writing a single route. That order is deliberate: an engineer who knows what blocks the thread and what already ships with Node makes better decisions in every later chapter than one who has memorised more middleware.

The rule throughout is the same as the rest of this series: every listing was executed before it was printed. The Express transcripts are curl against a server that was running while this page was generated. The database queries ran against the live PostgreSQL cluster from Volume 6. The stream measurement is a real 168 MB file. Where a measurement failed to support the claim it was meant to illustrate, the claim changed — chapter 0 contains a behaviour that contradicts what almost every article on the subject says, and it is there because the program printed it.

Who should read this

Someone who writes JavaScript and wants to build a backend properly. You should be comfortable with promises, modules and objects — Volume 3 is that material. Chapters 5 and 12 lean on Volume 6 for the database side, but do not require it.

How this book is organised

Then chapters 1–16, mapping one-to-one onto the sixteen modules of the Node.js & Express track in Code Lab, each ending with that module’s ten graded exercises.

Read supplement A before chapter 3. Twenty minutes with node:http makes every Express concept obvious rather than magical.

1. process.nextTick does not beat promises at the top level of an ES module — demonstrated, and explained (§0.3). 2. Express 5 forwards async errors to your error handler, so the asyncHandler wrapper in every v4 codebase can go (§3.4).

Chapter Zero · Orientation

What Node Is, and the One Thread

A JavaScript runtime with one thread for your code and a pool of threads for waiting. Almost every Node performance problem is a misunderstanding of which is which.

By the end of this chapter you will be able to
  • Explain the event loop and its phases
  • Say what blocks it and what does not
  • Predict the order of nextTick, microtasks and timers — including the case every tutorial gets wrong
  • Choose between Node, Deno and Bun with a real reason

0.1 One thread, and a pool

Node runs your JavaScript on one thread. Everything that waits — a file read, a database query, an HTTP request — is handed to the operating system or to libuv’s thread pool, and your thread carries on. When the wait finishes, a callback is queued and runs when the thread is next free.

That design is why Node handles ten thousand idle connections on one core, and why one badly-placed loop stops all ten thousand at once.

0.3 The case the tutorials get wrong

Why this is worth two pages

Not because you should ever depend on it — you should not. Because it is a clean demonstration that ESM and CJS are different execution contexts, not just different syntax. The same difference explains why top-level await works in one and not the other, why __dirname is missing, and why a module’s side effects can happen at a different moment than you expect. If you have been told these are interchangeable, they are not.

The rule

Nothing in a request handler may take more than a few milliseconds of CPU. If it does, it belongs in a worker thread (chapter 7), a queue (chapter 13), or the database (Volume 6). “It is only 200 ms” means every other request waits 200 ms, and under load those add up in a straight line.

What Node absorbed recently

Several reasons to reach for a dependency have quietly disappeared: a built-in test runner (node --test, chapter 8), a watch mode (node --watch), .env loading (--env-file), fetch, and TypeScript type-stripping. If your project has nodemon, dotenv, node-fetch and a test framework, check whether you still need all four.

Checkpoint

Why does one slow loop affect every connected user?

Because all your JavaScript runs on one thread. While that loop runs, no callback fires, no request is accepted and no timer is serviced. Concurrency in Node comes from not blocking, not from parallelism.

Does process.nextTick always run before promises?

Inside a callback, yes. At the top level of an ES module, no — module evaluation is itself part of a promise chain, so pending microtasks drain first (§0.3). Never rely on either ordering; the point is that ESM and CJS are different execution contexts.

Five files read concurrently and one is slow. Why?

File I/O goes to the libuv thread pool, which has four threads by default. The fifth read waits for a free one. Raise UV_THREADPOOL_SIZE if you genuinely do heavy file or zlib work — network I/O does not use the pool and is unaffected.

A.1 A server, in thirty lines

A.2 The request is a stream

This is the thing frameworks hide most completely

req is a readable stream. The body has not arrived when your handler is called — you get headers, and the body follows in chunks. express.json() is middleware that buffers those chunks, parses the result, and hands you req.body. Knowing that explains three things at once: why req.body is undefined without the middleware, why the order of app.use matters, and why a webhook signature must be computed over the raw bytes before parsing (Volume 5, chapter 6).

A.3 The hole in Listing A.1

body += chunk has no limit

A client that sends a 2 GB body will make your process allocate 2 GB and die. There is no default cap in node:http; the connection is simply a stream and you kept reading it. This is a one-line denial of service against any hand-rolled Node server, and it is present in a great many of them.

No validation, no authentication, no ORM, no logging, no rate limiting, no CORS. Express is deliberately small — the ecosystem provides the rest, and choosing those pieces is most of what chapters 3 to 6 are about. That minimalism is the reason Express is still the default after fifteen years, and also the reason two Express codebases can look nothing alike.

Express 5 or Fastify?

Express 5 for the ecosystem, the familiarity, and the fact that every tutorial and every AI assistant knows it. Fastify for roughly two to three times the throughput on JSON-heavy workloads, schema-based validation and serialisation built in, and a plugin system with real encapsulation. Neither choice is wrong; Express is the safer default and Fastify is the better one if throughput is a stated requirement. This book uses Express because that is what the track teaches — the HTTP knowledge transfers unchanged.

Checkpoint

Why is req.body undefined without express.json()?

Because req is a stream — the body has not arrived when your handler runs. express.json() is middleware that buffers the chunks and parses them onto req.body. No middleware, no property.

What is wrong with req.on("data", c => body += c)?

It is unbounded. A large body allocates until the process dies, with no error and no default limit in node:http. Count the bytes, reply 413, and call req.destroy() to stop reading. Express caps bodies at 100 kb by default.

When would you use raw node:http in production?

A health-check sidecar, a single webhook endpoint, or a proxy that mostly pipes streams — cases with almost no routing and no middleware. Beyond a handful of routes the framework is paying for itself in the HTTP details you would otherwise reimplement.

Why console.log is not enough

It writes synchronously to a file or pipe, which blocks the event loop (§0.4) — measurably, under load. It has no levels, no structure and no redaction. pino writes asynchronously and is one of the few dependencies that pays for itself immediately.

Threading the request id without passing it everywhere

AsyncLocalStorage from node:async_hooks keeps a value for the lifetime of an async call chain, so a function five levels deep can read the current request id without it being a parameter. It is the one legitimate use of implicit context in Node, and it is what every tracing library uses.

B.3 When the process cannot continue

Since Node 15, an unhandled rejection exits by default

Which is correct, and it surprises people upgrading from 14 where it was a warning. If your service has been silently swallowing rejections, upgrading makes them visible as crashes — that is the bug becoming apparent, not the upgrade breaking it.

A process that exits on a bug and is restarted by systemd, PM2 or an orchestrator is more available than one that limps on with corrupted state. Crash-only design is not defeatism; it is the reason your service recovers from a bug at 3 a.m. without anyone waking up.

It costs nothing while the process is healthy and it is the difference between a post-mortem and a shrug.

Checkpoint

Why should an uncaught exception exit the process?

Because arbitrary code was interrupted at an arbitrary point: a lock may be held, a transaction half-applied, an invariant broken. Continuing produces corrupted state that surfaces later as an unrelated bug. Log it, exit, and let a supervisor restart you.

Why pino rather than console.log in production?

console.log writes synchronously — it blocks the event loop under load — and produces unstructured text with no levels and no redaction. pino writes async JSON with child loggers, which is what lets you find every line of one request.

What is the difference between an operational error and a programmer error?

Operational is expected and handled: a 404, a timeout, invalid input. A programmer error is a bug — handling it means hiding it. Return a status for the first; crash on the second and fix the code.

The mistake Promise.all hides

It rejects on the first failure, but the other promises keep running — they are not cancelled, and if one of them rejects later you get an unhandled rejection. If the tasks have side effects, use allSettled and decide what to do, or pass an AbortSignal (§1.3) so the rest can actually stop.

1.3 Cancellation

The keepAlive line is not padding

AbortSignal.timeout uses an unref’d timer: it deliberately does not keep the process alive. Without something else holding the event loop open, Node exits before the signal fires — and prints “Detected unsettled top-level await”, which is exactly what happened the first time this listing was run. That is correct behaviour and a genuinely useful design (a pending timeout should never delay shutdown), and it is not in most documentation.

Cancellation is a request, not a guarantee

Aborting a fetch closes the socket — the server may already have processed the request. Aborting a database query needs the driver to support it. Treat abort as “stop waiting and stop doing further work”, not as “undo”; anything that must be undone needs a transaction or a compensating action.

1.4 Errors

Custom errors with a code

Give your errors a stable code property — class NotFoundError extends Error { code = "NOT_FOUND" } — and branch on that, never on err.message. It is the same argument as SQLSTATE in Volume 6 §1.4, and for the same reason: messages are for humans and change; codes are for programs and should not.

Checkpoint

Three awaits in a row on independent work. What is wrong?

They run sequentially, so the total is the sum. await Promise.all([...]) starts all three and takes the longest. Only chain awaits when the second genuinely needs the first result.

Promise.all rejected. What happened to the other promises?

They kept running. all rejects on the first failure but cannot cancel the rest, so their side effects still happen and a later rejection can surface as unhandled. Use allSettled, or pass an AbortSignal so the others can actually stop.

Why does __dirname not exist in an ES module?

Because ESM has no module wrapper function — those “globals” were parameters of the CommonJS wrapper. Use import.meta.dirname (Node 20.11+), or path.dirname(fileURLToPath(import.meta.url)) on older versions.

2.2 Streams

Back-pressure is the point

If you read faster than you write, something must hold the difference. pipeline propagates back-pressure automatically: the reader pauses when the writer is busy. A hand-written on("data") loop that pushes into an array does not — and that is how a program that “streams” still runs out of memory.

2.4 Running other programs

Checkpoint

Why pipeline() rather than .pipe()?

Because .pipe() does not forward errors and does not destroy the other streams when one fails, so a failure leaks file descriptors and can leave the process hanging. pipeline from node:stream/promises handles both and gives you a promise to await.

Why write node:crypto instead of crypto?

Because the prefix resolves unambiguously to the built-in and cannot be shadowed by a package of that name in node_modules. It is a free defence against a dependency — or an attacker — shipping a module that shadows a core one.

Your CI installs a version that is not in the lockfile. Why?

It is running npm install, which may resolve newer versions and rewrite the lockfile. npm ci installs exactly what the lockfile says and fails if package.json and the lockfile disagree — which is the behaviour you want from a build.

3.3 Middleware

Everything in Express is middleware: a function taking (req, res, next). Routes are middleware that also match a path. The stack runs in the order you registered it, and that is the whole model.

Where to put things on the request

Express lets you set any property on req, and codebases end up with req.user, req.tenant, req.db and no record of who set what. Two disciplines help: namespace them (req.ctx = { user, tenant }), and if you use TypeScript, declare them by augmenting the Express Request interface (Volume 4 §C.3) so the compiler knows.

3.5 Error handling in one place

Returning the request id to the client

It costs one line and turns a support conversation from “it broke” into a string you can grep for across every log line of that request. Pair it with the requestId middleware in Listing 3.5 and structured logging (§B.2).

Checkpoint

Your request hangs with no error. What is the first thing to check?

A middleware that neither called next() nor sent a response. Express has no timeout for this — the request simply waits. Check every app.use on the path, especially ones with an early return.

Why does an error handler need four arguments?

Because Express identifies it by arity. (err, req, res, next) is an error handler; (req, res, next) is ordinary middleware. Omit the unused next and your error handler silently becomes a normal one that never runs.

What does Express 5 change about async handlers?

A rejected promise is forwarded to the error-handling middleware. In Express 4 it was an unhandled rejection, which since Node 15 kills the process — which is why every v4 codebase has an asyncHandler wrapper. In v5 you can delete it.

Why idempotency is not academic

A mobile client sends POST /orders, the response is lost to a flaky network, and the client retries. You now have two orders. What actually counts as breaking

Breaking: removing a field, renaming one, changing a type, tightening validation, changing a status code, adding a required parameter. Not breaking: adding an optional field, adding an endpoint, adding an enum value if you documented that clients must tolerate unknown values. Deprecation, properly

Announce, then send the Deprecation and Sunset headers (RFC 9745 / 8594), then measure who is still calling it, then contact them, then remove it. Skipping the fourth step is how an API removal becomes an incident.

Checkpoint

Why does an idempotency key matter for POST?

Because POST is not idempotent: a client that retries after a lost response creates a second resource. A client-generated key stored with the result lets the server recognise the retry and return the original response instead.

When 400 and when 422?

400 when the request could not be parsed — malformed JSON, wrong content type. 422 when it parsed fine and the values fail validation. The distinction lets a client tell “my serialiser is broken” from “the user typed something invalid”.

Why omit total from a paginated response?

Because counting the whole result set is frequently the most expensive part of the query, and most clients only need “is there more”. Return a cursor and hasMore, and offer the count behind an explicit opt-in for the few who need it.

Chapter Five · Part III

Database Integration

Getting rows out of PostgreSQL and into your handlers, without a connection leak, an injection, or an ORM you cannot see through.

By the end of this chapter you will be able to

  • Parameterise every query, and say why that is sufficient

5.1 The pool

Parameterisation is sufficient; escaping is not

You will still see advice to “escape user input”. Do not: escaping is a game you eventually lose, and it is unnecessary. The extended query protocol sends the SQL and the values in separate messages, so the value is never parsed as SQL. The only place parameters cannot go is an identifier — a table or column name — and for those you need an allowlist, not escaping.

5.2 Pool size

The number is smaller than you think

Start from (cores × 2) + 1 — about 17 on an 8-core database server, not 200. Then remember the pool is per process: ten application instances with max: 20 is 200 connections at the database, and PostgreSQL forks a process per connection. Divide the cluster budget by your maximum instance count, and put PgBouncer in front (Volume 6 §16.4).

5.3 The type surprises

The date in that output is the day before

The row’s published is 1974-05-01, and the output shows 1974-04-30T16:00:00.000Z. node-postgres turns a PostgreSQL date into a Date at local midnight, and this machine is at UTC+7 — so in UTC it is the previous evening. Serialise that to JSON and your API reports the wrong day for every user west of you. Fix it at the boundary: either return the raw string (pg.types.setTypeParser(1082, v => v)) or format explicitly with a date library. A bare date column has no time and no zone, and turning it into an instant is always a lie.

Three consequences of the bigint string

1. row.id === 1 is false; row.id === "1" is true. 2. Sorting ids in JavaScript sorts them as text — "10" < "9". 3. Your API returns "id": "1", and a client written against a mock returning a number breaks. Decide once, at the boundary: either accept strings everywhere, or use integer/uuid keys and avoid the question.

Checkpoint

Is escaping user input a valid defence against SQL injection?

It is unnecessary and error-prone. Parameterised queries send SQL and values in separate protocol messages, so a value is never parsed as SQL — there is nothing to escape. The exception is identifiers (table and column names), which cannot be parameters and need an allowlist.

Your service hangs under load with no errors. What would you check first?

A leaked pool connection: a code path that calls pool.connect() and throws before release(). Once the pool is exhausted every request waits for a connection that will never be returned. Use pool.query() for single statements and try/finally whenever you check a client out.

Why does row.id === 1 fail?

Because a PostgreSQL bigint is returned as a string — it can exceed Number.MAX_SAFE_INTEGER, and silently losing precision would be worse. Compare as strings, or use integer or uuid keys if you would rather not think about it.

Checkpoint

Why is a fast hash wrong for passwords?

Because speed helps the attacker, not you. A leaked table of SHA-256 hashes is cracked at billions of guesses per second on a GPU. argon2id is deliberately slow and memory-hard, which makes that hardware advantage largely disappear.

When is a JWT the wrong choice?

When you need to revoke immediately — log out everywhere, ban a user, respond to a leak. A JWT is valid until it expires, and adding a revocation list rebuilds the session store you were avoiding. Sessions are the better default for a normal web application.

A route is authenticated and still leaks other users’ data. What is missing?

Authorisation on the record. Being logged in says who you are, not that this order is yours. Check ownership where the data is fetched, so no route can forget — or enforce it with row-level security below your code entirely.

7.1 Worker threads

When a worker is worth it

Starting one costs a new V8 isolate — tens of milliseconds and several MB. That is fine for a job that runs for a second and wasteful for one that runs for ten milliseconds. Checkpoint

Why did four workers give 2.4× rather than 4×?

Startup cost. Each worker is a fresh V8 isolate — tens of milliseconds — and the task itself was only a few hundred. Use a worker pool so that cost is paid once, and reserve workers for work long enough to amortise it.

What breaks the first time you run more than one process?

Everything in memory: an in-process cache becomes N inconsistent caches, an in-memory rate limiter allows N× the traffic, setInterval jobs run N times, and WebSocket connections are only reachable from the process that holds them. All of it needs shared state.

Why is event loop delay the most useful Node metric?

Because it measures the thing that is unique to Node: whether your one thread is available. When it rises, every request is slow regardless of what the database says — and no other dashboard shows it.

The step almost everyone misses

Failing the readiness check and waiting a few seconds. The load balancer needs time to stop routing to you; closing immediately refuses connections it is still sending. Readiness off, short sleep, then drain.

The browser WebSocket constructor cannot set headers, so there is no Authorization. 9.3 More than one process

The problem, stated exactly

9.4 The three failures that only happen in production

Back-pressure

Check socket.bufferedAmount before sending. A client on a slow connection cannot drain as fast as you produce, and the buffer is in your process memory. Drop messages, coalesce them, or disconnect the client — but do not keep writing into a buffer nobody is reading.

Reconnection is the client’s job, and it needs jitter

A browser that reconnects immediately after a server restart, multiplied by ten thousand clients, is a self-inflicted denial of service — they all arrive in the same millisecond. Exponential backoff with random jitter, capped at about thirty seconds. SSE does this for you; with WebSockets you write it.

Checkpoint

When is SSE the better choice?

Whenever the traffic is server-to-client only — notifications, progress, a live feed, streaming model output. It is plain HTTP, reconnects automatically, and needs no protocol upgrade. WebSockets are for genuinely bidirectional, low-latency traffic: chat, games, collaborative editing.

Your broadcast reaches a quarter of users after scaling to four processes. Why?

Each WebSocket is a TCP connection to one process, and that process only knows its own clients. You need a pub/sub bus — Redis is the usual answer — so every process forwards published messages to the sockets it holds.

Why does a connection count only ever rise?

Because closed laptops, lost mobile signal and proxy timeouts do not send a close frame — TCP simply stops. Without a ping/pong heartbeat that terminates unresponsive sockets, they stay in your client set forever.

The reasons that hold up

1. Different teams need to deploy without coordinating. 2. One part has genuinely different scaling needs — video encoding beside a CRUD API. 3. One part needs a different runtime. 4. A hard compliance boundary. Everything else — “clean architecture”, “modern”, “it will scale” — buys you a network in the middle of your call stack and no benefit.

Start with a modular monolith

Retries need three things or they make it worse

Idempotency — retrying a POST without a key creates two orders (§4.1). Jitter — synchronised retries are a thundering herd that keeps the dependency down. 10.3 Circuit breakers

The fallback is the design decision

A breaker without a fallback just fails faster. The interesting question is what your service does when a dependency is gone: serve stale data, degrade the feature, queue the work for later, or return 503. Answer that per dependency, before the incident.

The distributed monolith

Six services that must all be deployed together, all read the same database, and where one being down takes the others with it. 10.5 Data

One database per service is the rule that makes the rest work

Shared tables re-couple services through the schema: a migration in one breaks another, and no service can be reasoned about alone. Checkpoint

Give two reasons to split a service that are actually good.

Teams that need to deploy independently, and one component with genuinely different scaling or runtime needs. Both are organisational or physical constraints. “It is cleaner” is not — you can have module boundaries inside one deployable, without a network.

What is missing from await fetch(url) in a service call?

A timeout — fetch has none by default and will wait for minutes. Also a correlation id header, error classification so you retry 5xx and not 4xx, and something that decides what happens when the dependency is simply gone.

How do you know you have a distributed monolith?

The services must be deployed together, or they share database tables, or one being down takes the others with it. Two questions settle it: can each be deployed alone, and does each own its data?

Checkpoint

Why did the author resolver run twice for two books?

Because GraphQL resolves fields per object — the author resolver runs once for every Book in the list. That is N+1 by construction, not a bug in the resolver, and DataLoader is the standard fix: batch the ids from one tick into a single query.

Why must a DataLoader be created per request?

Because it caches. A shared loader is a cache with no expiry that can return one user’s data to another — a correctness and a security problem at once. Create it in the context factory, once per request.

Your 5xx alert never fires despite a GraphQL outage. Why?

GraphQL returns 200 OK with an errors array. Every HTTP-level tool sees success. Monitor the errors array explicitly, and count GraphQL errors as a first-class metric.

Doing work later. The single highest-value architectural move available to a web service, and the one most often skipped because “it is only 300 milliseconds”.

Table 12.1 The test: does the user need the result to see their response? If not, it is queued work — and the request stops depending on the availability of whatever it calls.

The two things you actually gain

Latency: the response returns as soon as the durable write is done. Availability: your checkout does not fail because the email provider is down — the message waits. That second one is the reason this is architectural rather than a performance tweak.

12.2 A queue in the database you already have

Why this is a better default than it sounds

You get transactional enqueue — the job and the row it refers to commit together, so there is no window where the order exists and the email job does not. Redis and SQS cannot do that; they need an outbox table to approximate it. You also get one system to operate, back up and monitor. Up to a few thousand jobs per second this is genuinely the right answer, and pg-boss or graphile-worker package it properly.

Queue and event bus are different things

A queue delivers a job to exactly one worker: “send this email”. An event bus broadcasts a fact to anyone interested: “order 123 was paid”. Using a queue for events means the publisher knows every consumer, which is the coupling you were trying to remove. Using events for jobs means nobody is definitely responsible for doing the work.

12.4 Delivery is at-least-once

Assume every message arrives twice

A worker that finishes the job and dies before acknowledging leaves the message to be redelivered. Every queue has this; exactly-once delivery does not exist in a distributed system. What exists is at-least-once delivery plus idempotent consumers, which is the same guarantee from the outside.

Alert on its depth. The whole point of moving a message aside is that a human decides what to do with it — and the default outcome, if nothing alerts, is that the message is silently gone.

12.5 The outbox pattern

And if the queue is in the same database

You do not need an outbox at all — the job is a row in the same transaction (§12.2). That is the strongest argument for a database-backed queue, and the reason to be sure before adopting a broker.

Checkpoint

What belongs in a queue rather than a request?

Anything the user does not need the result of: emails, PDFs, thumbnails, analytics, third-party calls. You gain latency and availability — checkout stops failing because the email provider is down.

Why is FOR UPDATE SKIP LOCKED the key to a database queue?

Without it every worker blocks on the same first pending row and the queue processes serially. SKIP LOCKED makes each worker take the next unlocked row, so they proceed in parallel, and the whole claim is one atomic statement.

Your consumer sent the same email twice. Is the queue broken?

No — delivery is at-least-once by design, and a worker that crashes after doing the work but before acknowledging will see the message again. The consumer must be idempotent: record the message id under a unique constraint and return early on a duplicate.

Do the sum before the architecture

Take your requests per month, your average duration and your memory setting, and put them into the provider’s calculator. Then price a small VPS or container that would serve the same load. Teams regularly discover that a $20 machine replaces $400 of function invocations — and the reverse, that a service used twice a day costs nothing serverless and $20 a month otherwise. Both answers are common; the mistake is not checking.

15.5 A defensible default

Where to put what

A container or a VPS for the main API: connection pools work, no cold starts, predictable cost, and everything in this book applies unchanged. Serverless for spiky and occasional work: webhooks, scheduled jobs, image processing, anything that runs a few thousand times a day. Edge for the things that genuinely need to be near the user and need no database. That combination is what most teams converge on after trying to make one model do everything.

Checkpoint

Why do database connections become a problem on serverless?

Because each concurrent invocation is its own instance with its own pool, so a hundred concurrent requests is a hundred connections against a database that allows a hundred in total — and it happens at your traffic peak. Use a wire-protocol pooler or an HTTP data API, and set max: 1.

Why can an edge function not query PostgreSQL directly?

Because edge runtimes are V8 isolates with Web APIs and no TCP sockets. The pg driver needs one. You need an HTTP-based data proxy — which lives in one region, so the edge saved you distance to the compute but not to the data.

When is a plain server the cheaper answer?

Under sustained traffic. Serverless wins on idle and on bursts; a machine wins once it is busy most of the time. Do the arithmetic with your actual request count, duration and memory before deciding — both answers are common, and not checking is the only mistake.

Chapter Sixteen · Part VIII

Architecture, and Deciding

How to lay out a service so it can be changed, and how to make the decisions this book has been deferring.

By the end of this chapter you will be able to
  • Structure a codebase by feature rather than by layer
  • Keep the domain independent of Express and of the database
  • Choose dependencies with a stated reason
  • Write down a decision so the next person knows why

16.1 Layout

The rule that keeps it honest

No cross-feature deep imports. orders may use books/index.js’s public exports; it may not reach into books/repository.js. Enforce it with an ESLint no-restricted-imports rule, because a convention nobody checks lasts about three weeks.

16.2 Keeping the domain independent

Do not build the hexagon on day one

Interfaces, ports, adapters and a dependency-injection container in a service with six endpoints is more machinery than domain. Start with three files per feature and the dependency direction above. Add an interface when you have a second implementation — not in anticipation of one.

16.5 Writing the decision down

Why this is the last section of the book

Every chapter here has offered a default and a reason to deviate. In two years someone — possibly you — will look at the queue table and wonder why it is not Redis, at the monolith and wonder why it is not services, at the sessions and wonder why not JWTs. Without a written reason they will assume there was none, and rewrite it. Six headings prevent that.

Checkpoint

Why organise by feature rather than by layer?

Because change arrives by feature. “Add a field to orders” touches one folder instead of four, the tests sit beside the code, and if a feature later becomes its own service the boundary already exists. Layers optimise for a browsing pattern nobody actually uses.

What should a service function not know about?

req, res and SQL. Dependencies point inward — routes know Express, services know the rules, repositories know the database. That is what lets you test the rules by calling a function, and change the framework or the database in one file per feature.

What is the most valuable line in an ADR?

Revisit if. It converts a decision into a trigger, so a future reader can distinguish a choice that is still correct from one that nobody has re-examined. Everything else is context; that line is what makes the document useful two years later.
