About this book

Almost everything confusing about Docker follows from one sentence: a container is an ordinary process on your kernel with a restricted view of the system. This book starts there and derives the rest.

That is not a philosophical preference. It is what explains why containers start in milliseconds, why a Linux container needs a VM on a Mac, why a file you wrote disappeared, why your firewall is not protecting the port you thought it was, and why docker stop takes exactly ten seconds. Each of those is a consequence, and each is demonstrated here with output you can reproduce.

The rule for the whole book is the one this series keeps: every command was run before it was printed. The image sizes are real images built during writing. The 925 ms against 10,144 ms in chapter 7 is a real measurement of a real container. The PostgreSQL 18 volume failure in chapter 4 was discovered by the stack refusing to start, and the chapter says so.

Who should read this

Someone who has run docker run and would like to know what it did. No prior container knowledge is assumed. Chapters 4, 7 and A deploy a Node service — Volume 7 is that application, though nothing here requires it.

How this book is organised

Chapter 0 is what a container is. Supplement A — deploying to a single VPS with TLS — is the deployment most projects actually need and the one the Code Lab track does not cover. Then chapters 1–16, mapping one-to-one onto the sixteen modules of the Docker track in Code Lab, each ending with that module’s ten graded exercises.

Chapters 0, 2, 6 and 7 are the ones that matter most. Between them they cover what a container is, how to build one that is small and cached, how to make it not run as root, and how to stop it without dropping requests.

Three things here that most Docker material has not caught up with

1. The PostgreSQL 18 image wants its volume at /var/lib/postgresql, not /var/lib/postgresql/data — every older compose file fails against it (§4.2). 2. Kubernetes removing dockershim changed nothing about your images, and the panic was misplaced (§9.2). 3. arm64 is now a mainstream target on both laptops and servers, so a single-architecture image is a bug waiting to be found (chapter 10).

Chapter Zero · Orientation

What a Container Actually Is

Not a small virtual machine. A normal Linux process with a restricted view of the system — and once that is clear, most of Docker’s behaviour stops being surprising.

By the end of this chapter you will be able to
  • Say what a container is made of, in kernel terms
  • Explain the difference between an image and a container
  • Say what Docker is not: not a VM, not a security boundary by default
  • Read docker images and docker ps properly

0.1 A process with a restricted view

Kernel featureGives the container
NamespacesIts own view of PIDs, mounts, network, hostname, users, IPC
cgroupsA limit on CPU, memory, PIDs, block I/O
Union filesystemA read-only image plus a thin writable layer
Capabilities / seccompA reduced set of things it may ask the kernel to do

Table 0.1 That is the entire list. There is no hypervisor, no guest kernel, no emulation — the process runs on your kernel, which is why it starts in milliseconds and why the next note matters.

Why it is not a VM

A virtual machine boots its own kernel and takes seconds; a container is a clone() with some flags set and takes milliseconds. The consequence people trip over: you cannot run a Linux container on a Windows kernel. Docker Desktop runs a small Linux VM to host them — so on macOS and Windows you are, in fact, using a VM after all, and file I/O across that boundary is slow.

0.2 Image and container

ImageContainer
IsA stack of read-only layers plus metadataA running (or stopped) process using one
Analogous toA class, or an executableAn instance, or a process
MutableNo — content-addressedYes, in its thin writable layer
Made bydocker builddocker run
SharedLayers are shared between imagesNothing is shared

Table 0.2 The last row is the one that costs data: anything written inside a container and not to a volume is gone when the container is removed (chapter 3).

0.3 Two words about security

A container is not a security boundary by default

It shares your kernel. A kernel vulnerability reachable from inside a container is a vulnerability in your host. And by default the process inside runs as root — a root that is namespaced, but still root, with more capabilities than it needs. If you run untrusted code, you want a VM, gVisor, or Kata Containers; if you run your own code, you want the hardening in chapter 7, and it takes about four lines.

Images are a standard, and that is why this matters

An image you build with docker build runs on Podman, on containerd, on Kubernetes and on every cloud container service, because they all implement the same OCI specification. You are not learning a vendor’s format — that is the reason to invest in this at all.

0.5 Reading the two commands you will type most

docker runCreate and start a new container — a new one every time

The mistake in the first row

docker run creates a new container each time. Running it ten times leaves nine stopped containers, each holding its writable layer on disk. Use --rm for anything throwaway, and check docker system df occasionally — a development machine can quietly accumulate tens of gigabytes.

Checkpoint

Why does a container start in milliseconds and a VM in seconds?

Because there is no kernel to boot. A container is an ordinary process on your existing kernel with namespaces and cgroups applied. The same fact explains why a Linux container cannot run on a Windows kernel without a VM underneath.

You wrote a file inside a container and it is gone. Why?

Because it went to the container’s thin writable layer, which is deleted with the container. Anything that must survive belongs in a volume or a bind mount (chapter 3) — or, better, in a database outside the container.

Is a container a security boundary?

Not by default. It shares your kernel, and the process inside is root unless you say otherwise. For your own code, hardening (chapter 7) is enough; for untrusted code you want a real VM boundary — gVisor, Kata, or an actual VM.

Chapter A · Supplement

Docker on a VPS

One machine, a domain, TLS, and a stack that survives a reboot. The deployment most projects actually need, and it does not involve a cluster.

By the end of this chapter you will be able to
  • Prepare a server so Docker is safe to run on it
  • Put a reverse proxy in front with automatic certificates
  • Deploy and update without downtime
  • Survive a reboot, a disk filling and a bad release

A.1 The server, before Docker

Membership of the docker group is root

Anyone in it can run docker run -v /:/host and read or write the entire filesystem as root. It is not a lesser privilege — it is a different spelling of root. Grant it as carefully as you would grant sudo, and consider rootless Docker (§9.4) if that is not acceptable.

UFW does not see Docker’s rules

Docker writes its own iptables rules in a chain UFW does not manage, so -p 5432:5432 exposes the port through your firewall. Bind to localhost — -p 127.0.0.1:5432:5432 — or do not publish it at all and let containers reach it over the Docker network (§3.1). Every “my database was on the internet” story is this.

A.2 A reverse proxy with automatic TLS

The volume that must not be pruned

caddy_data holds your certificates and the ACME account key. Lose it and you re-issue — which is fine occasionally and hits Let’s Encrypt rate limits if it happens repeatedly. It is exactly the kind of “unused” volume docker volume prune deletes (§1.4).

A.3 Deploying

A rollback is only fast if the old image is still on the machine. Do not docker image prune -a as part of the deploy — prune on a schedule with --filter until=168h, so last week’s images are still there when you need them at 2 a.m.

A.4 Keeping it alive

Table A.1 The first five are configuration. The sixth is the only one that requires you to have thought about it in advance, and it is the only one that is unrecoverable.

Checkpoint

You added a firewall rule and your database is still reachable from the internet. Why?

Docker writes its own iptables rules that UFW does not manage, so -p 5432:5432 punches through. Bind to 127.0.0.1, or do not publish the port at all and let containers reach it over the Docker network.

Why expose rather than ports for the API in Listing A.2?

Because only Caddy needs to reach it, and Caddy is on the same Compose network. ports would publish it on the host, where anyone could bypass the proxy — and with it your TLS, rate limiting and access logs.

What makes a rollback fast?

The previous image still being on the machine. Deploy by immutable tag, and prune on a schedule with a time filter rather than as part of the deploy — otherwise a rollback becomes a pull and a build at the worst possible moment.

1.3 Logs

The default log driver will fill your disk

json-file with no limit grows forever. A chatty service can produce tens of gigabytes and take the host down — and it is one of the most common causes of “the server ran out of space”. Set it once in /etc/docker/daemon.json:

{"log-driver":"json-file","log-opts":{"max-size":"10m","max-file":"3"}}

1.4 Reclaiming disk

docker image pruneDangling images onlyYes
docker image prune -aEvery image not used by a containerRe-pull everything

docker system prune -a --volumesAll of the aboveRead it twice

Table 1.1 The volume row is the one that destroys data. “Unused” means “not attached to a container right now” — which includes the database volume of a stack you stopped for the weekend.

The habit that avoids the whole problem

--rm on everything interactive, named volumes for anything that matters, and a scheduled docker image prune -f --filter until=168h. Then you never need the dangerous command.

Checkpoint

You ran a container without -p and cannot reach it. Why?

Because a container’s ports are in its own network namespace. EXPOSE in a Dockerfile is documentation only; -p host:container is what creates the mapping. From another container on the same network you would not need it (chapter 3).

Your host ran out of disk and Docker is the cause. Where do you look first?

docker system df. Then, most often, the json-file log driver with no size limit — set max-size and max-file in daemon.json. After that, stopped containers and dangling images.

Why is docker volume prune dangerous?

Because “unused” means “not currently attached to a container”. Stop a stack for the weekend and its database volume qualifies. Prune images and containers freely; treat volumes as data and delete them by name.

ChangeSaved

2.2 The cache

The rule

Each instruction produces a layer keyed by the instruction plus the content it touched. If that key is unchanged, the layer is reused — and if any layer misses, every layer after it is rebuilt. So the order of your Dockerfile is a performance decision: put what rarely changes first.

BuildKit mounts, for the cache that survives even that

RUN --mount=type=cache,target=/root/.npm npm ci keeps the package manager’s own cache between builds without putting it in a layer. On a large dependency tree this is a much bigger win than layer ordering, and it is one line.

2.3 The instructions

InstructionNote
FROMPin it — node:22.11-alpine, or a digest. latest is not a version
WORKDIRCreates and enters. Never RUN cd — it does not persist
COPYPrefer over ADD; ADD also unpacks archives and fetches URLs
RUNOne layer each — chain with && where they belong together
ENVBaked into the image and visible in inspect. Not for secrets
ARGBuild-time only; also visible in history
USEREverything after it runs as that user
EXPOSEDocumentation only — publishes nothing
HEALTHCHECKWhat “healthy” means to the orchestrator

.dockerignore is not optional

Without it, COPY . . sends your entire working directory to the daemon as build context — node_modules, .git, build output, .env. That is slow, it makes the cache miss constantly, and it is how secrets end up in published images. At minimum: node_modules, .git, .env*, dist, *.log.

2.4 What the image says about itself

Labels, for the things a registry cannot infer

LABEL org.opencontainers.image.source="https://github.com/you/repo" is what makes a package on GHCR link back to its repository. The OCI label set also covers revision, created and licenses, and CI can fill them in automatically.

Checkpoint

Why copy package.json before the rest of the source?

So the expensive npm ci layer is keyed only on the manifest. Editing source then hits the cache for dependencies; only a real dependency change re-runs the install. If any layer misses, every layer after it rebuilds — so ordering is a build-time decision.

Why does the shell form of CMD break graceful shutdown?

Because it runs your process under /bin/sh -c, and that shell becomes PID 1. It does not forward SIGTERM, so your handler never fires, the container is eventually SIGKILLed, and every deploy drops in-flight requests. Use the exec form: CMD ["node", "server.js"].

Does EXPOSE 3000 publish a port?

No. It is metadata — documentation for a human and a hint for docker run -P. Only -p host:container, or a Compose ports entry, creates a mapping to the host.

3.1 Networks

noneNo networkingA batch job that must not reach out

Table 3.1 The difference between the first two rows is the one thing to remember: the default bridge has no DNS. Containers on it can only reach each other by IP, which changes. A user-defined network gives you names.

What -p 8080:80 actually is

A rule in the host’s firewall (an iptables/nftables DNAT) forwarding host port 8080 to the container’s port 80. Two consequences: it binds all interfaces by default, so -p 5432:5432 on a cloud VM exposes your database to the internet — write -p 127.0.0.1:5432:5432. And it bypasses UFW, which does not see Docker’s rules, so a firewall you configured may not be protecting the port you think it is.

Bind mounts and file ownership

A bind mount keeps the host’s uid and gid. Run as USER node (uid 1000) and mount a directory owned by uid 1001, and the container cannot write to it — with a permission error that mentions neither Docker nor the mount. Match the uid (--user $(id -u):$(id -g)), or use a named volume, where Docker gets it right for you.

3.3 Backing up a volume

A database volume is not backed up by copying it

Copying a live PostgreSQL data directory gives you a torn snapshot. Use pg_dump or pg_basebackup from inside the container (Volume 6, chapter 20), or stop the container first. The tar approach above is right for uploads and generated files — not for a running database.

Checkpoint

Why create a network instead of using the default bridge?

DNS. On a user-defined network containers resolve each other by name; on the default bridge they can only use IPs, which change on every restart. Compose creates one automatically, which is part of why it is worth using (chapter 4).

Does one container need -p to reach another?

No. -p publishes to the host. Containers on the same user-defined network reach each other on the container port directly — so a database should have no published port at all, and then it is unreachable from outside the host by construction.

Your container cannot write to a bind-mounted directory. Why?

uid mismatch: the mount keeps the host’s ownership, and the container’s user is a different uid. Either match it with --user $(id -u):$(id -g), fix the host directory’s ownership, or use a named volume where Docker manages permissions.

4.1 A stack

4.2 The version 18 trap

/var/lib/postgresql/data no longer works

Every PostgreSQL Compose file on the internet mounts the volume at /var/lib/postgresql/data. The official PostgreSQL 18 image refuses to start that way and prints a long explanation about pg_upgrade --link and mount-point boundaries. The correct mount for 18 and later is one level up: dbdata:/var/lib/postgresql.

This book hit it while being written — the first version of Listing 4.1 had the old path and the stack would not come up. If you are pinning postgres:18 or postgres:latest and your previously-working compose file stops working, this is why.

Which is an argument for pinning

image: postgres:latest means a major version upgrade arrives on whichever Tuesday you next pull. postgres:18-alpine means you choose when. Pin the major version of everything, and read the release notes before moving.

4.3 depends_on does less than it looks like

FormWaits for
depends_on: [db]The container to be started — not ready
condition: service_healthyIts health check to pass
condition: service_completed_successfullyA one-shot container (migrations) to exit 0

Table 4.1 The plain form is the cause of “it works the second time”: the database process is up but still initialising, the API connects, fails, and exits. Always use a condition, and always give the dependency a health check.

And your application should still retry

Compose orchestration is not available in production on Kubernetes, and a database can restart at any time. Retry the initial connection with backoff regardless — the health-check ordering removes the noise in development; the retry loop is what makes it correct.

Table 4.2 Compose is genuinely enough for a great many production services: one VPS, a reverse proxy, an application and a database. Reaching for Kubernetes because Compose is “only for development” is a large cost for a benefit you may not need.

The one thing Compose really cannot do

A zero-downtime deploy. up -d stops the old container and starts the new one, so there is a gap. Workarounds exist — --scale with a proxy that health-checks, or a blue/green pair behind Caddy or Traefik — and if you need it reliably, that is a genuine reason to move up.

Checkpoint

Your API fails on the first compose up and works on the second. Why?

depends_on without a condition waits only for the container to start, not to be ready. The database is still initialising. Add a health check to the dependency and condition: service_healthy — and retry the connection in the application anyway.

Why does the database service have no ports: entry?

Because nothing outside the host needs to reach it. The API resolves db on the Compose network and connects to 5432 directly. Publishing it would expose the database on every interface of the host — which is how databases end up on the public internet.

A working PostgreSQL compose file stopped starting after a version bump. What changed?

PostgreSQL 18’s image expects the volume at /var/lib/postgresql, not /var/lib/postgresql/data. It refuses to start with the old mount and explains why in the logs. Pin major versions so this arrives when you choose.

Chapter Six · Part III

Security Hardening

Four lines that close most of the easy holes, and an honest account of what a container does and does not protect you from.

By the end of this chapter you will be able to

  • Drop capabilities and make the filesystem read-only

6.1 The four lines

Why images default to root

Because installing packages during the build needs it, and because it is the path of least surprise for a base image author. It is a default, not a recommendation. One USER line as the last instruction of your Dockerfile is the single highest-value change in this chapter — and note it must come after anything that needs to write to the image.

Alpine uses musl rather than glibc. Most things work; native modules occasionally do not, and DNS resolution has historically had edge cases. If you hit something strange on Alpine that works on Debian, that is usually why — node:22-slim is the Debian-based middle ground.

Rebuilding is a security control

An image built three months ago has three months of unpatched base-image CVEs, even if your code has not changed. A weekly scheduled rebuild-and-redeploy of unchanged code is one of the cheapest security measures available, and almost nobody does it.

Checkpoint

Why is USER the highest-value line in a Dockerfile?

Because the default is root. A namespaced root is still root inside the container, with capabilities it does not need, and it is one kernel bug away from being root on the host. One line removes that, and it must come after anything in the build that needs to write.

You added a secret in one layer and deleted it in the next. Is it gone?

No. Layers are immutable and additive — the file is still in the earlier layer and anyone with the image can extract it. Use a BuildKit --secret mount for build-time secrets, and rotate anything that was ever baked in.

Why is a distroless image safer if it is barely smaller?

Because there is no shell and no package manager. A remote code execution that would otherwise spawn sh, download a tool and pivot has nothing to work with. The size is a side effect; the missing shell is the point.

Production Deployments

Getting a container onto a machine and keeping it there — including the signal handling that decides whether a deploy drops requests.

7.1 PID 1, and the signal that decides everything

Your process is PID 1, and PID 1 is special

The kernel does not apply default signal handlers to PID 1. A process with no explicit SIGTERM handler simply ignores it — so docker stop waits ten seconds and then SIGKILLs you, and every in-flight request is dropped on every deploy. This is the most common production Docker bug and it is completely silent.

Table 7.1 The last row: if your container spawns children, PID 1 must reap them. docker run --init inserts a tiny init that does, and it costs nothing.

7.2 Health checks

What a health check should check

That this instance can serve. Not that the database is up — if it checks a shared dependency, one database blip marks every instance unhealthy and the orchestrator restarts your entire fleet at once (Volume 7 §8.4). Liveness: is the process wedged. Readiness: should traffic come here.

The exit code that means OOM

137 = 128 + 9 (SIGKILL). Check docker inspect --format '{{.State.OOMKilled}}' to confirm. A container that restarts every few hours with 137 is not crashing — it is being killed for exceeding its memory limit, and the fix is a heap dump, not a bigger limit.

Do the migrations separately

Run schema migrations as a step before starting the new version, not in the container’s entrypoint. Three containers starting at once means three migration runs racing each other, and the failure is not always obvious. A one-shot job — or service_completed_successfully in Compose (§4.3) — is the fix.

Checkpoint

Why does docker stop take ten seconds on your container?

Because nothing handled SIGTERM. PID 1 does not get default signal handlers, so the signal is ignored, the grace period expires and Docker sends SIGKILL. Usually the cause is the shell form of CMD, or an application with no handler.

Your container restarts in a loop and looks like it is crashing. What would you check?

The exit code. 137 means SIGKILL — check State.OOMKilled; it exceeded its memory limit. Also check whether the health check lacks --start-period and is failing a slow boot before the process is ready.

Why should a health check not test the database?

Because a shared dependency failing would mark every instance unhealthy at once, and the orchestrator would restart the whole fleet — turning a degradation into an outage. Check that this instance can serve; put dependency health in readiness only.

Checkpoint

Your CI build is slow even though nothing changed. What is missing?

A remote cache. Each CI run is a fresh machine with an empty local cache, so every layer rebuilds. cache-from/cache-to with type=gha or type=registry restores the layers from the previous run.

What does a cache mount give you that layer caching does not?

It survives a layer cache miss. When a dependency changes, the install layer must rerun — but with --mount=type=cache the package manager still finds most packages locally instead of downloading them again. And it is not stored in any layer, so it does not bloat the image.

Why sign images if the registry already requires authentication?

Because authentication controls who can push, not what happened afterwards — a compromised CI token, a mutable tag, or a registry compromise all produce an image that pulls fine. A signature plus verification at deploy time means only images built by your workflow can run.

Table 9.1 Three OCI specifications — image, runtime, distribution — are why every one of these pieces is swappable and why an image you build works everywhere.

9.2 Why Kubernetes “removed Docker”

It removed dockershim, not your images

Kubernetes talks to a runtime through the CRI. Docker never implemented CRI, so Kubernetes shipped an adapter called dockershim and maintained it. In 1.24 that adapter was removed, and Kubernetes now talks to containerd directly — which was already underneath Docker anyway.

Your images are unaffected. They are OCI images; containerd runs them natively. The 2020 headlines saying “Kubernetes drops Docker” caused a great deal of unnecessary alarm about a change that removed a layer of translation.

9.3 Looking one level down

An OCI bundle is a directory and a JSON file

config.json plus a root filesystem. Everything Docker does above that — building, tagging, networks, volumes, Compose — is convenience on top. Reading one config.json once is the fastest way to see that a container really is just a process configuration.

Rootless Docker, and Podman

Rootless mode runs the daemon and containers as your user, so a container escape lands as an unprivileged user rather than root. Podman is rootless and daemonless by default with a Docker-compatible CLI — alias docker=podman works for most day-to-day use. Checkpoint

Did Kubernetes removing Docker break your images?

No. It removed dockershim, the adapter between Kubernetes and the Docker daemon, and now talks to containerd directly — which was already underneath Docker. Images are OCI images and run unchanged.

Why does restarting the Docker daemon not kill running containers?

Because runc exits after setting up the sandbox, and each container’s parent is a shim process, not the daemon. The shim keeps the container alive and reconnects when the daemon returns.

When would you replace runc?

When you run code you do not trust. gVisor intercepts syscalls in user space and Kata gives each container a lightweight VM — both provide a real boundary that namespaces do not. For your own code, hardening (chapter 6) is the proportionate answer.

A container exits with 137. What are the two possibilities?

SIGKILL: either the kernel OOM-killed it for exceeding its memory limit, or docker stop’s grace period expired because nothing handled SIGTERM (§7.1). docker inspect --format '{{.State.OOMKilled}}' distinguishes them.

Your Prometheus dashboard loses its history on every deploy. Why?

The metrics are labelled with the container id, which is new every time. Relabel to something stable — the Compose service name or a custom label — so a redeploy continues the same time series instead of starting a new one.

Performance and Capacity

Where the time and the memory go, and how to decide how much of each to give a container.

By the end of this chapter you will be able to

  • Say what a CPU limit actually does to a process
  • Diagnose slow builds and slow filesystem access

12.1 What a limit does

FlagEnforced byWhat happens at the limit
--memory 512mcgroup memory controllerOOM-killed — exit 137 (§11.2)
--cpus 1.5CFS quotaThrottled — the process is descheduled
--pids-limit 200pids cgroupfork fails
--blkio-weightblkio cgroupRelative I/O priority

Table 12.1 The first two rows fail very differently. Exceeding memory is fatal and obvious; exceeding CPU is silent and shows up as latency, which is much harder to attribute.

CPU throttling is the invisible one

A container at its CPU quota is not slowed smoothly — it is stopped until the next 100 ms period. So p50 latency looks fine and p99 is terrible. Check nr_throttled and throttled_time in /sys/fs/cgroup/cpu.stat inside the container; if nr_throttled is rising, the limit is your latency.

Runtimes need to be told about the limit

Node and the JVM historically read the host’s CPU and memory, not the cgroup’s — so a JVM in a 512 MB container would size its heap for 32 GB and be OOM-killed. Modern Node and JDK 11+ are cgroup-aware, but availableParallelism(), thread pools and worker counts still deserve checking. Set UV_THREADPOOL_SIZE and any pool size explicitly rather than deriving them from the host.

12.2 Sizing, from measurement

Requests and limits are different questions

In Kubernetes, requests are what the scheduler reserves and limits are where you get killed. Setting them equal is predictable and wasteful; setting limits far above requests is efficient and risks noisy-neighbour effects. Docker has only the limit, which is the same decision with fewer words.

Copy-on-write, and databases

The first write to any file in the image layer copies the whole file into the container’s writable layer. For a database file that is disastrous — which is one more reason database data belongs in a volume, where there is no copy-on-write layer in the path.

Checkpoint

Your p99 latency is bad and CPU usage looks low. What would you check?

CPU throttling. A container at its quota is stopped until the next scheduling period, so average usage stays low while tail latency is terrible. nr_throttled in /sys/fs/cgroup/cpu.stat is the number to read.

Why is a bind mount slow on macOS but not on Linux?

Because Docker Desktop runs a Linux VM, and a bind mount crosses the host↔VM boundary on every file operation. On Linux the container shares your kernel and there is no boundary. Put node_modules in a named volume and mount only the source.

How do you choose a memory limit?

Measure the peak under realistic load and add about 50%. Guessing produces a limit that either protects nothing or causes the OOM kill it was meant to prevent — and either way you find out during an incident rather than during a load test.

Checkpoint

Your container is not in docker ps and never appeared to run. What next?

An application in a container cannot reach the database at localhost:5432. Why?

Because localhost inside a container is that container. The database is a different container with a different network namespace — use its service name on a shared user-defined network.

Plugins, custom drivers and the CLI surface. A short chapter, because the honest advice for most of it is “probably not”.

By the end of this chapter you will be able to

  • Install and inspect one
  • Write a CLI plugin, which is genuinely easy
  • Decide when extending Docker is the wrong layer

14.1 Four extension points

KindProvidesExample
VolumeA storage backendNFS, cloud block storage, encrypted volumes
NetworkA network driverWeave, Calico, an overlay of your own
LogA log destinationSplunk, Loki, an internal collector
AuthorizationA veto on every API callPolicy enforcement on the daemon
CLIA docker x subcommanddocker compose, docker buildx, docker scout

Table 14.1 The first four are daemon plugins — a running service the daemon talks to over a socket, with real operational weight. The fifth is just a binary on your PATH.

14.2 CLI plugins are trivial, and useful

This is how compose and buildx ship

They are not built into the Docker binary; they are CLI plugins that happen to be installed by default. That is why docker compose (a plugin) and docker-compose (the old Python program) are different things — and why the second is deprecated.

14.3 When not to extend Docker

You wantBetter layer
Custom schedulingAn orchestrator
Policy on what may runAn admission controller, or a signed-image check (§8.4)
A different storage backendA CSI driver, if you are on Kubernetes
Automation around buildsA script, or CI

A team-specific workflowA CLI plugin, or a Makefile

Table 14.2 Almost everything on the left is better solved above or below Docker rather than inside it. The last row is the exception, and it is the one worth doing.

The operational cost of a daemon plugin

It is a process the daemon depends on. If it stops, volumes or networks or logging using it stop with it — and the failure is reported by the daemon, not by the plugin, so the message rarely names the cause. Upgrading Docker means checking the plugin is compatible. That is a real burden for something that usually could have been a script.

Checkpoint

What is the difference between a CLI plugin and a daemon plugin?

A CLI plugin is an executable on your PATH that adds a subcommand — no daemon involvement, no operational risk. A daemon plugin is a running service the daemon depends on for volumes, networks, logging or authorization; if it fails, those features fail.

Why is docker compose different from docker-compose?

The first is a CLI plugin shipped with Docker; the second is the older standalone Python tool, now deprecated. They differ in behaviour and in the compose file features they support, which is why old tutorials with a hyphen sometimes do not match what you see.

You want to enforce that only signed images run. Is a plugin the answer?

Usually not. An authorization plugin can do it, but the same policy belongs in the deploy pipeline or in an admission controller, where it is testable and does not put a veto on every daemon API call. Verify signatures where you deploy (§8.4).

Chapter Fifteen · Part VIII

Windows Containers and Mixed Environments

The part of Docker most Linux developers never touch, and the constraint that explains all of it: a container shares the host kernel.

By the end of this chapter you will be able to

  • Distinguish process isolation from Hyper-V isolation
  • Say what Docker Desktop is actually doing

15.1 The constraint

One kernel, one kind of container

A container is a process on the host’s kernel (§0.1). A Linux container needs Linux syscalls; a Windows container needs Windows ones. There is no translation layer — so a Windows host runs Windows containers natively and Linux containers in a VM, and a Linux host cannot run Windows containers at all.

The reason to containerise development at all

Not because containers are fashionable, but because they make the three operating systems irrelevant. Everyone runs the same base image, the same dependency versions and the same commands, and “works on my machine” stops being a category of bug. That is worth the slower file I/O on two of the three platforms.

Checkpoint

Why can a Linux host not run a Windows container?

Because a container is a process on the host kernel, and Windows binaries need Windows syscalls. There is no translation layer — Windows hosts run Linux containers in a VM, and Linux hosts cannot run Windows containers at all.

Your Windows containers stopped starting after a host update. Why?

Process isolation requires the container’s base image build to closely match the host’s Windows build. Update the base image to match, or switch to Hyper-V isolation, which does not have that coupling.

An import works on a colleague’s Mac and fails in CI. What is the likely cause?

Case sensitivity. macOS filesystems are usually case-insensitive and Linux is not, so ./User and ./user are the same file locally and different files on the build server. Containerising development catches it before CI does.

Gateway API is replacing Ingress

The Kubernetes Ingress resource was underspecified, so every controller added incompatible annotations. Gateway API is the standard replacement — role-oriented, portable, and supported by Traefik, Envoy, NGINX, Cilium and Istio. New clusters should start there.

Checkpoint

What does an overlay network cost?

Encapsulation: every packet is wrapped in UDP on the way out and unwrapped on the way in, which costs CPU and MTU. It is portable and works anywhere; routed mode (Calico) or eBPF (Cilium) avoids the wrapping when you control the network.

When is a service mesh worth it?

Several services in several languages, where you want mTLS, retries, timeouts and tracing applied uniformly without changing each application — or a compliance requirement for encryption between services. Below about ten services in one language, a good HTTP client and an ingress controller do the same work for far less.

Which of a mesh’s features must stay in your application?

Authorisation of the specific request. An edge or a sidecar can authenticate the caller, but neither knows whether this user may read this record — that requires the data. Coarse-grained at the edge, fine-grained in the application.
