About this book

Most people use Git as a set of memorised incantations that usually work, and panic when they do not. The alternative is not more commands — it is one correct mental model, which takes about twenty minutes to acquire.

That model is chapter 0: Git stores snapshots in a content-addressed object database, and a branch is a file containing one hash. Everything that seems arbitrary follows from it — why a rebase changes every hash, why branching is instant, why git status has two columns, why a merge needs three commits and not two, and why almost nothing you do can actually be lost.

The rule for the whole book is the series rule: every command was run before it was printed. The lab repository has fixed commit dates, so its hashes are the same every time it is built — the 6bbd407 you see in chapter 3 is the same object as the one in chapter 12. Where a demonstration failed the first time, the chapter shows the failure.

Who should read this

Anyone who commits code. Chapters 0 to 6 assume nothing beyond having installed Git. From chapter 7 the material is what distinguishes someone who can recover a bad afternoon from someone who re-clones and copies files across.

How this book is organised

Chapter 0 is the object model — read it first even if you have used Git for years. Then chapters 1–16, mapping one-to-one onto the sixteen modules of the Git track in Code Lab, each ending with that module’s ten graded exercises. The contents below group them by theme rather than by number, which is the order they are best read in.

Four settings that make Git noticeably better, today

merge.conflictstyle = zdiff3 shows the common ancestor in a conflict (§4.2). rebase.autosquash = true makes --fixup commits fold themselves in (§6.2). rerere.enabled = true remembers how you resolved a conflict (§4.4). git maintenance start keeps a large repository fast (§14.3). All four are off by default and almost nobody turns them on.

Chapter Zero · Orientation

What Git Actually Stores

Not diffs. Snapshots, in a content-addressed object store, joined by a chain of pointers. Everything confusing about Git becomes simple once that sentence is true for you.

By the end of this chapter you will be able to
  • Name the four object types and what each contains
  • Explain why a commit hash changes when you rebase
  • Say what a branch is — and it is smaller than you think
  • Read git cat-file and see the model directly

0.1 Four kinds of object

ObjectContainsNamed by
blobThe contents of one file — no name, no permissionsThe SHA of its content
treeA directory listing: names, modes, and the hashes they point toThe SHA of that listing
commitOne tree, zero or more parents, author, committer, messageThe SHA of all of that
tagA pointer to an object, with a message and a signatureIts own SHA

Table 0.1 That is the entire database. Everything else — branches, the index, the stash, HEAD — is a pointer or a file referring to these.

0.2 Snapshots, not diffs

The most common wrong model

Most tools store a base version plus a chain of changes. Git does not. Every commit references a full tree; identical files across commits are the same blob, stored once. The diffs you see in git log -p and git diff are computed on demand by comparing two trees, not read from storage.

Two consequences worth having: a commit is complete on its own, and Git is fast at things that would be expensive in a diff-based system — git checkout of an old commit is reading a tree, not replaying history backwards.

0.3 A branch is a file with a hash in it

ThingReally is
A branchA file in .git/refs/heads/ with one hash
A tagThe same, in refs/tags/ — but not moved by commits
HEADA file saying which branch you are on
Detached HEADHEAD holding a hash instead of a branch name
main after a commitThe same file, with a new hash written into it
The index (staging area)A binary file, .git/index, listing what the next commit will contain
Why a rebase changes every hash

A commit’s hash is computed over its tree, its parent, its author, its dates and its message. Rebasing gives a commit a different parent, so its hash necessarily changes — and so does every commit after it, because their parent changed too. Nothing was “modified”: new objects were created and the branch pointer was moved to the new chain (chapter 6).

0.4 The three places a file can be

git status tells you the command you want

It is not just a report — it prints the exact command to unstage, to discard, to continue a rebase. Reading its suggestions rather than searching the internet is the single fastest way to become comfortable with Git.

0.5 Setting it up once

Signing commits

git config --global gpg.format ssh and user.signingkey ~/.ssh/id_ed25519.pub lets you sign with the SSH key you already have — no GPG. Add commit.gpgsign = true and GitHub shows a Verified badge. Five minutes, and it makes commit authorship something more than a text field anyone can set.

Checkpoint

Does Git store diffs?

No. Every commit points to a tree — a complete snapshot. Identical files share one blob because objects are named by their content. The diffs you see are computed on demand by comparing two trees.

Why does rebasing change commit hashes?

Because a hash covers the commit’s tree, its parent, its author, its dates and its message. A rebase gives commits new parents, so new hashes are unavoidable — and every commit after also changes, because its parent did. Nothing is edited; new objects are written and a pointer moves.

What is a branch?

A file containing one hash. Creating, deleting and switching branches are cheap because there is nothing to copy — which is why Git workflows use branches so freely compared with older systems.

Almost nothing is really lost

git reflog records every position HEAD has held for 90 days, including commits you “deleted”. A hard reset to a commit you can name in the reflog gets it back. The only genuinely unrecoverable loss is a change that was never committed and was discarded — which is why git stash is worth using even for a moment.

Checkpoint

What does git add -p buy you?

The ability to commit one idea at a time when your working tree contains two. Stage the hunks that belong together, commit, then stage the rest. It turns a clean history from something requiring discipline into something requiring one extra flag.

When is reset wrong and revert right?

When the commit has been pushed. reset rewrites history, so anyone who pulled it now diverges from you. revert adds a new commit that undoes the change, which everyone can pull normally.

You discarded changes with git restore by mistake. Can you get them back?

Only if they were committed or stashed at some point — then the reflog or the stash has them. A change that only ever existed in the working tree is genuinely gone; Git never saw it. That is the one irreversible operation in daily use.

Remotes and Collaboration

Other people. A remote is a name for another repository, and every confusing thing about pushing and pulling comes from what a tracking branch is.

By the end of this chapter you will be able to

  • Say what git pull does, and why the default surprises people

2.1 Three kinds of branch

NameIsUpdated by
mainA local branchYour commits
origin/mainA remote-tracking branch — your cached copy of theirsgit fetch only

Table 2.1 The middle row is the one nobody explains. origin/main is not live — it is what the remote looked like the last time you fetched. It never changes on its own.

2.2 fetch, then decide

CommandDoes
git fetchDownload; update origin/*; change nothing else
git pullfetch, then merge (default) or rebase
git pull --rebaseReplay your local commits on top of theirs
git pushSend your commits — only if it is a fast-forward
git push --force-with-leaseOverwrite, but only if the remote is where you last saw it
git push --forceOverwrite regardless — this is how colleagues lose work
Set pull.rebase = true and stop thinking about it

The default git pull creates a merge commit every time your branch and the remote have both moved — so a busy repository accumulates “Merge branch main of github.com:...” commits that carry no information. pull.rebase = true replays your work on top instead, and the history stays readable. Add rebase.autostash = true so it works with a dirty tree.

2.3 The rejected push

DoResult
git pull --rebase then pushRight almost always. Your commits go on top
git pull then pushWorks; adds a merge commit
git push --forceDeletes their commits. Never do this on a shared branch
git push --force-with-leaseSafe force: fails if the remote moved since your last fetch
--force-with-lease, always, instead of --force

It checks that origin/main still points where you last saw it. If someone pushed in between, the push is rejected instead of silently overwriting them. There is no situation where plain --force is better, and one where it costs a colleague a day. Alias it.

Checkpoint

Why does origin/main sometimes look out of date?

Because it is a cache, updated only by git fetch (or the fetch inside pull). It is what the remote looked like when you last asked. Nothing about it is live.

Your push was rejected. What is the safe response?

git fetch, then git rebase origin/main (or git pull --rebase), then push. The rejection means the remote has commits you do not — forcing would delete them.

When is --force-with-lease different from --force?

When someone pushed after your last fetch. --force overwrites them silently; --force-with-lease notices the remote moved and refuses. It is strictly better, so use it every time.

Switching branches changes your files

git switch rewrites the working tree to match the target. Uncommitted changes that would be overwritten stop it with an error — commit them, stash them, or add rebase.autostash/--merge. Git will not silently destroy work here, which is worth knowing so the error does not look like a failure.

The golden rule, and why it is not dogma

Do not rebase commits other people have. Not because it is forbidden, but because rebasing creates new commits: anyone who already has the old ones will end up with both, and their next merge will be a mess. On a branch only you have pushed, rebase freely — --force-with-lease (§2.3) is exactly for that.

3.4 Detached HEAD

If you committed in a detached HEAD and switched away

The commits are still there for about 90 days. git reflog lists them; git branch rescue <hash> gives them a name. This is a routine recovery, not a disaster — chapter 9.

Checkpoint

What is a fast-forward?

A merge where the target branch is an ancestor of the branch being merged, so Git just moves the pointer forward. No merge commit, no conflict, nothing combined — which is why it feels like nothing happened.

When should you rebase and when should you merge?

Rebase your own work that nobody else has, to tidy it before sharing. Merge anything others already have, because a rebase creates new commits and leaves them with duplicates.

You are in a detached HEAD with two commits you want to keep. What now?

git switch -c some-name right there — that creates a branch pointing at your current commit. If you already switched away, git reflog finds the hash and git branch name <hash> rescues it.

Chapter Four · Part II

Merging, and Conflicts

What Git does when two people changed the same thing, and the setting that makes conflicts much easier to resolve correctly.

By the end of this chapter you will be able to

  • Read conflict markers, including the common ancestor
  • Choose a merge strategy deliberately

4.1 Three-way merge

Git compares three commits, not two

To merge B into A, Git finds their common ancestor and compares each side against it. A file changed on only one side is taken from that side, automatically. A file changed on both sides, in the same region, is a conflict — because Git cannot know which change you meant. That is the whole algorithm, and it explains why most merges have no conflicts at all.

4.2 Reading the markers

Table 4.1 The last row is the one to remember when you are lost: abort returns you exactly to where you started, every time.

“ours” and “theirs” swap during a rebase

In a merge, --ours is your branch. In a rebase, Git is replaying your commits onto the other branch, so --ours is the branch you are rebasing onto and --theirs is your commit. This reversal has caused a great many wrong resolutions; when in doubt, look at the content rather than trusting the word.

Checkpoint

Why does Git need a common ancestor to merge?

To tell a change from a difference. Comparing two versions only shows they differ; comparing each against the ancestor shows which side actually changed, so unchanged sides can be taken automatically and only genuine collisions become conflicts.

What does zdiff3 add to a conflict?

The common ancestor, as a third section. It usually makes the resolution obvious — if one side matches the ancestor, that side did not change and the other side is the answer.

Why is --ours confusing during a rebase?

Because a rebase replays your commits onto the other branch, so “ours” is the branch you are rebasing onto and “theirs” is your own commit — the reverse of a merge. Read the content rather than trusting the label.

5.1 The three buttons

Table 5.1 The bisect row is the strongest argument for squashing: if every commit on main is a complete, reviewed change, bisect always lands somewhere meaningful.

A defensible default: squash

One commit per pull request on main, with the pull request number in the subject. Reverting a feature is one command. Bisect is reliable. And nobody has to keep their branch tidy — the mess is squashed away, which removes an entire category of process argument.

Choose merge commits instead when individual commits genuinely carry information a reviewer will want later — a long refactor done in deliberate steps. Choose rebase and merge if you want linear history and individual commits, and your team actually curates them.

5.2 Reverting a merge

Reverting a merge, then wanting it back

This is the classic trap. Once you have reverted a merge, re-merging the same branch brings in nothing — Git considers those commits already merged. You must revert the revert. Squashing avoids the whole problem, which is one more argument for it.

The one people regret not setting on day one

Block force pushes to the default branch. Everything else can be fixed later; a force push over shared history costs everyone on the team an afternoon, and it happens by accident, usually at a bad moment.

Checkpoint

Why does squash merging make git bisect more reliable?

Because every commit on main is then a complete, reviewed change that builds and passes tests. With individual commits merged, bisect can land on a work-in-progress commit that does not compile — and you have to skip it and lose resolution.

Why does git revert need -m on a merge commit?

Because the merge has two parents and reverting means “go back to one of them” — Git cannot know which. -m 1 keeps the first parent, which is normally the branch you merged into.

You reverted a merge and now want the feature back. What happens?

Re-merging brings in nothing: Git already considers those commits merged. You must revert the revert. It is the sharpest edge of merge-commit workflows and squashing avoids it entirely.

Rewriting History

Interactive rebase, and the small set of operations that turn a messy branch into a reviewable one. Plus the two rules that keep it safe.

By the end of this chapter you will be able to
  • Reorder, squash, edit and drop commits
  • Use fixup! commits and --autosquash
  • Say exactly when rewriting is safe
  • Remove a secret from history, properly

6.1 Interactive rebase

You want toDo
Fix a messagereword, or --amend for the last one
Combine two commitssquash (keep both messages) or fixup (discard one)
Split one commitedit, then git reset HEAD~ and commit in pieces
ReorderMove the lines
Remove a commitDelete the line, or drop
Insert a commitedit the one before, commit, --continue

6.2 fixup! — the workflow that makes this painless

The habit

During review, when a reviewer points at something from commit 3, do not add “address review comments” on top. Run git commit --fixup <hash>. When the branch is approved, one git rebase -i --autosquash collapses every fix into the commit it belongs to, and the history reads as though you got it right first time.

6.3 When rewriting is safe

SituationSafe?
Commits only in your working copyYes
Pushed to your own feature branch, no reviewer yetYes — --force-with-lease
Pushed, review in progressAvoid — it destroys the comparison view
Merged to a shared branchNo
Anything on mainNo
A secret that must be purgedYes, with coordination — §6.4

Table 6.1 The rule underneath all of these: rewriting creates new commits, so anyone holding the old ones now has a divergent history. That is fine if nobody does.

And it is recoverable

A rebase that goes wrong is not a disaster: git rebase --abort during, and git reflog plus git reset --hard <hash> afterwards. The old commits survive in the reflog for 90 days. Practise the recovery once and the operation stops being frightening.

6.4 Removing a secret from history

Step 1 is not optional and step 3 is not sufficient

The secret was cloned, cached, and possibly indexed. On GitHub, old commits remain reachable by hash until support garbage-collects them, and forks keep their own copies. Rotating the credential is the fix; rewriting history is tidying up afterwards. Reversing that order is the most common mistake in a leaked-secret incident.

Prevent it instead

gitleaks or trufflehog as a pre-commit hook (chapter 11), plus GitHub’s push protection. A secret that never reaches a commit needs no incident response.

Checkpoint

Why is the rebase todo list in the opposite order from git log?

Because it is a script executed top to bottom, replaying commits oldest first. git log shows newest first because that is what you usually want to read. It catches everyone once.

What does git commit --fixup <hash> buy you?

A commit marked as belonging to an earlier one. git rebase -i --autosquash then moves it into place and folds it in automatically — so review fixes end up inside the commit they fix rather than piling up as “address comments” on top.

You have pushed a file containing an API key. What is the first step?

Rotate the key. It is already public — cloned, cached, possibly indexed. Rewriting history is step two and does not undo the exposure. Doing them in the other order is the standard mistake.

Why .git is often smaller than the working tree

Packfiles store objects delta-compressed against similar objects and then zlib-compressed. A repository with a long history of small text changes packs extremely well — which is also why a single large binary, changed often, destroys that (chapter 15).

Checkpoint

What is the difference between HEAD~2 and HEAD^2?

~ walks back N commits along first parents. ^ selects which parent of one commit — only meaningful on a merge, where ^1 is the branch merged into and ^2 is the branch merged.

Why is .git sometimes smaller than the checked-out files?

Packfiles delta-compress similar objects against each other and then zlib-compress the result. Text with a long history of small edits packs very well. The same mechanism is why one frequently-changed binary bloats a repository enormously.

You want to see the history of main without every merged branch. What do you use?

git log --first-parent. It follows only the first parent of each merge, so the log reads as the sequence of things merged into main rather than every commit that ever happened on a branch.

How a team agrees to use branches. Four common shapes, and the question that decides between them.

By the end of this chapter you will be able to

8.1 Four shapes

WorkflowBranchesDeploysFits
Trunk-basedMain, plus branches lasting hoursContinuouslyStrong CI, feature flags
GitHub FlowMain, plus feature branchesOn mergeMost teams
Release branchesMain, features, release/1.4On a scheduleVersioned software
Git Flowmain, develop, feature, release, hotfixOn a scheduleRarely worth it now

Table 8.1 Git Flow was designed in 2010 for software shipped as versioned downloads. For a web service deployed several times a day it adds two long-lived branches and a merge dance for no benefit — and its author has since said so.

The question that decides it

How often do you deploy, and do you support old versions? Deploy on merge and support only the latest: GitHub Flow. Ship versions customers stay on: release branches. Deploy many times a day with feature flags: trunk-based. Everything else is a variation.

8.2 GitHub Flow, in full

What makes it work is not the branching

It is CI that blocks the merge and branches that live for a day, not a month. A team doing GitHub Flow with two-week branches and no required checks has the diagram and none of the benefit — they have long-lived branches with extra steps.

8.3 Releases and hotfixes

The step everyone forgets

Getting the fix back into main. A hotfix branched from a tag and never merged forward means the next release silently reintroduces the bug — and it is always noticed by a customer rather than by a test.

8.4 What a workflow costs

ChoiceCost
Long-lived branchesConflicts, and integration risk at the end

The metric worth tracking

Time from first commit to merged. If it is measured in days, the workflow is the bottleneck, not the developers — and the fix is almost always smaller pull requests rather than more process. Everything else in this chapter is downstream of that number.

Checkpoint

Why is Git Flow usually the wrong choice today?

It was designed for versioned software shipped as downloads, with parallel supported releases. A web service deployed several times a day gets two extra long-lived branches and a merge ritual for no benefit. Its author has said the same.

Why branch a hotfix from the tag rather than from main?

Because main contains unreleased changes you do not want in an emergency deploy. Branching from the released tag means the hotfix contains exactly one change — and then it must be merged forward into main, which is the step teams forget.

What actually makes GitHub Flow work?

CI that blocks the merge, and branches that live for a day. Without both, you have long-lived branches and a diagram. The branching pattern is the least important part.

Chapter Nine · Part IV

Debugging and Recovery

Finding the commit that broke something, and getting back work you thought you had destroyed. Two commands, and almost nothing in Git is unrecoverable.

By the end of this chapter you will be able to
  • Find a regression with git bisect, including automatically
  • Use the reflog to recover almost anything
  • Find lost commits with fsck
  • Attribute a line past a reformatting commit

9.1 bisect

Bisect needs commits that build

If half your history does not compile, bisect lands on those and you have to git bisect skip them, losing resolution. This is the practical argument for squash merging (§5.1): every commit on main is a complete, reviewed change, so every bisect step is a real answer.

9.2 The reflog

You didRecover with
reset --hard to the wrong placegit reset --hard HEAD@{1}
Deleted a branchgit branch name <hash from reflog>
A rebase that went wronggit reset --hard branch@{1}
Committed on a detached HEAD, then switchedgit branch rescue <hash>
Amended away a commitIt is in the reflog
Force-pushed over someoneTheir reflog has it; ask them

Table 9.1 The reflog is local and per-repository. It does not travel with a clone and it does not exist on the server — so a colleague who force-pushed cannot help you from the remote, but their own reflog can.

The one thing the reflog cannot save

Work that was never committed. A git restore over an uncommitted edit, or a reset --hard with unstaged changes, is genuinely gone — Git never saw it. This is why git stash is worth using for even a moment’s uncertainty: it makes a commit.

9.3 When the reflog is not enough

Do not run gc --prune=now while looking for lost work

That is the command that actually deletes unreachable objects. Until it runs, they are still on disk. If you have just lost something, stop, and look with fsck and reflog before running any maintenance.

9.4 Blame past a reformatting

FlagDoes
-wIgnore whitespace changes
-CDetect lines moved from another file
-MDetect lines moved within the file
-L 10,20Only those lines
--ignore-rev hashSkip one commit
The habit that avoids the problem

Format in its own commit, touching nothing else, and add its hash to .git-blame-ignore-revs in the same pull request. It costs one line and preserves the history for everyone who comes after.

Checkpoint

Why does squash merging make bisect more useful?

Because every commit on main is a complete, reviewed change that builds. With individual commits merged, bisect can land on a work-in-progress commit that does not compile, which you must skip — losing resolution exactly where you need it.

You reset --hard to the wrong commit. What now?

git reflog, find where you were, git reset --hard HEAD@{1}. The reflog keeps every position HEAD held for 90 days. The only thing it cannot recover is work that was never committed.

A reformatting commit ruined git blame. What fixes it?

A .git-blame-ignore-revs file listing that commit, plus git config blame.ignoreRevsFile. Blame then looks through it to the commit that actually wrote each line, and GitHub honours the same file.

Submodules and Subtrees

Putting one repository inside another. Two mechanisms with opposite trade-offs, and an honest account of why most teams end up regretting the first one.

By the end of this chapter you will be able to
  • Add, update and clone a repository with submodules
  • Say why a submodule is pinned to a commit and what that costs
  • Use a subtree instead, and when to

10.2 Living with them

The failure that costs a day

You edit inside the submodule, commit there, commit the parent’s new pointer, and push only the parent. Everyone else now has a parent pointing at a commit that does not exist on their remote, with an error that mentions neither of those facts. Push the submodule first, always. git push --recurse-submodules=check makes Git refuse the parent push if you have not.

10.3 Subtree — the other trade-off

Table 10.2 The “team needs to know” row decides it for most projects: a subtree fails safe for people who do not know it is there, and a submodule does not.

10.4 Or neither

The honest recommendation

Try, in order: a package, then a monorepo, then a subtree, then a submodule. Submodules are the right answer when you genuinely need an independent repository with independent history and a pinned reference — a vendored fork, a shared configuration repository, a specification. For “we want to share some code”, they are the most expensive option available.

Checkpoint

Why is a submodule directory empty after a normal clone?

Because the parent stores only a commit hash (a gitlink), not the files. git clone --recurse-submodules, or git submodule update --init --recursive afterwards, fetches the contents.

You committed inside a submodule and pushed only the parent. What breaks?

Everyone else’s clone: the parent points at a commit that exists nowhere they can fetch. Push the submodule first. git push --recurse-submodules=check makes Git refuse the parent push otherwise.

When is a subtree better than a submodule?

Almost always, unless you specifically need an independent repository with a pinned reference. A subtree puts the real files in your repository, so a plain clone works and a colleague who has never heard of subtrees is unaffected.

Checkpoint

Why is a pre-commit hook not a control?

Because it lives in .git/hooks/, which is not committed and not cloned, and because git commit --no-verify skips it. It is fast feedback for the author. Enforcement belongs in branch protection and required CI checks.

How do you share hooks with a team?

core.hooksPath pointing at a committed directory, or a tool — pre-commit, husky, Lefthook — that installs them. Any of these still needs each developer to run a setup step once, which is why the server rules matter.

Your team keeps using --no-verify. What went wrong?

The hook is too slow. Anything over a couple of seconds gets bypassed. Lint only the staged files in pre-commit, move the slow checks to pre-push, and let CI be the thing that actually blocks.

Chapter Twelve · Part V

Worktrees

Several branches checked out at once, from one repository. The feature that replaces most uses of git stash, and almost nobody knows it exists.

By the end of this chapter you will be able to
  • Create and remove worktrees
  • Say what they share and what they do not
  • Use one for a hotfix without disturbing your work
  • Avoid the two constraints they impose

12.1 The problem they solve

The interruption

You are halfway through a feature, with a dirty tree and a half-built node_modules. Something urgent needs a one-line fix on main. The usual answer is git stash, switch, fix, switch back, pop — and hope nothing was lost. A worktree gives you a second directory with main checked out, leaving your first one exactly as it was.

12.2 Using them

The one constraint

A branch can be checked out in only one worktree at a time. Trying to check out main in a second one fails with “already checked out at …”. That is protecting you: two directories with the same branch and different states would be a mess. Use --detach if you only want to look.

Table 12.1 The last row has become the common one: a tool that checks out and builds a branch should do it in a worktree, not in the directory you are typing in.

12.3 Housekeeping

If you delete the directory by hand

Git still thinks the worktree exists and will refuse to check that branch out elsewhere. git worktree prune clears the stale entry. It is the only maintenance worktrees need, and forgetting it produces a confusing “already checked out” for a directory that is not there.

Checkpoint

What does a second worktree share with the first?

Everything in .git: objects, refs, tags, config, hooks and the reflog. What is separate is the working tree, the index and HEAD — which is exactly what you want for working on two branches at once.

Why can a branch not be checked out in two worktrees?

Because they would have independent working trees and indexes pointing at the same branch, and committing in one would make the other’s state meaningless. Use --detach if you only need to look at the same commit.

When is a worktree better than git stash?

Almost whenever the interruption will take more than a minute — a hotfix, a review, a long build. Stashing discards your build state and risks losing untracked files; a worktree leaves the original directory untouched.

13.2 Cherry-pick

The cost

The same change now exists as two commits. If both branches are later merged, Git usually notices they produce the same result and resolves it silently — usually. When they have both been modified since, you get a conflict that is genuinely confusing, because both sides look like they made the same change.

git cherry-pick -x appends “(cherry picked from commit …)” to the message. Always use it: it is the only record of where the commit came from, and it is what tells the next person that the duplicate is deliberate.

Good useRisky use
A hotfix onto a release branchRoutinely moving commits between long-lived branches
One commit from an abandoned branchCherry-picking a whole feature commit by commit
Backporting a fixUsing it instead of merging
Recovering a commit from the reflog

13.3 Bundles — a repository in one file

Where this still matters

Air-gapped networks, moving a large repository once without cloning over a slow link, and backups — a bundle of --all is a complete, verifiable copy in one file. It is also the fastest way to hand someone a repository that is not on any server.

Checkpoint

What does git am do that git apply does not?

Creates a commit, with the original author, date and message from the patch header. git apply only changes the working tree — you would then commit under your own name and lose the attribution.

Why always use cherry-pick -x?

It records the source commit in the message. Without it, the same change exists twice in history with nothing linking them, and the next person to hit a conflict between the two has no way to tell it was deliberate.

What is a bundle for?

Moving a repository as a single file — across an air gap, onto a USB stick, or as a self-contained backup. git clone and git pull both accept one as if it were a remote.

The asymmetry that matters

Adding a large file is one commit. Removing it is a history rewrite that every collaborator must respond to (§6.4). That asymmetry is why a pre-receive hook or a CI check on file size is worth the ten minutes it takes to write — it is the only intervention that happens at the cheap end.

Checkpoint

Your clone is slow but status is fast. What is the problem?

History and object count, not the working tree. --filter=blob:none for development, or --depth 1 in CI. Sparse-checkout would not help — it addresses the number of files checked out, which is not your problem.

Why prefer --filter=blob:none over --depth 1 for daily work?

Because it keeps the full commit graph, so log, blame and bisect all work — only file contents are fetched on demand. A shallow clone has no history at all, which breaks those and makes fetching more later awkward.

A 50 MB binary was committed and then deleted. Is the repository smaller?

No. Every version is still in history and in every clone. Removing it requires rewriting history and coordinating with everyone. That asymmetry is why blocking the commit is worth more than any cleanup tool.

15.2 Using it

The migration is a history rewrite

lfs migrate import rewrites every commit that touched those files, so all hashes change (§6.4). Everyone must re-clone. Plan it like any other rewrite: announce it, do it at a quiet moment, and expect to help two people who pushed in between.

The alternative worth considering first

Do the binaries need to be versioned with the code? Design sources, sample media and build artefacts usually do not — object storage with a manifest file in the repository gives you the same reproducibility with none of the LFS machinery. Reserve LFS for assets that genuinely must move in lockstep with a commit: game assets, firmware images, test fixtures a specific version depends on.

Checkpoint

What does a committed LFS file actually contain?

A pointer: a version line, a SHA-256 of the content, and a size — about 130 bytes. The content is on an LFS server and is fetched on checkout by a filter.

A colleague clones and the images are broken. What happened?

They do not have git-lfs installed, so the smudge filter never ran and they have the pointer files as literal text. Same for a CI runner that has not enabled LFS — and the error rarely mentions LFS at all.

When would you not use LFS?

When the binaries do not need to move in lockstep with commits. Design sources, sample media and build outputs are usually better in object storage with a manifest in the repository — same reproducibility, no client requirement, no quota, no extra server.

Checkpoint

What makes a repository “bare”?

It has no working tree — it is the contents of .git at the top level. That is what a remote is, and it is why you cannot push to a normal repository’s checked-out branch.

What does GitHub give you that Git does not?

Pull requests, issues, permissions, CI, a web UI, branch protection and registries. Git handles version control; everything a team calls “our Git workflow” is usually the forge.

Is self-hosting Git hard?

Hosting Git is trivial — a bare repository and SSH. Hosting a forge with CI is a real service with backups, upgrades and security exposure. Do not confuse the two when estimating the cost.
