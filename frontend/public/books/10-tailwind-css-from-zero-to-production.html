About this book

Tailwind is easy to use badly and easy to dismiss. Used well, it is the reason a large application’s stylesheet stops growing — and understanding why that is true is worth more than memorising the utility names.

So this book does two things most Tailwind material does not. It shows you, for every concept, the CSS that Tailwind actually generated — run through the real CLI, pasted verbatim — because the whole point of the tool is invisible until you see that a class is just a rule. And it renders the components in a real browser and shows you the screenshot, so the class string, the generated CSS, and the pixels are all on the same page.

It is also written entirely against Tailwind CSS 4, which rewrote how the framework is configured. If you have used Tailwind before, four things are different: configuration moved from a JavaScript file into your CSS (@theme), the content array is gone, the colours are OKLCH, and the engine is Rust with autoprefixing built in. A v3 tutorial will have you writing a config file you no longer need. Chapter 0 lays out the differences; the rest of the book assumes v4 throughout.

Who should read this

Anyone who writes HTML and wants their CSS to stop being a liability. You need no prior Tailwind. Chapters 5 and 12 touch React and Vue lightly, but the ideas are framework-independent.

How this book is organised

Chapter 0 is the mental model. Then chapters 0–15 map one-to-one onto the sixteen modules of the Tailwind CSS track in Code Lab, each ending with that module’s ten graded exercises. Read chapter 0, then 1 to 6 in order; after that, dip in as needed.

Three things here that most Tailwind material has not caught up with

1. Configuration is CSS-first — no tailwind.config.js, no content array (§0.3, §6). 2. Every theme token is a real CSS variable, which is what makes runtime theming and dynamic values clean (§6.2, §10, §14). 3. Container queries, cascade layers and autoprefixing are all built in, not plugins or separate tools (§3.3, §7).

Chapter Zero · Orientation

What Tailwind Is, and What Changed in v4

A utility-class framework that generates exactly the CSS your markup uses, and nothing else. Version 4 rewrote almost everything about how you configure it — most tutorials you will find describe version 3.

By the end of this chapter you will be able to
  • Say what a utility class is and why the approach scales
  • Explain what Tailwind generates, and prove it
  • Name the four things v4 changed that break older guides
  • Set up a project with the new CSS-first configuration

0.1 Utilities, not components

Traditional CSS gives you semantic classes — .card, .btn-primary — and a separate stylesheet that grows forever and that nobody dares delete from. Tailwind gives you single-purpose utility classes composed directly in the markup: p-6 is padding: 1.5rem, flex is display: flex.

The objection is immediate — “that is just inline styles with extra steps” — and it is wrong for three concrete reasons.

Utility classInline style
Constrained to a design scaleAny value — padding: 13px
Responsive: md:flexNo media queries
States: hover:, focus:No pseudo-classes
One shared, cached stylesheetRepeated on every element
Purged of what you do not usen/a

Table 0.1 The design-scale constraint is the underrated one: p-4 p-6 p-8 come from a spacing scale, so a team’s spacing stays consistent without anyone maintaining a spacing document.

The real problem it solves

Not typing speed — the unbounded growth of a stylesheet. In utility-first CSS there is no per-component CSS to write, so there is none to grow, none to conflict, and none to be afraid of deleting. The stylesheet size depends on how many distinct utilities you use across the whole project, which plateaus, rather than on how many components you have, which does not.

0.2 What it actually generates

Tailwind scans your markup, finds the classes you used, and emits a stylesheet containing only those rules. This is not a runtime; it is a build step that produces plain CSS. Here is that build, run for real.

This is why the stylesheet stays small

A project using 400 distinct utilities ships 400 rules, whether those utilities appear ten times or ten thousand. Delete a component and the utilities it alone used vanish from the next build. There is no dead CSS because there is no CSS that is not traceable to a class in your markup.

0.3 Four things v4 changed

1 · Configuration moved into CSS

Version 3 had a tailwind.config.js with a JavaScript object. Version 4 configures in your CSS file with @theme, and the three @tailwind directives became one @import. Every v3 tutorial opens with a config file you no longer write:

2 · No content array

Version 3 needed content: ["./src/**/*.html"] so it knew where to look for classes. Version 4 detects your source files automatically. The most common v3 bug — “my styles are not applying” because a path was missing from content — no longer exists.

3 · Colors are OKLCH, and the engine is Rust

The default palette moved from sRGB hex to OKLCH, a perceptually-uniform colour space, so the built-in colours are more vivid on modern displays and blend more evenly. The engine (“Oxide”) is rewritten in Rust with Lightning CSS built in — so PostCSS and Autoprefixer are no longer separate dependencies, and a full build that took seconds takes milliseconds.

4 · Native cascade layers and container queries

v4 emits real @layer rules, which fixes the specificity fights that made v3 utilities occasionally lose to component CSS. Container queries (@container, @sm:) are built in rather than a plugin. Both are covered in later chapters; the point here is that advice predating them is describing a different framework.

0.4 A project in three files

SetupWhich to use
CLI — @tailwindcss/cliA plain project, or learning (this book)
Vite plugin — @tailwindcss/viteAny Vite app — the fastest option
PostCSS — @tailwindcss/postcssA build already using PostCSS
A CDN <script>A quick experiment only — never production

Table 0.2 The CLI is used throughout this book because it makes the build visible: you can see the CSS come out. In a real app the Vite plugin does the same thing with no separate command.

The framework integrations do the same thing

Next.js, Vite, Astro and the rest all run the same engine — they differ only in when the build happens. Everything in this book about what a class generates is identical regardless of how the build is wired; only chapter 13 (framework integration) touches the wiring.

Checkpoint

Is a utility class the same as an inline style?

No. A utility is constrained to a design scale, works with responsive prefixes and pseudo-class states, and lives in one shared, cacheable stylesheet that is purged of what you do not use. Inline styles have none of those properties.

Why does a Tailwind stylesheet stay small as the project grows?

Because its size depends on the number of distinct utilities used, which plateaus, not on the number of components, which grows without limit. Unused utilities are never generated, and utilities of deleted components vanish from the next build.

You are following a tutorial and it starts with tailwind.config.js and a content array. What version is it?

Version 3. In v4, configuration is CSS-first (@theme in your stylesheet) and source detection is automatic — no config file and no content array. The concepts transfer; the setup does not.

Chapter One · Part I

Typography and Colour

Text and colour are where a design either reads as considered or as default. Tailwind gives you a constrained scale for both, and in v4 the colours live in a place you can reach.

By the end of this chapter you will be able to
  • Set size, weight, leading and tracking from the scale
  • Use the colour palette and its opacity syntax
  • Say where the OKLCH values come from and how to read them
  • Style long-form text with the typography plugin

1.1 The type scale

PropertyUtilities
Sizetext-xs … text-9xl
Weightfont-thin … font-black
Line heightleading-none … leading-loose, or leading-6
Letter spacingtracking-tighter … tracking-widest
Alignmenttext-left, text-center, text-balance, text-pretty
Familyfont-sans, font-serif, font-mono

Table 1.1 text-balance on a heading and text-pretty on a paragraph are the two newest and most underused — they let the browser avoid orphans and ragged last lines.

1.2 Colour, and its opacity

Where the colours actually live now

In v4 every colour is a CSS variable — --color-sky-500 — defined in the default theme and overridable in @theme. That is why you can write bg-sky-500 in a class and var(--color-sky-500) in hand-written CSS and get the same colour. In v3 the palette was locked inside the JavaScript config and unreachable from CSS.

1.3 OKLCH, briefly

You rarely write OKLCH by hand

The palette is already tuned. You reach for raw OKLCH only when defining a brand colour in @theme, and even then a hex value is accepted and converted. The reason to know it exists is that when you read the generated CSS — as this book does throughout — the colours will be in OKLCH, and that is not a bug.

1.4 Long-form text

@plugin is the v4 way to load one

In v3 plugins went in the config file’s plugins: [] array. In v4 they load from CSS with @plugin "name". The typography, forms and container-query plugins are the three worth knowing; chapter 8 shows how to write your own.

Checkpoint

Why are the text sizes named rather than numbered?

Because they are a typographic scale, not pixel values — text-lg also carries a matching line-height, and the steps are chosen to look harmonious together. Naming keeps authors on the scale instead of inventing one-off sizes.

What does text-slate-900/70 mean?

Slate-900 at 70% opacity. The slash-opacity syntax works on any colour utility and is how you make translucent text, hairline borders (/5) and subtle overlays without defining new palette entries.

Why are the generated colours in OKLCH rather than hex?

Because v4’s default palette is defined in OKLCH, a perceptually-uniform space where equal lightness steps look equally bright. It makes hover states and gradients uniform, and it is what you will see whenever you read the generated CSS.

Layout and Spacing

Flexbox, grid, and the spacing scale that ties a layout together. Most of a real interface is these utilities; the rest is decoration.

By the end of this chapter you will be able to

  • Space children with gap and the space scale

2.1 Flexbox

2.2 The spacing scale

UtilitySpacingWhere
p-4padding, all sides1rem
px-6 py-3padding, x and ya button
pt-8padding, one side
m-4 mx-automargin, and horizontal centring
gap-4between flex/grid childrenthe modern default
space-y-4between stacked childrena form

Table 2.1 The numbers are quarters of a rem: p-4 is 1rem, p-6 is 1.5rem. The whole scale derives from one variable, --spacing (§0.2), so changing it rescales the entire design.

2.3 Grid

grid-cols-[…] for the awkward cases

When the columns are not equal — a fixed sidebar and a fluid main — use an arbitrary value: grid-cols-[16rem_1fr]. The underscore is the space. Arbitrary values (§7) are the escape hatch for anything the scale does not cover, and they still generate a single utility.

2.4 Centring, three ways

SituationUtilities
One item, both axesflex items-center justify-center
One item, both axes (grid)grid place-items-center
A block horizontallymx-auto with a max-w-*
Texttext-center
Absolute, dead centreabsolute inset-0 m-auto, or top-1/2 left-1/2 -translate-1/2

Table 2.2 grid place-items-center is the shortest true centre. mx-auto only centres horizontally and only works on a block with a width — the classic “why won’t mx-auto centre my flex item” is because flex items are not blocks with auto margins in that axis.

Checkpoint

Why prefer gap over margins on flex children?

Because gap spaces between children with no edge margins to cancel, no last-child special case, and no collapsing. Margins on flex children require the space-x workaround and break when items wrap; gap just works, including on wrap.

mx-auto is not centring your flex item. Why?

Because the item is not a block with a definite width in that axis. mx-auto centres a block by splitting leftover horizontal space into equal margins; a flex child is laid out by the flex algorithm instead. Use justify-center on the container, or mx-auto works once the item has a width.

How do you make a fixed sidebar next to a fluid main column?

grid grid-cols-[16rem_1fr] — an arbitrary column template, fixed then fractional. The underscore is the space in an arbitrary value, and it generates one utility like any other class.

Chapter Three · Part II

Responsive Design

One set of classes, every screen size. The mental model is the one thing to get right, and it is the opposite of what most people assume.

By the end of this chapter you will be able to
  • Use breakpoint prefixes correctly
  • Explain why Tailwind is mobile-first and what that means for you
  • Reach for container queries when the viewport is the wrong question
  • Build a layout that reflows at every size

3.1 Mobile-first, and why it matters

The consequence: style the small screen with no prefix

An unprefixed class is the phone layout. md:, lg: and xl: are progressive enhancements for larger screens. Writing md:hidden hides something from medium up; to hide it only on small you write hidden md:block. Reading the prefix as “and larger” makes every responsive class obvious.

PrefixApplies fromTypical
(none)0pxphone
sm:40remlarge phone
md:48remtablet
lg:64remlaptop
xl:80remdesktop
2xl:96remwide

Table 3.1 Breakpoints are in rem now, so they scale with the user’s font size. Override them, or add your own, in @theme with --breakpoint-*.

3.2 A layout that reflows

3.3 Container queries

Sometimes the viewport is the wrong question

A card in a sidebar and the same card in a wide main column should lay out differently — but the viewport is identical. Breakpoints cannot help. Container queries respond to the size of the parent, not the screen, and in v4 they are built in.

This is the more correct default for components

A genuinely reusable component should not care what the whole screen is doing. Container queries make “this card lays out based on how much room it has” expressible directly. They were a plugin in v3 and a reason many teams skipped them; being built in changes that.

Checkpoint

Does md:flex-row apply on a phone?

No. Prefixed utilities are min-width — they apply at their breakpoint and larger. The phone gets the unprefixed flex-col. To target only small screens, style them with no prefix and override upward.

How do you hide an element only on mobile?

hidden md:block — hidden by default, shown from medium up. md:hidden would do the opposite: visible on mobile, hidden on larger screens.

When are container queries the right tool over breakpoints?

When a component must adapt to the space it is given rather than the screen — a card that appears in both a narrow sidebar and a wide column at the same viewport. Mark the parent @container and use @md: on the children.

Chapter Four · Part II

States and Transitions

Hover, focus, active, disabled — and the movement between them. The variant system that makes these one class each is the same system that does dark mode and responsive.

By the end of this chapter you will be able to
  • Style interactive states with variants
  • Chain and stack variants
  • Add transitions without over-animating
  • Handle focus visibly, for keyboard users

4.1 Variants

VariantFires on
hover:Pointer over
focus: / focus-visible:Focused / focused via keyboard
active:Being pressed
disabled:A disabled form control
group-hover:A parent marked group is hovered
peer-checked:A sibling marked peer is checked
has-[:checked]:A descendant matches — the :has() variant
dark:Dark mode (chapter 10)

Table 4.1 group-* and peer-* style one element based on another’s state — a caption that changes when the card is hovered, an error message that shows when the input is invalid — with no JavaScript.

4.2 group and peer

peer is the same idea for siblings

Mark an input peer; a following peer-invalid:block element shows only when the input is invalid. Combined with :has() variants (has-[:checked]:), a great deal of interactivity that used to need JavaScript is now pure CSS — chapter 11 builds a whole form this way.

4.3 Transitions, sparingly

UtilityAnimates
transitionThe common set — colour, opacity, transform, shadow
transition-colorsOnly colours
transition-transformOnly transforms
transition-allEverything — usually a mistake
duration-* ease-* delay-*Timing
motion-reduce:transition-noneRespect the user’s setting

Table 4.2 The last row matters: some users set “reduce motion” for a medical reason. motion-reduce: lets you turn animation off for them in one class.

transition-all is the usual over-animation bug

It animates layout properties too, so a hover that changes padding causes a reflow every frame — visibly janky and expensive. Name the properties you actually change. If you find yourself wanting transition-all, you are probably animating too much.

4.4 Focus, for keyboard users

Never remove focus without replacing it

A keyboard user who cannot see which element is focused cannot use your site. outline-none alone is one of the most common accessibility regressions on the web. If you turn the default outline off, you owe a focus-visible:ring-* in return — and this book’s stylesheet does exactly that.

Checkpoint

How does a hover: class actually work?

It generates a normal rule with the selector wrapped in :hover. The variant system is uniform: md: wraps a media query, dark: wraps a dark selector, focus: wraps :focus. One mechanism, every state.

Why group-hover: rather than hover: on a child?

Because hover: on the child fires only when the pointer is over that child. group-hover: fires when the marked container is hovered, so the whole card can respond to being hovered anywhere.

What is wrong with focus:outline-none on its own?

It removes the only indicator a keyboard user has of where they are. Pair it with focus-visible:ring-2, which shows a ring for keyboard focus and stays out of the way for mouse clicks.

Chapter Five · Part III

Reuse Without Repeating Yourself

The honest objection to utility classes is repetition. Here is what to do about it, in the right order — and the one answer that is almost always wrong.

By the end of this chapter you will be able to
  • Extract a component, not a CSS class
  • Say why @apply is the wrong first reach
  • Use loops in your templating layer
  • Reach for @apply only where it belongs

5.1 The problem, stated fairly

A styled button is a dozen utilities. Used in forty places, that is forty copies of the same class string, and changing the button means changing forty lines. This is the real cost of utility-first CSS, and pretending otherwise is dishonest.

The answer is a component, in your framework

You already have a mechanism for reuse: a component. A React <Button>, a Vue <Button>, a Blade partial, an Astro component. The class string lives once, in the component; the forty call sites use the component. This is not a Tailwind feature — it is the thing your framework is for, and it is the correct answer to repetition.

5.2 A component owns the classes

cva and tailwind-merge, when variants multiply

Once a component has size and colour and state variants, hand-concatenating strings gets error-prone. class-variance-authority (cva) turns variants into a typed API; tailwind-merge resolves conflicts when a caller overrides a class (so px-8 passed in beats the component’s px-4 instead of both appearing). They are the two libraries a real design system reaches for.

5.3 Loops, for repetition in one place

Most “repetition” is a list

A grid of forty cards is not forty copies of a class string — it is one card markup in a loop. The utilities appear once in the source. Before extracting anything, check whether the repetition is really iteration, because iteration needs no extraction at all.

5.4 @apply, and its narrow place

Why @apply is not the default answer

It recreates the exact problem utilities were meant to solve: a growing stylesheet of semantic classes, indirection between the markup and the styles, and specificity to reason about. You have written CSS again. The Tailwind team’s own guidance is to prefer a component. Reserve @apply for the genuine cases: styling third-party HTML you cannot add classes to, a few global base styles (a, body), and the odd repeated pattern that is not a component — never as a habit.

RepetitionFix
A styled element used everywhereA component
A list of similar itemsA loop
Many variants of a componentcva + tailwind-merge
HTML from a library you cannot edit@apply, or prose
Global element defaults@layer base
“It would be tidier”Nothing — leave the utilities

Table 5.1 The last row is the discipline: tidiness in the markup is not a reason to move styles into CSS, because the untidiness is the visible, greppable, deletable record of what an element looks like.

Checkpoint

What is the right first answer to a class string repeated 40 times?

A component. The class string lives once, in a <Button> or a partial, and the 40 sites use the component. Reuse is what your framework’s components are for; it is not a Tailwind-specific problem.

Why is @apply not the default way to reuse?

Because it rebuilds the growing, indirection-heavy semantic stylesheet that utilities exist to avoid. You end up writing CSS again, with specificity to manage. Use it only for HTML you cannot add classes to and for a few global base styles.

When variants multiply, what two libraries help?

cva (class-variance-authority) turns size/colour/state variants into a typed API, and tailwind-merge resolves conflicts so a caller’s override actually wins instead of both classes landing in the output.

How do you add a brand colour in v4?

How do you replace the default colour palette entirely?

--color-*: initial; in @theme clears the defaults, then define only your own colours. It keeps the autocomplete and the output limited to the palette you actually use.

Advanced Patterns and Performance

7.1 The escape hatch

7.2 Why the output stays small

The measurement, and what it means

Real numbers from this book’s lab: 200 cards, 74 KB of markup, 13 KB of CSS — because those 200 cards use only about twenty distinct utilities, and Tailwind emits each rule once. Two thousand cards would produce the same 13 KB. The CSS size is a function of how varied your design is, not how large your site is, and it plateaus early. This is the property that makes utility-first CSS scale to enormous applications.

7.3 The purge trap

Tailwind scans text, so the whole class must be in the text

The scanner looks for complete class strings in your source files. text-${color}-500 is never a complete string, so the rule is never generated and the colour silently does nothing in production — while working in development if that class happened to be generated by something else. Always write the full class name somewhere the scanner can see it; a lookup object is the standard fix. The old safelist escape hatch still exists for the rare truly-dynamic case.

Table 7.1 There is little to do: the framework integrations handle minification and cache-busting, and the output is one small, highly compressible file. The performance work in a Tailwind project is almost entirely in the images and JavaScript, not the CSS.

The build is fast enough to ignore

The Rust engine builds this book’s 200-card page in 39 milliseconds. On a real application the CSS build is never the slow part of your pipeline. If a build feels slow, it is the bundler or the framework, not Tailwind.

Checkpoint

When should an arbitrary value become a theme token?

When you write it more than once. A genuine one-off — a single pixel nudge, one brand hex used in one place — is fine in brackets. The same arbitrary value repeated is a design decision that belongs in @theme so it has a name and one source of truth.

Why does text-${color}-500 produce no styles in production?

Because Tailwind scans source text for complete class strings, and that is never a complete string, so the rule is never generated. Map to full class names in a lookup object, or safelist the class.

Two thousand cards instead of two hundred — how much bigger is the CSS?

Not at all, if they use the same utilities. Output size tracks the number of distinct utilities, and each rule is emitted once. This is why utility-first CSS scales — the stylesheet plateaus while the site keeps growing.

Custom Utilities and Plugins

When the built-in utilities and arbitrary values are not enough, you add your own. In v4 the simplest cases are one CSS rule; the complex ones are a plugin.

8.1 @utility, the common case

Why not just a plain CSS class?

A plain .content-auto {} class does not compose with variants — you cannot write hover:content-auto. @utility registers it properly, so it behaves like a built-in. That variant composability is the whole reason the directive exists.

8.2 @custom-variant

Variants are how you hook into state you own

A dropdown that sets data-state="open", a table row with aria-selected, a parent with a theme class — @custom-variant turns any of these into a prefix you can use like hover:. It is the bridge between JavaScript that toggles attributes and CSS that responds, with no per-state class juggling.

Checkpoint

Why use @utility instead of a plain CSS class?

Because a plain class does not compose with variants — no hover:, no md:. @utility registers the class into Tailwind’s system so it behaves exactly like a built-in utility, which is usually the whole point of adding one.

You toggle data-state="open" in JavaScript. How do you style it with Tailwind?

@custom-variant open (&[data-state="open"]), then use open:rotate-180 and the like. The variant turns your attribute into a prefix, bridging JS state and CSS with no manual class swapping.

When do you actually need a JavaScript plugin?

When the utilities must be computed — a whole family generated from theme values, or utilities that take an argument via matchUtilities. Static additions are simpler as @utility in CSS.

9.1 The built-ins

Table 9.1 animate-pulse on grey blocks is the standard loading skeleton, and animate-spin on an SVG is the standard spinner — two of the most common UI needs, each one class.

9.2 Your own animation

Keyframes go inside @theme now

In v3 the animation name went in the config and the keyframes went in a separate @layer. In v4 both live together in @theme: --animate-* names the utility, and the @keyframes block sits right beside it. One place, and the animation is a first-class token like a colour.

9.3 Animate transforms, not layout

The two properties that are always safe

transform and opacity. They are handled on the compositor thread, so they animate smoothly even while the main thread is busy. Everything else — width, height, top, left, margin, padding — can be animated but risks jank. If an animation stutters, check whether it is moving layout.

9.4 Reduced motion

The inverse exists too

motion-safe: applies animation only when motion is not reduced — so motion-safe:animate-fade-in is a way to add animation that is off by default for reduced-motion users. Either direction works; the point is that a significant animation must have a reduced-motion path.

Checkpoint

What is the standard loading skeleton in Tailwind?

Grey blocks with animate-pulse — bg-slate-200 animate-pulse on divs sized like the content that will replace them. The spinner counterpart is animate-spin on a bordered circle with one coloured segment.

Where do custom keyframes go in v4?

Inside @theme, right next to the --animate-* token that names the animation. v3 split the name and the keyframes across the config and a layer; v4 keeps them together as one token.

An animation stutters. What is the most likely cause?

It is animating a layout property — width, height, top, margin — which forces a reflow every frame. Rewrite it in terms of transform and opacity, which the compositor handles smoothly.

Multi-Theme and Dark Mode

One design, several looks — light, dark, high-contrast, per-brand. The v4 answer is CSS variables, which you already have, because every theme token is one.

By the end of this chapter you will be able to

  • Switch themes at runtime by swapping variables
  • Say why variables beat duplicated utilities for theming

10.1 Dark mode

10.2 Runtime theming with variables

The scalable approach is not dark: on everything

Prefixing every colour with dark: works for two themes and collapses for three. The better pattern: define semantic tokens — --color-surface, --color-text — and redefine those variables per theme. Utilities reference the semantic token, so switching theme is redefining a handful of variables, not touching any markup.

This is why v4’s variables matter

Because a theme token is a real CSS variable (§6.2), a runtime theme switch is a class on <html> that redefines a dozen variables — and every utility across the entire app updates instantly, with no re-render and no duplicated dark: classes. Three themes cost the same as two. This is the pattern real design systems use.

10.3 The flash

The flash of the wrong theme is a real bug

If you set the theme class after the page renders — in a React effect, say — the user sees a flash of light before dark applies. The fix is a tiny synchronous script in <head>, before the stylesheet, that sets the class from localStorage immediately. Every framework’s dark-mode guide includes some version of this; it is not optional, and it is the one piece that cannot be a normal component.

Checkpoint

Why prefer semantic tokens over dark: on every colour?

Because dark: doubles your colour classes and does not extend to a third theme. Semantic tokens (--color-surface) are redefined per theme in one place; the markup references the token and never mentions a specific theme, so N themes cost the same as one.

How does a runtime theme switch update the whole page with no re-render?

By redefining CSS variables. Every utility resolves to var(--color-…), so changing those variables on <html> repaints everything that uses them instantly — CSS does the work, not JavaScript.

What causes a flash of the wrong theme, and what fixes it?

Setting the theme class after render. The fix is a synchronous inline script in <head>, before the CSS, that reads localStorage and sets the class immediately — so the correct theme is applied on the very first paint.

Chapter Eleven · Part VI

Forms

The controls users actually interact with, styled and — more importantly — accessible. Native form elements resist styling until you reset them, and validation state can be pure CSS.

By the end of this chapter you will be able to

  • Style inputs, selects and checkboxes
  • Show validation state without JavaScript

11.1 The forms plugin

Native controls are nearly unstylable without it

A bare <select> or <input type="checkbox"> ignores most CSS — the browser draws it. The forms plugin applies a reset that makes them behave like normal elements you can style with utilities. Without it, you fight the browser; with it, an input is just a box you add rounded-lg border px-3 py-2 to.

11.2 A styled field

The label must be associated

A <label> next to an input is not enough — it must be linked, either by wrapping the input or with for/id. A screen reader announces the label when the input is focused only if they are associated. Styling is the easy half of a form; the association and the error announcement are the half that determines whether the form is usable by everyone.

11.3 Validation state, in pure CSS

Use native validation as the first layer

required, type="email", min, pattern and maxlength give you client-side validation the browser enforces, with :valid/:invalid you can style. It is not a replacement for server validation (Volume 7 §6.1) — the server must never trust the client — but it is instant feedback for free, and peer-invalid: turns it into visible messages with no script.

Checkpoint

Why do you need the forms plugin?

Because native form controls — select, checkbox, radio — are drawn by the browser and ignore most CSS. The plugin resets them so utilities apply, turning an input into an ordinary stylable box.

How do you show an error message with no JavaScript?

Mark the input peer and the message hidden peer-invalid:block. The browser’s native :invalid state, surfaced through the peer- variant, shows the message when the field is invalid.

A label sits visually next to an input but a screen reader does not read it. Why?

They are not associated. Wrap the input in the label, or link them with for/id. Visual proximity is not association; only the markup relationship reaches assistive technology.

12.2 Conditional classes

clsx for conditions, tailwind-merge for conflicts

clsx (or classnames) turns conditional classes into readable data instead of nested template strings. But it does not resolve conflicts: clsx("p-4", "p-8") emits both, and which wins depends on source order in the stylesheet, not the order you wrote them. tailwind-merge knows that p-4 and p-8 are the same property and keeps the last — essential when a component accepts a className override from its caller.

12.3 The two together

cn() is the helper every Tailwind React project has

The one-liner combining clsx and tailwind-merge — usually called cn — is in almost every serious Tailwind codebase, and it is what shadcn/ui and similar libraries build on. It makes components overridable: a caller’s className reliably beats the component’s defaults, which is exactly what you want and what naive concatenation gets wrong.

Checkpoint

Does Tailwind behave differently in Next.js versus Vite?

No. The same engine runs; the integration only decides when the build fires. Everything about what a class generates is identical. Only the setup line differs.

What does clsx do that tailwind-merge does not, and vice versa?

clsx builds a class string from conditions readably but keeps conflicting classes. tailwind-merge resolves conflicts — p-4 and p-8 to just p-8 — but does not handle conditions. You use both, usually wrapped as cn().

Why does a component need tailwind-merge to accept a className prop?

So a caller’s override wins. Without it, cn("p-6", "p-8") emits both and the winner depends on stylesheet source order, not intent — the override might silently do nothing. tailwind-merge makes the last value for a property win predictably.

tabular-nums on any column of figures

Proportional digits make numbers in a column jitter left and right because 1 is narrower than 8. tabular-nums forces equal-width digits so they line up — essential for prices, counts and anything you scan vertically. It is one of the highest-value one-class fixes in the whole framework and almost nobody uses it.

13.3 A chart with no library

When to stop and use a real library

Pure-CSS charts are right for the simple, static, non-interactive case: a sparkline, a progress bar, a small bar summary. The moment you need axes, tooltips, legends, animation on data change, or accessibility for the data points, use a real charting library (and Volume 5’s note on server-rendering it). Building those by hand in Tailwind is a trap — you will reimplement a charting library badly. Know where the line is.

Checkpoint

Why put tabular-nums on a price column?

So the digits are equal width and the numbers align vertically. Proportional digits make a column of figures jitter, because 1 is narrower than 0. It is the single most effective class for any scannable column of numbers.

How do you draw a bar chart with no library?

flex items-end on a fixed-height container, with each bar a flex child given a percentage height. It handles static bars and sparklines. It does not handle axes, tooltips or interaction — that is where a real library starts.

When should a Tailwind chart become a charting library?

The moment you need axes, tooltips, legends, animated data updates, or accessible data points. Below that — a static sparkline or progress bar — pure CSS is simpler. Above it, hand-rolling is reimplementing a library badly.

Chapter Fourteen · Part VII

Dynamic and Runtime Styling

The values you cannot know at build time — a progress percentage, a user-chosen accent, a computed position. Tailwind is a build-time tool; the bridge to runtime values is the CSS variable.

By the end of this chapter you will be able to
  • Pass a runtime value through a CSS variable
  • Say why you cannot build a class from a runtime value
  • Combine Tailwind with inline styles correctly
  • Choose between a variable and an arbitrary value

14.1 The build-time boundary

Tailwind cannot generate a class it never saw

A class is generated only if its full string appears in your source at build time (§7.3). A progress bar at 67% where 67 comes from data can never be w-[67%] — the number does not exist when Tailwind runs. This is not a limitation to work around; it is the nature of a build-time tool, and the answer is to hand the runtime value to CSS through a variable.

14.2 Variables carry the dynamic part

Where each thing belongs

Classes for everything known at build time — layout, spacing, the palette, states. Variables for values that change at runtime — a theme accent, a computed dimension, a position from a drag. Inline style for the truly per-element one-off value. Mixing them this way keeps 95% of the styling in greppable, purgeable classes and confines the dynamic 5% to where it genuinely must be dynamic.

Only TailwindVariables cover almost every dynamic case (§14.2)

Table 14.1 The frequent question — “Tailwind or styled-components?” — is usually a false choice. Tailwind handles the 95% that is static; a runtime CSS-in-JS library, or just inline variables, handles the genuinely dynamic remainder. They are not competitors for the same job.

Reach for CSS-in-JS only when variables are not enough

A CSS variable handles a dynamic colour, size, position or count. You need a runtime CSS-in-JS library only when the dynamic part is structural — generating whole rules from data, which is rare in application code. Before adding a styling library to a Tailwind project, check whether a variable does it; usually it does.

Checkpoint

Why can a progress bar not be w-[${percent}%]?

Because the value is not in the source at build time, so Tailwind never generates the class. Put the runtime value in an inline style (width) or a CSS variable the utility reads; keep the rest of the styling in static classes.

What does the bg-(--accent) syntax do?

Makes a utility read a CSS variable set at runtime, so a user-chosen accent flows through every element that uses it. The utility is static (and generatable); only the value is dynamic. It is v4’s clean bridge between build-time classes and runtime values.

Is it Tailwind or styled-components?

Usually both, for different jobs. Tailwind handles the large static majority; a variable or a runtime CSS-in-JS library handles the genuinely dynamic minority. They are not competing for the same styling.

Production Workflow

The tooling around Tailwind that a team needs: the editor experience, the linters that catch mistakes, and the build that ships.

By the end of this chapter you will be able to
  • Set up the IntelliSense and sorting tools
  • Catch class mistakes with a linter
  • Sort classes consistently

15.1 The editor

ToolDoes
Tailwind CSS IntelliSense (VS Code)Autocomplete, hover previews, colour swatches
Prettier + prettier-plugin-tailwindcssSorts classes into a canonical order on save
eslint-plugin-better-tailwindcssFlags unknown classes, conflicts, arbitrary-value overuse
The v4 language serverUnderstands @theme, @utility, @custom-variant

Table 15.1 IntelliSense is the one that changes the experience most — a hover shows exactly what a class generates (which is what this whole book has been doing by hand), and autocomplete makes the huge utility vocabulary navigable.

The Prettier plugin ends the class-order argument

Left alone, class strings drift into random order and diffs become noisy. prettier-plugin-tailwindcss sorts them into the recommended order — layout, then box model, then typography, then colour, then state — automatically on save. It is not cosmetic: consistent order makes classes scannable and makes git blame meaningful, and it removes an entire category of review comment.

15.2 Catching mistakes

MistakeCaught by
A typo’d class (flexx)IntelliSense (no completion), the linter
Two conflicting classes (p-4 p-8)The linter, tailwind-merge at runtime
An arbitrary value that should be a tokenThe linter, warns on repeats
A dynamic class that will be purgedCode review, and §7.3 discipline
A class that no longer exists after upgradeThe upgrade tool, then the linter

Table 15.2 A typo in a class name fails silently — the style just does not apply. The linter and IntelliSense turn that silent failure into an editor warning, which is the difference between catching it now and catching it in QA.

The v3 → v4 upgrade tool

npx @tailwindcss/upgrade migrates a v3 project: it converts the config to @theme, updates renamed utilities, rewrites the directives, and flags what it cannot do automatically. Run it on a branch, read the diff, and test — it does most of the mechanical work of the migration, which is otherwise the tedious part.

15.3 The build

ConcernReality
Build speedMilliseconds — never the bottleneck (§7.4)
Output sizeTracks distinct utilities; small and plateaus
PurgingAutomatic; no content config in v4
AutoprefixingBuilt in via Lightning CSS — no separate step
CacheOne rarely-changing file; hash and cache hard

Table 15.3 The production story is almost boringly short: the framework integration builds and minifies, the output is tiny, and there is nothing to tune. The effort a Tailwind project spends on CSS in production is close to zero — which was the point.

What is left to optimise is not the CSS

Once Tailwind is wired in, your performance budget goes on images, fonts and JavaScript — never the stylesheet. If someone proposes a project to “optimise the Tailwind CSS”, the honest answer is that there is almost nothing there to optimise, and the time is better spent on the megabytes of JavaScript that every real app actually ships.

Checkpoint

Why is the Prettier Tailwind plugin more than cosmetic?

Consistent class order makes strings scannable and keeps diffs and git blame meaningful, and it removes class-ordering as a category of review comment. Random order is noise that the plugin eliminates on save.

A style is not applying and there is no error. What is the first check?

A typo in the class name — it fails silently because the class simply does not exist, so no rule is generated. IntelliSense (no autocomplete) and the linter catch this; the dynamic-class purge trap (§7.3) is the other common cause.

What is left to performance-optimise in a Tailwind project?

Not the CSS — it is small, plateaus, and builds in milliseconds. The budget belongs to images, fonts and JavaScript. “Optimise the Tailwind” is almost always misdirected effort.
