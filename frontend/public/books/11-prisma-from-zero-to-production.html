About this book

An ORM is a promise: write your database code in your language, with your types, and never hand-concatenate SQL again. Prisma keeps that promise better than any other tool in the TypeScript world — and Prisma 7 rebuilt its foundations to do it on serverless and the edge as well as on a server.

So this book does the one thing most ORM tutorials refuse to: for every query, it shows you the SQL Prisma actually generated, captured from the query log, right beside the code that produced it and the real result it returned. Nothing here is asserted from memory. The connection pooling, the EXPLAIN plans, the transactions, the passing test suite — all of it ran against a live PostgreSQL 18 database while the book was being written, and the output on the page is the output that came back.

It is written entirely against Prisma 7, which changed four things every older tutorial gets wrong. The Rust query engine is gone; the client is pure TypeScript and talks to your database through a driver adapter you configure. There is no url in the datasource — connection details live in prisma.config.ts. The client generates into your own source tree. And the whole thing is ESM-first, which is what makes it run on the edge. Chapter 0 lays these out; the rest of the book assumes them throughout.

Who should read this

Developers who know some SQL — ideally from Volume 6, PostgreSQL from Zero to Production, which this book leans on whenever it explains why a query is shaped the way it is — and want to build a typed, safe, production data layer in TypeScript. You need no prior Prisma.

How this book is organised

Chapter 0 is the mental model and the four v7 changes. Then the chapters map onto the sixteen modules of the Prisma ORM track in Code Lab, each ending with that module’s ten graded exercises. Read 0 through 6 in order; after that, dip in as the work demands.

Four things here that most Prisma material has not caught up with

1. No Rust engine — a pure-TypeScript client over a driver adapter you own (§0.3, Ch 9). 2. No url in the datasource — connection lives in prisma.config.ts (§0.3). 3. The client generates into your own src/ tree, not node_modules (§0.3). 4. ESM-first, which is what puts Prisma on serverless and the edge at all (Ch 9).

Chapter Zero · Orientation

What Prisma Is, and What v7 Changed

A type-safe database toolkit: a schema you write, a client it generates, and migrations it manages. Version 7 changed how the client connects and how it is generated — enough that most tutorials you find will not run.

By the end of this chapter you will be able to
  • Say what the three parts of Prisma are
  • Explain the driver-adapter model that is now the default
  • Name the four v7 changes that break older guides
  • Set up a project and run a real query

0.1 Three parts

PartIsYou
The schemaschema.prisma — your models, in one fileWrite it
The clientGenerated TypeScript, typed to your schemaImport and use it
MigrateTurns schema changes into SQL migrationsRun it
The configprisma.config.ts — connection and settingsWrite it once (v7)

Table 0.1 The schema is the single source of truth: the client’s types and the database’s structure are both derived from it, so they cannot drift apart. That is the whole value proposition — the types you code against and the tables you query are guaranteed to match.

0.2 The query, the SQL, the result

This is the discipline of the whole book

An ORM that hides the SQL is an ORM you cannot debug. Every query here is shown with the SQL Prisma sent to Postgres, captured from the query log. When a query is slow (chapter 13), that SQL and a Volume 6 EXPLAIN are how you find out why.

0.3 Four things v7 changed

1 · The connection URL left the schema

In v6 the datasource had url = env("DATABASE_URL"). In v7 that is an error — the connection lives in prisma.config.ts, and the client connects through a driver adapter you pass to its constructor. Every older tutorial’s schema will fail to validate with a message telling you to move the URL.

2 · The Rust query engine is gone

v6 shipped a Rust binary that every query went through — a large dependency and a source of deployment friction (the right binary for the platform, the serverless cold-start cost). v7 removed it: the client talks to your database through a driver adapter — @prisma/adapter-pg for node-postgres, adapters for Neon, PlanetScale, D1 and others — which is plain JavaScript. Smaller, faster to start, and it works anywhere the driver works (chapter 11).

3 · The generator is prisma-client, and it emits TypeScript

v6’s prisma-client-js generated into node_modules/.prisma. v7’s prisma-client generates real TypeScript into a folder you choose and commit-ignore — which is faster, works with every bundler, and means you can read the generated types. You import from ./src/generated/prisma/client.ts, not from @prisma/client.

4 · It is ESM-first

The generated client is ES modules, and the config is .ts. This is the modern default and it is the right one, but it means require("@prisma/client") from a v6 CommonJS codebase needs the migration (§7).

0.4 A project, end to end

Checkpoint

What are the three parts of Prisma?

The schema (your models, one file), the generated client (TypeScript typed to the schema), and Migrate (schema changes → SQL migrations). The schema is the single source of truth from which both the client types and the database structure derive.

Where does the connection URL go in v7?

Not in the schema — that is now an error. It lives in prisma.config.ts for migrations, and the client connects at runtime through a driver adapter passed to its constructor. The Rust query engine that used to sit between the client and the database is gone.

Why does a v6 tutorial’s schema fail to validate?

Because it has url = env("DATABASE_URL") in the datasource, which v7 rejects. Move the URL to the config, add a driver adapter, and switch the generator to prisma-client — the four v7 changes in §0.3.

1.2 Read

findUnique versus findFirst

findUnique requires a unique field and is the one to use for “get by id” — it is optimised and can be batched. findFirst accepts any filter and ordering. Using findFirst({ where: { id } }) where findUnique would do works but tells the reader (and Prisma) less about your intent.

1.3 Update and upsert

Atomic update operators avoid the lost-update race

increment, decrement, multiply, set and push (for arrays) let the database compute the new value from the old one in a single statement. Reading a value into JavaScript, changing it, and writing it back is the classic lost-update bug; these operators are how you avoid it in Prisma.

1.4 Delete, and the batch forms

The batch forms are a different tool

create returns the record and can nest relations; createMany returns a count, cannot nest, and is far faster for bulk inserts because it is one statement. Reach for the batch forms when you have many rows and do not need each one back — a data import, a bulk cleanup. For one record you want to use, the singular forms.

Checkpoint

Why is { increment: 1 } better than reading and writing back?

Because it is atomic: it becomes col = col + 1 in one SQL statement, so two concurrent increments both take effect. Reading into JS, adding, and writing back loses one of them under concurrency — the classic lost update.

What does createMany return, and why does it matter?

A { count }, not the created rows — it is a single bulk INSERT. If you need the rows back, use createManyAndReturn (Postgres) or create per row. The trade is speed for the return value.

When would you use findFirst over findUnique?

When filtering on non-unique fields or needing ordering — findFirst({ where: { tags: { has: "scifi" } }, orderBy: … }). For “get by id”, findUnique is clearer and can be batched.

2.3 Pagination

Cursor pagination also fixes the shifting-window bug

With OFFSET, a row inserted while the user reads page 1 shifts everything and page 2 repeats a row. Cursor pagination anchors on a value, not a count, so it never skips or duplicates. For an infinite scroll or an API feed, it is the correct choice; offset is fine only for small, shallow result sets.

Checkpoint

How do you filter books by a property of their author?

Nest the relation in where: author: { country: { not: "US" } }. Prisma generates the join. To filter a parent by its children, use the quantifiers some, every, none — books: { some: { … } }.

Why does offset pagination slow down at depth?

Because OFFSET n makes the database read and discard the first n rows before returning any. Page 5,000 reads 10,000 rows to return 2. Cursor pagination seeks straight to the anchor via the index and stays constant.

What bug does cursor pagination fix beyond speed?

The shifting window. With offset, a row inserted between page loads shifts everything and page 2 repeats a row you already saw. A cursor anchors on a value, so it never skips or duplicates — which matters for feeds and infinite scroll.

3.1 Reading relations

includeselect
Adds relationsYesYes (nested)
Keeps scalar fieldsAll of themOnly the ones you list

Table 3.1 include and select cannot appear at the same level — pick one. Use select when you want a narrow shape (an API response), include when you want the whole record plus relations.

3.2 Nested writes

connect versus create

create makes a new related record; connect links an existing one by a unique field; connectOrCreate does whichever applies. Assigning a book to an existing author is connect: { id }, not a new author. Getting these confused is how you end up with duplicate parent rows.

3.3 The N+1 problem, solved

Prisma batches relation loads for you

Load 100 authors and include their books, and a naive ORM runs 1 query for the authors and 100 for the books — the N+1 problem (Volume 7 §5.4). Prisma runs two queries total: one for the authors, one WHERE author_id IN (…) for all their books, then stitches them in memory. You get the nested shape without the N+1, automatically.

The exception: a relation inside a loop

Prisma batches a relation loaded via include/select. It cannot batch a query you write yourself inside a for loop — for (const a of authors) await prisma.book.findMany({ where: { authorId: a.id } }) is N+1 again, by your hand. Load relations declaratively and the batching is free; load them imperatively and you own the problem.

Checkpoint

When do you use select versus include?

select for an exact set of fields (a narrow API shape); include for the whole record plus its relations. They cannot be mixed at the same level — select can nest a relation with its own select, which is how you shape deeply.

How many queries does include run for 100 authors?

Two — one for the authors, one WHERE author_id IN (…) for all their books, stitched in memory. Prisma’s relation loader avoids N+1 automatically, so you do not need a DataLoader as you would with a hand-rolled resolver.

How do you reintroduce N+1 in Prisma?

By loading a relation imperatively — a prisma.book.findMany inside a for loop over authors. Prisma only batches relations loaded declaratively via include/select. Load them that way and the batching is free.

Types Without a Build Step

The reason Prisma exists. Your schema becomes TypeScript, and the compiler knows the exact shape of every query result before you run it. This chapter shows how to use that, not just enjoy it.

By the end of this chapter you will be able to

4.1 The types come from the schema

One source of truth

In Volume 7 you wrote SQL as strings and cast the rows to a hand-written interface — two sources of truth that drift the moment someone alters a column. Prisma generates the types from the schema, into src/generated/prisma. Change a field, run prisma generate, and every query that touched it stops compiling until you fix it. The schema is the single source; the types follow.

4.2 select narrows the type

4.3 Naming a query result: GetPayload

Types for the shapes you build

What is the type of “an author with their books included”? You did not write that interface — but Prisma can compute it. Prisma.AuthorGetPayload<{ include: { books: true } }> is exactly that type, derived from the same args you pass to the query. Define your query args const, feed them to GetPayload, and a function can accept the result with full safety.

4.4 Input types for your own functions

Checkpoint

Where do the TypeScript types come from?

Generated from the schema into src/generated/prisma by prisma generate. The schema is the single source of truth; the types follow it, so a column change breaks every query that used the old shape until you fix it — the opposite of hand-written interfaces that drift silently.

How does select affect the return type?

It narrows it to exactly the selected fields. select: { title: true } gives a result typed { title: string } — accessing any other field is a compile error, not a runtime undefined. The type tracks the query shape automatically.

The exact result type of a query with those args — e.g. an author with books included. Paired with a satisfies-typed args object, one definition drives both the query and the type of its result, so they can never disagree.

5.2 Group by

where versus having

where filters rows before grouping; having filters groups after aggregating. “Books over $10” is where; “authors whose average book is over $10” is having. Prisma keeps both, in the right order, and checks that the aggregate you filter on is one you computed.

5.3 Raw SQL, safely

Never build raw SQL by concatenation

$queryRaw`… ${x}` (tagged template) parameterises x. $queryRawUnsafe("… " + x) interpolates it into the string — the injection hole from Volume 7 §9, reopened. Use the tagged form for values; reserve Unsafe for the rare case of a dynamic identifier you have allow-listed yourself, never for user input.

Checkpoint

Why aggregate on the database instead of in Node?

Because the work happens where the data lives — one SELECT count(*), avg(…) returns a handful of numbers instead of shipping every row to Node to reduce in JavaScript. It is dramatically less data over the wire and lets the database use indexes and parallelism you cannot match in application code.

When do you need having instead of where?

When the filter is on an aggregate. where filters rows before grouping and cannot see a group average; having filters groups after aggregating. “Authors whose average book price exceeds $10” is a having on _avg.

Why the tagged template over $queryRawUnsafe?

The tagged template turns every ${…} into a bound parameter, so values can never be interpreted as SQL — injection-safe by construction. Unsafe concatenates into the query string; use it only for an identifier you have allow-listed yourself, never for user-supplied data.

Chapter Six · Part III

Migrations and the Schema Workflow

How a change to schema.prisma becomes a versioned SQL file, and how that file reaches production unchanged. The two commands that matter — migrate dev and migrate deploy — and why you must never confuse them.

By the end of this chapter you will be able to
  • Turn a schema edit into a migration with migrate dev
  • Read the SQL Prisma generates and keep it under version control
  • Deploy migrations safely with migrate deploy
  • Recognise a destructive change before it runs

6.1 From schema to SQL

You edit the schema; Prisma writes the SQL

You never write CREATE TABLE by hand. You edit schema.prisma to describe the shape you want, run migrate dev, and Prisma diffs the schema against the database, generates a timestamped SQL file, applies it, and regenerates the client. The SQL file is committed to git — it is the migration, and every environment replays the same file.

6.2 Evolving the schema

Each change is a new migration, never an edit of an old one

To add columns you edit the schema and run migrate dev again. Prisma diffs against the current database and writes only the delta — an ALTER TABLE, not a fresh CREATE. Applied migrations are immutable history: you add new ones, you never rewrite a migration that has already run somewhere.

6.3 Review before you apply: --create-only

Generate the SQL, read it, then apply it

For anything non-trivial — a data backfill, an index on a huge table, a rename — generate the migration without applying it (--create-only), read and edit the SQL, then apply it in a second step. This is how you take control of what Prisma generated instead of trusting it blindly.

6.4 Deploying: migrate dev is not migrate deploy

The one distinction you must never get wrong

migrate devmigrate deploy
ForYour laptopCI / staging / production
Creates migrationsYesNever
Applies pending onesYesYes
Uses a shadow DBYesNo
Can reset / drop dataYes, when it mustNo, ever
InteractiveYesNo — safe for automation

Table 6.1 migrate dev is a development tool that may reset the database to reconcile drift. Running it in production risks your data. Deployments run only migrate deploy: it applies committed migrations in order and does nothing else.

6.5 When a change is destructive

Prisma warns before it can lose data

Add a required column with no default, add a @unique to a column that may hold duplicates, or drop a column, and migrate dev stops and warns rather than silently proceeding. In a non-interactive shell it refuses outright — which is exactly why the command is banned from production.

db push is for prototyping, not history

prisma db push syncs the schema straight to the database with no migration file — fast for throwaway spikes, but it leaves no history to deploy and can drop data without a trace. Use it to sketch; use migrate dev the moment the schema matters.

Checkpoint

What does migrate dev produce, and what do you commit?

A timestamped folder under prisma/migrations containing one migration.sql — the DDL Prisma diffed from your schema change. You commit that folder to git; it is the migration, replayed identically in every environment by migrate deploy.

Why must production use migrate deploy, never migrate dev?

migrate dev may reset or drop data to reconcile drift and is interactive; migrate deploy only applies already-committed migrations in order, non-interactively, and never resets. Running migrate dev against production risks the data it was trying to protect.

How do you add a required unique column to a populated table?

In three steps: add it nullable, run a migration to backfill and de-duplicate the data, then a final migration adding NOT NULL and @unique. Doing it in one shot triggers Prisma’s destructive-change warning because existing rows would violate the new constraint.

All-or-nothing operations. The sequential array form for independent writes, the interactive form when a later write depends on an earlier read, and the bulk verbs that turn a thousand inserts into one round trip.

By the end of this chapter you will be able to

  • Use an interactive transaction when writes depend on reads
  • Choose an isolation level and know what it prevents

7.1 The sequential array form

7.2 The interactive form

When a write depends on a read

The array form cannot express “read the stock, and only if it is positive, decrement it” — the decision happens in JavaScript, between two queries that must share one transaction. The interactive form gives you a transaction client tx; every query on tx is inside the transaction, and throwing rolls the whole thing back.

Do not mix prisma and tx

Inside the callback, use only tx. A query on the outer prisma client runs on a different connection, outside the transaction — it will not see the uncommitted changes and will not roll back with them. Every query that must be atomic goes through tx.

7.3 Isolation levels

LevelPreventsCost
ReadCommitted (default)Dirty readsCheapest
RepeatableRead+ non-repeatable readsModerate
Serializable+ phantoms; full isolationMay fail & need retry

Table 7.1 Higher isolation prevents more anomalies but risks more conflicts. Reach for Serializable around invariants that must hold under concurrency (no double-spend, no oversold stock), and wrap it in a retry loop.

7.4 Batch writes

createManyAndReturn when you need the rows

If you need the inserted rows back — their generated ids, say — use createManyAndReturn, which does one INSERT … RETURNING. It costs slightly more than createMany (it ships the rows back) but far less than inserting one at a time. updateMany and deleteMany round out the set for bulk edits and removals.

Checkpoint

When do you use the array form versus the interactive form?

Array form for independent writes that do not need each other’s results — Prisma runs them atomically in one transaction. Interactive form when a write depends on a read (check stock, then decrement), because that decision happens in JavaScript between two queries that must share one transaction via tx.

Why must you use only tx inside an interactive transaction?

Because the outer prisma client runs on a different connection, outside the transaction. A query on prisma would not see the uncommitted changes and would not roll back with them. Keep transactions short, too — they hold a connection and locks for their whole duration.

What does createMany return, and why?

A count, not the rows — it runs a single multi-row INSERT with no RETURNING, so nothing is shipped back. When you need the rows (e.g. generated ids), use createManyAndReturn, which does INSERT … RETURNING at a small extra cost.

You declare the index; the migration creates it

8.3 Profiling from the client

You do not need psql to read a plan

You can run EXPLAIN through Prisma itself with $queryRawUnsafe — useful for profiling a query in a script or a test. (It is Unsafe only because EXPLAIN is a fixed string with no user input; never interpolate input here.)

8.4 Fetch less

The fastest query is the one that moves the least data

Two habits cut most needless load. First, select only the columns you use — a list view that needs title should not drag tags and every other column across the wire. Second, turn on the query log in development so you can see what Prisma sends: the N+1 in a loop, the accidental full-table read, the SELECT * you meant to narrow.

One PrismaClient per process, not per request

Why it matters

Each PrismaClient owns a connection pool (via the driver adapter). Create one per request and you open pools faster than you close them, and the database hits too many clients under load — the exhaustion failure from Volume 7 §10. Instantiate the client once at module scope and import that single instance; connection reuse is then automatic.

Checkpoint

Where do indexes live, and how are they created?

In schema.prisma — @unique, @@index, @@unique — so they are versioned and travel through migrations. Running migrate dev emits the CREATE INDEX. An index is never an out-of-band change; it is part of the schema like any column.

What in an EXPLAIN plan tells you an index is missing?

A Seq Scan with a large Rows Removed by Filter — PostgreSQL read the whole table to return a handful of rows. After the right index the same query becomes an Index Scan that visits only the matching rows; in the chapter’s 50k-row table that was ~1.3 ms down to ~0.02 ms.

Why one PrismaClient per process?

Each client owns a connection pool. One per request opens pools faster than they close and exhausts the database’s connection limit under load. Instantiate once at module scope, import that instance everywhere, and connection reuse is automatic.

Chapter Nine · Part IV

Pooling, Serverless, and the Edge

Prisma 7 talks to PostgreSQL through a driver adapter — the same pg pool you met in Volume 7, now driving the client. That one architectural change is what makes Prisma run on serverless functions and edge runtimes, and it puts connection pooling back in your hands.

By the end of this chapter you will be able to
  • Configure the pool on the driver adapter
  • Explain why serverless multiplies your connections
  • Put a pooler in front of PostgreSQL and set the URL correctly
  • Understand what the edge runtime allows and forbids

9.1 The pool is the adapter

No hidden engine — your pool, configured by you

Prisma 6 pooled connections inside a Rust engine you could not see. Prisma 7 removed that engine: the client speaks to the database through @prisma/adapter-pg, which wraps a real node-postgres pool — the one from Volume 7 §10. The upside is control. Pool size, idle timeout, connection timeout are the adapter’s options, and they behave exactly as they did when you used pg directly.

Size the pool to the database, not the app

max is the ceiling on connections this process opens. PostgreSQL has a global max_connections (often ~100). If you run 8 app instances each with max: 20, you have asked for 160 connections against a 100-connection server — and the ninth query blocks or errors. The pool sizes must sum to less than the server allows.

9.2 Why serverless is different

Every concurrent invocation is its own process

A traditional server is one long-lived process with one pool. A serverless function is spun up per request: 200 concurrent requests can mean 200 isolated processes, each opening its own pool. Even max: 1 each is 200 connections — instant exhaustion. The fix is not a bigger database; it is a pooler that sits between your functions and PostgreSQL.

Long-lived serverServerless function
Process lifetimeHoursMilliseconds to minutes
Pools per appOneOne per concurrent invocation
Right client pool sizeModerate (10–20)Tiny (1–5)
Needs an external poolerOptionalEffectively required

Table 9.1 On serverless, keep the client pool small and put a real pooler in front. The pooler holds a modest set of PostgreSQL connections and multiplexes thousands of short-lived function connections onto them.

9.3 Putting a pooler in front

PgBouncer, or a managed equivalent

A pooler such as PgBouncer (or the pooled endpoint of Supabase, Neon, RDS Proxy) accepts many client connections and maps them onto few database connections. Your app connects to the pooler’s port instead of PostgreSQL’s. In transaction-pooling mode it hands a database connection to a client only for the duration of a transaction, so a handful of real connections serve a flood of functions.

Transaction-mode poolers and prepared statements

In transaction pooling a connection is not stable across statements, so server-side prepared statements break. The ?pgbouncer=true flag (and the adapter’s defaults) tell the stack to stop relying on them. This is the one serverless gotcha that bites everyone once; set the flag and move on.

9.4 The edge

Driver adapters are what make the edge possible

Edge runtimes (Vercel Edge, Cloudflare Workers) are not Node — no TCP sockets, no native modules, a tiny API surface. Prisma 6’s Rust engine could not run there at all. Prisma 7’s pure-TypeScript client can, provided the driver adapter can too: pair it with an HTTP-based driver such as @prisma/adapter-neon or @prisma/adapter-d1, which reach the database over HTTP instead of a raw socket.

RuntimeAdapter to useTransport
Node server@prisma/adapter-pgTCP socket
Serverless (Node)@prisma/adapter-pg + poolerTCP via pooler
Edgeadapter-neon / adapter-d1HTTP

Table 9.2 The client code you write is identical across all three — same queries, same types. Only the adapter changes with the runtime, because only the adapter knows how to reach the database from where you are.

Same queries, three homes

This is the reward for the v7 architecture: one Prisma client, one schema, one set of typed queries, deployable to a fat Node server, a serverless function, or an edge worker by swapping the adapter. The database code stops caring where it runs.

Checkpoint

Where is the connection pool in Prisma 7, and who configures it?

On the driver adapter — @prisma/adapter-pg wraps a real node-postgres pool, and you pass max, idleTimeoutMillis, connectionTimeoutMillis to it. Prisma 6 hid pooling inside a Rust engine; v7 removed the engine and handed pooling back to you.

Why does serverless exhaust connections, and what fixes it?

Each concurrent invocation is its own process with its own pool, so 200 requests can open 200+ connections and overrun the database’s limit. The fix is an external pooler (PgBouncer or a managed equivalent) that multiplexes many short-lived function connections onto a few database ones, plus a tiny per-client pool.

What makes an edge deployment possible, and what changes in your code?

The pure-TypeScript v7 client plus an HTTP-based driver adapter (adapter-neon, adapter-d1) that reaches the database without a raw socket. Your queries, schema, and types are identical across Node, serverless, and edge — only the adapter changes with the runtime.

Chapter Eleven · Part V

Security and Data Validation

Prisma closes the injection hole for you — but it cannot stop you from writing the wrong row, leaking a column, or trusting a request body. This chapter covers the security work that stays yours: validation at the boundary, explicit field selection, and least privilege.

By the end of this chapter you will be able to
  • Trust Prisma’s parameterisation — and prove it
  • Stop mass-assignment by never spreading request bodies
  • Validate input at the boundary with a schema
  • Avoid leaking columns and over-granting database rights

11.1 Injection is closed by default

The only way back in is $queryRawUnsafe

Prisma’s safety ends exactly where you reach for string concatenation. $queryRawUnsafe("… " + input) reopens the hole; the tagged $queryRaw`… ${input}` does not (Chapter 5). If you never concatenate input into SQL, injection is simply not one of your problems.

11.2 Mass assignment: never spread a request body

The vulnerability is convenience

data: req.body is the trap. If your User has a role or isAdmin column, a caller who adds "role": "admin" to the JSON just promoted themselves — Prisma faithfully wrote what you passed. Prisma checks types, not intent: it will happily set any field the schema allows.

Allow-list, never block-list

Pick the fields you do want, one by one. Do not start from req.body and try to delete the dangerous keys — you will forget one, or a new column will be added later and silently become assignable. The safe direction is naming what is allowed.

11.3 Validate at the boundary

Prisma types are not input validation

TypeScript checks types at compile time; at runtime, req.body is any. Prisma will reject a wrong type, but not a 10,000-character name, a negative price, or a malformed email — those are business rules. Validate untrusted input with a schema (Zod, Valibot) before it reaches Prisma, and hand Prisma only data you have already vouched for.

Two layers, two jobs

The schema guards shape and rules at the edge; the database guards invariants with constraints (NOT NULL, @unique, checks) as the last line. Validate at the boundary and constrain in the schema — belt and braces, because the boundary can be bypassed but the database constraint cannot.

11.4 Do not leak columns

11.5 Least privilege at the database

The app’s database user is a control, too

Defence in depth does not stop at the app. The role in your DATABASE_URL should own data rights (SELECT/INSERT/UPDATE/DELETE) but not necessarily DROP or superuser. Migrations can run as a higher-privileged role (via the direct URL of Chapter 9); the running app connects as a restricted one. If the app is ever compromised, the blast radius is bounded by what that user can do.

The security checklist

① Never concatenate input into SQL. ② Never spread req.body into data. ③ Validate untrusted input with a schema before Prisma. ④ select the columns a caller may see. ⑤ Constrain invariants in the schema. ⑥ Run the app as a least-privilege database user. Six habits; none of them is Prisma’s job to do for you.

Checkpoint

Is Prisma safe from SQL injection, and where does that safety end?

Yes, through the query API — every value is a bound parameter, as Listing 11.1 proves (an injection string matched nothing and dropped no table). The safety ends at $queryRawUnsafe with string concatenation. Never concatenate input into SQL and injection is not one of your problems.

Why is data: req.body dangerous?

Mass assignment — the client controls which columns get written, so a caller can set role: "admin" or any field the schema allows. Prisma checks types, not intent. Always allow-list: name the fields you accept explicitly, never start from the body and remove dangerous keys.

Why validate input when Prisma already checks types?

Because types are not business rules. At runtime req.body is any; Prisma rejects a wrong type but not a negative price, an over-long string, or a malformed email. Validate with a schema at the boundary, and back it with database constraints as the last line of defence.

Logging, Metrics, and Tracing

Seeing what Prisma does at runtime. The query log with real durations and parameters, how to turn it into slow-query detection, and how tracing stitches a database call into a distributed request — so a slow endpoint tells you which query to blame.

By the end of this chapter you will be able to

12.1 The query event

Every query, with its timing and parameters

Construct the client with log: [{ emit: "event", level: "query" }] and subscribe with $on("query", …). Each event carries the exact SQL, the bound parameters, and the wall-clock duration — the raw material for every performance question you will ask.

12.2 From log to slow-query detection

Log the query only when it is slow

You do not want every query in production logs — but you very much want the slow ones. Threshold the duration inside the handler: below the line, stay silent; above it, log the SQL and params so you can take them straight to an EXPLAIN (Chapter 8). This is a five-line slow-query monitor built into the client.

Close the loop

A slow-query warning gives you the SQL; paste it into EXPLAIN ANALYZE; if it is a Seq Scan with a big Rows Removed by Filter, add the index; redeploy; the warning stops. Log → explain → index → verify is the entire performance workflow, and it starts here.

12.4 Tracing

Which query made the request slow?

Logs tell you a query was slow; tracing tells you it was slow inside this specific request, between the auth check and the response serialise. Prisma integrates with OpenTelemetry through @prisma/instrumentation: register it once, and every Prisma operation becomes a span nested under your HTTP request’s trace.

The three, layered

Logs — discrete events (“this query took 120 ms”). Metrics — aggregates over time (p95 query duration, pool utilisation). Traces — one request’s path across services, database spans included. You want all three: logs to read, metrics to alert, traces to pinpoint.

12.5 What never to log

Parameters are user data

The rule

Query parameters contain real values — emails, names, tokens, whatever your users typed. Logging params in production writes that data into your log store, where it outlives the request and widens every breach. Log the SQL shape and the duration freely; redact or omit params in production. In development, log everything — the data is yours.

Checkpoint

What does a Prisma query event contain?

The generated SQL, the bound parameters, and the wall-clock duration (plus a timestamp and target). You get it via log: [{ emit: "event", level: "query" }] and $on("query", …). It is the raw material for slow-query detection and the source of every “the SQL” listing in this book.

How do you build slow-query detection?

Threshold e.duration inside the query handler: log only when it exceeds a limit (say 100 ms), emitting the SQL so you can take it to EXPLAIN. That closes the loop — log the slow query, explain it, add the missing index, verify the warning stops.

Why omit query parameters from production logs?

Parameters are real user data — emails, names, tokens. Logging them writes that data into your log store where it outlives the request and widens any breach. Log the SQL shape and duration freely; redact or omit params in production. Tracing (via @prisma/instrumentation) then pinpoints which query slowed a given request.

13.1 Test against a real database

The thing worth testing is the SQL

You could mock Prisma — but then you are testing your mock, not your query. The bugs that Prisma code actually has live in the SQL: a wrong where, a missing relation, a constraint you forgot, an increment that races. A mock returns whatever you told it to; only a real database tells you the truth. With a disposable local Postgres (Volume 6’s Docker one is perfect), integration tests are cheap — so prefer them.

13.2 An isolated test database

Separate database, migrations applied, never your dev data

Point tests at their own database via a test DATABASE_URL, and bring its schema up with migrate deploy (Chapter 6) — the same migrations production runs, so the test schema is production’s schema. Never test against your development database: tests truncate tables, and you do not want that aimed at data you care about.

13.3 Reset before every test

Each test starts from the same known state

Tests must not depend on each other. The simplest reliable reset is TRUNCATE … RESTART IDENTITY CASCADE before each test, followed by seeding the minimum rows that test needs — fast, total, and it resets the id counters so your assertions can name id: 1. Run it in a beforeEach hook.

Faster isolation: transaction rollback

An alternative that avoids re-seeding: run each test inside an interactive transaction and roll it back at the end, so nothing ever commits. It is faster but fiddlier (every query must use the transaction client, and you cannot test commit behaviour itself). TRUNCATE-and-seed is the honest default; reach for rollback when the suite gets big enough to feel the seeding cost.

Why test Prisma against a real database instead of a mock?

Because the bugs in database code live in the SQL — wrong where, missing relation, forgotten constraint, racing update — and a mock returns whatever you told it, testing nothing. A real (disposable) database is the only thing that catches constraint violations and wrong queries. Integration tests are cheap with a local container, so prefer them.

How do you keep tests isolated from each other?

Reset to a known state before each test — TRUNCATE … RESTART IDENTITY CASCADE then seed the minimum rows — in a beforeEach hook. It is total, fast, and resets id counters so assertions can name id: 1. A faster alternative is wrapping each test in a transaction and rolling it back.

How do you bring the test database’s schema up?

With migrate deploy against a dedicated test DATABASE_URL — the same committed migrations production runs, so the test schema matches production exactly. Never point tests at your development database; they truncate tables.

Chapter Fourteen · Part VI

Multi-tenancy

One application, many customers, and the rule that must never break: tenant A can never see tenant B’s data. Three ways to draw that boundary, and — for the common shared-schema approach — how to enforce it on every query at once instead of hoping every developer remembers.

By the end of this chapter you will be able to
  • Compare shared-row, schema-per-tenant, and database-per-tenant
  • Add a tenantId and see why discipline is not enough
  • Force tenant scoping with a query extension
  • Back it with Row-Level Security in the database

Table 14.1 Shared schema is where almost everyone starts — one table, a tenantId column, cheapest to run and scale. The stronger isolations cost more per tenant and multiply migration work. Pick the weakest boundary that satisfies your compliance and blast-radius needs; the rest of this chapter makes the shared-schema boundary safe.

14.2 Shared schema, and its one danger

The boundary is a column — and one forgotten where

In the shared model, every tenant-owned row carries a tenantId, and every query must filter by it. That is the whole risk: the isolation depends on every query, written by every developer, remembering where: { tenantId }. One findMany without it, and a customer sees everyone’s data. You cannot ship a security boundary that rests on discipline.

14.3 Force the filter with an extension

Make scoping the default, not a thing to remember

The fix from Chapter 10: a query extension that injects where: { tenantId } into every operation. Build a per-request client bound to the caller’s tenant, and route all their queries through it. Now a developer cannot forget the filter — it is added underneath them, on every call.

Extend every operation, not just reads

A read-only guard is a false comfort — an unscoped update or delete can modify another tenant’s rows. Cover findFirst, findUnique, updateMany, deleteMany, count, and aggregates too. Missing one reopens the boundary for that operation.

14.4 The database backstop: Row-Level Security

Defence in depth for the boundary that matters most

An application-layer filter is enforced by your code; a bug, a raw query, or a direct database connection bypasses it. PostgreSQL Row-Level Security (RLS) enforces the boundary in the database itself — a policy that silently adds tenant_id = current_setting('app.tenant') to every statement, no matter who issues it. The application sets the tenant per connection; the database refuses to return anything else.

Two layers, one guarantee

Use both: the extension so application code is clean and scoped by default, and RLS so the isolation survives a forgotten filter, a raw query, or a bug. The stronger the tenancy requirement, the more you want the guarantee living in the database, not only in the code that happens to run above it.

Checkpoint

What are the three multi-tenancy strategies, and which is most common?

Shared schema (a tenantId column), schema-per-tenant (a PostgreSQL schema each), and database-per-tenant (a database each) — increasing isolation, increasing cost, decreasing scale. Shared schema is where almost everyone starts: cheapest to run, scales to millions, but its boundary rests on every query filtering correctly.

Why is a tenantId column not enough on its own?

Because isolation then depends on every query, by every developer, remembering where: { tenantId }. One forgotten filter leaks all tenants’ data. You cannot ship a security boundary that rests on discipline — enforce it with a query extension that injects the filter automatically, covering writes and reads alike.

Why add Row-Level Security on top of the extension?

The extension is enforced by your code, so a bug, a raw query, or a direct connection bypasses it. RLS enforces the boundary in the database — every statement gets tenant_id = current_setting(...) added, no matter who issues it. The extension keeps app code clean; RLS makes the isolation actually true.

Chapter Fifteen · Part VI

Full-text Search and JSON

Two things relational rows do not do well on their own — searching prose and storing flexible shapes — and how PostgreSQL does both, reached through Prisma. Real search ranking and real JSON containment queries, run against the live database.

By the end of this chapter you will be able to
  • Search text with to_tsvector, to_tsquery, and rank results
  • Store flexible data in a Json column
  • Query inside JSON with ->> and containment @>
  • Index both so they stay fast

15.1 Full-text search

LIKE is not search

WHERE title LIKE '%dark%' cannot rank, cannot stem (“running” vs “ran”), and cannot use an index for a leading wildcard. PostgreSQL’s full-text search turns text into a tsvector of normalised lexemes and matches it against a tsquery, with relevance ranking. You reach it through Prisma’s $queryRaw.

Make it fast, and make it native

For real tables, store the tsvector in a generated column and put a GIN index on it, so search does not recompute the vector every query. Prisma can also expose PostgreSQL FTS through a native search filter on string fields (a preview capability that maps to to_tsquery); the raw form above always works and shows exactly what runs.

15.2 The Json type

A typed hole for untyped data

Some data is genuinely schemaless — user preferences, event payloads, third-party blobs. A Json column (PostgreSQL jsonb) stores it without a migration per field. Use it deliberately: reach for real columns when a field is queried or constrained, and Json only for shapes that are truly variable. Everything you put in a Json column, you give up column-level types and constraints for.

15.3 Querying inside JSON

Containment: @>

data @> '{"city":"Hanoi"}' asks “does this document contain that fragment?” — the fastest JSON filter, because a GIN index serves it directly. Prisma’s native Json filters (path, equals, string_contains, array_contains) compile to these same operators; use them for simple cases and drop to $queryRaw when the JSON logic gets involved.

Checkpoint

Why is full-text search better than LIKE for searching prose?

LIKE cannot rank, cannot stem (“running”/“ran”), and cannot use an index behind a leading wildcard. Full-text search normalises text into a tsvector of lexemes, matches it with @@ against a tsquery, and scores relevance with ts_rank — reached through Prisma’s $queryRaw, with a GIN index for speed.

When should data go in a Json column versus a real column?

Json for genuinely variable shapes (preferences, payloads, third-party blobs) that you would otherwise migrate for constantly. A real column the moment a field is queried often or must be constrained — a Json field gives up column-level types, constraints, and the cleanest indexing.

What is the difference between ->> and @>?

->> extracts a field from a JSON document as text (-> keeps it as JSON); @> tests whether a document contains a given fragment and is GIN-index-backed, making it the fastest JSON filter. Prisma’s native path/equals/array_contains filters compile down to these operators.
