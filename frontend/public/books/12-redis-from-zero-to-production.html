About this book

Redis is deceptively simple. SET and GET you learn in a minute; the difference between a team that uses Redis and one that relies on it is everything after that — the right structure for the job, the single-threaded discipline, replication and failover, and knowing which command will quietly freeze production at the worst moment.

So every command in this book was run against a real Redis 7 server, and the reply you read on the page is the reply that came back — the (integer), the (nil), the numbered array, verbatim. The replication chapter attaches a real replica and reads its sync log; the cluster chapter builds a real six-node cluster and follows a MOVED redirect; the streams, pub/sub, Lua, and Stack chapters all run live. Nothing here is typed from memory of how Redis behaves.

It is built on Redis 7.4, so it teaches the current shape of things: the multi-part AOF, ACL users and categories, Redis Functions rather than only EVALSHA, and Redis Stack’s JSON and search modules. Where a feature replaced an older way of doing things, the book says so and teaches the new one.

Who should read this

Any developer who has reached for a cache, a queue, a rate limiter, or a leaderboard and wants to build it on Redis properly. You need no prior Redis; you should be comfortable in a terminal. The caching and transaction chapters lean on Volumes 6 and 7 (PostgreSQL and Node.js) for the database Redis sits in front of.

How this book is organised

Chapter 0 is the mental model. Chapters 1–15 then map one-to-one onto the sixteen modules of the Redis track in Code Lab, each ending with that module’s ten graded exercises. Read 0 through 3 in order; after that the parts are largely independent — jump to replication, streams, or caching as your work demands.

The one idea the whole book returns to

Redis runs your commands on a single thread, one at a time. That is why every command is atomic without locks (§0.4), why INCR, MULTI, WATCH, and Lua scripts are safe under concurrency (Ch 7, 11), and why one O(n) command over a huge key can freeze the entire server (§0.4, §15.3). Master that single fact and most of Redis follows from it.

Chapter Zero · Orientation

What Redis Is, and How to Think in It

Redis is a server that keeps your data in memory, organised as a handful of familiar data structures, and answers commands in microseconds. This chapter installs it, connects to it, and gives you the one mental model the rest of the book builds on.

By the end of this chapter you will be able to
  • Say what Redis is — and what it is not
  • Run a server and talk to it with redis-cli
  • Read the mental model: keys mapping to typed structures
  • Explain why a single-threaded server is this fast

0.1 What Redis is

An in-memory data-structure server

A relational database (Volumes 6 and 11) keeps data on disk, organised as rows in tables, and you query it with SQL. Redis is a different animal: it keeps data in RAM, organised as data structures — strings, lists, sets, hashes, sorted sets — and you manipulate them with commands named after the operations you already know: GET, LPUSH, SADD, INCR. There is no query language and no schema. There is a key, and behind it a structure, and commands that act on it.

What it is for

Because everything is in memory, Redis answers in microseconds, not milliseconds — often 50–100× faster than a round trip to PostgreSQL. That speed is the whole point. Redis is where you put the data that must be instant: a cache in front of your database (Chapter 14), a session store, a rate limiter, a job queue, a leaderboard, a real-time feed. It complements a durable database; it rarely replaces one.

0.3 The mental model: keys to structures

Every key names one structure

Picture Redis as one enormous dictionary. Each key is a string you choose; each value is a data structure of a specific type. The type is fixed when you first write the key, and the commands you may use are exactly the commands for that type — LPUSH works on a list, not on a string. TYPE tells you what a key holds; the command you reach for follows from that.

The naming convention

Keys like user:1 and profile:1 are not special syntax — the colon is just a character. But the convention object-type:id:field is universal in Redis, because it keeps a flat keyspace legible and lets you match families of keys (user:*) when you scan (Chapter 2). Adopt it from your first key.

0.4 Why single-threaded is fast

One command at a time — and that is a feature

Redis runs your commands on a single thread: one command finishes before the next begins. That sounds like a limit, but it is why Redis is both fast and simple. There are no locks, no race conditions between commands, and every individual command is atomic — an INCR can never lose an update to a concurrent INCR, because there is no concurrency at the command level. The work each command does is tiny (a hash-table lookup, a list push), so the thread never blocks for long, and memory access is nanoseconds.

The one rule that follows

Because there is one thread, a slow command blocks every other client. A KEYS * over a million keys, or a Lua script that loops for a second, freezes the whole server for that time. Almost everything in the performance and operations chapters comes back to this: keep each command small, and never make the single thread wait.

Checkpoint

How is Redis different from a relational database?

It keeps data in memory (not on disk) organised as data structures (not rows in tables), and you manipulate it with commands (not SQL). There is no schema and no query language. The result is microsecond latency, which is why Redis is used for caches, sessions, queues, and leaderboards alongside a durable database rather than instead of one.

What does a key map to, and what fixes the commands you can use?

Each key maps to one data structure of a specific type — string, list, set, hash, or sorted set. The type is set on first write, and it determines the legal commands: LPUSH only works on a list, HSET only on a hash. TYPE key tells you what a key holds.

Why is a single-threaded server fast and safe — and what is the catch?

One command runs to completion before the next, so every command is atomic with no locks (an INCR can never lose an update), and each command touches memory for only nanoseconds. The catch: a slow command blocks all clients, because there is only one thread — so never run an O(n) command over a huge keyspace on a live server.

Chapter One · Part I

The Five Core Data Structures

Strings, lists, sets, hashes, and sorted sets. Learn these five and you can model most of what Redis is used for. Each one comes with commands tuned to a job — a counter, a queue, a tag set, a record, a leaderboard.

By the end of this chapter you will be able to
  • Use strings as text, counters, and flags
  • Build queues and stacks from lists
  • Track membership and do set algebra with sets
  • Store records in hashes and rankings in sorted sets

1.1 Strings — text, numbers, flags

The simplest value, and the most versatile

A Redis string holds up to 512 MB of any bytes — text, a number, JSON, even a small image. But its real power is the commands: INCR and DECR treat it as an integer, APPEND grows it, SETNX writes only if absent (a lock), and SET with options sets a value and its expiry in one atomic step.

1.2 Lists — queues and stacks

An ordered sequence, fast at both ends

A list is a sequence of strings ordered by insertion, with O(1) push and pop at either end. Push left, pop right and you have a FIFO queue; push and pop the same end and you have a LIFO stack. The blocking variants (BLPOP) turn a list into a work queue a worker can wait on.

1.3 Sets — membership and algebra

Unordered, unique, and built for “is it in there?”

A set holds unique strings in no particular order. SADD is idempotent — adding a member twice stores it once — and SISMEMBER answers membership in O(1). Beyond that, sets do algebra: intersection, union, and difference across whole sets in one command, which is how you compute “users who like both” or “tags in A but not B”.

1.4 Hashes — records

A key that holds a small table of fields

A hash is a map of field → value under a single key — a record. Instead of one key per attribute (user:1:name, user:1:email), you keep one key user:1 with fields name, email, born. You can read or write one field or all of them, and increment a numeric field in place.

1.5 Sorted sets — rankings

A set where every member carries a score

A sorted set is the crown jewel: unique members like a set, but each has a floating-point score, and Redis keeps them ordered by it. That makes leaderboards, priority queues, rate-limit windows, and time-ordered indexes all O(log n). You can read a rank range, a score range, or a single member’s position.

Choosing the structure

The type is the design decision. Need a counter or flag? String. A queue? List. Membership or algebra? Set. A record? Hash. Anything ranked, ordered, or windowed by a number? Sorted set. Model the access pattern first, and the right structure — and its commands — follows.

Checkpoint

How can a Redis string be both text and a counter?

The value is just bytes, but the commands interpret it: GET/SET/APPEND treat it as text, while INCR/INCRBY/DECR treat it as an integer and update it atomically. SET … NX EX also makes a string a lock with an expiry in one atomic command.

How do you make a FIFO queue versus a LIFO stack from a list?

Queue: push one end and pop the other — RPUSH to append, LPOP to take the oldest. Stack: push and pop the same end — LPUSH then LPOP. RPOPLPUSH moves an item between lists atomically, which is how a worker takes a job without losing it if it crashes mid-processing.

When do you reach for a sorted set?

Whenever members must be ordered or selected by a number: leaderboards (rank by score), priority queues (score = priority), rate-limit windows and time indexes (score = timestamp). It keeps members unique like a set but ordered by score, with O(log n) rank and range queries — ZRANGE, ZRANGEBYSCORE, ZRANK.

Chapter Two · Part I

Expiration, TTL, and Key Management

Keys that delete themselves are what make Redis a cache. This chapter covers time-to-live, the commands that set and read it, how to walk a large keyspace without freezing the server, and what Redis does when memory runs out.

By the end of this chapter you will be able to
  • Give a key a lifetime with EXPIRE and read it with TTL
  • Set a value and its expiry atomically
  • Walk millions of keys safely with SCAN, never KEYS
  • Choose an eviction policy for when memory is full

2.1 Time to live

A key can carry an expiry

Any key can be given a lifetime in seconds; when it elapses, Redis deletes the key automatically. EXPIRE sets it, TTL reads the seconds remaining, and PERSIST removes it so the key lives forever again. A TTL of -1 means “no expiry”; -2 means “the key does not exist”.

Set value and expiry together

Always prefer SET key val EX seconds over SET followed by EXPIRE. The single-command form is atomic; the two-command form has a window where the process can die and leave an immortal key — the classic cause of a cache that never evicts and slowly eats all your memory.

2.2 Walking the keyspace

KEYS is a trap; SCAN is the tool

To find keys matching a pattern, KEYS user:* is tempting — and forbidden in production. It scans the entire keyspace in one blocking pass, freezing the single thread (Chapter 0) for as long as it takes. SCAN does the same job incrementally: it returns a cursor and a handful of keys each call, so the server stays responsive. You loop until the cursor comes back 0.

The family of scanners

SCAN walks keys; HSCAN, SSCAN, and ZSCAN walk the fields of one large hash, set, or sorted set the same incremental way. Any time you would iterate a big collection, reach for the SCAN-family cursor, not the O(n) command (KEYS, HGETALL, SMEMBERS) that returns everything at once.

2.3 How expiry actually happens

Lazy plus sampled, not a timer per key

Redis does not run a timer for every key. It expires keys two ways: lazily — when you touch an expired key, it is deleted then and reported as gone — and actively — a background cycle samples a few keys with expiries ~10 times a second and deletes those that lapsed. So an unaccessed expired key can sit in memory briefly after its time, but you will never read a stale value, and memory is reclaimed steadily.

2.4 When memory is full

The eviction policy decides what goes

Set a maxmemory limit and Redis will, when it is reached, evict keys to make room according to maxmemory-policy. The default noeviction refuses new writes with an error — safe for a database, wrong for a cache. For a cache you want allkeys-lru (drop the least-recently-used key) or allkeys-lfu (least-frequently-used). The volatile-* variants only evict keys that have an expiry set.

Checkpoint

Why prefer SET key val EX 30 over SET then EXPIRE?

Because the combined form is atomic. With two commands, the process can crash between them, leaving a key with a value but no expiry — an immortal cache entry. The single-command form guarantees the value and its lifetime are set together or not at all. TTL of -1 means no expiry, -2 means the key is gone.

Why is KEYS dangerous, and what replaces it?

KEYS scans the whole keyspace in one blocking pass, freezing the single-threaded server for the duration. SCAN replaces it: it returns a cursor and a small batch each call, so you iterate without blocking. HSCAN/SSCAN/ZSCAN do the same for the fields of one large collection.

What does maxmemory-policy control, and which fits a cache?

What Redis evicts when maxmemory is reached. noeviction (the default) errors on new writes — right for a primary store, wrong for a cache. A cache wants allkeys-lru or allkeys-lfu so cold keys are dropped to make room; volatile-* policies only evict keys that carry an expiry.

Chapter Three · Part I

Bitmaps, HyperLogLog, and Geo

Three specialised types that solve problems the five core structures do not. Track millions of daily-active flags in a few kilobytes, count unique visitors in 12 KB flat, and answer “what is near me?” — each with commands built for the job.

By the end of this chapter you will be able to
  • Pack boolean flags into a bitmap
  • Count uniques in fixed memory with HyperLogLog
  • Store and query locations with geo commands
  • Know the accuracy and memory trade-offs of each

3.1 Bitmaps — a bit per thing

A string, addressed one bit at a time

A bitmap is not a new type — it is a string you address bit by bit with SETBIT and GETBIT. Give each user an offset (their id) and one key per day, and “was user 42 active today?” is a single bit. A million users is 125 KB — one bit each. BITCOUNT tallies the set bits (active users), and BITOP combines days with AND/OR to answer “active both days”.

3.2 HyperLogLog — counting uniques cheaply

Millions of distinct items, 12 KB, ~0.8% error

Counting unique things exactly means storing every thing — a set of a million visitors is megabytes. A HyperLogLog counts uniques probabilistically in a fixed 12 KB, whatever the count, with a standard error under 1%. PFADD observes items, PFCOUNT estimates the cardinality, and PFMERGE unions several — perfect for unique visitors, distinct search terms, or reach, where an approximate answer is fine and the memory saving is enormous.

Exact or estimated — choose deliberately

If you need the actual members, or an exact count, use a set. If you only need how many distinct, and can accept ~0.8% error, a HyperLogLog trades that tiny inaccuracy for constant, tiny memory. The wrong choice is a set of ten million members when all you ever call is SCARD.

3.3 Geo — what is near me

Sorted sets with a coordinate, and commands to search them

Redis stores locations by encoding longitude/latitude into a sorted-set score (a geohash). GEOADD adds named points, GEODIST measures between two, and GEOSEARCH finds every member within a radius or box of a point — the “restaurants near me” query, answered in O(log n).

The right tool per question

Bitmaps answer “is this one thing true, and how many are?” in minimal space. HyperLogLog answers “how many distinct?” in fixed space. Geo answers “what is near this point?”. None replaces the core five — they extend Redis into analytics and location without a second system.

Checkpoint

How does a bitmap track a million daily-active users cheaply?

Each user gets an offset (their id) in a per-day string; SETBIT day id 1 marks them active — one bit each, so a million users is ~125 KB. BITCOUNT tallies active users, and BITOP AND/OR across days answers retention questions like “active both days” server-side.

When is a HyperLogLog the right choice over a set?

When you only need the count of distinct items, not the members, and can accept ~0.8% error. An HLL uses a fixed ~12 KB no matter the cardinality, where a set grows with every unique member. Use a set when you need the actual members or an exact count; use an HLL for unique-visitor-style metrics at scale.

How does Redis answer a proximity query?

Geo commands encode each location’s longitude/latitude into a sorted-set score, so GEOSEARCH … BYRADIUS finds members within a distance of a point in O(log n), and GEODIST measures between two. It is a location index built on the sorted set, needing no separate geospatial database.

Chapter Four · Part II

Persistence and Backup

Redis lives in memory, but memory is lost on restart. Two mechanisms write it to disk — point-in-time snapshots and an append-only log of every write — and you choose based on how much data you can afford to lose. This chapter runs both against the live server.

By the end of this chapter you will be able to
  • Snapshot the dataset with RDB and BGSAVE
  • Log every write durably with AOF
  • Choose RDB, AOF, or both for a workload
  • Back up and restore a Redis instance

4.1 RDB — point-in-time snapshots

A compact dump of the whole dataset

RDB writes the entire dataset to a single dump.rdb file at intervals. It is compact and fast to load, and BGSAVE forks a child process to write it so the main thread keeps serving. The cost is data loss on crash: everything written since the last snapshot is gone. The save directive defines the snapshot triggers — “after N seconds if at least M keys changed”.

4.2 AOF — the append-only log

Every write, logged as it happens

The Append-Only File records every write command to a log as it executes. On restart Redis replays the log to reconstruct the exact state. With appendfsync everysec (the recommended default) you lose at most one second of writes on a crash — far better than RDB’s minutes. The cost is a larger file and slightly more disk I/O; Redis periodically rewrites the log to the smallest set of commands that rebuilds the data.

Redis 7 stores the AOF as a directory

Since Redis 7 the AOF is multi-part: an appendonlydir/ holding a base snapshot (.base.rdb), one or more incremental logs (.incr.aof), and a manifest that ties them together. The base is a compact RDB-format starting point; the incrementals are the writes since. This makes rewrites cheaper and is why you back up the whole directory, not a single file.

Checkpoint

What is the fundamental trade-off between RDB and AOF?

Data loss versus overhead. RDB snapshots periodically, so a crash loses everything since the last snapshot (minutes), but the file is small and loads fast. AOF logs every write, so a crash loses at most one second (with everysec), but the file is larger and replay is slower. Most production runs both.

Why use BGSAVE rather than SAVE?

SAVE writes the snapshot on the main thread, blocking every client until it finishes — the single-thread trap. BGSAVE forks a child process to write dump.rdb while the main thread keeps serving. You confirm completion by polling LASTSAVE or checking rdb_last_bgsave_status in INFO.

What changed about the AOF in Redis 7, and why does it matter for backups?

The AOF became multi-part: an appendonlydir/ with a base snapshot, incremental logs, and a manifest, instead of one file. It makes rewrites cheaper — but it means a backup must copy the whole directory, not a single appendonly.aof file as in older versions.

Chapter Five · Part III

Replication and High Availability

One server is a single point of failure. Replication keeps live copies of your data on other servers; Sentinel watches them all and promotes a replica automatically when the master dies. This chapter builds a real master, a real replica, and a real Sentinel, and reads their true state.

By the end of this chapter you will be able to
  • Attach a replica and watch it sync from the master
  • Understand why replicas are read-only
  • Run Sentinel to monitor a master
  • Explain automatic failover and the quorum rule

5.1 A master and a replica

Replicas hold a live copy

A replica connects to a master, performs an initial full sync (the master forks an RDB snapshot and ships it), then receives every subsequent write in a continuous stream. Reads can be served from any replica, spreading load; and if the master fails, a replica already holds the data. You start one with replicaof <master-host> <port>.

5.2 The master and replica, side by side

Replication is asynchronous

The master does not wait for replicas to confirm a write before replying OK to the client — replication is asynchronous. This keeps writes fast, but it means a master can acknowledge a write and then crash before the replica received it, losing that write. The WAIT command lets a client block until N replicas have the write, trading latency for stronger durability when you need it.

5.3 Sentinel — automatic failover

Something has to notice the master died

Replication gives you a copy; it does not promote it. Sentinel is a separate process that watches the master and replicas, and when enough Sentinels agree the master is unreachable, one replica is promoted to master and the others are repointed at it — no human at 3 a.m. Clients ask Sentinel “who is the master right now?” rather than hard-coding an address.

Quorum needs an odd number — usually three

Why three Sentinels, not one

The demo runs one Sentinel with a quorum of 1, which is enough to see the master but not safe for real failover. In production you run three Sentinels on separate machines with a quorum of 2. The odd number and majority rule prevent split-brain: a network partition cannot leave two halves each promoting their own master, because only the side with a majority of Sentinels can act. One Sentinel is a single point of failure watching for single points of failure.

Checkpoint

What happens when a replica first connects to a master?

A full sync: the master forks and produces an RDB snapshot, ships it to the replica, and the replica loads it (“keys loaded: N” in its log). From then on the master streams every write to the replica continuously, so the copy stays current. Reads can be served from the replica; writes cannot — it is read-only by default.

What does Sentinel add that replication alone does not?

Automatic failover. Replication keeps a copy but never promotes it; Sentinel monitors the master, and when a quorum of Sentinels agree it is down, promotes a replica and repoints the others. Clients ask Sentinel get-master-addr-by-name for the current master, so they follow the failover without a config change.

Why run three Sentinels with a quorum of two?

To prevent split-brain. A majority rule on an odd number means a network partition can only let the side holding most Sentinels perform a failover — the minority side cannot promote a rival master. One Sentinel is itself a single point of failure; three on separate hosts is the smallest configuration that actually tolerates a failure.

Cluster and Sharding

Replication copies one dataset; it does not let the data outgrow one machine. Redis Cluster shards the keyspace across many masters, each owning a slice, and keeps working when a node dies. This chapter builds a real six-node cluster and watches keys route to their shards.

By the end of this chapter you will be able to

6.1 Sharding by hash slot

16,384 slots, divided among masters

A cluster divides the keyspace into a fixed 16,384 hash slots. Every key belongs to exactly one slot, computed as CRC16(key) mod 16384, and each master owns a contiguous range of slots. Add masters and you redistribute slots — that is how the data (and the load) scales past one machine. No proxy decides where a key lives; the slot formula does, and every node knows the full map.

6.3 Keeping related keys together

Hash tags force co-location

A multi-key command (MGET, a transaction, a Lua script) only works if every key is on the same node — cluster cannot join across shards. To guarantee that, wrap the shared part of the key in braces: only the text inside {…} is hashed. So {user:1}:profile and {user:1}:inbox hash on user:1 alone and always land in the same slot, on the same master.

The trade-off of a hash tag

Do not over-tag

A hash tag concentrates keys on one slot — and therefore one master. Tag a whole tenant’s data under {tenant:42} and every key for a large tenant lives on one node, recreating the hotspot cluster was meant to spread. Tag only what a single operation must touch together (one user’s profile and inbox), never an entire large partition.

Checkpoint

How does a cluster decide which node owns a key?

By hash slot: CRC16(key) mod 16384 gives one of 16,384 slots, and each master owns a contiguous slot range. The key’s slot determines its node deterministically — no proxy, no lookup service. Adding masters redistributes slot ranges, which is how the keyspace scales beyond one machine.

What is a MOVED reply, and who handles it?

When you send a key to a node that does not own its slot, the node replies MOVED <slot> <node> instead of serving it. A cluster-aware client follows the redirect and caches the slot→node map so it goes straight to the right node next time. With redis-cli -c or a real client library, this is transparent — you never see it.

When and how do you use a hash tag?

When several keys must be touched by one multi-key command (MGET, transaction, Lua) — cluster requires them on the same node. Wrapping the shared part in braces, {user:1}:profile, hashes only user:1, forcing those keys into the same slot. Tag only what one operation needs together; tagging a whole large partition recreates a hotspot.

Chapter Seven · Part IV

Pipelining, Transactions, and Benchmarks

Redis commands are fast; the network between you and Redis is not. This chapter is about doing more per round trip — batching with pipelines, grouping with transactions, guarding with optimistic locks — and measuring the result with the tools Redis ships.

By the end of this chapter you will be able to
  • Cut round trips with pipelining, and measure the gain
  • Group commands atomically with MULTI/EXEC
  • Guard a read-modify-write with WATCH
  • Find slow commands with the slow log

7.1 The round trip is the cost

One command, one round trip — that adds up

A single GET takes microseconds inside Redis but a full network round trip to reach it — often 100–500 µs on a LAN. Do a thousand sequential GETs and you pay for a thousand round trips, and the network, not Redis, is your bottleneck. Pipelining fixes this: send many commands at once without waiting for each reply, then read all the replies together. The commands still run one at a time on the server; you have simply stopped waiting between them.

7.2 Transactions with MULTI/EXEC

A queued block that runs with nothing in between

MULTI starts a transaction; every command after it is queued (the server replies QUEUED) rather than run; EXEC then runs the whole queue as a single unit, with no other client’s command interleaved. Because Redis is single-threaded, the block is atomic and isolated. DISCARD throws the queue away instead.

Redis transactions are not SQL transactions

Two differences matter. First, there is no rollback: if one command in the block fails at runtime (say you INCR a key holding text), the others still execute — Redis does not undo them. Redis guards against queue-time errors (a malformed command aborts the whole EXEC), not logic errors. Second, you cannot decide a later command based on an earlier one’s result inside the block, because nothing runs until EXEC. For read-then-write logic, you need WATCH — or a Lua script (Chapter 11).

7.3 Optimistic locking with WATCH

Check-and-set without holding a lock

Some logic must read a value, decide, then write — “buy only if stock > 0”. Between your read and your write, another client could change the value. WATCH solves this optimistically: you watch the key, read it, build a MULTI/EXEC block, and if the watched key was modified by anyone before your EXEC, the whole transaction aborts and returns (nil). You detect the conflict and retry, rather than locking the key and making others wait.

7.4 Finding slow commands

The slow log records what took too long

On a single-threaded server, one slow command delays everyone (Chapter 0). The slow log records commands whose execution exceeded a threshold (slowlog-log-slower-than, in microseconds) — not counting network time, only the work Redis did. It is your first stop when latency spikes: it names the exact commands, with arguments, that are blocking the thread.

Checkpoint

What does pipelining change, and what does it not?

It changes how many commands are in flight — you send many without waiting for each reply, amortising network round-trip latency (the demo nearly tripled throughput). It does not change how Redis runs them: still one at a time, in order, on the single thread. Pipeline batches of independent commands; never loop one-at-a-time across a network.

How is a Redis MULTI/EXEC transaction different from a SQL one?

Two ways: there is no rollback — a runtime error in one queued command does not undo the others (Redis only aborts on queue-time errors like a malformed command); and you cannot branch on an earlier command’s result inside the block, because nothing runs until EXEC. For read-then-decide-then-write, use WATCH or a Lua script.

How does WATCH make a read-modify-write safe?

Optimistically. You WATCH the key, read it, queue a MULTI/EXEC block; if anyone modifies the watched key before your EXEC, the transaction aborts and returns (nil). You detect that, re-read, and retry — no lock is held, so other clients are never blocked, unlike a pessimistic lock.

Chapter Eight · Part IV

Security and Access Control

A default Redis trusts anyone who can reach the port — and the port is a database with a FLUSHALL command. This chapter locks it down: authentication, per-user permissions with ACLs, disabling the commands that can hurt you, and closing the network to the outside.

By the end of this chapter you will be able to
  • Require authentication and understand the default user
  • Create least-privilege users with ACLs
  • Restrict which keys and commands a user may touch
  • Disable dangerous commands and close the network

8.1 Authentication

No password is the default — and the danger

Out of the box Redis has a single user, default, with no password and all permissions (+@all on ~*). Anyone who reaches the port owns the data. The first hardening step is a password — historically requirepass, now expressed as a password on the default user — after which every connection must AUTH before it can do anything.

8.2 ACLs — least privilege per user

A user is a set of allowed keys, commands, and channels

Since Redis 6, ACL SETUSER defines named users with precise rules: which commands they may run (+get, -@dangerous, +@read), which keys they may touch (~cache:*), and which pub/sub channels (&news:*). Give each service its own user with exactly the rights it needs — the application that only caches should not hold a credential that can FLUSHALL.

8.3 Disabling dangerous commands

Some commands should not exist in production

FLUSHALL, FLUSHDB, KEYS, CONFIG, DEBUG, SHUTDOWN — each can destroy data or freeze the server. The modern way to remove them is an ACL category: -@dangerous strips the whole class from a user in one rule. You can also disable a command server-wide, or rename it to an unguessable string, in the config.

8.4 Closing the network

Bind, protected mode, and TLS

Authentication guards the data; the network guards the door. bind restricts which interfaces Redis listens on — bind to 127.0.0.1 or a private address, never 0.0.0.0 on a public host. Protected mode (on by default) refuses external connections when there is no password and no explicit bind, a safety net against accidental exposure. For traffic that crosses a network you do not trust, enable TLS so connections are encrypted and clients authenticate with certificates.

The hardening checklist

① Set a password on default (or disable it). ② Give each service its own least-privilege ACL user. ③ Scope users to the keys and commands they need — allow-list, not block-list. ④ Strip -@dangerous from application users. ⑤ bind to private interfaces and keep protected mode on. ⑥ Enable TLS across untrusted networks. A Redis reachable from the internet with nopass is compromised within minutes — this list is not optional.

Checkpoint

What is the default security posture, and what is the first fix?

One user, default, with nopass and +@all on ~* — anyone reaching the port has full control. The first fix is authentication: set a password on the default user so every connection must AUTH. A Redis exposed with no password is taken over within minutes.

How do ACLs enforce least privilege?

An ACL user is an allow-list of commands (+get, -@dangerous), keys (~cache:*), and channels — everything not granted is denied. So a cacheuser scoped to ~cache:* with +get +set +del cannot touch other keys (NOPERM on the key) or run FLUSHALL (NOPERM on the command), even if its credential leaks.

Give two ways to neutralise a dangerous command like FLUSHALL.

Per user: -@dangerous in an ACL strips the whole destructive category. Server-wide: rename-command FLUSHALL "" in the config removes it for everyone, or renaming it to a secret string leaves it usable only by operators who know the new name. Disabling KEYS the same way forces clients onto SCAN.

Chapter Nine · Part V

Streams and Event-Driven Systems

A stream is an append-only log built into Redis — every event kept in order, each with an id, readable by many independent consumers. It is the backbone of event-driven work: durable like a list, fan-out like pub/sub, with consumer groups that split a workload and never lose a message.

By the end of this chapter you will be able to
  • Append and read events with XADD and XRANGE
  • Understand stream ids and the append-only model
  • Split a workload across a consumer group
  • Recover unacknowledged messages after a crash

9.1 The append-only log

Events, in order, each with an id

A stream is a sequence of entries; each XADD appends one and returns its id — a <millisecond>-<sequence> value that always increases, so order is total and ids are unique. Unlike a list, entries are not consumed by reading; they stay until you trim them, and many readers can each read the whole history independently. Each entry is a set of field-value pairs, like a small hash.

9.2 Reading new events

XREAD, and the special id $

XREAD reads entries with an id greater than one you supply, so a reader tracks its position by remembering the last id it saw. The special id $ means “only entries added after now” — a tail. With BLOCK, XREAD waits for the next entry instead of returning empty, turning a stream into a push feed a consumer sleeps on.

9.3 Consumer groups

Split the work, track each message

One reader per stream does not scale. A consumer group lets several consumers share a stream: each entry is delivered to exactly one consumer in the group, so N workers process N times faster. The group remembers, per entry, whether it was acknowledged — so a message a consumer took but never finished is not lost. XREADGROUP delivers, XACK confirms done.

9.4 Recovering after a crash

The pending list is the safety net

If alice takes a message and crashes before XACK, that entry sits in the group’s pending list forever — visible, owned by the dead consumer. XPENDING shows what is stuck and for how long; XCLAIM (or XAUTOCLAIM) transfers ownership of a long-idle entry to a healthy consumer, which reprocesses and acknowledges it. That loop — deliver, and reclaim what was never acked — is what makes a stream a reliable queue, not a fire-and-forget one.

Stream, list, or pub/sub?

A list is a simple queue: a job is popped and gone, one worker. Pub/sub (Chapter 10) is fan-out with no memory: a subscriber offline at publish time never sees the message. A stream is both durable and fan-out, with consumer groups and acknowledgements — reach for it when events must be kept, replayable, and processed reliably by a pool of workers.

Checkpoint

How does a stream differ from a list as a queue?

A list entry is consumed when popped — one worker, gone after reading. A stream is append-only: entries stay after being read, carry increasing ids, and many consumers can read independently. With consumer groups it also tracks per-entry acknowledgement, so an unfinished message is recoverable rather than lost.

What does a consumer group give you over a plain XREAD?

Work splitting and reliability. Each entry goes to exactly one consumer in the group, so N workers share the load; and the group records every delivered-but-unacknowledged entry in a pending list, so a message a consumer took but never XACKed is not lost. XREAD alone has neither — every reader gets everything, with no tracking.

What happens to a message if a consumer crashes before XACK?

It stays in the group’s pending list, owned by the dead consumer, visible via XPENDING. Another consumer reclaims it with XCLAIM/XAUTOCLAIM (by idle time), reprocesses, and acknowledges it. That reclaim loop is what makes a stream an at-least-once reliable queue rather than fire-and-forget.

Pub/Sub and Real-Time Messaging

Redis can carry messages, not just store them. Publish/subscribe is instant fan-out — a message goes to every subscriber listening right now — and keyspace notifications turn the database itself into an event source. Both are built and run live in this chapter.

By the end of this chapter you will be able to
  • Fan a message out to many subscribers with pub/sub
  • Match many channels at once with pattern subscriptions
  • React to data changes with keyspace notifications
  • Choose pub/sub or streams by whether history matters

10.1 Publish and subscribe

Instant fan-out, no memory

SUBSCRIBE tunes a connection to one or more channels; PUBLISH sends a message to a channel, and every subscriber currently listening receives it at once. There is no queue and no history: a subscriber that connects a second later never sees the message. PUBLISH returns the count of subscribers it reached — 0 means nobody was home, and the message is gone.

10.2 Pattern subscriptions

Subscribe to a namespace with PSUBSCRIBE

PSUBSCRIBE subscribes by glob pattern, so news.* catches every channel under news. without naming each. Messages arrive as pmessage frames that include the pattern that matched, so one handler can route by channel. It is how a client follows a whole family of topics — every room in a chat, every region’s updates — with one subscription.

10.3 Keyspace notifications

The database as an event source

Turn on notify-keyspace-events and Redis publishes an event for every change to internal channels: __keyevent@0__:set when a key is set, :expire, :del, and so on. Subscribe with a pattern and your application reacts to data changes in real time — a classic use is acting when a key expires (a session ended, a hold timed out), which no command tells you about otherwise.

Notifications are pub/sub — so they can be missed

Keyspace events ride on pub/sub, which means they inherit its one weakness: a consumer that is disconnected when the event fires never sees it. For fire-and-forget reactions that is fine; for anything that must not be lost, drive the change through a stream (Chapter 9) instead, where the event is durable and acknowledged.

Checkpoint

What does PUBLISH return, and what does it tell you?

The number of subscribers that received the message. 0 means no one was listening and the message was dropped — pub/sub keeps no history and never redelivers. It is fire-and-forget fan-out to whoever is connected at that instant.

What are keyspace notifications, and what caveat comes with them?

With notify-keyspace-events enabled, Redis publishes an event (set, expire, del…) on internal channels for every change, so an app can react to data changes — notably key expiry. The caveat: they ride on pub/sub, so a disconnected subscriber misses them. Use a stream when the reaction must not be lost.

When do you choose a stream over pub/sub?

When a missed message is a bug. Pub/sub delivers only to current subscribers and keeps no history; a stream is a durable, append-only log with consumer groups and acknowledgements, so an offline consumer reads events later and nothing is lost. Live signals (presence, ticks) suit pub/sub; jobs and important events suit streams.

Chapter Eleven · Part V

Lua Scripting for Atomic Operations

When a job needs several commands to run as one indivisible step — read a value, decide, write — a Lua script is the cleanest tool Redis offers. The whole script runs atomically on the server, so no other client can slip in between your read and your write.

By the end of this chapter you will be able to
  • Explain why a script is atomic, and when to reach for one
  • Pass keys and arguments with KEYS and ARGV
  • Cache scripts by hash with SCRIPT LOAD and EVALSHA
  • Register reusable server-side logic with Redis Functions

11.1 Why script at all

The whole script is one atomic step

A Lua script sent with EVAL runs entirely on the server, as a single unit — like one command. Because Redis is single-threaded, nothing else executes while your script runs, so a read-modify-write inside it cannot race. This is stronger and simpler than the WATCH retry loop of Chapter 7: no optimistic check, no retry, no round trips between the steps. You move the logic to the data instead of pulling the data to your logic.

The rule that keeps scripts safe

Keep scripts short and deterministic

Because a script blocks the single thread for its entire duration (Chapter 0), a long-looping script freezes the server. And a script must be deterministic — same inputs, same effects — so it replicates correctly to replicas and the AOF. Do not call for the current time or a random number inside a script and then write it; pass such values in as ARGV from the client, where they are decided once.

11.2 EVAL, KEYS, and ARGV

Keys in KEYS, everything else in ARGV

EVAL script numkeys key1 … arg1 … passes the key names your script touches in KEYS and all other parameters in ARGV. Keeping keys separate is not a style rule — it is what lets Redis Cluster (Chapter 6) route the script to the right node, because it can see which keys are involved. Always name keys through KEYS, never hard-code them in the script body. The --eval flag reads the script from a file and puts everything before the comma in KEYS.

11.3 Cache the script: EVALSHA

Send the script once, call it by hash

Sending a long script on every call wastes bandwidth. SCRIPT LOAD stores the script on the server and returns its SHA-1 hash; thereafter you call it with EVALSHA <hash> — a few bytes instead of the whole body. Client libraries do this for you: try EVALSHA, and if the server replies NOSCRIPT (it was flushed), fall back to EVAL once to reload it.

11.4 Redis Functions

Named, persistent server-side libraries

Redis 7 added Functions: scripts you register as named functions in a library that persists (it survives restart and replicates to replicas), rather than loading an anonymous script each run. You FUNCTION LOAD a library once and call its functions with FCALL name numkeys …. It is the modern home for logic you want to live in the database as a stable, named API — an evolution of EVALSHA from “a cached blob” to “a deployed function”.

Checkpoint

Why is a Lua script atomic, and when is that better than WATCH?

The whole script runs on the single-threaded server as one unit, so no other command interleaves — a read-modify-write inside it cannot race. It is better than a WATCH retry loop when you want no retries and no round trips between steps: the logic runs where the data is, in one atomic call. The cost is that a long script blocks all clients, so keep scripts short.

Why must key names go through KEYS?

So Redis (and especially Redis Cluster) can see which keys a script touches and route it to the node that owns them. Hard-coding a key in the script body hides it from the cluster and breaks routing. Everything that is not a key — limits, values, timestamps — goes in ARGV, decided by the client so the script stays deterministic.

What do Redis Functions add over EVALSHA?

Persistence and names. A function library is loaded once, survives restart, replicates to replicas, and exposes named functions you call with FCALL — a stable server-side API. EVALSHA calls an anonymous cached script by hash that vanishes on SCRIPT FLUSH or restart; Functions are the deployed, named evolution of that idea.

Chapter Twelve · Part VI

Modules and Redis Stack

Redis can be extended with modules that add whole new data types and query engines. Redis Stack bundles the important ones — a JSON type, a search engine, probabilistic structures, time series — turning Redis from a key-value store into a small multi-model database. This chapter runs them live.

By the end of this chapter you will be able to
  • Say what a module is and what Redis Stack bundles
  • Store and query documents with RedisJSON
  • Build a secondary index and search with RediSearch
  • Reach for Bloom filters and time series when they fit

12.1 Modules and the Stack

New types, loaded into the server

A module is compiled code that adds commands and data types to Redis at load time — the same server, new capabilities. Redis Stack is the official bundle: RedisJSON (a real JSON type), RediSearch (secondary indexing and full-text search), RedisBloom (probabilistic structures), and RedisTimeSeries. It runs as the redis-stack-server image and speaks the same protocol, so everything you have learned still applies — there are simply more commands.

12.2 RedisJSON — documents as a native type

Store JSON, and update it in place

Without the module you store JSON as an opaque string — to change one field you fetch the whole document, parse it, edit, and write it all back. RedisJSON makes JSON a native type you address by path ($.price, $.tags): read or update a single field on the server, increment a number, append to an array — no fetch-modify-write round trip.

12.3 RediSearch — secondary indexes

Query Redis by value, not just by key

Plain Redis finds data by key. To find “all books under $14” or “books mentioning Dune” you would keep your own index by hand (sorted sets and sets, Chapter 1). RediSearch does it for you: define an index over your JSON or hash keys, and it maintains an inverted index so you can run full-text and numeric queries with FT.SEARCH — a secondary index engine inside Redis.

12.4 Probabilistic and time-series

Two more specialised types

RedisBloom adds a Bloom filter — “have I seen this before?” in tiny memory, with no false negatives and a tunable false-positive rate (deduplication, “already emailed?” checks). RedisTimeSeries adds a first-class time series with retention, downsampling, and range queries (metrics, sensor data). Both could be approximated with core structures, but the modules do it correctly and efficiently.

When to add a module

Reach for the Stack when you are reimplementing one of these on top of core Redis — hand-rolling a JSON fetch-modify-write, maintaining your own search indexes, faking a Bloom filter with a set. If core structures already model your problem cleanly (Chapters 1–3), stay with them; a module is worth its operational weight only when it removes real complexity you would otherwise own.

Checkpoint

What is Redis Stack, and how does it relate to plain Redis?

The same Redis server with official modules pre-loaded: RedisJSON, RediSearch, RedisBloom, RedisTimeSeries. Each adds a command namespace (JSON.*, FT.*, BF.*, TS.*) and, in some cases, a new data type. The protocol and every core command are unchanged — Stack is additive, turning Redis into a small multi-model database.

What does RedisJSON give you over storing JSON as a string?

Path-addressable, in-place updates. A JSON string is opaque — changing one field means fetch, parse, edit, and write the whole document back. RedisJSON makes JSON a native type: JSON.NUMINCRBY $.price or JSON.ARRAPPEND $.tags updates one field on the server, no fetch-modify-write round trip.

What problem does RediSearch solve?

Querying by value instead of by key. Plain Redis finds data only by key, so value queries mean maintaining your own indexes by hand. RediSearch defines an index over JSON or hash keys and maintains an inverted index automatically, so FT.SEARCH can run full-text and numeric-range queries — a secondary-index engine inside Redis.

Chapter Thirteen · Part VI

Observability and Diagnostics

When Redis misbehaves, it tells you exactly what is wrong — if you know where to look. This chapter reads the server’s vital signs with INFO, judges memory health, tracks the cache-effectiveness metric that matters most, and diagnoses a live latency problem.

By the end of this chapter you will be able to
  • Read a server’s vital signs with INFO
  • Judge memory use, peak, and fragmentation
  • Compute the cache hit rate and watch evictions
  • Diagnose latency with the slow log and latency monitor

13.1 INFO — the vital signs

One command, the whole health picture

INFO returns the server’s complete state, grouped into sections — server, clients, memory, persistence, stats, replication, keyspace. Ask for one section by name to keep it readable. It is the first thing to run on any Redis you are responsible for: version, uptime, connected clients, memory, and how many keys live in each database.

13.2 Memory health

Used, peak, and fragmentation

Redis lives in RAM, so memory is the resource to watch. used_memory is what it holds now; used_memory_peak is the high-water mark (memory Redis grabbed and may still hold); mem_fragmentation_ratio compares memory the OS gave Redis to memory Redis asked for — well above 1.0 means fragmentation is wasting RAM, below 1.0 means Redis is swapping (a serious problem). MEMORY USAGE key reports the bytes a single key costs.

13.3 The metric that matters: hit rate

Is the cache actually helping?

For a cache, one number decides whether it is worth having: the hit rate. keyspace_hits and keyspace_misses in INFO stats count lookups that found a key versus those that did not; the hit rate is hits / (hits + misses). A healthy cache sits well above 90%. A low rate means your TTLs are too short, your keys are wrong, or you are caching the wrong things — the cache is doing work without saving any.

13.4 Diagnosing a live problem

Slow log, latency monitor, and MONITOR

When latency spikes, three tools find the cause. The slow log (Chapter 7) names commands that took too long. The latency monitor tracks spikes across the server and explains them: enable it with a threshold, then LATENCY LATEST and LATENCY DOCTOR report and interpret events. And MONITOR streams every command the server runs, live — invaluable for “what is actually hitting this server?”, but it slows the server measurably, so use it briefly and never leave it running.

MONITOR is a loaded gun

Never leave MONITOR running

MONITOR makes the server send you a copy of every command it processes. It is the fastest way to see live traffic when debugging — and it can cut throughput by half while connected, because the single thread now also serialises every command to your stream. Run it for a few seconds to observe, then disconnect. It is a debugging tool, never a monitoring one; for continuous metrics, scrape INFO instead.

Chapter Fourteen · Part VII

Distributed Caching Strategies

The reason most teams adopt Redis: a cache in front of a slower database. This chapter covers the patterns that make caching correct — lazy loading, the write strategies, and the two genuinely hard problems, stampedes and invalidation — with the Redis mechanics run for real.

By the end of this chapter you will be able to
  • Implement the cache-aside (lazy-loading) pattern
  • Choose between write-through and write-behind
  • Prevent a cache stampede on a hot key
  • Reason about invalidation — the hard part

14.1 Cache-aside — the default pattern

Check the cache; on a miss, load and populate

Cache-aside (lazy loading) is how most caching works. On a read: look in Redis; if the value is there (a hit), return it; if not (a miss), load it from the database, write it into Redis with a TTL, and return it. The cache fills on demand with exactly the data that is actually read, and the TTL bounds how stale a value can get. The application owns the logic — Redis just stores and expires.

The TTL is the consistency knob

Cache-aside data can be stale for up to its TTL — the window between the database changing and the cached copy expiring. A short TTL means fresher data but more database load (more misses); a long TTL means less load but staler reads. The TTL is where you set that trade-off, per kind of data: seconds for a fast-moving count, hours for a rarely-changing profile.

14.2 Write strategies

PatternOn a writeTrade-off
Cache-asideWrite DB; delete/expire the cache keySimple; next read repopulates
Write-throughWrite DB and cache togetherCache always warm; slower writes
Write-behindWrite cache; flush to DB laterFast writes; risk on crash

Table 14.1 How a write keeps the cache correct. Cache-aside on write usually deletes the key (not updates it), so the next read reloads fresh from the database — simpler and less error-prone than trying to keep the cached copy in sync. Write-through keeps the cache always populated at the cost of write latency. Write-behind is fastest but can lose data if Redis dies before the flush — use it only where some loss is acceptable.

Prefer delete over update on write

When the underlying data changes, delete the cache key rather than writing the new value into it. A delete is idempotent and cannot leave a subtly-wrong value; the next reader takes one miss and repopulates correctly. Trying to update the cached copy in lockstep with the database invites the two from drifting — the classic source of “the cache says something the database does not”.

14.3 The stampede problem

When a hot key expires, everyone misses at once

A popular key expires. In the same millisecond, a thousand requests all miss, all query the database, and all try to repopulate — the database is hit by a thousand identical queries at once. This is a cache stampede (or thundering herd), and it can take down the very database the cache was protecting. Two defences: a short lock so only one request rebuilds while others wait, and TTL jitter so keys do not all expire together.

Jitter the TTLs

The other half of the fix: never give a batch of keys the same TTL. If you cache a thousand items for exactly 3600 s, they all expire in the same second an hour later — a synchronised stampede. Add a random spread — 3600 + rand(0, 300) — so expirations scatter across five minutes instead of landing together. A little randomness turns a cliff into a gentle slope.

14.4 Invalidation, the hard part

“There are only two hard things…”

Bound staleness, or invalidate on change

Keeping a cache consistent with its source is one of computing’s genuinely hard problems, and there is no perfect answer — only two strategies. TTL-based: accept staleness up to the TTL, and let keys expire; simplest, and right for most data. Event-based: when the source changes, actively delete the affected keys — via your write path, or by subscribing to database changes (keyspace notifications, Chapter 10, or your database’s change stream). Most systems combine them: a modest TTL as a backstop, plus explicit deletion on the changes you know about. The goal is not perfect freshness — it is bounded, understood staleness.

When a hot key expires and many requests miss simultaneously, all hammering the database with the same query at once. Prevent it two ways: a short SET NX EX lock so only one request rebuilds while others wait and retry, and TTL jitter (a random spread on expiries) so keys do not all expire in the same instant.

Chapter Fifteen · Part VII

Operational Excellence

Running Redis well in production is a discipline: change configuration safely, know and control who is connected, respect the single thread under load, and plan capacity before you hit the wall. This final chapter is the operator’s toolkit and the habits that keep Redis boring — which, for infrastructure, is the highest praise.

By the end of this chapter you will be able to
  • Change configuration live and make it persist
  • Inspect and manage client connections
  • Avoid the commands that block the single thread
  • Plan capacity and run safe upgrades

15.1 Configuration, safely

Change live, then persist

CONFIG GET and CONFIG SET read and change most settings without a restart — invaluable for tuning under load. But a live CONFIG SET is lost on restart unless you also write it to the config file: CONFIG REWRITE rewrites redis.conf with the current running values. The safe workflow is: change live, verify it helps, then CONFIG REWRITE (or edit the file) so it survives a restart.

15.2 Managing connections

Name them, list them, and kill the bad ones

Every connection is a client Redis tracks. CLIENT SETNAME labels a connection so it is identifiable in CLIENT LIST — do this in your app so a runaway connection is traceable to a service. CLIENT LIST shows every connection with its address, age, and last command; CLIENT KILL disconnects one by id or address — your emergency handle on a client running amok or holding a connection it should have released.

15.3 Respecting the single thread

The commands that can freeze production

Know the O(n) commands, and their safe forms

Chapter 0’s rule comes due in production: one slow command blocks every client. The offenders are the O(n) commands run over large collections. Know each one’s safe alternative:

DangerousWhyUse instead
KEYS *Scans the whole keyspace, blockingSCAN (cursor)
SMEMBERS on a huge setReturns everything at onceSSCAN
HGETALL on a huge hashSameHSCAN
DEL bigkeyFrees millions of elements, blockingUNLINK (async free)
FLUSHALLSynchronous by defaultFLUSHALL ASYNC

Table 15.1 Each dangerous command has a non-blocking form. The SCAN family iterates in small batches (Chapter 2); UNLINK deletes a large key by reclaiming its memory in a background thread instead of on the main one; the ASYNC flag does the same for flushes. Ban the left column from production code and reach for the right.

Big keys are a latency time-bomb

A single key holding millions of elements — a list that grew unbounded, a set of every user id — is dangerous even to delete, because freeing it blocks the thread. Find them before they bite: redis-cli --bigkeys samples the keyspace and reports the largest key of each type. Cap collections, or shard them across keys, so no single key becomes the thing that stalls the server.

15.4 Capacity and upgrades

Plan the ceiling; upgrade without downtime

Two operational habits close the book. Capacity: Redis is bounded by RAM, so track used_memory against your ceiling (Chapter 13) and set maxmemory with room to spare — running out of memory with noeviction means writes start failing. Size for peak plus headroom for the fork a snapshot needs. Upgrades: with replication (Chapter 5) you upgrade without downtime — upgrade a replica, fail over to it, then upgrade the old master. A single instance cannot be upgraded without a restart, which is one more reason production Redis is never a single instance.

The operator’s checklist

① Set maxmemory and an eviction policy suited to the role (Ch 2). ② Enable persistence appropriate to your loss tolerance (Ch 4). ③ Run with replication and Sentinel or Cluster — never a lone instance (Ch 5–6). ④ Authenticate and scope with ACLs; close the network (Ch 8). ⑤ Name connections and ban O(n) commands from app code (this chapter). ⑥ Scrape INFO for memory, hit rate, and evictions; alert on them (Ch 13). ⑦ Back up, and test the restore (Ch 4). Do these seven and Redis will be the most reliable part of your stack.

Checkpoint

How do you change a setting live and keep it after a restart?

CONFIG SET changes most settings instantly with no restart; the change is lost on restart unless you persist it with CONFIG REWRITE (which rewrites redis.conf with the running values) or by editing the file. The safe order is: change live, verify it helps, then persist.

Name three O(n) commands and their safe forms.

KEYS * → SCAN; SMEMBERS/HGETALL on huge collections → SSCAN/HSCAN; DEL bigkey → UNLINK (frees memory in a background thread); FLUSHALL → FLUSHALL ASYNC. Each avoids blocking the single thread, which would otherwise freeze every client for the command’s duration.

How does replication let you upgrade without downtime?

Upgrade a replica to the new version, fail over so it becomes master (clients following Sentinel move with it, Chapter 5), then upgrade the former master, now a replica. A single instance cannot be upgraded without a restart and its downtime — which is one more reason production Redis always runs replicated.
