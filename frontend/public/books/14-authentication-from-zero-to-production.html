About this book

Authentication is the one part of an application where a motivated adversary is guaranteed. That changes how it should be taught: not as a list of best practices to adopt on trust, but as a set of attacks you can watch succeed, and defences you can watch stop them.

So this book runs both halves. The CSRF chapter transfers real money from a cross-origin request and shows the 200 OK, then adds a token and shows the 403. The access-control chapter reads another user’s invoice by changing one digit in a URL, with a valid session and the correct role — the vulnerability class that tops the OWASP list — and then closes it with three lines. The refresh-token chapter steals a token and watches the whole family get revoked. Every number is measured: bcrypt cost 12 is 201 ms on this machine, a naive secret comparison leaks a 370× timing difference, a fixed-window limiter lets ten requests through a five-per-second limit.

The tools are current: bcrypt 6, jsonwebtoken 9 (which, pleasingly, now blocks the algorithm-confusion attack by default — Chapter 3 verifies it and explains why you should still pin), Auth.js v5, and otplib 13. Chapter 8 derives a TOTP code by hand and matches the library digit for digit.

Who should read this

Developers who are about to build, inherit, or review an authentication system. You should know Node and HTTP (Volume 7). Chapters 4, 10, and 11 reach for Redis (Volume 12) as the shared store; Chapter 6 assumes the Next.js of Volume 5; Volume 13 §5 applies the same handshake ideas to WebSockets.

How this book is organised

Chapters map one-to-one onto the twelve modules of the Authentication track in Code Lab, each ending with that module’s ten graded exercises. Read 0–4 in order: they are cumulative. After that, 5–6 (delegated identity), 7–8 (permissions and factors), 9–10 (attacks on the session), and 11 assembles everything into one server.

The distinction the whole book turns on

Authentication asks who are you and runs once. Authorisation asks may you do this, to this and runs on every request. Most real breaches are the second kind — a perfectly valid session reading data it was never entitled to (Chapter 7). Keep them separate in your head and in your code.

Chapter Zero · Orientation

What Authentication Actually Is

Two words that get confused constantly — authentication (who are you) and authorisation (what may you do) — and the threat model that shapes every decision after. This chapter is short on code and long on the reasoning you need before writing any.

By the end of this chapter you will be able to
  • Separate authentication from authorisation
  • Name the attacks every auth system must survive
  • Explain why you never store a password
  • Choose between sessions and tokens deliberately

0.1 Two different questions

AuthN and AuthZ

Authentication answers who is this? — a login, a token, a fingerprint. Authorisation answers may they do this? — an admin check, a resource owner check. They are separate systems with separate failure modes: a broken authN lets a stranger in as you; a broken authZ lets a legitimate user read someone else’s data. Most real breaches are authZ bugs — the login worked perfectly, and then nobody checked whether user 7 was allowed to open invoice 4,412.

0.3 You never store a password

Store proof of knowledge, not the secret

The single most important rule, and the reason Chapter 1 comes first: a password database must be useless to whoever steals it. So you never store the password — you store a one-way hash of it, computed with a function deliberately made slow and salted uniquely per user. At login you hash the attempt and compare hashes. You cannot recover the original, which is also why real systems reset passwords rather than email them.

0.4 Sessions or tokens?

The choice everything else follows from

After a successful login you need to remember the user across requests, because HTTP itself remembers nothing. Two families: a session (the server stores state, the client holds an opaque id in a cookie) or a token (the server stores nothing, the client holds a signed claim it presents each time). Neither is “more secure” — they fail differently, and the honest choice depends on whether you can afford server state and how fast you need revocation.

Sessions (Ch 2)JWTs (Ch 3)
State livesOn the serverIn the token itself
RevocationInstant — delete the recordHard — valid until it expires (Ch 4)
Scales byShared store (Redis)Nothing to share
Carried inA cookie, automaticallyA header, or a cookie
Natural fitServer-rendered apps, one domainAPIs, mobile, multiple services
Main hazardSession fixation, hijack (Ch 2, 9)Cannot un-issue; leakage (Ch 3, 4)

Table 0.3 The defining asymmetry is revocation. Deleting a session logs someone out instantly; a signed JWT is valid until it expires no matter what you do — which is why Chapter 4 exists, and why short-lived access tokens plus rotating refresh tokens is the pattern that makes JWTs safe in practice.

The default recommendation

If you are not sure, use sessions

For a single web application on one domain, a session in a cookie is simpler, revocable instantly, and immune to the token-storage problem (Chapter 3, §3.4). Reach for JWTs when you genuinely need statelessness across services or a mobile client — and then commit to the full machinery: short expiry, refresh rotation, reuse detection. The failure mode of “JWT because it is modern” is a fifteen-day access token in localStorage that cannot be revoked, which is strictly worse than a cookie.

Checkpoint

Why are most breaches authorisation bugs rather than authentication bugs?

Because authentication runs once and is usually a library call, while authorisation runs on every request and is written by hand, per endpoint. The login can be flawless while some route forgets to check whether this user owns that resource — a legitimate session reading someone else’s data. Identify in middleware, authorise per action.

Why is a fast hash like SHA-256 wrong for passwords?

Because speed helps the attacker. With your stolen database, a GPU computes billions of SHA-256 candidates per second; bcrypt at cost 12 took hundreds of milliseconds for one, making mass guessing infeasible. bcrypt also salts each hash uniquely, so identical passwords produce different hashes and cracking one reveals nothing about the rest.

What is the fundamental trade-off between sessions and JWTs?

Revocation versus statelessness. A session is server state, so deleting it logs the user out instantly; a JWT carries its own claims, so it stays valid until expiry regardless of what the server wants — you cannot un-issue it. That single fact drives the whole refresh-token machinery of Chapter 4. For one app on one domain, sessions are the simpler, safer default.

Chapter One · Part I

Password Hashing

The one part of authentication you must get right even if everything else fails, because it is your last defence after a database breach. This chapter reads a bcrypt hash field by field, benchmarks the cost factor on real hardware, and shows why comparison must never be an ===.

By the end of this chapter you will be able to
  • Hash and verify passwords with bcrypt
  • Read every field inside a bcrypt hash string
  • Choose a cost factor from measurements, not folklore
  • Compare in constant time, and migrate legacy hashes

1.1 Hash, verify, and what is inside

The hash carries its own parameters

A bcrypt hash is self-describing: the algorithm, the cost, and the salt all travel inside the string. That is why bcrypt.compare needs only the password and the stored hash — it reads the salt and cost from the hash, recomputes, and compares. It is also why raising your cost factor later does not break existing users: old hashes keep verifying at their old cost.

1.2 The cost factor, measured

Cost is a time budget you set for the attacker

The cost factor is a power of two: each +1 doubles the work. You are choosing a point on a curve where your login stays acceptably fast while an attacker’s offline guessing becomes hopeless. Do not take a number from a blog post — measure on hardware like your production server, and pick the highest cost your login latency budget tolerates.

Cost in tests versus production

A test suite that hashes at cost 12 will crawl — hundreds of tests × 200 ms each. Use a low cost in tests (via config, e.g. BCRYPT_COST=4) and the real cost in production. Just make sure the value comes from configuration, not a constant someone can accidentally ship.

1.3 Comparison must be constant-time

A fast rejection is information

Comparing secrets with === leaks: string comparison returns as soon as it finds a differing byte, so a wrong-at-the-first-character guess returns faster than one that matches ten characters. Measured across many requests, that timing difference reveals the secret byte by byte. bcrypt.compare is already constant-time; for any other secret you compare — a reset token, an API key, an HMAC — use crypto.timingSafeEqual.

1.4 Login, and migrating old hashes

Argon2, and when bcrypt is not enough

bcrypt is memory-light, which lets specialised hardware parallelise attacks better than against memory-hard functions. Argon2id (the current password-hashing competition winner) adds a memory cost specifically to blunt that, and is the better choice for a greenfield system. bcrypt remains entirely respectable and is what most ecosystems have; the unforgivable choices are the fast hashes of §0.3. Whichever you pick, keep the cost parameters in configuration so you can raise them without a code change.

Checkpoint

What is stored inside a bcrypt hash string, and why does it matter?

The algorithm ($2b$), the cost factor, the 22-character salt, and the digest — all in one ~60-character string. That is why compare needs no separate salt column, and why raising the cost later does not break existing users: each old hash still carries the cost it was created with.

How do you choose a cost factor?

By measuring on hardware like production and taking the highest value your login latency budget allows — each +1 doubles the work. The measured curve here: cost 10 = 50 ms, 12 = 201 ms, 14 = 802 ms. Cost 12 is the common production choice; use a low cost in tests via configuration, and re-measure every few years as hardware improves.

Why must an unknown username still cost a hash?

Otherwise the endpoint answers unknown accounts noticeably faster than real ones, turning login into a user-enumeration oracle. The fix is dummy work — hash the supplied password anyway — plus an identical error message for “no such user” and “wrong password”. The same principle at byte level is why secrets are compared with timingSafeEqual, never ===.

Chapter Two · Part II

Sessions and Cookies

HTTP forgets you between requests. A session is the server’s memory of who you are, and a cookie is the thread the browser carries back. This chapter builds one on a real Express server, reads the actual Set-Cookie headers, and fixes session fixation by watching the id change.

By the end of this chapter you will be able to
  • Set cookies with the four flags that matter
  • Build a login that creates a server-side session
  • Defeat session fixation by regenerating the id
  • Expire sessions on both idle and absolute limits

2.1 The cookie flags

Four flags carry most of cookie security

A session cookie holds the key to an account, so how it is set matters as much as what is in it. HttpOnly hides it from JavaScript, which is what stops an XSS bug (Chapter 9) from stealing sessions. Secure forbids sending it over plain HTTP. SameSite controls whether other sites can make the browser send it — the built-in CSRF defence (Chapter 9). Max-Age/Expires bounds its life.

FlagBlocksSet it to
HttpOnlyJavaScript reading the cookie (XSS theft)Always, for auth cookies

SameSite=LaxMost cross-site sends (CSRF)The sane default
SameSite=StrictAll cross-site sendsHigh-value apps; breaks inbound links
SameSite=NoneNothing — requires SecureOnly for genuine cross-site needs
Max-AgeLiving foreverMatch your session lifetime

Table 2.1 The defaults are all wrong for auth: no flags means a cookie readable by script, sent over HTTP, and attached to cross-site requests. Set all four deliberately. Note SameSite=None is less safe than omitting the attribute and must be paired with Secure, or browsers reject it.

2.2 A session, end to end

2.3 Session fixation

The attack: giving the victim a session id you already know

How it works, and the one-line fix

If your app accepts a session id supplied by the visitor and keeps it across login, an attacker can plant a known id (via a link, a subdomain, an injected cookie), wait for the victim to log in with it, and then use that same id — now authenticated — as them. The defence is a rule: regenerate the session id at every privilege change, most importantly on login. The pre-login id becomes worthless the instant the user authenticates.

2.4 Expiry, and where sessions live

Two clocks, not one

A session needs an idle timeout (log out after N minutes of no activity — the shared-computer case) and an absolute timeout (log out N hours after login regardless of activity — bounding a stolen session’s value). A rolling cookie maxAge gives you the first; the second needs a createdAt stored in the session and checked in middleware, because a rolling cookie will otherwise renew forever.

Sessions need a shared store to scale

express-session’s default MemoryStore keeps sessions in one process’s memory: they vanish on restart, and with two instances behind a load balancer a user is logged in on one and out on the other — the same split-brain shape as Volume 13, Chapter 6. Production uses a shared store, normally Redis (Volume 12): every instance reads the same sessions, restarts are survivable, and expiry comes free from Redis TTLs. Chapter 11 wires it up.

Checkpoint

What do the four cookie flags each defend against?

HttpOnly stops JavaScript reading the cookie, so an XSS bug cannot steal the session. Secure prevents transmission over plain HTTP. SameSite (Lax by default) stops other sites causing the browser to send it, which is the built-in CSRF defence. Max-Age bounds its lifetime. All four are off or permissive by default, so each must be set deliberately.

What is session fixation, and what is the fix?

An attacker plants a session id they know on a victim; if the app keeps that id through login, the attacker’s copy becomes authenticated. The fix is req.session.regenerate() on login — the demo showed the id changing, making any planted id worthless. Regenerate at every privilege change: login, logout, role escalation, MFA completion.

Why do you need both idle and absolute session timeouts?

An idle timeout logs out an inactive user, but never fires for an active attacker holding a stolen cookie — they simply keep making requests. An absolute timeout, checked against a createdAt stored in the session, forces re-authentication a fixed time after login regardless of activity, bounding how long a stolen session is useful.

Chapter Three · Part II

JSON Web Tokens

A JWT is a signed claim the client carries: the server verifies a signature instead of looking anything up. That statelessness is its whole appeal and the source of every one of its problems — starting with the fact that a JWT is readable by anyone and cannot be un-issued.

By the end of this chapter you will be able to
  • Decode a JWT and read its three parts
  • Sign and verify, and pin the algorithm
  • Validate claims: expiry, issuer, audience, role
  • Understand the algorithm-confusion attack and its defence

3.1 Three parts, and none of them secret

Signed, not encrypted

A JWT is header.payload.signature, each base64url-encoded. The header names the algorithm; the payload holds claims; the signature proves the first two were not altered by anyone lacking the key. Critically, base64 is encoding, not encryption — anyone holding the token can read every claim in it. A JWT guarantees integrity, never confidentiality. Never put anything private in one.

3.2 Verify — and what verification actually checks

3.3 Algorithm confusion

The attack that made JWT libraries infamous

Two classic forgeries

The header names the algorithm — and a naive verifier trusts the header. Two attacks follow. alg: none: strip the signature, set the algorithm to none, and a verifier that honours the header accepts an unsigned token. RS256→HS256 confusion: with asymmetric signing, the public key is public; an attacker re-signs a forged payload with HS256 using that public key as the HMAC secret, and a verifier that reads the algorithm from the header validates it — the public key was never meant to be a signing key. The defence is one option: pin the algorithms you accept and ignore the header’s claim.

3.4 Where do you put the token?

The storage question has no clean answer

This is where JWT’s statelessness stops being free. Put the token in localStorage and any XSS bug (Chapter 9) reads it — full account takeover, and you cannot revoke it. Put it in an HttpOnly cookie and script cannot touch it, but now the browser attaches it automatically, so you need CSRF defences (Chapter 9) — and you have reinvented most of what a session cookie already gave you, minus instant revocation.

StorageXSS can steal itCSRF riskNotes
localStorageYesNoConvenient; the standard bad advice
sessionStorageYesNoSame exposure, shorter life
JS variable in memoryOnly while the page livesNoLost on refresh — pair with a refresh cookie
HttpOnly cookieNoYes — needs SameSite/tokensSafest for browsers

Table 3.1 The practical modern answer for a browser app: keep the access token in memory only, and the refresh token in an HttpOnly, Secure, SameSite cookie scoped to the refresh endpoint. XSS cannot read either persistently; a page refresh silently gets a new access token. That is Chapter 4.

The revocation problem, stated plainly

A verified JWT is valid until exp. Ban a user, change their role, or discover a stolen token, and every issued JWT keeps working — the server has nothing to delete. Every workaround reintroduces state: a short expiry (minutes, so the window is small), a denylist of revoked token ids (a lookup on every request — you have rebuilt sessions), or a per-user token version counter bumped on revocation. Choose deliberately, and keep access-token lifetimes short. This single constraint is why Chapter 4 exists.

Checkpoint

What does a JWT guarantee, and what does it not?

Integrity: the signature proves the header and payload were not altered by anyone without the key. Not confidentiality — the payload is base64, decodable by anyone holding the token, as Listing 3.1 did with no secret. Never put private data in a JWT, and remember it also cannot be un-issued before exp.

Why pass algorithms: [...] to verify?

Because the token’s own header claims its algorithm, and a verifier that trusts that claim can be fed alg: none or an HS256 token signed with the public RSA key. jsonwebtoken 9 blocks both by inferring from the key type — but pinning is one option that documents intent and protects you across libraries and versions that have not caught up.

Where should a browser app keep its tokens?

Access token in memory (a JS variable), refresh token in an HttpOnly, Secure, SameSite cookie scoped to the refresh endpoint. localStorage is readable by any XSS; an HttpOnly cookie alone is CSRF-exposed. And keep access-token lifetimes short, because a JWT cannot be revoked before it expires.

Chapter Four · Part III

Refresh Tokens and Rotation

Chapter 3 left one problem unsolved: a JWT cannot be revoked. The answer is not a longer-lived token but a shorter one — minutes — paired with a refresh token that rotates on every use, so a stolen token betrays the thief. This chapter builds that machinery and then steals a token to watch the trap close.

By the end of this chapter you will be able to
  • Split short access tokens from long refresh tokens
  • Rotate the refresh token on every renewal
  • Detect reuse and revoke an entire token family
  • Handle concurrent refreshes and global logout

4.1 Two tokens, two jobs

Short life for the one that is used constantly

The tension: an access token is sent on every request, so exposure is high — it should be short-lived. But re-entering a password every fifteen minutes is unusable. So you issue two tokens. The access token is a JWT of 5–15 minutes, sent with each API call, never stored persistently. The refresh token is long-lived (days), sent only to the refresh endpoint, stored server-side so it can be revoked, and — critically — replaced every time it is used.

Access tokenRefresh token
Lifetime5–15 minutesDays to weeks
Sent toEvery API requestOnly /refresh
StoredMemory onlyHttpOnly cookie + server-side record
Verified bySignature alone (stateless)Database lookup (stateful)
RevocableNo — wait for expiryYes, instantly
On useNothing changesReplaced with a new one

Table 4.1 The design buys back revocation without giving up stateless request handling: the hot path (every API call) stays a signature check with no lookup, while the rare path (refresh, every few minutes) does one database read and gets the ability to shut an attacker out. The worst case for a stolen access token is now minutes, not weeks.

4.2 Rotation, and why it is not optional

Every refresh invalidates the token that was used

Without rotation, a stolen refresh token works for its full lifetime and nothing indicates the theft. With rotation, each refresh returns a new refresh token and marks the old one used. Now a stolen token creates a detectable event: eventually both the thief and the real user present tokens from the same lineage, and one of them will present a token that has already been used — which cannot happen in normal operation. That single signal is the alarm.

4.3 The endpoints, on a real server

4.4 The awkward parts

Concurrent refresh is a real race

A page fires three API calls at once; all three get 401; all three try to refresh with the same token. The first rotates it, and the other two now present a used token — which your reuse detector reads as an attack and logs everyone out. Three mitigations, in order of preference: single-flight on the client (one refresh promise shared by all callers — the standard interceptor pattern); a short grace window server-side where the immediately-previous token still works for a few seconds; or accepting the logout, which users will hate. Build the client-side lock first; it removes most of the problem.

Global logout needs a version counter

Revoking one family logs out one device. To log a user out everywhere instantly — after a password change or an account compromise — store a tokenVersion on the user, embed it in the access token, and reject any token whose version is stale. Bumping the number invalidates every access token immediately, without a denylist. It costs one integer per user and the version must be read where you verify — which for the hot path means keeping it somewhere fast, i.e. Redis (Volume 12).

EventWhat you revokeHow

Table 4.2 The revocation matrix. The row people forget is the last: a password change that does not invalidate existing sessions leaves an attacker logged in after the victim has locked the door.

Checkpoint

Why two tokens instead of one long-lived JWT?

Because the token sent on every request is the most exposed, so it must be short-lived (5–15 min) — but users cannot re-authenticate that often. The refresh token bridges the gap: long-lived, sent only to /refresh, stored server-side so it is revocable. The hot path stays a stateless signature check; the rare refresh path does one lookup and restores revocation.

How does rotation turn a stolen refresh token into a detectable event?

Each refresh retires the token used and issues a successor, so presenting an already-used token is something that cannot happen in normal operation. When it does, the server treats the entire token family as compromised and revokes it — locking out the attacker, and the real user too, who must log in again. That forced re-login is the correct price for shutting out indefinite access.

What breaks with concurrent refreshes, and how do you fix it?

Several parallel requests get 401 together and all refresh with the same token; the first rotates it, the rest present a used token and trip the reuse detector, logging the user out spuriously. Fix it primarily on the client with single-flight — one shared refresh promise for all callers — optionally backed by a few-second server-side grace window for the immediately-previous token.

Chapter Five · Part III

OAuth 2.0 and OpenID Connect

“Sign in with GitHub” — a protocol for letting a user prove their identity to you without ever giving you their password. This chapter runs a complete authorisation-code flow with PKCE against a real local provider, and shows precisely which parameter defeats which attack.

By the end of this chapter you will be able to
  • Distinguish OAuth 2.0 (authorisation) from OIDC (authentication)
  • Walk the authorisation-code flow end to end
  • Generate and verify a PKCE challenge
  • Validate state, redirect URIs, and ID tokens

5.1 Delegated access, and the four parties

OAuth authorises; OIDC identifies

OAuth 2.0 was designed to let an app act on a user’s behalf at another service — “this app may read your repositories”. It answers what may this app do, not who is this person. Using an access token as proof of identity is the classic misuse. OpenID Connect is the thin layer that fixes it: same flow, plus an id_token — a JWT (Chapter 3) making verifiable claims about who the user is. If you are implementing “sign in with X”, you want OIDC.

PartyAlso calledIn “Sign in with GitHub”
Resource ownerThe userThe person clicking the button
ClientYour applicationYour web app
Authorization serverThe providerGitHub’s login + consent screens
Resource serverThe APIGitHub’s API

Table 5.1 Four roles, and one thing that never happens: the user’s password never reaches the client. They authenticate directly with the provider, which hands your app a token instead. That is the entire point of the protocol.

5.2 PKCE: proving you started the flow

The authorisation code is not enough on its own

The flow returns an authorisation code to your redirect URI, which you then exchange for tokens. If an attacker can intercept that code — a malicious app registered on the same custom URI scheme, a leaked referrer, a shared device — they can exchange it themselves. PKCE (Proof Key for Code Exchange) closes this: before starting, the client invents a random code_verifier, sends only its SHA-256 hash (code_challenge) with the authorisation request, and must present the original verifier at exchange time. A stolen code is useless without the verifier, which never left the client.

Checkpoint

What is the difference between OAuth 2.0 and OpenID Connect?

OAuth 2.0 grants an application access — what it may do on the user’s behalf — and its access token says nothing reliable about identity. OIDC adds an id_token: a JWT with verifiable claims about who the user is, plus a nonce to bind it to your request. For “sign in with X”, you need OIDC; using an OAuth access token as proof of identity is the classic misuse.

What does PKCE protect against, and how?

Interception of the authorisation code. The client keeps a random code_verifier and sends only its SHA-256 hash up front; the token exchange requires the original verifier. Since the hash is one-way and the verifier never leaves the client, a stolen code cannot be exchanged — as the demo showed, the attacker’s attempt returned invalid_grant.

Why must state be verified on return, and redirect_uri match exactly?

state ties the callback to the request you started; without checking it, an attacker can hand you their own authorisation code and silently link your user’s session to the attacker’s account (login CSRF). Prefix-matched redirect URIs let an attacker register a lookalike host or a forwarding path and receive the code — so match the full string against a registered allow-list.

Roles, Permissions, and Access Control

Authorisation — the half where most breaches actually live. This chapter builds up from role checks to permissions to ownership, and demonstrates the vulnerability that role checks alone can never catch: one legitimate user reading another’s data.

By the end of this chapter you will be able to
  • Distinguish role-based from permission-based checks
  • Model roles, permissions, and inheritance
  • Catch the broken-object-level-authorisation bug
  • Centralise policy instead of scattering if statements

7.1 Roles are a shortcut, permissions are the thing

Check what a user may do, not what they are

Scattering if (user.role === "admin") through a codebase feels natural and ages badly: the day you add an editor who may publish but not delete, you must find and edit every one of those checks. The durable model is a layer of indirection — a role is a bundle of permissions, and code checks the permission: can(user, "article:publish"). Adding a role becomes a data change, not a code change.

7.2 Hierarchies, and where they help

7.3 The bug roles cannot catch

Broken object-level authorisation

“May you do this?” is not “may you do this to that?”

Here is the most common serious vulnerability in modern web applications, and it passes every role check. A user with a perfectly valid session and the correct role requests /api/invoices/4412 — an invoice belonging to someone else. The role says they may read invoices. Nothing said which invoices. If the handler fetches by id and returns it, every customer can read every other customer’s data by changing a number in the URL.

Checkpoint

Why check permissions rather than roles in code?

Because a role name embedded in a conditional is a fact that changes: adding an editor who may publish but not delete forces edits everywhere. Checking a named permission (can(user, "article:publish")) puts the role→permission mapping in data, so new roles are a configuration change and the rules can be tested in isolation.

What is broken object-level authorisation, and why do role checks miss it?

A user with a valid session and the right role requests a resource belonging to someone else — the role permits “read invoices”, but nothing checks which invoice. The demo returned a stranger’s record with 200 by changing one digit. The fix is comparing the resource’s owner to the id from the session, and returning 404 rather than 403 so existence is not leaked.

Why should an unknown action throw instead of returning false?

Because a typo in an action name would otherwise silently deny — behaviour indistinguishable from a working check until someone reports a bug in production. Throwing makes the mistake fail loudly at development and test time. Policies as pure functions of (user, resource) also make the entire authorisation model unit-testable without HTTP.

A password can be stolen, phished, or reused from another breach. A second factor means stealing it is not enough. 8.4 Where TOTP fails, and what fixes it

TOTP is phishable — by design

The six digits do not know which site they are for

A convincing fake login page asks for the password and the TOTP code, then relays both to the real site within the 30-second window. The user is authenticated — on the attacker’s session. Nothing in the algorithm prevents this, because the code is a function of a secret and the clock, with no notion of which website is asking. Real-time phishing proxies automate exactly this.

Risk-based prompting

Asking for a second factor on every login trains users to approve reflexively, which is what makes prompt-bombing work. Step up only when risk rises: a new device or IP range, an unusual location, a sensitive action (changing the password, adding a payout account), or a session older than some threshold. The signal that matters most is new device — remember trusted devices with a long-lived, revocable cookie so routine logins stay frictionless and the prompt keeps its meaning.

Checkpoint

What actually makes authentication multi-factor?

Factors from different categories: know (password), have (authenticator, security key), are (biometric). A password plus a security question is one category twice. Within “have”, SMS is weakest — a SIM swap transfers the factor without touching your systems — while a WebAuthn security key is strongest.

How is a TOTP code computed, and what is delta?

HMAC-SHA1(shared secret, current 30-second window), dynamically truncated to six digits — computed independently on both sides, so nothing is transmitted. delta reports how many windows off a submitted code was; accepting ±1 tolerates clock drift and slow typing, while a wider window needlessly enlarges the guessing surface.

Why is TOTP phishable, and what fixes it?

Because the code is a function of a secret and the clock only — it carries no notion of which site requested it, so a proxy page can relay password and code to the real site inside the 30-second window. WebAuthn fixes it by signing a challenge bound to the origin: a signature produced for a lookalike domain is invalid at the real one.

Chapter Nine · Part V

CSRF, XSS, and Session Security

Two attacks that target the session you worked so hard to issue. CSRF makes the victim’s browser act as them; XSS runs the attacker’s code inside your page, where every defence you have already lost. This chapter demonstrates both against a real server and fixes each.

By the end of this chapter you will be able to
  • Explain why CSRF works, and stop it two ways
  • Escape output per context, not once globally
  • Set a Content-Security-Policy that means something
  • Understand why XSS defeats every token-storage scheme

9.1 CSRF: the browser is too helpful

Cookies are attached by the browser, not by your app

A cookie is sent automatically with every request to its domain — including requests initiated by other sites. So a hostile page can contain a form that POSTs to your bank, and the victim’s browser attaches their session cookie. The server sees a perfectly authenticated request. The attacker never reads the response and never needs the cookie’s value; they only need the action to happen.

9.2 Two defences, and which to use

DefenceHow it worksCaveat
SameSite=LaxBrowser withholds the cookie on cross-site POSTsBrowser-dependent; not a server-side guarantee
SameSite=StrictWithholds on all cross-site requestsBreaks inbound links into logged-in pages

A custom header alone (e.g. X-Requested-With) also helps for JSON APIs, since simple HTML forms cannot set custom headers and anything that can must pass CORS preflight.

APIs that use tokens instead of cookies are not CSRF-prone

CSRF exists because the browser attaches credentials automatically. An API that requires an Authorization: Bearer … header has no such automatic attachment — the attacker’s page would have to read the token to send it, which is XSS, not CSRF. This is a genuine advantage of header-based tokens; it comes with the storage problem of §3.4, which is the trade you are making.

9.3 XSS: their code in your page

Escaping is per context, not global

XSS is untrusted data interpreted as code. The fix is escaping the data for the specific context it lands in — HTML text, an attribute, a URL, and JavaScript each need different treatment, and applying the wrong one leaves a hole. Watch the same input handled four ways:

9.4 CSP, and the honest conclusion about tokens

XSS beats every token-storage scheme

Why §3.4 has no perfect answer

Attacker JavaScript running in your origin can read localStorage, read the DOM, and call your API with the user’s cookies attached — HttpOnly stops the cookie being read, but not used. So an XSS bug is game over for that session regardless of where the token lives; storage choice only changes whether the attacker also gets a durable copy to use later. That is why the ordering of defences matters: escape output first, add CSP second, and treat token storage as damage limitation rather than protection.

Checkpoint

Why does CSRF work, and what stops it?

The browser attaches cookies automatically to requests for a domain, including ones initiated by other sites — so a hostile page can trigger an authenticated action without ever reading the cookie. Stop it with SameSite=Lax plus a session-bound CSRF token the attacker’s origin cannot read; the demo showed the same cross-origin transfer succeeding unprotected and returning 403 protected.

Why is escaping context-dependent?

Because each context parses differently: HTML entities neutralise < in text and attributes, but a javascript: URL contains nothing HTML escaping touches (so URLs need a protocol allow-list), and data inside a <script> needs JSON.stringify. Applying HTML escaping everywhere leaves precisely the holes that remain in framework-based apps.

If a page has an XSS bug, does HttpOnly save the session?

No. HttpOnly prevents the script reading the cookie, but the script runs in your origin and can simply call your API, with the cookie attached automatically by the browser. XSS defeats every token-storage scheme; storage choice only affects whether the attacker gets a durable copy. Escaping and CSP are the real defences.

Rate Limiting and Account Protection

Hashing makes each password guess expensive; rate limiting makes having guesses expensive. This chapter implements the three limiter algorithms, shows the boundary bug that makes the simplest one leak, and builds lockout that punishes attackers without handing them a way to lock out your users.

By the end of this chapter you will be able to
  • Implement fixed-window, sliding-window, and token-bucket limiters
  • Demonstrate the fixed-window boundary burst
  • Design lockout that cannot be weaponised
  • Choose what to key a limiter on

10.1 Three algorithms

They differ in how they treat time

A fixed window counts requests per clock interval — trivial and memory-cheap, but see §10.2. A sliding window keeps timestamps and counts the last N seconds from now, which is accurate but stores more. A token bucket refills at a steady rate and lets a saved-up burst through, which matches how humans actually behave. All three are shown here against the same traffic.

KeyStopsWeakness

Rate limits belong in shared state

An in-memory counter is per-process: two instances behind a load balancer double every limit, and a restart forgives every attacker. Production limiters live in Redis (Volume 12) — atomic INCR with a TTL for a fixed window, a sorted set of timestamps for a sliding window — so all instances enforce one shared budget. Chapter 11 wires it in.

10.4 Lockout without a denial-of-service

Naive lockout hands the attacker a weapon

“Lock the account after 5 failures” locks out your users

If five wrong passwords disable an account, anyone who knows a victim’s email can disable it — permanently, on a loop, for every user you have. The attack costs five requests. So graduate the response instead of flipping a switch: an exponential delay, then a CAPTCHA, then a step-up challenge — and reserve hard lockout for a genuinely extreme threshold, with a self-service unlock that does not require your support team.

And tell the user, quietly

Rate limiting is where detection lives. A spike of failures on one account, or successes from a new country, deserves an email to the account owner and an entry in your audit log — not just a silent 429. The signal that a stuffing campaign is running against you almost always shows up in these counters first.

Checkpoint

Why prefer a sliding window over a fixed window for login?

Because a fixed window resets its counter on a clock boundary: an attacker sends the full limit at the end of one window and again at the start of the next, achieving double the intended rate — the demo pushed ten requests through a five-per-second limit. A sliding window counts backwards from now, so the boundary burst is correctly refused.

Why key a login limiter on both IP and username?

Per-IP stops one machine trying many accounts; per-username stops many machines trying one account. Credential stuffing is built to evade IP limits by spreading across a botnet, so the username key is what catches it — and neither alone is sufficient. Both must live in shared state (Redis) or multiple instances multiply every limit.

What is wrong with “lock the account after 5 failed attempts”?

It is a denial-of-service anyone can trigger: knowing a victim’s email is enough to disable their account with five requests, repeatedly. Use graduated responses instead — exponential delay, then CAPTCHA, then step-up — so guessing becomes infeasible while a legitimate user with the right password only ever waits briefly. Clear the counter on success.

11.1 The whole thing, running

11.2 Password reset, done safely

The reset flow is an authentication bypass by design

It hands account access to whoever holds a link, so it needs the same rigour as login. Five rules: the token is random and long (never derived from the user id or a timestamp); it is stored hashed, like a password, so a database leak does not yield working reset links; it is single-use and short-lived (15–60 minutes); the request endpoint always responds identically whether or not the account exists; and completing a reset invalidates every existing session.

The full checklist

① Hash with bcrypt/Argon2 at a measured cost; never store or log a password (Ch 1). ② Prefer sessions for one-domain web apps; regenerate the id on login (Ch 2, 0). ③ If tokens: short access TTL, pinned algorithms, issuer and audience checked (Ch 3). ④ Refresh tokens rotate, with family revocation on reuse and a version counter for global logout (Ch 4). ⑤ OAuth with PKCE, verified state, exactly-matched redirect URIs (Ch 5). ⑥ Authorise the object, not just the role — ownership checks on every resource fetch (Ch 7). ⑦ Offer MFA; enrol with confirmation, hash backup codes, make codes single-use (Ch 8). ⑧ HttpOnly, Secure, SameSite; escape per context; CSP with nonces (Ch 2, 9). ⑨ Rate-limit on IP and username with graduated backoff, never a weaponisable lockout (Ch 10). ⑩ Reset flows: hashed, single-use, expiring tokens that kill existing sessions (§11.2). ⑪ Log auth events, redact credentials, and alert on failure spikes.

Use the boring, maintained thing

This book exists so you can evaluate a library, not replace it

Everything here was implemented from parts so the mechanisms are visible — but in production, prefer Auth.js (Ch 6), Lucia, Passport, or your platform’s managed identity service over a hand-built stack. The value of having read this book is that you can now tell whether one of those is configured correctly: whether its cookies carry the right flags, whether its refresh tokens rotate, whether its defaults leak account existence. That judgement is the deliverable — not a bespoke auth system.

Checkpoint

Trace an authenticated request through the layers.

Rate limit (Ch 10) → verify the token’s signature, algorithm, issuer, audience, expiry (Ch 3) → check the token version against the user record for revocation (Ch 4) → check the role permits the action (Ch 7) → check the caller owns the specific object, returning 404 rather than 403 (Ch 7) → serve. Skipping any one of these is a distinct, well-known vulnerability class.

Why must a password reset invalidate existing sessions?

Because the usual reason for resetting is that someone else may hold the old password — and therefore may hold a live session. Bumping tokenVersion (or deleting the user’s sessions) ends every one of them. Also: store reset tokens hashed, make them single-use and short-lived, and return an identical response whether or not the account exists.

What is the most commonly overlooked operational risk in auth?

Logging. Debug logs that dump headers write session cookies and bearer tokens into a searchable, widely-readable, long-retained store — an accidental credential database. Redact authorization and cookie centrally at the logger. Log auth events (login failures, resets, role changes) instead, and alert on spikes.
