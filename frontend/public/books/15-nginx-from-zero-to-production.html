About this book

Most nginx knowledge circulates as configuration snippets copied between projects, understood by nobody, and carried forward for years. This book takes the opposite approach: every directive is applied to a running server and its effect measured, so you learn what nginx does rather than what a blog post claimed it does.

That means the failures are here too, deliberately. Chapter 2 sends six requests through six location blocks so the precedence order stops being a table you half-remember. Chapter 4 stops a backend container mid-listing and shows every request still returning 200. Chapter 9 demonstrates the add_header inheritance rule silently deleting two security headers — the count goes 2, 0, 2 across three locations. Chapter 12 shows a WebSocket handshake failing through a naive proxy before the five directives that fix it. Chapter 13 runs 400 requests through a rolling deploy of both backends and counts zero failures.

The numbers throughout are measurements, not estimates: a cache HIT at 0.0004 s against a 1.50 s MISS, a file throttled from 36 MB/s to 13 KB/s, ten requests through a five-per-second limit in 1.82 s with burst versus 0.10 s with nodelay.

Who should read this

Anyone who has an nginx config they did not write and do not fully trust. You should be comfortable with HTTP and a terminal. The proxy chapters assume you have an application to put behind it (Volume 7); Chapter 12 pairs with Volume 13’s Socket.IO; Chapters 5 and 11 overlap with Volume 14’s security material from the other side of the connection.

How this book is organised

Chapters map one-to-one onto the fourteen modules of the Nginx track in Code Lab, each ending with that module’s ten graded exercises. Read 0–4 in order — they are the foundation everything else assumes. After that the parts are independent: TLS and caching, rate limiting, rewriting, logging, hardening, and finally the production chapter that assembles all of it.

The habit this book is really teaching

nginx -t, then nginx -s reload — never restart. A broken config is refused and the old one keeps serving; a reload replaces workers without dropping a single connection. Everything ambitious in this book, up to and including zero-downtime deploys, rests on that one property (§0.3, §13.1).

Chapter Zero · Orientation

Config Structure and Directives

nginx is a configuration language with a web server attached. Learn how that language nests, how a request finds its way to one block, and how to change it without ever dropping a connection — and the rest of the book is vocabulary.

By the end of this chapter you will be able to
  • Read the context hierarchy: main → http → server → location
  • Distinguish simple directives from block directives
  • Test a config before applying it, and reload without downtime
  • Predict how a value is inherited into nested blocks

0.1 What nginx is for

An event loop in front of everything else

Your application server (Volume 7) is good at running your code and bad at everything else — serving files, terminating TLS, absorbing slow clients, load balancing, caching. nginx sits in front and does exactly those things, in C, on a small number of event-driven worker processes that handle tens of thousands of concurrent connections without a thread each. Almost every production deployment has one, and the reason is this division of labour: nginx handles the network, your app handles the logic.

JobWhy not the app serverChapter
Serving static filesNode reads and streams; nginx uses sendfile to the kernel1
TLS terminationOne place to hold certificates and renew them5
Load balancingYour app should not know its siblings exist4
Slow-client bufferingA slow reader ties up a Node handler; nginx absorbs it3
CachingAnswer without waking the app at all6
Rate limitingReject floods before they reach your code7

Table 0.1 Everything in the middle column is work your application would otherwise do badly. The pattern for the whole book: let nginx handle the connection, and hand your app only real, complete, fast requests.

0.2 Contexts nest, and so does meaning

Four levels, each inheriting from the last

A config is a tree of contexts. The outermost (main) has no braces; events and http sit inside it; server blocks live in http; location blocks live in server. A directive is legal only in certain contexts, and — crucially — most directives are inherited downward unless the inner context overrides them. Almost every “why is this setting ignored?” question is a context question.

Where the config actually lives

Distributions split it up: /etc/nginx/nginx.conf holds the main and http contexts and ends with an include /etc/nginx/conf.d/*.conf;, so your site files drop into conf.d/ containing just the server block. Debian and Ubuntu add sites-available/ plus symlinks in sites-enabled/. Every config in this book is a file in conf.d/, loaded by the real nginx that produced the output below.

0.3 Test, then reload — never restart

A reload keeps every open connection alive

nginx -t parses the config and reports errors without applying it. nginx -s reload then tells the master process to start new workers with the new config and retire the old ones gracefully — in-flight requests finish on the old workers, new requests go to the new ones, and nothing is dropped. A restart kills the master and every connection with it. Always test, then reload; never restart a serving nginx.

What a broken config actually does

Here is the reassuring part, and the reason nginx -t is a habit rather than a ceremony: if you reload a broken config, nginx refuses to apply it and keeps running the old one. You get an error on stderr and a still-serving server. The dangerous command is restart, which stops first and then discovers your typo — leaving you with nothing running at all.

0.4 Variables, and the two-phase mindset

nginx evaluates per request, not once at startup

Values like $uri, $host, $remote_addr, and $request_method are computed per request. A config is therefore not a static description but a small program run against every request — which is why location matching (Chapter 2) has an order, why if is famously dangerous inside location, and why try_files exists instead of conditionals. Write configs declaratively and let nginx’s phases do the work.

Checkpoint

What are the four contexts, and why does nesting matter?

main (no braces) → events and http → server → location. Directives are legal only in certain contexts and are inherited downward until an inner context overrides them — by replacement, not merging. Most “my setting is ignored” problems are a directive placed in the wrong context, or an inner block silently replacing an outer value.

Why reload rather than restart?

A reload starts new workers with the new config and lets old workers finish their in-flight requests, so no connection is dropped. A restart stops the master — and every connection — first. And if the new config is broken, a reload is refused and the old config keeps serving; a restart discovers the typo after it has already stopped serving.

What does nginx -t check, and what can still fail after it passes?

It parses the configuration and reports syntax errors with the exact file and line, without applying anything. It does not guarantee the config will load: a missing certificate file, an unreadable root, or an upstream hostname that does not resolve can still fail at reload time — which is why the output says both “syntax is ok” and “test is successful” as separate statements.

1.1 root: URL path appended to a directory

1.2 alias: replace the matched prefix instead

The one that trips everybody

root appends the URI; alias replaces the matched location prefix. So with location /static/, a root /var/www looks for /var/www/static/… while an alias /var/www/ looks for /var/www/…. Get them backwards and you get 404s with a puzzling path in the error log. Watch both against the same directory:

1.3 Custom error pages

1.4 Cache headers: the fastest request is the one never made

Fingerprinted assets can be cached forever

Static files split into two kinds. Fingerprinted assets (app.4f9a2c.js) never change under that name, so they can be cached for a year — the browser will not even ask. Unfingerprinted files (index.html) must be revalidated, or a deploy leaves users on the old version indefinitely. Set both deliberately:

sendfile, and why nginx is fast at this

With sendfile on (the default in most packaged configs), nginx tells the kernel to copy the file straight from the page cache to the socket — the bytes never enter nginx’s own memory, and there is no per-file thread. That is the entire reason a static file is cheaper from nginx than from your application server, and it is why the advice in Chapter 0 stands: give nginx the files, give your app the logic.

Checkpoint

What is the difference between root and alias?

root appends the full request URI to the directory; alias replaces the matched location prefix with the directory. With location /cdn/, root /var/www looks for /var/www/cdn/… while alias /var/www/assets/ looks for /var/www/assets/…. Use root at server level for the site; reach for alias only when a URL prefix maps somewhere that does not mirror it.

Why mark a custom error page internal?

So it can be served as an error page but not requested directly — a bare /404.html returns 404 rather than 200. That keeps a stray URL from returning “page not found” with a success status, which would confuse crawlers and monitoring. error_page preserves the original status code unless you explicitly override it with =200.

How should HTML and fingerprinted assets be cached differently?

HTML gets no-cache so it is revalidated every time and a deploy takes effect immediately — the cheap ETag round trip usually returns 304 with no body. Fingerprinted assets (app.4f9a2c.js) get max-age=31536000, immutable, so the browser never asks again; a new build produces a new filename, which is what makes that safe.

Chapter Two · Part I

Location Matching and try_files

Which location block handles a request is decided by a precedence order that is not the order you wrote them in. This chapter runs every modifier against the same request so you can watch the winner emerge, then builds the SPA fallback that try_files exists for.

By the end of this chapter you will be able to
  • Rank the four location modifiers by precedence
  • Predict which block wins for a given URI
  • Use try_files for fallbacks instead of if
  • Serve a single-page app without breaking deep links

2.1 The precedence order

Not top to bottom

nginx picks one location per request, by this algorithm: first it scans all prefix locations and remembers the longest match; if that match used ^~, it stops there. Otherwise it tries the regex locations in file order and takes the first that matches. If no regex matches, the remembered longest prefix wins. An exact match (=) short-circuits everything immediately.

ModifierMeaningPrecedence
= /pathExact match1 — wins instantly
^~ /pathPrefix; skip regexes if longest2
~ regexCase-sensitive regex3 — first match in file order
~* regexCase-insensitive regex3 — same tier
/pathPlain prefix4 — longest wins, only if no regex matched

Table 2.1 Two consequences worth memorising. Regex blocks beat plain prefix blocks regardless of length — a two-character regex can steal a request from a long, specific prefix. And among regexes, file order decides, which is the one place where where-you-wrote-it matters.

2.2 try_files: the declarative fallback

An ordered list, ending in a definite answer

try_files takes a list of paths and tries each in turn, serving the first that exists. The last argument is special: it is either a status code (=404) or a URI that nginx internally redirects to. This replaces the conditional logic people reach for if to write — and if inside a location is genuinely dangerous (§2.4), so try_files is not just tidier, it is the supported way.

2.3 The SPA fallback

Deep links must reach the client-side router

A single-page app has one real HTML file and dozens of client-side routes. Request /app/settings directly — a bookmark, a refresh, a shared link — and there is no such file, so a naive config returns 404 before your router ever loads. The fix is one try_files: serve the file if it exists, otherwise hand back the shell and let the browser route.

2.4 Why not if

“If is evil” — and specifically why

if inside a location is a rewrite-phase trap

The nginx wiki page is literally titled IfIsEvil. Inside a location, if belongs to the rewrite module and runs during a specific phase, so only return and rewrite behave predictably in it. Directives like add_header, proxy_pass, or try_files inside an if produce results that surprise even experienced people — and two if blocks in one location can silently discard each other’s effects.

Instead of if…Use
Checking whether a file existstry_files
Choosing by URIA more specific location
Choosing by hostnameA separate server block
Choosing by a variable’s valuemap (§8.3)
Redirectingreturn 301 in its own location
Setting a header conditionallymap into the header value

Table 2.2 Every common use of if has a declarative replacement that runs in the right phase. The two safe uses that remain: if at server level, and if (…) { return … ; } — a bare return, nothing else. When you find yourself wanting more, reach for map.

Checkpoint

Rank the location modifiers, and name the counter-intuitive rule.

= exact wins instantly; then ^~ prefix (which suppresses regex evaluation); then regexes ~/~* in file order; then the longest plain prefix. The counter-intuitive part: a regex beats a plain prefix regardless of specificity, so a short regex can steal requests from a long prefix — which is exactly what ^~ exists to prevent.

What is special about the last argument of try_files?

It is the definite answer when nothing else matched: either a status code (=404) or a URI that nginx internally redirects to, restarting request processing so the fallback is served with a 200. Everything before it is a path to test for existence, in order.

Why must the SPA fallback exclude asset paths?

Otherwise a missing .js or .css returns index.html with a 200, and the browser tries to parse HTML as JavaScript — the classic “Unexpected token <”. Assets get try_files $uri =404 so a miss is a real 404; only application routes fall back to the shell.

Chapter Three · Part II

Reverse Proxy Fundamentals

Putting nginx in front of your application. The trailing-slash rule that decides what path your app receives, the four headers it must set or your app will lie about itself, and the timeouts and buffering that protect your backend from slow clients.

By the end of this chapter you will be able to
  • Predict the upstream path from proxy_pass and the location
  • Forward the client’s identity with the standard headers
  • Tune connect, send, and read timeouts
  • Explain what proxy buffering protects you from

3.1 The trailing slash changes everything

With a slash, the location prefix is stripped

The single most consequential character in an nginx config. If proxy_pass ends with a URI part (even just /), nginx replaces the matched location prefix with it. Without one, nginx passes the full original URI unchanged. Same location, same backend, completely different path arriving at your app:

3.2 The headers your app needs

Behind a proxy, your app sees nginx — not the client

Without extra headers, the backend’s idea of the request is wrong in four ways: the Host is the upstream name, the client IP is nginx’s, and the scheme looks like http even when the user arrived over HTTPS. That breaks absolute URL generation, redirects, rate limiting by IP, geolocation, and audit logs. Four headers fix it — and here is the same request with and without them:

Trust the header only from a proxy you control

X-Forwarded-For is client-supplied unless you overwrite it

Anyone can send X-Forwarded-For: 1.2.3.4. If your app trusts it blindly, an attacker forges their IP to bypass rate limits or IP allow-lists. The rule: your edge nginx must overwrite the header (as $remote_addr, or via real_ip_header with set_real_ip_from naming trusted proxy ranges), and your application must trust it only when the connection came from that proxy.

3.3 Timeouts: never wait forever

StatusMeaningUsual cause
502 Bad GatewayCould not reach or got garbage from upstreamApp crashed, wrong port, refused connection
504 Gateway TimeoutUpstream too slowLong query, deadlock, timeout set too low
499Client closed the connection firstUser navigated away; often a slow backend too

Table 3.1 The three proxy statuses you will meet in production logs. 499 is nginx-specific and worth knowing: a burst of them means users are giving up before your app answers.

3.4 Buffering: the slow-client shield

nginx absorbs the client so your app does not have to

With proxy_buffering on (the default), nginx reads the backend’s response as fast as the backend can produce it, stores it, releases the backend, and then drips it out to a slow client at whatever speed the client manages. Your application handler is freed in milliseconds instead of being held for the seconds a phone on a bad connection needs. This is one of the largest practical benefits of putting nginx in front of an app server, and it is on by default.

The other end: client body buffering

client_max_body_size (default just 1 MB) caps uploads — the cause of the mysterious 413 Request Entity Too Large that appears the first time someone uploads a photo. Set it per location to what that endpoint genuinely accepts; do not raise it globally, because a large global limit lets any endpoint absorb large bodies.

Checkpoint

How does the trailing slash on proxy_pass change the upstream path?

With a URI part (even a bare /), nginx replaces the matched location prefix — /api/users reaches the backend as /users. Without one, the full original URI is passed unchanged: /raw/users arrives as /raw/users. It is a one-character difference and the usual cause of a freshly-proxied app 404-ing on every route.

Which headers must a proxy set, and why?

Host (so the app sees the name the client used, not the upstream’s), X-Real-IP and X-Forwarded-For (the client’s address, for logging, rate limiting, geolocation), and X-Forwarded-Proto (so the app knows the user arrived over HTTPS). Without them the app generates wrong links and attributes every request to nginx’s own address. The edge must overwrite these, since clients can forge them.

What is the difference between a 502 and a 504?

502 Bad Gateway: nginx could not reach the upstream or got an invalid response — a crashed app, wrong port, refused connection. 504 Gateway Timeout: nginx reached it but the response did not arrive within proxy_read_timeout — a slow query or a timeout set too low. 502 is a connectivity problem, 504 a latency problem.

Chapter Four · Part II

Load Balancing with Upstreams

One backend becomes several. This chapter distributes requests across two real app containers, weights them, pins a client to one server, and then kills a backend mid-traffic to watch nginx route around the failure automatically.

By the end of this chapter you will be able to
  • Define an upstream pool and distribute requests
  • Choose between round-robin, least_conn, and ip_hash
  • Weight servers of unequal capacity
  • Watch passive health checks remove a dead backend

4.1 An upstream is a named pool

Balancing state is per worker process

A detail that confuses people benchmarking a load balancer for the first time: each nginx worker process keeps its own round-robin cursor and its own connection counts. With worker_processes auto on a 14-core machine you have fourteen independent balancers, each starting at the first server — so a handful of sequential curl requests can look badly skewed even though the config is perfect. Over real traffic volumes it evens out. If you need to see the distribution while learning (as this lab does), set worker_processes 1; if you need genuinely global balancing decisions, that is what a dedicated load balancer or nginx Plus’s shared zones provide.

4.2 Choosing a distribution method

MethodSends the request toUse when
round-robin (default)The next server in turnRequests cost roughly the same
least_connThe server with fewest active connectionsRequest durations vary a lot
ip_hashA server chosen by hashing the client IPYou need sticky sessions
hash $keyA server chosen by hashing any variableCache affinity, sharding by user
random two least_connBest of two random picksLarge pools; avoids herd effects

Table 4.1 Round-robin is right far more often than people expect. Reach for least_conn when some requests take a second and others take a millisecond, since counting requests then misrepresents load. ip_hash is a workaround for state that should not be on the server — prefer a shared session store (Volume 12) and keep your backends stateless.

4.3 Failover, demonstrated by killing a backend

Passive health checks are on by default

Open-source nginx does not poll your backends. Instead it watches real traffic: if a server fails max_fails times within fail_timeout, it is marked down and skipped for the rest of that window, then quietly retried. Combined with proxy_next_upstream, a request that hits a dying server is retried on a healthy one before the client ever learns anything went wrong.

Retry only idempotent requests

proxy_next_upstream defaults to retrying on error and timeout, and by default it will not retry non-idempotent methods after the request has been sent — because retrying a POST that already reached a backend can charge a card twice. Adding non_idempotent to the list overrides that, and you should only do so if your endpoints are genuinely idempotent (Volume 13’s acknowledgement discussion is the same problem, one layer up).

4.4 Keepalive to the upstream

Do not open a fresh TCP connection per request

By default nginx opens a new connection to the backend for every proxied request — a TCP handshake each time, and a pile of sockets in TIME_WAIT under load. Checkpoint

When would you choose least_conn over round-robin?

When request durations vary widely. Round-robin counts requests, which misrepresents load if some take a second and others a millisecond — a server can accumulate several slow requests while its turn keeps coming. least_conn sends work to whoever is least busy right now. ip_hash is a different axis: stickiness, needed only when backends hold per-user state they should not.

How does nginx know a backend is down without health checks?

Passively, from real traffic: max_fails failures within fail_timeout mark a server down and it is skipped for that window, then retried. Paired with proxy_next_upstream, the request that discovered the failure is retried on a healthy server, so the client sees a 200 — as the demo showed with a genuinely stopped container.

Why does keepalive need two other directives?

Because nginx proxies with HTTP/1.0 by default, which has no persistent connections, and forwards a Connection: close. You must add proxy_http_version 1.1 and proxy_set_header Connection "", or the keepalive pool has no effect at all. The count is idle connections per worker process, not a concurrency cap.

Chapter Five · Part III

TLS, HTTPS, and Certificates

Terminating TLS at the edge. This chapter serves real HTTPS from a real certificate, redirects HTTP to it, turns on HTTP/2, adds HSTS, and explains what Let’s Encrypt automates — including the renewal that must not need a restart.

By the end of this chapter you will be able to

5.1 A working HTTPS server

Two files and two directives

TLS needs a certificate chain (your certificate followed by any intermediates) and a private key. Point ssl_certificate and ssl_certificate_key at them, add ssl to the listen line, and you are serving HTTPS. The lab below uses a self-signed certificate — the only difference from a real one is that no browser trusts it, which is why curl -k appears in the requests.

5.2 Hardening the TLS layer

ssl_prefer_server_ciphers off is the current advice

Old guides set this on with a long hand-written cipher list. With TLS 1.3 the cipher suites are already few and all good, and modern clients pick correctly — including choosing ChaCha20 on phones without AES hardware, which a server-imposed order would prevent. Leave it off, keep ssl_protocols at 1.2+, and do not paste cipher strings from a blog post older than your certificate.

5.3 Let’s Encrypt, and the renewal that matters

ACME automates issuance; you automate the reload

A public certificate comes from an ACME certificate authority — usually Let’s Encrypt — which verifies you control the domain and issues a certificate valid for 90 days. Short lifetimes are deliberate: they force automation, and automation is what prevents the classic outage of a certificate quietly expiring on a Sunday. The verification is normally the HTTP-01 challenge: the CA asks for a file at /.well-known/acme-challenge/… over plain HTTP.

ChallengeProves control byUse when
HTTP-01Serving a file on port 80The default; needs public port 80
DNS-01Creating a TXT recordWildcards, or no public HTTP
TLS-ALPN-01A special TLS handshake on 443Port 80 unavailable

Table 5.1 HTTP-01 is what most setups use. DNS-01 is required for wildcard certificates (*.example.com) and is the only option for a server with no inbound HTTP — at the cost of giving your renewal automation API credentials for your DNS provider.

Checkpoint

Which two files does an HTTPS server need, and what is in each?

A certificate chain (ssl_certificate) — your certificate followed by any intermediates, so clients can build a path to a trusted root — and the private key (ssl_certificate_key), which must be readable only by root. Missing intermediates is the classic “works in my browser, fails on mobile” bug, because some clients cannot fetch them on their own.

What must the HTTP-to-HTTPS redirect preserve, and what must it not catch?

It must preserve the path and query, via $request_uri — redirecting everything to / is a common and very annoying bug. It must not catch /.well-known/acme-challenge/, which Let’s Encrypt fetches over plain HTTP; redirecting it breaks renewal, and you find out 60 days later.

Why is --deploy-hook "nginx -s reload" essential?

Because nginx loads certificates into memory at startup or reload. Certbot rewrites the files on disk, but the running nginx keeps serving the old certificate until it is reloaded — producing an expired certificate in browsers while the file on disk is perfectly valid. The deploy hook reloads on every successful renewal, and a reload drops no connections.

Caching

6.1 A cache in three directives

The zone lives in http, the switch in a location

proxy_cache_path declares where cached responses live and names a shared-memory zone for their keys — it belongs in the http context. Then proxy_cache switches that zone on for a location, and proxy_cache_valid says how long each status code stays fresh. Add $upstream_cache_status as a response header and every request tells you what happened.

6.3 What to cache, and under what key

The cache key decides correctness

The default key is $scheme$proxy_host$request_uri — note what is missing: cookies, Authorization, and Accept-Encoding. Cache a personalised page with that key and you will serve one user’s dashboard to everyone, which is the single worst bug in this chapter. So: never cache authenticated responses by default, and add anything that changes the response to the key.

6.4 Stale content is better than an error

Purging is a paid feature — design around it

Open-source nginx has no proxy_cache_purge directive (it is in nginx Plus, or the third-party ngx_cache_purge module). Practical alternatives: keep TTLs short enough that staleness is acceptable; include a version or build id in the cache key so a deploy invalidates everything at once; or delete files under the cache path directly, since the key is hashed into the filename. Plan for this before you rely on instant invalidation.

Checkpoint

Which three directives set up proxy caching, and where does each go?

proxy_cache_path in the http context (storage path, shared-memory keys_zone, size caps); proxy_cache <zone> in the location to switch it on; proxy_cache_valid to say how long each status stays fresh. Adding add_header X-Cache-Status $upstream_cache_status makes every response report MISS/HIT/EXPIRED/STALE/BYPASS.

Why must proxy_cache_bypass and proxy_no_cache be set together?

bypass means “do not serve from cache for this request”; no_cache means “do not store this response”. Setting only bypass still writes a logged-in user’s personalised page into the cache, where the next anonymous visitor receives it. The default cache key ignores cookies and Authorization entirely, which is what makes this so easy to get wrong.

What does proxy_cache_use_stale buy you?

It serves an expired cached copy when the backend errors or times out, so an outage becomes slightly-stale content with a 200 instead of a 502 — as the demo showed with the container stopped. Paired with proxy_cache_lock and background_update, only one request refreshes an expired popular entry while others are served stale, preventing a cache stampede.

Rate Limiting and Access Control

Rejecting abuse at the edge, before it reaches your application. nginx implements a leaky bucket that smooths traffic rather than counting windows — this chapter floods it for real to show what burst and nodelay actually do, then limits connections and bandwidth and locks down paths by IP.

By the end of this chapter you will be able to

7.1 The leaky bucket

nginx smooths, it does not count windows

Volume 14 §10 built fixed and sliding window limiters. nginx uses a leaky bucket instead: rate=5r/s does not mean “five per second” — it means one request every 200 ms. Requests arriving faster than that are rejected immediately with 503 unless a burst queue absorbs them. This is why the behaviour surprises people: send five requests in the same millisecond with rate=5r/s and no burst, and four are rejected.

7.4 Access control by address and password

Behind a proxy, allow sees the proxy

If another proxy or CDN sits in front of nginx, $remote_addr is its address, and an IP allow-list will either block everyone or nobody. Fix it with set_real_ip_from naming the trusted upstream ranges plus real_ip_header X-Forwarded-For, so nginx replaces $remote_addr with the true client address — and only for connections that genuinely came from those trusted proxies (Volume 14 §10.3 makes the same point about forged headers).

Checkpoint

Why does rate=5r/s not mean “five requests per second”?

Because nginx implements a leaky bucket: 5r/s is a drip rate of one request every 200 ms. Five requests in the same millisecond will see four rejected unless a burst queue absorbs them — as the demo showed, ten instant requests yielded one 200 and nine 429s, while the same requests paced 250 ms apart all succeeded.

What does nodelay change?

Whether burst-queued requests wait. Plain burst=10 accepts ten excess requests but releases them at the drip rate — the demo took about two seconds for ten. With nodelay the allowance is spent immediately and merely refills at the rate, so the same ten complete at once. For user-facing traffic nodelay is almost always right, since one page load can legitimately fire twenty requests.

When is limit_conn the right tool instead of limit_req?

When the abuse is concurrency rather than frequency — a client opening many long-lived connections (large downloads, slow reads). The request rate stays low so limit_req never fires, but the connections tie up workers. limit_conn caps simultaneous connections per key, and limit_rate/limit_rate_after cap bandwidth per connection.

Rewrites and Redirects

Changing URLs — either invisibly inside nginx, or visibly by telling the browser to go elsewhere. This chapter separates return from rewrite, gets the 301-versus-302 choice right, and introduces map, the tool that replaces almost every if you were about to write.

8.1 return: the simple, fast redirect

If you are not rewriting a pattern, use return

return ends the request immediately with a status and optional URL. It is faster than rewrite, cannot loop, and covers the majority of real cases: canonical hostnames, moved pages, retired endpoints. Reach for rewrite only when you genuinely need a regular expression.

StatusCached by clientsMethod preservedUse for
301 Moved PermanentlyAggressively, sometimes foreverMay become GETCanonical host, permanent moves

Table 8.1 The row people need and do not know: 307/308 preserve the request method and body, while 301/302 historically allow a client to turn a POST into a GET. Redirecting an API endpoint that receives POSTs with a 301 silently loses the body — use 308.

Test a 301 before you ship it

Browsers cache permanent redirects almost permanently

A wrong 301 is remembered by every browser that saw it, and no server-side change clears it — visitors must clear their cache. Ship redirects as 302 first, confirm they behave, and only then promote to 301. This single habit prevents the worst self-inflicted outage in this chapter.

8.2 rewrite: when you need a pattern

Table 8.2 last versus break is the classic confusion. last re-enters location matching — powerful, and the way to loop forever if two rewrites point at each other. break stays put, which is what you want when rewriting a path inside a location that already has the right proxy_pass.

8.3 map: the replacement for if

A lookup table evaluated lazily

map builds a variable from another variable — a declarative switch statement in the http context. It is evaluated only when the resulting variable is used, it costs a hash lookup, and it does exactly the job people misuse if for (§2.4): choosing a value based on a condition. Once you know map, most conditional configs become table lookups.

Checkpoint

When do you use return versus rewrite?

return for a fixed destination — canonical host, moved page, retired endpoint. It is faster, cannot loop, and covers most cases. rewrite only when you need a regular expression to capture part of the URL and rebuild it, e.g. ^/user/([0-9]+)$ → /profile?id=$1.

Which redirect status preserves a POST body?

307 (temporary) and 308 (permanent). 301 and 302 historically permit a client to convert a POST into a GET, silently dropping the body — which breaks API endpoints. Also: ship redirects as 302 first and promote to 301 only once verified, because browsers cache a permanent redirect almost permanently and you cannot take it back server-side.

What problem does map solve?

Choosing a value based on a condition, without if. It builds one variable from another as a lazily-evaluated lookup table in the http context — legacy-URL tables, bot detection, per-content-type cache policy. It turns conditional logic into data, so adding a case is a one-line table edit.

What does gzip_vary on prevent?

A shared cache serving a gzipped body to a client that did not ask for one. Vary: Accept-Encoding tells caches this URL has multiple representations keyed by that request header. They are all discarded. add_header directives are inherited only into blocks that define none of their own — adding a single Cache-Control in a location removes every server-level security header there, as the demo showed (2 headers → 0). Repeat them explicitly, ideally via an included snippet.

11.4 Slow attacks, and the timeouts that stop them

Slowloris: exhaustion without bandwidth

A handful of very slow connections can occupy every worker

The attack is elegant and cheap: open many connections and send headers one byte at a time, very slowly, never finishing the request. Each connection is legitimate as far as the protocol is concerned, so a server that waits patiently runs out of connection slots without ever seeing meaningful traffic. The defence is impatience — bound how long a client may take to send a request, and how many connections one address may hold.

The hardening checklist

① A default_server returning 444, so an unknown Host reaches nothing (§11.1). ② server_tokens off and no version in error pages (Ch 9). ③ Deny dotfiles, backups, and scripts in upload directories (§11.2). ④ Bound body size, header buffers, and methods (§11.3). ⑤ Short client timeouts plus limit_conn and limit_req (§11.4, Ch 7). ⑥ TLS 1.2+ with HSTS (Ch 5). ⑦ The security header set, repeated in every location that adds its own (Ch 9). ⑧ Run workers as an unprivileged user, keep nginx patched, and never expose stub_status or /admin paths without an IP allow-list (Ch 7, 10).

Checkpoint

What happens to a request whose Host matches no server block?

nginx serves it with the first block for that port — so a scanner hitting your bare IP gets whatever happens to be first, which is how staging sites get indexed. Define an explicit listen 80 default_server that return 444s: the connection is closed with no response at all, giving a scanner nothing to fingerprint.

Why is location ~ /\. one of the highest-value rules in nginx?

Because dotfiles are where secrets live. A deployed .git directory lets an attacker reconstruct your source and its history; a readable .env hands over database credentials directly. Both are probed constantly by automated scanners. Denying anything containing /. closes the whole class in three lines.

How does Slowloris work, and what stops it?

Many connections that send headers extremely slowly and never finish, occupying connection slots without bandwidth. Short client_header_timeout and client_body_timeout stop it — nginx drops a client that takes too long to send its request, as the demo showed — combined with limit_conn to cap simultaneous connections per address.

Chapter Twelve · Part VI

WebSockets and gRPC

Proxying connections that are not request/response. A WebSocket starts as HTTP and then stops being HTTP entirely — nginx will break it silently unless you tell it to forward the upgrade. This chapter proves that with a real WebSocket that fails, then works.

By the end of this chapter you will be able to
  • Forward an HTTP upgrade to a WebSocket backend
  • Explain why a naive proxy_pass fails
  • Set timeouts appropriate to long-lived connections

12.1 Why the naive proxy fails

The upgrade handshake is hop-by-hop

A WebSocket begins as a normal GET carrying Upgrade: websocket and Connection: Upgrade. Those are hop-by-hop headers — by the HTTP specification a proxy must not blindly forward them — so nginx strips them, and it proxies with HTTP/1.0 by default, which has no upgrade mechanism at all. The backend therefore never sees an upgrade request, answers with ordinary HTTP, and the client’s handshake fails with “non-101 status”. You must explicitly opt in.

The map refinement

Hard-coding Connection "upgrade" forces that value on every request through the location, including plain HTTP ones, which prevents upstream keepalive (Chapter 4). The idiomatic fix is a map — map $http_upgrade $connection_upgrade { default upgrade; "" close; } — then proxy_set_header Connection $connection_upgrade;. Upgrades get upgrade, everything else gets close, and the config serves mixed traffic correctly.

12.2 Timeouts for connections that are meant to be idle

The default read timeout will disconnect your users

proxy_read_timeout defaults to 60 seconds — measured between reads. A WebSocket that sits quietly between messages therefore gets closed after a minute of silence, which appears to users as an app that mysteriously disconnects when idle and to you as a reconnect storm in the logs (Volume 13 §8). Raise it, and add application-level pings so genuinely dead connections are still detected.

Table 12.1 Raising the read timeout is not a licence to ignore dead connections: nginx now waits an hour before noticing, so your application must send periodic pings (Socket.IO does this by default — Volume 13). The pings keep the timeout from firing on healthy idle sockets, and their absence is what reveals a dead one.

12.3 gRPC

A different protocol, a different directive

gRPC runs over HTTP/2 with its own framing and trailers, so proxy_pass is wrong — nginx has grpc_pass instead. The important detail is that gRPC requires HTTP/2 end to end, so the listen line needs http2, and a plain-HTTP downgrade anywhere breaks it.

gRPC-Web needs a translation layer

Browsers cannot speak native gRPC — they lack the necessary control over HTTP/2 framing. gRPC-Web is a different wire format that a proxy must translate. nginx cannot do that translation itself; you need Envoy, or the grpc-web proxy, in front of or beside your gRPC service. If a browser client is in your plans, decide this early — it is an architectural choice, not a configuration one.

Checkpoint

Why does a naive proxy_pass break WebSockets?

Because Upgrade and Connection are hop-by-hop headers that a proxy must not forward by default, and nginx proxies with HTTP/1.0, which has no upgrade mechanism. The backend never sees an upgrade request and answers with ordinary HTTP, so the client’s handshake fails with a non-101 status. You need proxy_http_version 1.1 plus explicit Upgrade and Connection headers.

Why raise proxy_read_timeout, and what must accompany it?

The 60-second default is measured between reads, so a quiet WebSocket is disconnected after a minute of silence — users see random disconnects, you see a reconnect storm. Raise it to an hour or more, and rely on application-level pings to detect genuinely dead connections, since nginx will now wait a long time before noticing.

What changes when proxying gRPC instead of HTTP?

Use grpc_pass (or grpcs:// for a TLS backend) with grpc_set_header and grpc_read_timeout, and enable http2 on the listener, because gRPC requires HTTP/2 end to end. Note that balancing distributes long-lived multiplexed connections rather than individual RPCs — and browsers need gRPC-Web, which nginx cannot translate on its own.

13.1 What a reload actually does

New workers start, old workers retire gracefully

On nginx -s reload the master process re-reads the configuration, starts new workers with it, and tells the old ones to stop accepting new connections. The old workers keep serving their in-flight requests and exit when finished. For a moment both generations are running — which is why a reload never drops a request, and why an in-progress 30-second download is not interrupted by a deploy.

HUPnginx -s reloadReload config; graceful worker replacement

TERMnginx -s stopFast shutdown — drops connections
USR1—Reopen log files (for rotation, Ch 10)
USR2—Start a new binary alongside the old

Table 13.1 Use quit, never stop, when taking nginx down deliberately — and make sure your service manager and container runtime do too. A Docker STOPSIGNAL of SIGQUIT turns container replacement into a graceful drain instead of a hard cut.

Checkpoint

What happens to in-flight requests during a reload?

They finish. The master keeps its PID and its listening sockets, starts new workers with the new config, and tells the old workers to stop accepting connections but complete what they are serving — the demo showed the master PID unchanged and the worker PID replaced. That is why a reload is safe on a live server and a restart is not.

What makes a rolling deploy produce zero failed requests?

Two or more backends, passive health checks (max_fails/fail_timeout), and proxy_next_upstream so a request that hits a draining server is retried on a healthy one — with only one backend taken out at a time. The chapter’s measured run restarted both containers under continuous traffic and every request returned 200.

Why must a maintenance page return 503 rather than 200?

Because 503 means “temporarily unavailable”: search engines keep your pages indexed and come back, especially with a Retry-After header. A 200 tells them the maintenance notice is your content, and they will index it in place of your site. Using a file flag also means switching it on and off needs no reload.
