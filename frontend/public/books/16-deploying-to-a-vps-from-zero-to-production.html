About this book

A managed platform hides the server from you. A VPS hands you the whole machine for a few dollars a month and expects you to know what to do with it — which is an excellent trade once you know, and an unpleasant surprise until then. This book is the path between those two states.

It is built around a running server rather than a description of one. The listings are captured from genuine SSH sessions: Chapter 1 hardens sshd and then proves it by attempting a login and reading the methods the server now advertises — (publickey,password) becomes (publickey). Chapter 3 shows a database container that the host has literally no port mapped to. Chapter 6 sends 250 requests through a proxy while both application containers are stopped and replaced, and counts zero failures. Chapter 9 takes a backup, runs DROP TABLE, restores it, and checks the row came back. Chapter 10 breaks containers deliberately to show a real exit 127 and a real oom-killed: true at exit 137.

The stack it deploys is the one most small applications actually need: Docker Compose with health-gated startup, an nginx edge terminating TLS from Let’s Encrypt, secrets in a file rather than an image, images tagged by commit SHA in a registry, and a CI pipeline whose deploy key is restricted to a single command. Nothing here requires Kubernetes, and Chapter 11 is honest about when you would actually need it.

Who should read this

Developers with an application to deploy and no operations team. You should be comfortable in a terminal and know some Docker (Volume 8) — the containers chapters move quickly. Chapter 4 is Volume 15’s nginx applied to containers; Chapter 5 pairs with Volume 14 on where credentials belong.

How this book is organised

Chapters map one-to-one onto the twelve modules of the VPS deployment track in Code Lab, each ending with that module’s ten graded exercises. Read 0 through 4 in order and in that order on a real server — they are cumulative, and Chapter 1 in particular should be done before the machine has been online for long.

The two habits this book is really teaching

Nothing is real until it has been tested. A backup you have not restored, a rollback you have not run, a certificate renewal you have not watched succeed — each is an assumption, and each fails at the worst possible moment. And deploy small, deploy often: the entire pipeline in Chapters 6–8 exists to make deploying boring enough that you do it constantly, because small changes fail rarely and obviously.

Chapter Zero · Orientation

The VPS and Your First Login

A VPS is a computer you rent, reach over SSH, and are entirely responsible for. This chapter gets you onto one with a key instead of a password, explains what the key exchange actually proves, and sets up the config file that makes every later chapter shorter.

By the end of this chapter you will be able to

  • Log in with a key and stop using passwords

0.1 What you are renting

A whole machine, and a whole job

A VPS — virtual private server — is a slice of a physical machine with its own kernel, filesystem, IP address, and root account. Unlike a platform (Vercel, Heroku, Render), nothing is managed for you: no automatic TLS, no restarts, no patches, no backups. You get complete control, a low fixed price, and the entire operations burden. That trade is the subject of this book.

A VPS is dramatically cheaper and infinitely more flexible; it is also a machine that will be attacked within minutes of getting a public IP, and nobody else is watching it. Choose it when you want control and can accept the responsibility — and then read Chapter 1 before you do anything else.

Everything here runs against a real server

The listings in this book were executed over a genuine SSH connection to an Ubuntu 24.04 server, and the output is verbatim — including the failures. Your provider (Hetzner, DigitalOcean, Vultr, Linode) and IP will differ; nothing else will.

0.2 Keys, not passwords

What the key pair actually proves

An SSH key pair is a private key that never leaves your machine and a public key you copy everywhere. At login the server sends a challenge; your client signs it with the private key; the server verifies the signature against the public key in ~/.ssh/authorized_keys. The secret is never transmitted — which is the whole difference from a password, and why key authentication survives an attacker watching the connection or running the server.

0.3 Getting the key onto the server, and logging in

0.4 The config file that saves you from yourself

Stop typing IP addresses

~/.ssh/config turns ssh -i ~/.ssh/id_ed25519 -p 2222 deploy@203.0.113.10 into ssh prod. That is not only convenience: it puts the port, user, and key for each server in one reviewed place, so you stop guessing and stop pasting credentials into shell history. Every tool that speaks SSH — scp, rsync, git, Ansible, VS Code Remote — reads this file too.

Host key verification is the other half

On first connection ssh shows the server’s fingerprint and stores it in ~/.ssh/known_hosts. If it ever changes, ssh refuses to connect with a loud warning — that check is what stops someone impersonating your server. When you legitimately rebuild a machine, remove the stale entry with ssh-keygen -R hostname; never respond to the warning by deleting the whole file out of frustration.

Checkpoint

What does SSH key authentication prove, and why is it better than a password?

The client signs a server-issued challenge with the private key and the server verifies it against the public key in authorized_keys — the secret is never transmitted. So an attacker watching the connection, or even running the server, learns nothing reusable, and there is no password to brute-force. The private key must still be protected with a passphrase.

A key is installed but the server still asks for a password. What is the usual cause?

Permissions. sshd silently refuses authorized_keys if ~/.ssh is not 700 or the file is not 600, or if the home directory is group-writable. Fix those first. The other common cause is offering the wrong key — set IdentitiesOnly yes so ssh presents only the one you configured.

What does ~/.ssh/config buy you beyond typing less?

One reviewed place holding each server’s host, port, user, and key — so credentials stop living in shell history and every SSH-based tool (scp, rsync, git, editors) inherits the same settings. It also lets you set ServerAliveInterval so long deploys are not killed by an idle timeout.

Chapter One · Part I

Securing the Server

A new VPS is being scanned within minutes of getting its IP. This chapter does the four things that matter before anything else is installed: a non-root user, key-only SSH, a firewall that denies by default, and fail2ban — each verified by watching the server’s behaviour change.

By the end of this chapter you will be able to
  • Create a non-root sudo user and stop using root
  • Disable password and root SSH logins, and prove it
  • Configure a default-deny firewall with UFW
  • Block brute-force attempts with fail2ban

1.1 Stop using root

root has no undo

Every command as root is one typo from an unrecoverable mistake, and a root session hijacked is the whole machine. The convention is a normal user who can escalate deliberately with sudo: mistakes need an extra word, actions are logged with the invoking user, and the account can be disabled without touching root.

1.2 Key-only SSH, verified

The config, and how to prove it took effect

Three directives do most of the work: PasswordAuthentication no ends brute-forcing outright, PermitRootLogin no removes the account every scanner tries first, and PubkeyAuthentication yes keeps the method you actually use. The trick to verifying it is that sshd tells you which methods it will accept in its rejection message — so a failed login is the test.

Changing the SSH port is noise reduction, not security

Moving to port 2222 removes most automated log noise, because scanners mostly hit 22. It stops no targeted attacker — a port scan finds it in seconds. Do it if you want quieter logs, but remember to update ~/.ssh/config, your firewall rule, and any CI that connects, before reloading sshd. Never treat it as a substitute for key-only authentication.

1.3 A firewall that denies by default

Default deny, then open what you need

UFW is a friendly front end to the kernel’s netfilter. The correct posture is deny-everything-inbound, allow-everything-outbound, and then a short explicit list of ports you serve. Allow SSH before you enable it — enabling a default-deny firewall without an SSH rule disconnects you permanently.

Docker punches through UFW

Published container ports bypass the firewall entirely

This surprises almost everyone and is a real, exploited exposure. docker run -p 5432:5432 writes its own iptables rules ahead of UFW’s chain, so the port is reachable from the internet even though ufw status shows it denied. Two correct fixes: bind to localhost — -p 127.0.0.1:5432:5432 — so the port is not published publicly at all (this is the one to reach for), or install the ufw-docker rules that teach UFW about Docker’s chain. Check with ss -tlnp what is actually listening on 0.0.0.0, and never trust ufw status alone on a Docker host (Chapter 3).

1.4 fail2ban: banning what keeps knocking

Automatic, temporary, and enough

Even with passwords disabled, scanners will hammer your SSH port continuously. fail2ban watches the auth log and firewalls an address that fails repeatedly. It is not a substitute for key-only auth — it is what keeps the noise, and the CPU cost of answering it, off your server.

The four-step checklist for a brand-new server

① Create a sudo user and install your key (§1.1). ② Disable password and root SSH, verify with the probe from §1.2, keeping your session open. ③ ufw default deny incoming, allow SSH first, then 80/443 (§1.3) — and check ss -tlnp because Docker ignores it. ④ Install fail2ban (§1.4). ⑤ Then, and only then, sudo apt update && sudo apt upgrade -y and enable unattended-upgrades so security patches land without you (Chapter 11). This takes ten minutes and prevents the overwhelming majority of what happens to unattended servers.

Checkpoint

How do you verify that password authentication is really disabled?

Attempt a login and read sshd’s rejection: it lists the methods it will accept. Permission denied (publickey,password) means passwords are still accepted; Permission denied (publickey) means they are not. That probe works against any server, including ones someone else configured.

What is the order of operations for enabling UFW, and why does it matter?

Set default deny incoming, then allow SSH, then the ports you serve, and only then ufw enable. Enabling default-deny without an SSH rule disconnects you from a machine you can no longer reach — recoverable only through the provider’s rescue console.

Why can a port be open on a Docker host despite UFW showing it denied?

Because docker run -p inserts iptables rules ahead of UFW’s chain, so published ports bypass it entirely. Bind to localhost instead — -p 127.0.0.1:5432:5432 — or install the ufw-docker rules, and always confirm with ss -tlnp what is genuinely listening on 0.0.0.0.

Chapter Two · Part II

Installing Docker and Compose

Why containers are the right unit of deployment for a VPS, how to install Docker from the official repository rather than the distribution’s stale package, and the daemon settings that prevent the two problems every long-lived Docker host eventually has: full disks and unbounded logs.

By the end of this chapter you will be able to
  • Install Docker Engine from the official APT repository
  • Run Docker without sudo, and understand the risk
  • Configure the daemon with daemon.json
  • Prevent logs and images from filling the disk

2.1 Why containers on a VPS

The image is the deployment artefact

Without containers, deploying means installing runtimes, libraries, and services directly on the machine — and the machine slowly becomes unique, undocumented, and impossible to rebuild. With containers, the artefact you deploy is an image: a fixed filesystem plus a command, identical on your laptop, in CI, and on the server. Rollback becomes running the previous tag; “works on my machine” becomes a shipping detail; and the VPS itself stays boring, holding little more than Docker and your compose file.

The distribution package is not the one you want

Ubuntu’s docker.io package lags upstream badly and lacks the Compose v2 plugin. Install from Docker’s own repository — it is three commands more and gives you current Engine, BuildKit, and docker compose as a first-class subcommand.

2.2 Installing from the official repository

2.3 Running Docker without sudo — and what it means

The docker group is root, spelled differently

Adding yourself to docker grants full root

The Docker daemon runs as root, and anyone who can talk to its socket can start a container that mounts / and edit anything on the host. So usermod -aG docker deploy is equivalent to passwordless root for that user — it is a convenience, not a privilege reduction. Do it for your deploy user if that user is already trusted with sudo (it is), and understand that it means every process running as that user has root available.

2.4 The daemon settings that prevent disk disasters

Put a prune on a timer

A weekly docker system prune -af --filter "until=168h" from cron or a systemd timer keeps a deploy-heavy server from silently accumulating gigabytes of superseded images. Combine it with the log limits above and the two ways a Docker host fills its disk are both closed — before they page you.

Checkpoint

Why install Docker from its own repository rather than the distribution’s?

Because the distribution package lags upstream and ships without the Compose v2 plugin. The official repository gives current Engine, BuildKit, and docker compose as a subcommand. Use a signed-by keyring entry so Docker’s key is trusted for that repository only, and avoid piping install scripts into a root shell.

What does adding a user to the docker group really grant?

Root. The daemon runs as root and anyone who can reach its socket can mount the host filesystem into a container and edit anything — docker run -v /:/host … chroot /host is a root shell. It is fine for a user already trusted with sudo, but it is not a privilege reduction and must never be used to give untrusted users “just container access”.

What is the most important line in daemon.json on a long-lived VPS?

The log-opts limit. Docker’s default json-file driver has no size cap, so one chatty container can fill the disk and take down every service on the machine. max-size plus max-file bounds it. Pair that with a scheduled docker system prune to stop superseded images accumulating.

Chapter Three · Part II

Docker Compose for a Full-Stack App

One file describing your whole application: services, networks, volumes, secrets, and the health checks that make startup order deterministic. This chapter runs a real two-service stack and proves the database is unreachable from outside while the app can still reach it.

By the end of this chapter you will be able to
  • Describe a multi-service app in one compose.yml
  • Persist data in named volumes
  • Order startup with health checks, not sleeps

3.1 The whole application in one file

3.2 Volumes: what survives, and what does not

Named volumes outlive containers; bind mounts are your files

Containers are disposable — everything written inside one is destroyed with it. A named volume is storage Docker manages, which survives down, image upgrades, and container replacement; it is where databases belong. A bind mount maps a host directory into the container, which is right for configuration and code you edit. Confusing them is how people lose a production database during a routine docker compose down -v.

3.3 Health checks make startup deterministic

“Started” is not “ready”

A Postgres container is running long before it accepts connections. Plain depends_on only waits for the container to start, so an app that connects at boot crashes on a race that appears intermittently and disappears when you add a sleep 10 — the fix everyone reaches for and nobody trusts. A healthcheck plus condition: service_healthy replaces the guess with a fact.

depends_on conditionWaits untilUse for
service_started (default)The container has startedNothing that connects immediately
service_healthyIts healthcheck passesDatabases, caches, APIs
service_completed_successfullyIt ran and exited 0Migrations, seed jobs

Table 3.1 The third row is how you run database migrations correctly: a one-shot service that exits 0, with the app depending on its completion. That guarantees the schema is in place before the first request, without the app racing its own migration on every replica.

3.4 Network isolation, demonstrated

Put the database where the internet is not

Compose gives every service DNS by name on the networks it joins. Putting the database on a backend network that the proxy is not on — and marking that network internal: true — means the database has no route to or from the outside, while the app still resolves db and connects normally. This is defence in depth: even a mistaken ports: entry cannot expose what has no path.

One more layer: read-only and non-root

Two compose.yml settings cost nothing and remove whole classes of exploit: read_only: true makes the container filesystem immutable (add tmpfs for paths that genuinely need writes), and user: "1000:1000" runs the process as a non-root user so a container escape lands somewhere harmless. Add cap_drop: [ALL] and you have a container that can serve traffic and do very little else.

Checkpoint

What is the difference between a named volume and a bind mount?

A named volume is Docker-managed storage that survives container replacement and compose down — the demo destroyed the whole stack and the database row was still there. A bind mount maps a host directory in, which suits config and code. The command that does delete volumes is docker compose down -v; treat it like rm -rf.

Why is plain depends_on not enough?

It waits only for the container to start, not to be ready — Postgres is running long before it accepts connections, so the app races it and fails intermittently. condition: service_healthy waits for the healthcheck to pass; service_completed_successfully is how you gate on a migration job finishing.

How do you make a database unreachable from the internet?

Publish no ports for it and put it on a separate internal: true network that the public-facing service is not on. The app still resolves it by service name over the shared backend network, while the host shows the port refused — which also sidesteps the Docker-bypasses-UFW trap, since the safest port is one that was never published.

Chapter Four · Part III

Nginx and TLS in Front of the Stack

Putting a proxy at the edge of your Compose stack: one container that terminates TLS, routes to services by name, and is the only thing on the machine with a published port. Then Let’s Encrypt, automated, including the renewal step that people forget.

By the end of this chapter you will be able to
  • Add nginx as the edge service of a Compose stack
  • Publish only the proxy, and reach services by name
  • Obtain and renew certificates with certbot in Docker
  • Reload the proxy after renewal without downtime

4.1 The proxy is the only door

One published port for the whole machine

The pattern for a containerised VPS: nothing publishes a port except the proxy. Application containers listen on the internal network, the proxy resolves them by service name, and ports 80 and 443 are the entire attack surface. This also sidesteps the Docker-bypasses-UFW trap from §1.3, because there is nothing else to bypass it with.

4.2 TLS, terminated at the proxy

4.3 Certificates, obtained and renewed

Rate limits are real

Let’s Encrypt allows 5 duplicate certificates per week per exact set of domains. Debugging an issuance problem by re-running certbot repeatedly will exhaust that quota and lock you out for days. Use --dry-run (which hits the staging environment and has generous limits) until the flow works, and only then issue for real.

Checkpoint

Why should only the proxy publish ports?

It makes ports 80/443 the entire attack surface: application and database containers listen only on internal networks and are reached by service name. It also removes the Docker-bypasses-UFW risk from §1.3, because there are no other published ports to bypass the firewall with.

Why must the backend receive X-Forwarded-Proto?

Because TLS terminates at the proxy and the app sees plain HTTP. Without that header it generates http:// links and, if it enforces HTTPS itself, redirects in a loop. The proxy must set it explicitly — along with Host, X-Real-IP, and X-Forwarded-For.

Certbot renewed the certificate but browsers still see the old one. Why?

nginx loaded the certificate into memory at startup and keeps serving it until reloaded. Renewal must be paired with a reload — a --deploy-hook on a host install, or a periodic nginx -s reload in the containerised pattern. Verify the whole flow with certbot renew --dry-run, since real issuance is rate-limited to 5 duplicates per week.

5.1 Three places a value can live, and which to use

MethodVisible toUse for
Hard-coded in the imageAnyone who pulls the imageNothing, ever

For a single VPS, a 0600 .env file owned by the deploy user is a reasonable, honest answer — the machine’s security is the secret’s security, which is why Chapter 1 came first.

5.2 What .env does not protect against

Environment variables are visible to more things than you think

Four ways a variable leaks even when the file is 0600

1. docker inspect prints every environment variable of a container — anyone in the docker group (which is root anyway, §2.3) sees them. 2. A crash dump or error page that serialises process.env ships the lot to your logging service. 3. docker compose config renders them (§5.1). 4. Child processes inherit them, so any dependency can read them. So treat .env as protection against casual exposure and other users on the box, not as a vault. Where it matters more — a Swarm or a team — use Docker secrets, which mount the value as a file at /run/secrets/name so it is not in the environment at all.

5.4 Rotating a credential without downtime

Two valid credentials, briefly

Rotation fails when it is a hard cutover: change the password, restart everything, and hope nothing was mid-request. The safe sequence overlaps them — create the new credential while the old still works, roll the application onto it, and only then revoke the old. For a database that means adding a second user or a second password rather than editing one in place.

Generate secrets, do not invent them

openssl rand -base64 32 or head -c 32 /dev/urandom | base64. A human-chosen database password on an internet-facing machine is a matter of time, and there is no upside to being able to remember it — it lives in a 0600 file and a password manager, not in your head.

Checkpoint

Why is a secret in a Dockerfile worse than one in .env?

Because it is baked into the image layers permanently: anyone who can pull the image can read it, and a later commit removing the line does not remove it from the layer history. A 0600 .env on the server is readable only by its owner and root, and never travels with the image.

Name two ways an environment variable leaks despite a 0600 file.

docker inspect prints every container’s environment; docker compose config renders the interpolated file with values; a crash handler that serialises process.env ships them to your log service; and child processes inherit them. Docker secrets (*_FILE) avoid the environment entirely by mounting the value as a file.

A password was committed to git. What is the first action?

Rotate the credential. History rewriting does not help if anyone cloned or forked the repository, or if it was ever public — the value must be assumed compromised. Clean the history afterwards as housekeeping, and add .gitignore entries plus a .env.example so it cannot recur.

Chapter Six · Part IV

Zero-Downtime Deploys

Replacing a running application without anyone noticing. This chapter measures a real rolling deploy under continuous load, explains the graceful shutdown your application must implement to earn it, and lays out blue-green and canary as the next steps.

By the end of this chapter you will be able to
  • Explain why a naive compose up drops requests
  • Roll instances one at a time behind the proxy
  • Implement graceful shutdown in the application
  • Choose between rolling, blue-green, and canary

6.1 Why the obvious deploy drops requests

Down, then up, is an outage

docker compose up -d with a new image stops the container and starts the replacement. With one instance that is a gap — seconds of 502s while nginx has nothing to talk to. Users notice, health checks fire, and the deploy looks risky, so it gets done rarely and at night, which makes each one bigger and riskier still. The fix has three parts: more than one instance, a proxy that skips unhealthy ones (Volume 15 §4), and an application that shuts down gracefully (§6.3).

StrategyExtra capacityRollbackComplexity
RecreateNoneRedeploy the old imageTrivial — but has downtime
Rolling1 spare instanceRoll back the same wayLow — this chapter
Blue-green2× for the switchFlip the proxy backMedium
Canary1 extra instanceShift weight to 0High — needs metrics

Table 6.1 Rolling is the right default for a VPS: it needs one spare instance and no extra infrastructure. Blue-green buys an instant, atomic rollback at the cost of running two full stacks during the switch; canary buys risk reduction at the cost of needing per-version metrics to decide on. Start rolling, and add the others when a specific failure justifies them.

6.2 A rolling deploy, measured under load

6.3 Graceful shutdown is the application’s half

Docker asks politely, then stops asking

SIGTERM, then ten seconds, then SIGKILL

On stop, Docker sends SIGTERM and waits stop_grace_period (default 10 s) before SIGKILL. An application that ignores SIGTERM is killed mid-request — every in-flight response is lost, which is exactly the failure a rolling deploy is supposed to prevent. Handling it is a few lines, and without them the rest of this chapter does not deliver what it promises (Volume 15 §13 makes the same point for nginx itself).

6.4 Blue-green and canary, briefly

Canary needs metrics to be worth it

A canary sends a small share of traffic to the new version and promotes it if the error rate and latency hold. Without per-version metrics it is just a rolling deploy with extra steps — the value is entirely in the decision, which needs a dashboard or an automated threshold (Chapter 9). On a single VPS, weight it with nginx: server new:3000 weight=1; server old:3000 weight=9; and raise the weight as confidence grows.

Checkpoint

What three things make a rolling deploy produce zero failed requests?

More than one instance; a proxy that skips instances that are down or unhealthy; and an application that shuts down gracefully. Then replace instances one at a time, waiting for each replacement to become healthy — the measured demo restarted both containers under 250 requests of continuous load with zero failures.

Why must readiness fail before the server stops accepting connections?

Because the proxy needs a moment to notice. If you close the listener first, requests already being routed to you are refused. Failing the health check first makes the proxy stop sending new work, and only then do you drain the in-flight requests — with a hard deadline just under stop_grace_period so a stuck request cannot get you SIGKILLed mid-write.

What does blue-green buy, and what does it constrain?

Instant rollback: the previous version stays running, so reverting is a proxy config flip and a reload. It costs double the resources during the overlap and constrains your database — both versions share one schema, so migrations must be backwards-compatible (expand and contract), never a change only the new version understands.

Chapter Seven · Part IV

The Container Registry

Where your images live between the build and the server. This chapter uses GitHub Container Registry: authenticating with a scoped token, the tagging discipline that makes rollback possible, and multi-architecture builds for the ARM servers that are now cheaper than x86.

By the end of this chapter you will be able to
  • Authenticate to GHCR with a scoped token
  • Tag images so a rollback is one command
  • Push, pull, and control image visibility
  • Build multi-architecture images

7.1 Why a registry at all

Build once, on a machine that is not your server

Building on the VPS means installing toolchains there, spending its CPU on compilation, and having no artefact to roll back to. A registry inverts that: CI builds the image, pushes it under an immutable tag, and the server only ever pulls. The VPS needs Docker and nothing else, deploys become “pull this tag and restart”, and rollback becomes “pull the previous tag” — the same operation, which is what makes it reliable under pressure.

7.2 Tags are your rollback plan

latest is not a version

latest is a mutable label — it means “whatever was pushed most recently”, which is unknowable after the fact. Deploying it means you cannot say what is running, cannot reproduce it, and cannot roll back to a specific build. Tag every image with something immutable: the git SHA is ideal because it ties the running container to exact source.

Tag styleImmutableGood for
:latestNoLocal convenience only
:4f9a2c1 (git SHA)YesWhat you deploy
:1.4.0By conventionReleases, changelogs
:mainNoNothing in production
@sha256:… (digest)AbsolutelyMaximum reproducibility

Table 7.1 A digest pin (image: ghcr.io/you/app@sha256:…) is the strongest form — it names exact bytes and cannot be re-pointed even by someone who can push tags. Use it where supply-chain integrity matters; use the SHA tag everywhere else because it is readable and traceable to a commit.

7.3 Multi-architecture images

ARM servers are cheaper, and your laptop may be ARM too

An image built on x86 will not run on an ARM VPS (Ampere, Graviton, and most of the cheap tiers now), and one built on an Apple Silicon laptop will not run on an x86 server. buildx solves it by building both and publishing a manifest list — one tag that resolves to the right architecture per host, automatically.

Slow ARM builds have a fix

Cross-building ARM on x86 uses QEMU emulation and can be several times slower. If it becomes painful, use GitHub Actions’ native ARM runners and let each architecture build on its own hardware, then merge the manifests — considerably faster than emulating, and free for public repositories.

7.4 Housekeeping and scanning

Old tags accumulate

Every deploy pushes another SHA tag, and GHCR keeps them all against your storage quota. Set a retention policy — keep tagged releases and the last N SHA builds, delete untagged manifests — with the actions/delete-package-versions action on a schedule. It is one of those chores that is trivial to automate now and tedious to do by hand later.

Checkpoint

Why is deploying :latest a problem?

It is mutable — it means “whatever was pushed last”, so you cannot say what is running, reproduce it, or roll back to a specific build. Deploy an immutable tag (the git SHA, which ties the container to exact source) or a digest, and keep latest as a convenience pointer only.

Why does the server’s registry credential need only read:packages?

Because a write-capable token on your most internet-exposed machine can push a malicious image to the very tag production pulls. The server only ever pulls, so scope its token to reads; use the repository-scoped, job-lifetime GITHUB_TOKEN for pushing from CI.

What does buildx --platform produce, and how do you verify it?

A manifest list: one tag resolving to the right architecture per host, so the same tag runs on x86 and ARM servers. It must be --pushed because a multi-arch result cannot live in the local single-arch store. Verify with docker buildx imagetools inspect — a silently single-arch image fails on the server with exec format error.

8.2 The deploy key, scoped as tightly as it can be

This key is root on your server — treat it that way

What CI can reach, an attacker with CI access can reach

A stolen deploy key is a shell on your VPS as a user in the docker group, which is root (§2.3). You cannot make it harmless, but you can make it narrow: a dedicated key used nowhere else, restricted in authorized_keys to a single command, and a server-side script that takes only an image tag as input.

8.3 Push or pull?

Push (CI → SSH → VPS)Pull (agent on the VPS)
CI needsSSH access to productionNothing — no inbound access
Server needsAn open SSH portOutbound to the registry only
Blast radius of stolen CI credsShell on the serverA push to the registry

Table 8.1 Push is what this chapter builds, and it is right for a small deployment. The trade is that “deploy” becomes eventually-consistent and harder to gate — you lose the health-check-then-rollback loop unless the agent implements it.

Whichever you choose, deploy small and often

The operational argument underneath this whole chapter: a pipeline that deploys on every merge produces small, individually-understandable changes, so failures are rare and their cause is obvious. A pipeline used monthly produces large, entangled releases that fail in ways nobody can attribute — and the fear that creates makes the next release even larger. The tooling in this book exists to make deploying boring enough to do constantly.

Checkpoint

Why does the workflow set concurrency and explicit permissions?

concurrency prevents two merges deploying at once and interleaving container restarts — a race that produces a half-old, half-new stack. permissions narrows the automatic GITHUB_TOKEN to only packages: write, so a compromised action cannot use it to modify code or releases.

How do you limit what a stolen deploy key can do?

Use a dedicated key used nowhere else, and in authorized_keys restrict it with command="…/deploy.sh" plus no-pty, no-port-forwarding, and no-agent-forwarding. The key then runs one script rather than granting a shell. Inside the script, validate the requested image against your registry prefix instead of trusting the client.

What does a pull-based deploy change about the threat model?

CI no longer needs credentials for production and the server needs no inbound access — an agent on the VPS polls the registry and updates itself, so stolen CI credentials buy a registry push rather than a shell on the server. The cost is that deploys become eventually-consistent and the health-gate-then-rollback loop must be implemented by the agent.

9.1 Backing up a live database

Dump through the engine, do not copy the files

Copying a running database’s data directory produces a torn, inconsistent snapshot. Use the engine’s own dump tool, which takes a consistent view: pg_dump for PostgreSQL, mysqldump --single-transaction for MySQL. It runs against the live database with no downtime and produces a file you can restore anywhere.

9.3 Logs that do not fill the disk

Bound them at the daemon, then read them centrally

Checkpoint

Why dump a database instead of copying its data directory?

A file copy of a running database is torn and inconsistent. pg_dump (or mysqldump --single-transaction) takes a consistent logical view through the engine while it serves traffic, producing a file that restores cleanly anywhere. What makes a backup real rather than hopeful?

A restore you have actually performed. The chapter dumped, dropped the table, restored, and verified the row count and a specific row. Schedule that exercise quarterly against a scratch database — every organisation that lost data had backups; what they lacked was a practised restore. Also: off-site, or it does not survive losing the server.

Which signals deserve an alert, and which does not?

Disk over 80%, health-check failure, certificate expiry under 14 days, a missing backup ping, OOM kills, and restart loops — symptoms users notice plus failures that are otherwise silent. Not raw CPU: high CPU on a busy server is normal, and paging on it teaches you to ignore alerts.

10.1 The order to check things in

Four commands, in this sequence

Under pressure the temptation is to change things. Resist it for sixty seconds and run these in order: docker compose ps (what state is everything in?), docker compose logs --tail 50 <svc> (what did it say before dying?), docker inspect (exit code, health, config as actually applied), and docker stats (is it starved?). Most incidents are identified by the second command, and changing things before reading them is how a small failure becomes a long one.

10.4 Getting inside a container that will not start

The discipline that makes 3 a.m. shorter

Write down what you changed and when. Checkpoint

A container exits with 137. What does it mean and how do you confirm?

It was SIGKILLed — usually the kernel’s OOM killer. Confirm with docker inspect --format '{{.State.OOMKilled}}': true means memory, since a 137 can also come from a manual docker kill. Then set a memory limit that matches the workload and find out why the process wanted that much.

What are the first four commands of any container incident?

docker compose ps (state), logs --tail 50 (what it said before dying), docker inspect (exit code, health, applied config), docker stats (starvation). Read all four before changing anything — and watch the restart count, since a crash-looping container makes a site look “up” while failing a share of requests.

“The app cannot reach the database.” What resolves this fastest?

docker compose exec web getent hosts db. If the name resolves, DNS and the shared network are fine — look at ports, credentials, or app config. If it does not, check which networks each container is on: they are not on a common one. Note that a service deliberately excluded from the backend network (the proxy) is supposed to fail this test.

Scaling and Hardening

Getting more out of one server before you need two, and closing the gaps that time opens. Resource limits, restart policies, unattended security updates, and the honest signals that tell you a single VPS is no longer the right answer.

11.1 Limits: one container should not take the machine down

Unlimited is the default, and it is wrong

Without limits, any container can consume all memory on the host — and the kernel’s OOM killer then picks a victim by its own heuristics, which is frequently your database rather than the process that caused it. Setting limits converts “the server died” into “one container was restarted”, which is the difference between an outage and an incident.

Crash-looping is invisible unless you look for it

A container that crashes every ninety seconds and is restarted every ninety seconds presents as a service that is “up” while dropping every in-flight request at each restart. Checkpoint

Why set memory limits on every container?

Without them one container can exhaust host memory and the kernel’s OOM killer chooses a victim by its own heuristics — often the database rather than the culprit. Limits convert “the server died” into “one container was restarted”. Size them from docker stats under real load plus about 50% headroom; too tight produces exit 137.

Why unless-stopped rather than always?

Both restart on crash and on reboot, but unless-stopped respects a deliberate docker stop — a container you took down for maintenance stays down. always brings it back, which is surprising exactly when you are trying to keep something off. Neither is a fix: watch RestartCount, because a crash-loop looks “up” while dropping requests.

What does unattended-upgrades not cover?

The packages inside your containers. It patches the host only; container contents are frozen at build time and stay vulnerable until the image is rebuilt. Schedule a monthly rebuild-and-redeploy on fresh base images with vulnerability scanning in CI — which also keeps the deploy pipeline exercised.
