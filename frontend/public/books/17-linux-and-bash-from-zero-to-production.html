About this book

Most people learn bash by accumulating fragments — a command copied from an answer, a script inherited from someone who left. It works until the day a filename contains a space, a variable is misspelled, or a cron job silently stops running. This book replaces the fragments with the underlying model, and then makes you watch it behave.

Everything here was executed. When Chapter 4 says that piping into a while loop loses your variables, you see the same arithmetic print 0 after a pipe and 6 after process substitution. When Chapter 8 argues against subprocesses in loops, the measurements are on the page: basename takes 211 ms where ${p##*/} takes 3.7 ms, and summing 5,000 numbers goes from 898 ms to 1.6 ms depending on the design. Chapter 13 deletes a file that a process still holds open and shows du reporting nothing while two megabytes stay allocated.

The failures are deliberate and the surprises are kept. A chmod 0777 that leaves setgid still set on a directory (§1.3). An associative-array counter that dies under set -u on its first increment (§4.2). A named pipe that hangs the script that writes to it (§9.3). Each was hit while writing the book, and each is explained where it happened rather than smoothed over.

Who should read this

Anyone who uses a terminal daily and wants to stop guessing — and anyone who has inherited shell scripts they do not trust. You need no prior scripting. The later chapters connect outward: Chapter 6 to Volume 16’s VPS work, Chapter 10 to Volume 14’s security, Chapter 12 to observability generally.

How this book is organised

Chapters map one-to-one onto the sixteen modules of the Linux & Bash track in Code Lab, each ending with that module’s graded exercises — 175 in total, all linked. Read 0 through 4 in order; they are cumulative and everything later assumes them. After that the parts stand alone.

The three habits this book is really teaching

Quote every expansion — it is a correctness issue in Chapter 3 and a security issue in Chapter 10, and it is the same fix. Start every script with set -euo pipefail, so a failure stops loudly instead of quietly doing half the job. Send logs to stderr and data to stdout, so your script can be composed with others. Everything else is vocabulary.

Chapter Zero · Part I

The Command Line, and How to Move Around It

The filesystem is a tree, your shell is always standing somewhere in it, and every path is either an instruction from the root or from where you are. Get those three ideas straight and the rest of Linux stops being memorisation.

By the end of this chapter you will be able to
  • Navigate with pwd, cd, and ls
  • Write absolute and relative paths, and convert between them
  • Read the Filesystem Hierarchy Standard well enough to guess
  • Inspect files with cat, less, head, and tail

0.1 Where you are, and what is here

Three commands you will run a hundred times a day

pwd prints the working directory — where the shell currently stands. cd moves it. ls lists what is here. Everything else in this book assumes you know, at all times, which directory a command will act on, because almost every destructive mistake in a shell is a correct command run in the wrong place.

0.2 Absolute and relative paths

One rule: does it start with a slash?

A path beginning with / is absolute — it starts at the root of the filesystem and means the same thing from anywhere. Anything else is relative — it starts from the current directory. That is the entire distinction, and it is the source of most “file not found” confusion: the path was fine, you were somewhere else.

And /tmp being cleared is not a detail: it is exactly how this book’s own working directory was lost once.

0.4 Reading files

less is the one to use interactively

less file opens a pager you can scroll and search: /pattern searches forward, n repeats, G jumps to the end, q quits. It loads lazily, so it opens a huge file instantly where cat would flood your terminal. The name is a joke — it replaced a program called more.

tail -f is how you watch something happen

Checkpoint

What makes a path absolute, and why does it matter?

A leading /. An absolute path means the same thing from any directory; a relative path is resolved from wherever the shell currently stands, which is why the same string can work and then fail after a cd. In scripts, resolve paths with realpath up front so behaviour does not depend on the invoking directory.

Why must you write ./script.sh rather than script.sh?

Because the current directory is deliberately not on PATH. If it were, an attacker who could write a file called ls into a shared directory would have it run whenever someone typed ls there. The explicit ./ says “the one in this directory, and I mean it”.

What is /proc, and why is it unlike /etc?

/etc holds real configuration files on disk. /proc is a virtual filesystem: the kernel generates its contents on read, exposing live process and system state as files — so cat /proc/loadavg reports the current load. It is why much of Chapter 5’s monitoring needs no special tools at all.

Chapter One · Part I

Files, Permissions, and Ownership

Every file carries an owner, a group, and nine permission bits — and a tenth set most people never learn until something breaks. This chapter reads them, changes them, and derives umask from first principles by watching it act.

By the end of this chapter you will be able to
  • Decode the ten characters of an ls -l listing
  • Set permissions with symbolic and octal notation
  • Explain the special bits: setuid, setgid, sticky
  • Predict what umask will do to a new file

1.1 Reading the permission string

Ten characters, four groups

The first column of ls -l is -rw-r--r--. Character 1 is the type: - file, d directory, l symlink. The remaining nine are three triples — owner, group, other — each being read, write, execute. Nothing else is encoded there, and once you can read it aloud you can fix most permission problems by inspection.

BitOn a fileOn a directory
rRead the contentsList the names inside
wModify the contentsCreate and delete entries
xExecute itEnter it / traverse through it

Table 1.1 The directory column is the one that surprises people. w on a directory lets you delete a file you do not own, because deleting is modifying the directory, not the file — which is exactly why /tmp needs the sticky bit (§1.3). And without x on a directory you cannot cd into it or even reach a file inside it whose name you already know.

1.2 Changing permissions

Octal for setting, symbolic for adjusting

Each triple is a three-bit number: r=4, w=2, x=1. So 644 is rw-r--r-- and 755 is rwxr-xr-x. Octal replaces the whole mode; symbolic notation (u+x, go-w, a=r) adjusts it. Use octal when you know exactly what you want, symbolic when you want to change one thing without disturbing the rest.

ModeSymbolicUse for
644rw-r--r--Ordinary files, web content
600rw-------Secrets, private keys, .env
755rwxr-xr-xDirectories, scripts, binaries
700rwx------Private directories, ~/.ssh
664rw-rw-r--Files a group edits together
777rwxrwxrwxAlmost never — see below

Table 1.2 chmod 777 is the reflex that makes an error message go away and leaves a hole behind: it lets any user on the machine rewrite the file, including a compromised service account. If a permission problem tempts you toward 777, the real fix is almost always ownership (chown) or the directory’s x bit.

Recursive changes need X, not x

chmod -R 755 dir makes every file executable too, which is wrong. chmod -R u=rwX,go=rX dir uses capital X: apply the execute bit only to directories and to files that already had one. That single capital letter is the difference between a correct recursive chmod and a mess.

1.3 The bits nobody teaches you

setuid, setgid, and sticky

Beyond the nine there is a fourth octal digit. setuid (4000) makes a program run as its owner rather than the caller — how passwd can edit /etc/shadow for you. setgid (2000) does the same for the group, and on a directory it makes new files inherit that directory’s group, which is how shared project folders work. sticky (1000) on a directory means only a file’s owner may delete it, however writable the directory is.

setuid binaries are a standing risk

Audit them; never create one casually

A setuid-root program with a bug is a local privilege escalation — the attacker does not need to be root, only to run your program. Find every one on a machine with find / -perm -4000 -type f 2>/dev/null and be able to justify each. Writing your own setuid binary is almost always the wrong answer; sudo with a narrowly-scoped rule (Volume 16 §1.1) does the same job with an audit trail.

1.4 umask, derived by watching it

Permissions are subtracted, not chosen

New files do not get the mode you expect — they get a default minus your umask. The base is 666 for files and 777 for directories (files are never created executable), and the umask bits are removed. A umask of 022 therefore yields 644 files and 755 directories, which is why almost everything you create looks like that.

Set it inside the script, not in your profile

A backup script that writes archives should begin with umask 077 so its output is private regardless of who runs it or what their login profile says. Relying on the invoking user’s umask means the same script produces world-readable backups on one machine and private ones on another — and you find out which when the wrong person reads them.

Checkpoint

What does w on a directory actually permit?

Creating and deleting entries in it — including deleting files you do not own, because deletion modifies the directory, not the file. That is why world-writable shared directories need the sticky bit, as /tmp has, which restricts deletion to each file’s owner. And without x on a directory you cannot traverse into it at all.

When do you use symbolic notation rather than octal?

When adjusting one thing without disturbing the rest — u+x adds execute for the owner only; go-r removes read from group and other. Octal replaces the entire mode, which is right when you know exactly what you want. For recursive changes use capital X (u=rwX,go=rX) so files do not all become executable.

Why does a new file come out as 644 rather than 666?

Because umask clears bits from the base mode — 666 for files, 777 for directories. A umask of 022 gives 644 and 755. Scripts that write secrets should set umask 077 themselves so their output is private no matter whose profile invoked them.

Text Processing, Pipes, and Regular Expressions

The idea that makes Unix Unix: small programs that read text and write text, composed with a vertical bar. This chapter builds real log-analysis pipelines from grep, sed, awk, sort, and uniq — and every number in it came out of the demo logs.

2.1 Pipes and redirection

Three streams, and an arrow for each

Every process gets stdin (0), stdout (1), and stderr (2). > redirects stdout to a file (truncating), >> appends, < feeds a file to stdin, and | connects one program’s stdout to the next one’s stdin. Keeping stdout and stderr separate is what lets you pipe results while still seeing errors.

FormMeans
cmd > fstdout to f, truncating
cmd >> fstdout appended to f
cmd 2> fstderr to f
cmd &> fboth streams to f (bash)
cmd 2>&1stderr into wherever stdout goes
cmd < ff as stdin
cmd1 | cmd2stdout of one into stdin of the next
cmd | tee fthrough to the screen and into f

Table 2.1 Order matters in a way that catches everyone: cmd > f 2>&1 sends both streams to the file, but cmd 2>&1 > f does not — the second form points stderr at the terminal (where stdout was at that moment) and only then moves stdout to the file. Read redirections left to right as reassignments.

2.3 sed: editing a stream

Substitute, delete, and print ranges

sed applies an editing script to each line as it flows past. Ninety per cent of real use is s/pattern/replacement/ — add g for every occurrence on the line, I for case-insensitive. It edits the stream, not the file, unless you pass -i.

-i edits files in place — with a safety net

Always take a backup suffix the first few times

sed -i.bak 's/old/new/g' *.conf rewrites every matching file and leaves .conf.bak copies. Without the suffix there is no undo, and a regex that matched more than you intended has already been applied to every file. Test the expression without -i first — the output is right there on screen — and only then add it.

2.4 awk: fields and arithmetic

Every line is split into fields for you

awk splits each line on whitespace (or -F for another separator) and gives you $1, $2, … with $0 as the whole line and NF as the field count. Add a pattern before the block to filter, BEGIN/END for setup and totals, and associative arrays for grouping — which is most of what people reach for a spreadsheet to do.

2.5 Putting a pipeline together

Build pipelines left to right, checking as you go

Write the first stage, run it, look. Add | head and run again. Only when each stage does what you expect do you add the next. Debugging a six-stage pipeline you wrote all at once means guessing which stage is wrong; building it incrementally means you never have more than one candidate. And put a tee /tmp/stage3.txt in the middle when you need to see what is actually flowing through.

Checkpoint

Why does cmd 2>&1 > f not do what it looks like?

Redirections are applied left to right as reassignments. 2>&1 points stderr at wherever stdout is at that moment — the terminal — and only afterwards does > f move stdout to the file. To capture both, write cmd > f 2>&1 (or cmd &> f in bash).

What does grep -o give you that plain grep does not?

Only the matched text, not the whole line — which turns grep into a field extractor. grep -oE '^[0-9.]+' access.log | sort -u pulls every distinct client address out of a log without writing a parser. Anchor your patterns, or a status code of 200 will also match a byte count of 12200.

What is the sort | uniq -c | sort -rn idiom for?

Turning any stream of repeated values into a frequency table, most-common first. uniq -c only collapses adjacent duplicates, which is why it must be preceded by sort; the final sort -rn orders by the count numerically, descending. It answers “which is most common?” for IPs, paths, status codes, and error messages alike.

Bash Scripting Fundamentals

From typing commands to writing programs. Variables, conditionals, loops, functions, arguments, and exit codes — plus the three-line header that turns a fragile script into one that fails loudly instead of silently doing half the job.

By the end of this chapter you will be able to
  • Write and run a script with a shebang and safe defaults
  • Use variables, quoting, and command substitution correctly
  • Branch with if/case and loop over files safely

3.1 The header every script should start with

Three lines that prevent most disasters

set -euo pipefail, explained

By default bash continues after errors, treats unset variables as empty, and reports only the last command’s status in a pipeline. Each default is reasonable interactively and dangerous in a script. set -e exits on any unhandled failure; set -u makes an unset variable an error; set -o pipefail makes a pipeline fail if any stage fails. The classic disaster this prevents is cd "$DIR" && rm -rf * where DIR was never set.

3.2 Variables and quoting

The rule: quote every expansion

Unquoted $var is split on whitespace and glob-expanded. That is occasionally what you want and usually a bug — a filename with a space becomes two arguments, a value containing * becomes a directory listing. Quote it unless you have a specific reason not to.

ExpansionGives you
${v:-alt}alt if v is unset or empty
${v:=alt}Same, and assigns it
${v:?msg}Error with msg if unset — use for required config
${#v}Its length
${v#pre} / ${v%suf}Strip a prefix / suffix (shortest match)
${v##pre} / ${v%%suf}Strip the longest match
${v/old/new}Replace first occurrence (// for all)
${v^^} / ${v,,}Upper / lower case

Table 3.1 These are string operations without calling out to sed or basename — and being builtins they are dramatically faster in a loop (Chapter 8 measures exactly how much). ${CONFIG:?config file required} is the idiomatic way to demand a value at the top of a script.

3.3 Conditionals and loops

Looping over files: the one that bites

for f in $(ls) is wrong — it splits on whitespace, so any filename with a space breaks it, and it globs. Use for f in *.log, which bash expands correctly including spaces. For a recursive search use find … -print0 | while IFS= read -r -d '' f, which separates names with a NUL byte — the one character that cannot appear in a filename.

3.4 Functions, arguments, and exit codes

ExpressionMeans

Table 3.2 "$@" versus $* is the distinction that matters: "$@" preserves argument boundaries, so a filename with a space stays one argument when you forward it to another command. Write cmd "$@" and essentially never cmd $*.

Exit codes are your script’s API

exit 0 means success and anything else means failure — that is what &&, set -e, cron, CI, and systemd all read. Use distinct non-zero codes for distinct failures (1 general, 2 usage error, 3 dependency missing …) and document them in a comment. A script that always exits 0 cannot be automated safely, because nothing calling it can tell whether it worked.

Checkpoint

What does each part of set -euo pipefail do?

-e exits on an unhandled failure instead of continuing; -u makes an unset variable an error rather than an empty string; -o pipefail makes a pipeline fail if any stage fails, not just the last. Together they turn silent partial success into a loud, early stop — and -u specifically prevents a typo’d variable from expanding to nothing in a path.

Why quote every variable expansion?

Because an unquoted expansion is word-split on whitespace and glob-expanded — a filename containing a space becomes two arguments, and a value containing * becomes a directory listing. The demo showed an unquoted loop iterating twice over one filename. Quote unless you specifically want splitting, and forward arguments as "$@".

How does a bash function return a value?

It does not — return sets an exit code (0 = success). To return data, echo it and capture with $(func). Declare variables local or they are global, and send diagnostics to stderr with >&2 so they survive stdout being redirected.

5.2 /proc: the kernel as files

No special tools required

Every process has a directory /proc/<pid>/ containing its command line, environment, open file descriptors, memory map, and status — as readable files. Every monitoring tool you have used is reading these. Knowing that means you can extract exactly what you need with cat and awk on a machine with nothing installed.

Load average is not a percentage

A load of 4.0 means four processes were runnable on average. On a 4-core machine that is fully busy; on a 16-core machine it is a quarter loaded. Always divide by core count (nproc), and remember that processes blocked in D state count toward Linux’s load figure — so a high load with idle CPUs points at storage, not compute.

5.3 Signals

Ask politely, then insist

SIGKILL (9) cannot be caught, blocked, or ignored: the kernel destroys the process immediately, so buffers are unflushed and temporary files are left behind. Reach for 15 first, always.

5.4 Zombies, orphans, and runaways

A zombie is an accounting entry, not a process

When a process exits, its parent must call wait() to collect the exit status. Until then the kernel keeps a stub — state Z — holding only that status. A zombie uses no CPU and no memory; it occupies a PID. So a handful are harmless and normal, while thousands mean the parent has a bug (it is not reaping) — and the fix is to fix or restart the parent, because you cannot kill something that has already exited.

Checkpoint

What does process state D mean, and why is it worse than it looks?

Uninterruptible sleep — blocked in the kernel, almost always on storage or a network filesystem. Signals are not delivered in that state, so even kill -9 does nothing. Several processes stuck in D means the underlying device is the problem; killing the processes is not an available fix.

Why prefer SIGTERM over SIGKILL?

SIGTERM can be caught, so a program runs its cleanup — flushing buffers, removing lock files, finishing in-flight work. SIGKILL cannot be caught at all: the demo showed the same worker leaving a stale lock file behind when killed with 9 and cleaning it up properly on 15. Use 9 only when 15 has been given time and refused.

Are zombie processes a resource problem?

Not directly — a zombie holds only an exit status and a PID slot, using no CPU or memory. A few are normal. Thousands mean the parent is failing to call wait(), and since the child has already exited you cannot kill it; you fix or restart the parent. Zombies whose parent exits are re-parented to init and reaped immediately.

Reach a service that is not exposed

Checkpoint

How do you check a TCP port with no tools installed?

What does the trailing slash change in an rsync source?

rsync dir/ dest/ copies the contents of dir into dest; rsync dir dest/ creates dest/dir. Combined with --delete — which removes files on the destination that are absent from the source — getting it wrong can delete the wrong tree, which is why -n (dry run) comes first.

What is the difference between -L and -R, and why prefer -J to nested ssh?

Local opens the port on your machine and forwards outward; Remote opens it on the far host and forwards back to you. -J/ProxyJump hops through a bastion at the transport level, so your keys stay local, the bastion never handles them, and scp/rsync keep working — unlike nested ssh or agent forwarding, which exposes your agent to anyone with root on the bastion.

7.1 cron, and why your job did not run

Cron gives you almost no environment

The four reasons a cron job fails when the script works by hand

1. PATH is minimal — usually just /usr/bin:/bin, so docker, node, and anything in /usr/local/bin are not found. Use absolute paths or set PATH at the top of the crontab. 2. No shell profile is read — ~/.bashrc and ~/.profile are not sourced, so your aliases, nvm, and environment variables do not exist. 3. The working directory is $HOME, not wherever the script lives, so every relative path is wrong. 4. Output goes to mail that nobody reads — redirect it to a log or you will never see the error.

7.2 systemd timers

More to write, far more to work with

A systemd timer is two files instead of one line, and in exchange you get: logging into the journal, dependency ordering, resource limits, automatic retries, Persistent=true to catch up after downtime, randomised delays to avoid thundering herds, and systemctl list-timers to see when everything next runs. On any machine already running systemd, timers are the better default.

7.3 Locking: never let two runs overlap

The failure that only happens under load

A backup normally takes four minutes and runs every five. One day the database is larger and it takes six — so a second copy starts while the first is still writing, and now two processes are appending to the same archive. flock makes the second invocation either wait or exit, and it costs one line.

Choose blocking or non-blocking deliberately

flock -n (non-blocking) is right for periodic jobs: if the previous run is still going, skipping this one is correct. Plain flock waits, which is right when every invocation must eventually happen — but on a five-minute timer it silently builds a queue of waiting processes. And flock -w 30 waits with a timeout, which is usually the honest middle ground.

7.4 Log rotation

Checkpoint

Why does a script that works by hand fail under cron?

Cron gives a minimal environment: PATH is usually just /usr/bin:/bin, no shell profile is sourced, the working directory is $HOME, and output goes to unread mail. Fix all four — set PATH explicitly, cd "$(dirname "$(readlink -f "$0")")", source any env file yourself, and redirect with >> log 2>&1.

What do systemd timers give you that cron does not?

Journal logging without redirection, dependency ordering, resource limits, RandomizedDelaySec to avoid herds, systemctl list-timers for visibility, and above all Persistent=true — a job missed because the machine was off runs at next boot rather than being silently skipped. Verify schedules with systemd-analyze calendar before deploying.

Why is flock better than checking for a PID file?

Because the lock is an open file descriptor that the kernel releases when the process exits however it exits, including a crash or kill -9. A PID file left behind by a crashed run blocks every future run until a human deletes it. Use flock -n for periodic jobs so an overlapping run skips rather than queues.

Why is a subprocess inside a loop the first thing to look for?

9.2 Traps: cleaning up whatever happens

trap … EXIT is the one that always runs

A script that creates a temporary directory must remove it — on success, on error, and on Ctrl-C. Writing the cleanup at the end covers only the first case. trap cleanup EXIT covers all three, because bash runs an EXIT trap however the script terminates (short of SIGKILL, which nothing can catch — §5.3).

9.3 Named pipes

A pipe with a name in the filesystem

mkfifo creates a FIFO: it looks like a file but holds no data — a writer blocks until a reader arrives, and vice versa. That makes it the simplest way for unrelated processes to stream to each other, where an anonymous | only connects processes you started together.

FIFOs block, and that is the point

An unread FIFO will hang your script

Opening a FIFO for writing blocks until something opens it for reading. A script that writes to a FIFO nobody is reading simply stops, with no error and no output — which looks like a hang and is one of the more baffling failures in this chapter. Either guarantee a reader exists, or open non-blocking (exec 3<>"$FIFO" opens read-write, which never blocks), or use a plain file if you do not actually need streaming.

9.4 Coprocesses

A background process you can talk to and hear from

A pipe is one-way. A coprocess gives you both directions: coproc NAME { cmd; } starts a command in the background and hands you ${NAME[1]} to write to and ${NAME[0]} to read from. That is how you drive an interactive program — a database client, a calculator, an SSH session — from a script, keeping it open across many requests instead of starting it once per query.

Reaping, and why supervisors leak

A long-running script that starts children must wait for them, or their exit statuses accumulate as zombies (§5.4) and eventually exhaust the PID space. In a supervisor loop that means calling wait -n as jobs finish rather than only at the end. And if you background something you genuinely never want to wait for, disown it so bash stops tracking it at all.

Checkpoint

Why put cleanup in a trap … EXIT rather than at the end of the script?

Because the end is only reached on success. An EXIT trap runs on every termination path — normal exit, an error under set -e, or Ctrl-C — so temporary files are removed regardless. Capture $? as the trap’s first statement to preserve the original exit code, and use mktemp -d so concurrent runs never share a path.

What is a FIFO, and what is its characteristic failure?

A named rendezvous point in the filesystem — it holds no data (its size is always 0) and lets unrelated processes stream to each other. Its failure mode is blocking: opening one for writing waits until a reader appears, so a script writing to an unread FIFO hangs silently with no error at all.

Why does a coprocess usually appear to hang on the first attempt?

Buffering. A program writing to a pipe buffers in blocks rather than lines, so your read waits for output still sitting in the child’s buffer. stdbuf -oL (or the program’s own line-buffering flag) fixes it. The payoff is one long-lived process answering many requests instead of one process per request.

Coordination and High Availability

Scripts that run on several machines at once and must not tread on each other. Health checks, distributed locks with real expiry, quorum arithmetic, and the split-brain problem that quorum exists to prevent.

11.1 Health checks that mean something

Liveness and readiness are different questions

Liveness asks “is this process alive?” — if not, restart it. Readiness asks “should it receive traffic?” — a service that is alive but cannot reach its database is live and not ready. Conflating them produces the classic outage where a slow database triggers a restart loop across the entire fleet (Volume 16 §13.4).

11.2 A distributed lock that expires

The lock must survive the holder dying

flock (§7.3) coordinates processes on one machine. Across machines you need a lock in shared storage — and it must carry an owner and an expiry, or a node that crashes while holding it blocks everyone forever. The three rules: acquire atomically, record who and until when, and never let a holder release someone else’s lock.

The uncomfortable truth about lock expiry

A TTL can expire while the work is still running

If the holder is merely slow rather than dead — a long GC pause, a stalled disk — the lock expires and a second node starts the same work while the first is still going. No pure-timeout lock avoids this. The mitigations are fencing tokens (each lock grant carries an increasing number; the storage layer rejects writes from an older token) or making the protected operation idempotent so a double execution is harmless. Choose one deliberately rather than assuming the lock is enough.

11.3 Quorum, and why the number is odd

NodesQuorumFailures toleratedVerdict
110No redundancy at all
220Worse than one — either failure stops writes
321The practical minimum
431No better than 3, costs more

743Rarely worth the coordination cost

Table 11.1 The two-node row is the trap: people add a second machine for “redundancy” and get a system that stops working when either machine fails, having doubled the failure surface. Three is the first genuinely redundant count — which is why Sentinel, etcd, ZooKeeper, and Consul all recommend it (Volume 12 §5.3 makes the same argument for Redis Sentinel).

11.4 Split brain

Two halves that both think they are in charge

A network partition splits a cluster, and each side concludes the other has died and promotes itself. Now both accept writes, both believe they are authoritative, and when the network heals the two histories cannot be reconciled — data is lost whichever side you choose. Quorum prevents it by making it arithmetically impossible for two sides to both hold a majority.

Fencing is the other half

Quorum stops a minority from promoting. It does not stop a node that was already primary from continuing to write before it notices the partition. Production clusters add fencing — STONITH (“shoot the other node in the head”) power-cycles it, or the storage layer rejects writes carrying a stale fencing token. If you are coordinating anything where a double-write matters, quorum alone is not the whole answer.

Checkpoint

Why must a distributed lock carry an owner and an expiry?

The expiry stops a crashed holder blocking the cluster forever; the owner stops one node releasing another’s lock. Acquire atomically — mkdir succeeds or fails with no check-then-act window, unlike testing for a file and creating it. And accept the residual risk: a merely slow holder can have its lock expire mid-work, which needs fencing tokens or idempotent operations, not a longer timeout.

Why are even node counts wasteful?

Because quorum is a strict majority: four nodes need three, tolerating one failure — exactly what three tolerate, at higher cost. Two nodes are actively worse than one, since either failure stops writes. Three is the practical minimum for real redundancy; five is standard for important clusters.

What is split brain, and what actually prevents it?

A partition where both sides promote themselves, accept conflicting writes, and produce histories that cannot be reconciled. Quorum prevents it arithmetically — two sides cannot both hold a majority — at the cost that an exact even split leaves everyone read-only. Quorum does not stop an existing primary writing before it notices the partition; that needs fencing (STONITH or fencing tokens).

Logging, Metrics, and Observability

12.1 A logging function worth reusing

Logs go to stderr, results go to stdout

The split matters: a script’s output is data a caller may capture with $( ) or pipe onward, while its logs are commentary for a human or a log file. Send logs to >&2 and both work at once — result=$(myscript) captures only the data, while the progress messages still appear on the terminal.

12.2 Structured logs from bash

Hand-built JSON breaks on the first quotation mark

Escape properly, or your log pipeline silently drops lines

printf '{"msg":"%s"}' "$m" produces invalid JSON the moment $m contains a quote, a backslash, or a newline — and a log aggregator responds by discarding the line, so the message you most needed disappears. Use jq if it is available; if it is not, escape deliberately and know the limits of what you wrote.

12.3 Metrics a scraper can read

Never label with something unbounded

Labels multiply the number of time series: {file="app.log"} is fine because there are a handful of files, but {request_id="…"} or {user_email="…"} creates a new series per value and will exhaust the memory of whatever is storing them. High-cardinality data belongs in logs (§12.2), not in labels.

12.4 Correlating across sources

One id, threaded through everything

When a request touches three services, three log files each hold a fragment. A correlation id generated at the edge and passed along makes them one story — and reconstructing that story is a grep for the id followed by a sort by timestamp.

Log timestamps in UTC, ISO-8601, always

date -u +%Y-%m-%dT%H:%M:%SZ. Local time in logs means that during a daylight-saving change an hour repeats or vanishes, and that servers in different regions produce logs that cannot be merged. UTC and ISO-8601 sort correctly as plain text, which is what every tool in this chapter relies on.

Checkpoint

Why must logs go to stderr?

So a script’s output stays composable. With logs on stderr, value=$(script) captures only the data while progress messages still reach the terminal; with logs on stdout, the caller captures both and the data is corrupted. Levels are then a numeric comparison, so verbosity becomes an environment variable rather than a code change.

What goes wrong with hand-built JSON, and what is the escaping order?

A message containing a quote, backslash, or newline produces invalid JSON, and log aggregators silently drop the malformed line — losing exactly the message you needed. Escape backslashes first, then quotes, then control characters; doing quotes first would double the backslashes they introduce. Prefer jq --arg, which handles all of it.

When is a metric a gauge rather than a counter, and what must not be a label?

A gauge moves up and down (queue depth, disk usage); a counter only increases (total errors), and scrapers compute rates from it — mislabelling produces nonsense. Never label with unbounded values such as request ids or email addresses: each distinct value creates a time series and will exhaust the storage backend. High-cardinality data belongs in logs.

By the end of this chapter you will be able to

  • Diagnose a full disk — including the invisible case
  • Mount filesystems durably with UUIDs

13.1 Inodes, hard links, and symlinks

A filename is a pointer, not the file

The file is an inode — the metadata and the data blocks. A directory entry merely maps a name to an inode number, and several names can map to the same one. A hard link is another such name: indistinguishable from the “original”, sharing the same inode, and the data survives until the last name is removed. A symlink is a different thing entirely — a small file whose contents are a path, so it breaks if the target moves.

13.2 A full disk, including the invisible kind

df and du disagree — that is the diagnosis

A deleted file still held open occupies space nothing can see

The classic 3 a.m. problem: df reports the disk 100% full, du accounts for far less, and nothing you delete helps. The cause is a file that was rmed while a process still had it open — the directory entry is gone so du cannot see it, but the inode and its blocks are not released until the last file descriptor closes. It is almost always a log that was deleted instead of truncated (§7.4).

13.3 Mounting, durably

Never mount by device name

/dev/sdb1 is assigned in detection order, so adding a disk or a slow controller can renumber your devices and a reboot mounts the wrong filesystem — or refuses to boot. UUIDs are stable: they live in the filesystem itself. Use blkid to read them and reference the UUID in /etc/fstab.

13.4 LVM and encryption

A layer that lets storage grow

A raw partition is fixed at creation. LVM inserts a layer: physical volumes (disks) join a volume group (a pool), and logical volumes are carved from the pool — so you can extend a filesystem by adding a disk, with no downtime and no repartitioning. Its other gift is snapshots: a frozen point-in-time view you can back up consistently while the system keeps writing.

Back up the LUKS header

cryptsetup luksHeaderBackup. The header holds the encrypted master key; if it is corrupted, every byte on the device is permanently unrecoverable — passphrase or not. It is a few kilobytes, it takes one command, and it is the difference between a recoverable incident and total data loss.

Checkpoint

What is the difference between a hard link and a symlink?

A hard link is another name for the same inode — indistinguishable from the original, sharing content, and the data survives until the last name is unlinked. A symlink is a small file containing a path, so it dangles if the target moves or is deleted. Hard links cannot cross filesystems (inode numbers are per-filesystem) or point at directories; symlinks can do both.

df says full, du says otherwise, and deleting files does not help. Why?

A file was deleted while a process still held it open: the name is gone so du cannot see it, but the blocks are not freed until the last descriptor closes. Find them with lsof +L1 and fix by restarting the holder — and prevent it by truncate -s 0ing logs rather than rming them. If “No space left” contradicts df -h entirely, check df -i for inode exhaustion.

Why mount by UUID, and what must you never skip with LUKS?

Device names like /dev/sdb1 depend on detection order, so adding a disk can silently remount the wrong filesystem or break the boot; UUIDs live in the filesystem and are stable. With LUKS, back up the header — it holds the encrypted master key, and losing it makes every byte unrecoverable regardless of the passphrase.

14.1 Which file actually runs

The question everyone gets wrong

Bash reads different files depending on how it started, and putting a setting in the wrong one is why “my alias works in the terminal but not over ssh”. A login shell (ssh, a console login) reads /etc/profile then the first of ~/.bash_profile, ~/.bash_login, ~/.profile. An interactive non-login shell (a new terminal tab) reads ~/.bashrc. A non-interactive shell (a script) reads neither — which is exactly why cron jobs do not see your aliases (§7.1).

14.2 Aliases and functions

Aliases are text substitution; functions are programs

An alias replaces the first word of a command and cannot take arguments in the middle. A function can — it has $1, $@, local variables, and control flow. The rule: if it needs an argument anywhere but the end, or any logic at all, write a function. And aliases do not work in scripts (they are off in non-interactive shells), so anything a script needs must be a function or a real command.

14.3 A prompt that tells you something

Put the facts you keep asking for into PS1

The prompt is free screen space that can answer, continuously: did the last command fail, which git branch am I on, am I root, and which machine is this? The last is not cosmetic — a prompt that looks identical on your laptop and on production is how the wrong command gets run in the wrong place.

14.4 Dotfiles you can restore

Version them, and make setup one command

Your shell configuration is code. Keep it in git, and a new machine — or a rebuilt server — is a clone and a script rather than an afternoon of remembering. The bare-repository technique below tracks files in place in $HOME, with no symlink farm and no extra tooling.

Checkpoint

Why does an alias work in your terminal but not over ssh or in a script?

Different startup files. An interactive non-login shell reads ~/.bashrc; a login shell (ssh) reads ~/.bash_profile; a script reads neither, and has expand_aliases off besides. Source .bashrc from .bash_profile, keep interactive settings in .bashrc, and never rely on an alias inside a script — use a function.

Why must local code=$? be the first line of a prompt function?

Because $? is overwritten by the next command, including an assignment containing a command substitution. The demo showed an echo in between replacing a failure status with its own success. The same bug appears throughout error handling generally: capture the status immediately or lose it.

What must never go in a dotfiles repository?

Secrets — private keys (~/.ssh/id_*), ~/.aws/credentials, .env files, or any token pasted into .bashrc. ~/.ssh/config is fine; the keys it names are not. And once committed, the fix is rotating the credential, not rewriting history (Volume 14 §5.3).

Cloud Automation with Bash

Where bash still wins in a cloud world: gluing APIs together. Parsing JSON with jq, retrying with backoff because networks fail, paginating properly, and knowing the point at which a shell script should become a program.

By the end of this chapter you will be able to

15.1 jq is the missing piece

Never parse JSON with grep and sed

JSON is not line-oriented, so regular expressions on it break the moment a field contains a brace, an escaped quote, or the formatting changes. jq is a proper JSON processor: it filters, reshapes, and — critically — emits values safely for the shell with -r. Treat it as a required dependency for any script touching an API.

15.2 Retry, because the network will fail

A single API call is not reliable

Rate limits, brief outages, and DNS hiccups are normal. A script that gives up on the first non-zero exit will fail nightly for reasons that fix themselves in two seconds. Retry — but with exponential backoff so you do not hammer a struggling service, jitter so a fleet of machines does not retry in lockstep, and a cap so a genuine outage does not hang forever. And retry only what is safe to repeat.

Retry only idempotent operations

Repeating a GET is free; repeating a POST may charge a card twice

Retry reads and idempotent writes (PUT to a known key, a delete of a specific id) freely. For anything that creates, either use the API’s idempotency key if it offers one, or check whether the resource already exists before retrying. A retry loop wrapped blindly around a payment or an instance launch is a way to create two of something — the same argument Volume 15 §4.3 makes about proxy_next_upstream.

JSON is not line-oriented, so a regex breaks on a brace inside a string, an escaped quote, or reformatted output. jq parses properly and — with -r and @sh — emits values safely for the shell. from_entries converts the [{Key,Value}] shape cloud APIs use into an indexable object, and group_by aggregates without leaving jq.

Why does a retry loop need jitter as well as backoff?

Backoff stops one client hammering a struggling service; jitter stops many clients retrying in lockstep. Fifty machines that failed at the same instant will, without randomisation, retry at exactly the same moments and keep the recovering service down. Also retry only idempotent operations — a blind retry around a create can produce two of something.

When has a script outgrown bash?

When it stops orchestrating and starts computing: nested data structures, decimal arithmetic, real error handling, or non-trivial parsing. Bash’s advantage is calling other programs concisely; beyond about three hundred lines it has no modules, no exceptions, and fragile quoting. Rewrite early — a nine-hundred-line production script is one nobody will touch.
