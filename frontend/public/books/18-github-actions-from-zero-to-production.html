About this book

A workflow file is easy to write and hard to trust. It holds credentials, it is triggered by strangers, and it runs third-party code nobody on your team has read. Worst of all it reports success in green, which is the one signal everybody believes. This book is about the distance between a green check and a pipeline that did what you meant.

Everything here was run. When Chapter 6 claims that npm test | tail -5 can fail its tests and still pass its job, two jobs run a byte-identical script and finish with opposite results — the only difference is one line of YAML. When Chapter 8 says a deploy can exit 0 and change nothing, the log shows ln -sf returning zero while the server still serves the old release. When Chapter 7 argues for layer caching, the two builds are on the page: 11.5 s and then 5.7 s, with CACHED beside the install step.

The security chapters are demonstrations rather than warnings. Chapter 3 masks a token and then prints it anyway, three different ways. Chapter 10 publishes a small, harmless action, uses it, and then republishes it under the same reference — the workflow file is not touched, and the second run reads a secret out of the job and prints it past the masking, while the job stays green. That is not an exploit. It is what a version tag is.

Who should read this

Anyone maintaining a pipeline they did not write, and anyone about to write one. You need to be comfortable at a shell and to have used git; nothing else is assumed. The lab is local — act runs the workflows in Docker — so every listing can be reproduced without pushing to anybody’s repository.

How this book is organised

Chapters map one-to-one onto the thirteen modules of the GitHub Actions track in Code Lab, each ending with that module’s graded exercises — 130 in total, all linked. Read 0 through 3 in order. After that, Chapters 6 and 10 are the two worth reading even if you skip everything else.

Where the book says “this cannot be shown here”

Three features are enforced by GitHub’s own services rather than by the workflow file: environment approvals (§8.5), concurrency groups (§12.3), and OIDC (§10.4). A local runner has nothing to enforce and runs straight through. Those sections say so plainly instead of printing something that looks like proof — and the warning is practical, because testing a workflow locally does not prove that a protected deploy is protected.

Four lines that prevent most of what this book demonstrates

defaults: run: shell: bash so a pipe cannot hide a failed test. permissions: contents: read so a compromised step cannot push. Third-party actions pinned to a commit SHA, so the code you reviewed is the code that runs. And concurrency on CI, so a superseded run stops burning minutes. All four are cheap, all four apply everywhere, and between them they cover the majority of the failures on these pages.

Chapter Zero · Part I

Workflows, Jobs, and Steps

A workflow is a YAML file that GitHub runs on a machine it rents you when something happens in your repository. This chapter runs one for real, takes the three-level hierarchy apart, and shows what actually makes a job fail.

By the end of this chapter you will be able to
  • Write a workflow and understand where it lives
  • Distinguish workflows, jobs, and steps
  • Read a run’s output and diagnose a failure
  • Run workflows locally before pushing them

0.1 The smallest workflow that does something

One file, three levels

A workflow lives at .github/workflows/*.yml and is triggered by an event. It contains jobs, which run in parallel by default, each on its own fresh virtual machine. A job contains steps, which run sequentially in the same machine and share its filesystem. Everything else in this book is detail on those three levels.

0.2 Jobs are parallel; steps are sequential

Each job gets a clean machine

This is the consequence people trip over: first and second share nothing — not the checked-out code, not installed packages, not files written to disk. A job that needs the output of another must publish it as an artifact or an outputs value (Chapter 5). If two jobs both need the repository, both must run actions/checkout.

0.3 What makes a step fail

The exit code, and nothing else

A step fails when its command exits non-zero — the same contract as any shell script. GitHub runs each run: block with bash -e, so the first failing command ends the step, and a failed step ends the job unless you say otherwise.

0.4 Running workflows before you push

The feedback loop matters more than it sounds

Editing a workflow, pushing, waiting two minutes, and reading a log is a terrible way to iterate — and it fills your history with “fix ci” commits. Two tools fix it. actionlint checks a workflow statically in milliseconds, catching YAML errors, bad expressions, and unknown fields. act actually executes the workflow locally in Docker, which is how every listing in this book was produced.

Checkpoint

What is the difference between jobs and steps?

Jobs run in parallel, each on its own fresh machine, sharing nothing — no code, no installed packages, no files. Steps run sequentially inside one job and share that machine’s filesystem. Use needs: to make one job wait for another, and artifacts or job outputs to pass anything between them.

What makes a step fail, and how do you let one fail safely?

A non-zero exit code — each run: block executes under bash -e, so the first failing command ends the step and a failed step ends the job. continue-on-error: true lets a step fail without failing the job; if: always() makes a step run regardless, which is how cleanup and log upload survive a failure.

Why run workflows locally, and what are the limits?

Push-and-wait is a two-minute feedback loop that fills history with “fix ci” commits. actionlint catches YAML and expression errors statically — including a misspelled context that would silently expand to an empty string. act executes the workflow in Docker. Neither is identical to GitHub: no OIDC, differing action behaviour, so treat them as a fast first check.

1.3 pull_request versus pull_request_target

The distinction that has caused real breaches

One of these runs untrusted code with your secrets

pull_request checks out the fork’s code and runs with no secrets and a read-only token — safe, because the code came from a stranger. pull_request_target runs in the context of the base repository, with secrets and a write token, and by default checks out the base branch. It exists so a workflow can label or comment on a PR from a fork.

The danger is combining them: pull_request_target plus an explicit checkout of the PR’s head means you are running an attacker’s code with your repository’s secrets. That pattern has leaked production credentials from real projects.

Table 1.2 The rule: use pull_request for anything that runs the contributor’s code, and pull_request_target only for jobs that read metadata (labelling, commenting, size checks) and never execute the PR’s contents. If you find yourself writing ref: ${{ github.event.pull_request.head.sha }} under pull_request_target, stop.

1.4 Skipping work you do not need

Concurrency: cancel the run nobody is waiting for

Pushing three times in a minute starts three runs of the same workflow, and the first two are already obsolete. A concurrency group fixes it — and Chapter 12 goes further, but the two-line version below is worth adding to every CI workflow today.

Checkpoint

How do multiple filters on one event combine?

With AND. A push with both branches and paths filters runs only when the push is to a matching branch and touches a matching path. The paths filter is what stops a documentation commit triggering a full build, and types: [opened, synchronize, reopened] is what makes PR CI re-run on later pushes.

Why is pull_request_target dangerous?

It runs with your secrets and a write token. That is safe only because it checks out the base branch by default — code you control. Explicitly checking out the PR’s head under that trigger executes a stranger’s code with your credentials, a pattern that has leaked real production secrets. Use pull_request to run contributor code, and pull_request_target only for metadata work.

When should cancel-in-progress be false?

For deploys. Cancelling a superseded CI run is free — nobody wants the result of an obsolete commit. Cancelling a deploy part-way through leaves infrastructure in an unknown state, so deploy workflows should queue instead. Same directive, opposite setting, decided by whether the work is interruptible.

2.2 Pinning: a tag is not immutable

@v4 is a moving target

Whoever owns the action can repoint the tag at any time

uses: some/action@v4 resolves to whatever commit v4 points at today. Tags in git are mutable, so the author — or anyone who compromises their account — can move v4 to new code, and every workflow in the world that references it runs that code on the next execution, with your secrets in scope. This is not theoretical: it is how the tj-actions/changed-files compromise of 2025 reached tens of thousands of repositories.

Pinning to a full commit SHA makes the reference immutable. It is uglier and it needs Dependabot to keep current, and it is the correct default for anything touching secrets.

GitHub also lets an organisation require SHA pinning through an allow-list policy, which is worth turning on.

2.3 Judging an action before you use it

You are adding a dependency that executes with your permissions

Checkpoint

Why does almost every job need actions/checkout?

Because a runner starts empty — your repository is not present until something clones it. Jobs do not inherit files from each other either, so every job that touches the code needs its own checkout. Note the default is a shallow clone of one commit; set fetch-depth: 0 if anything reads history.

Why pin actions by SHA rather than by tag?

Git tags are mutable: the owner, or an attacker with their account, can repoint v4 at new code, and every workflow referencing it runs that code with your secrets on the next execution — which is how the 2025 tj-actions/changed-files compromise spread. A full SHA cannot be repointed; add a version comment and let Dependabot update both.

When should you write run: instead of using an action?

Whenever the action does something a few lines of shell would do — reading a version, formatting a date, counting changed files. Every action is third-party code executing with your job’s permissions, plus an update burden and a pin to maintain. Reserve actions for genuinely hard work: toolchain setup, artifact handling, multi-arch image builds.

3.2 Environment variables at three scopes

Multi-line values need a delimiter

echo "KEY=$MULTILINE" >> $GITHUB_ENV silently corrupts the file when the value contains newlines. The heredoc form is required: { echo "KEY<<EOF"; cat file; echo "EOF"; } >> "$GITHUB_ENV". Choose a delimiter that cannot appear in the content — a random one if the content is untrusted, since a value containing your delimiter can otherwise inject arbitrary variables.

Checkpoint

What is the difference between vars and secrets?

vars holds non-secret configuration (regions, URLs, flags), visible in logs and available to fork workflows. secrets is encrypted, masked in logs, and withheld from forks. Use vars for anything merely environment-specific; reserve secrets for credentials — and prefer OIDC over storing long-lived cloud keys at all.

Why does export FOO=bar not survive to the next step?

Because each run: block is a separate shell process. To carry a value forward, append NAME=value to the file at $GITHUB_ENV, which the runner reads between steps — using the heredoc form for multi-line values, since a plain echo corrupts the file on a newline.

Why is log masking not a security control?

It works by matching the secret’s exact string in output. Any transformation defeats it — the demo printed the token base64-encoded, reversed, and space-separated, all unmasked. Masking catches accidental echoes only. Pass secrets through env:, never echo them, and never route untrusted text like a PR title into a run: block, where it becomes executable script.

Matrix Builds

4.1 One job, many combinations

The product grows faster than people expect

Three axes of 4, 3, and 3 values is 36 jobs — each starting a fresh machine, installing dependencies, and consuming minutes. Matrices are the most common cause of a surprising CI bill. 4.4 A matrix computed at runtime

Guard the empty case

if: needs.discover.outputs.targets != '[]' on the build job. A matrix built from an empty array is a configuration error, not a no-op, and it fails the run — which is a confusing way to learn that no packages changed.

Checkpoint

How many jobs does a two-axis matrix produce?

The Cartesian product — three Node versions × two suites is six jobs, each on its own machine. Three axes of 4×3×3 is 36. Always set a name: that interpolates the matrix variables, or the UI shows identically-named jobs and a failure does not tell you which combination broke.

What does include do that exclude does not?

Two things, depending on its keys. If they match an existing combination it adds variables to that combination; if they do not, it adds a whole new combination outside the product. exclude only ever subtracts. That dual behaviour is the most confusing part of matrix syntax.

Why turn fail-fast off?

Because the default cancels every other combination on the first failure, so you learn that something broke but not the pattern — whether one version fails or all of them, which are very different diagnoses. Turning it off costs minutes and buys information; pair it with max-parallel when the jobs share a rate-limited resource.

Two things that persist beyond a job, and they are not interchangeable. A cache makes the next run faster; an artifact carries a build result to another job or to a human. Confusing them is the source of both slow pipelines and lost outputs.

  • Understand restore-keys and partial matches
  • Upload and download artifacts between jobs
  • Choose cache or artifact for a given need

Caching a build output and depending on it is the mistake this table exists to prevent — caches are evicted without warning, and the pipeline then fails mysteriously days later.

5.2 Caching, and the key

The two ways to get caching wrong

A static key (key: node-modules) means the first cache written is restored forever, including after you upgrade a dependency — producing a build that tests the wrong code and is maddening to debug. Because caches are immutable, the fix is never "overwrite the cache"; the key itself must change, which is exactly what hashFiles does. Caching the wrong path is the other: caching node_modules is common, but caching ~/.npm and running npm ci is often better, because ci then still reconciles the tree against the lockfile while skipping the network.

What restore-keys buys you

On an exact-key miss, each prefix in restore-keys is tried in order and the most recent cache whose key starts with it is restored. So when you add one dependency, the key changes and the exact match fails, but Linux-node- still matches yesterday’s cache — you start from a nearly complete node_modules instead of an empty one. The restored entry is a partial match, so cache-hit is false and your install step still runs; that is correct, and it is why the install must be idempotent rather than conditional on the directory merely existing.

5.3 Artifacts

v4 artifacts are immutable

In upload-artifact@v4 each artifact name may be uploaded once per run — a second upload with the same name fails rather than merging, which is a deliberate change from v3. In a matrix, every combination must therefore use a distinct name (dist-${{ matrix.os }}-${{ matrix.node }}), and download-artifact can then take a pattern: with merge-multiple: true to collect them. Migrating a v3 matrix workflow without changing the names is the most common v4 upgrade failure.

Checkpoint

How do you decide between a cache and an artifact?

Ask whether the pipeline would still be correct if the data vanished. If yes it is a cache — an optimisation, evicted at will. If a later job needs it to exist, it is an artifact. Depending on a cache produces a pipeline that fails mysteriously days later when it is evicted.

Why must a cache key include a hash of the lockfile?

Because caches are immutable: writing to an existing key does nothing. A static key therefore restores the first cache forever, including after a dependency upgrade — so the build tests the wrong code. hashFiles makes the key change with the dependencies, and restore-keys supplies a prefix fallback so a small change still reuses most of the previous cache.

What changed about artifact names in v4?

Each name may be uploaded only once per run — a second upload with the same name fails instead of merging. Matrix jobs must therefore use distinct names such as dist-${{ matrix.os }}, collected later with pattern: and merge-multiple: true. Also set if-no-files-found: error, since the default merely warns.

6.2 The job that passes while its command fails

This is the single most expensive default in GitHub Actions, and it is invisible until it bites. Two jobs below run a byte-identical script. One line of YAML differs between them.

The default shell on Linux is bash -e, without pipefail

Omit shell: and GitHub runs bash -e {0}. Write shell: bash and it runs bash --noprofile --norc -eo pipefail {0}. The -e is there either way, which is why most people never notice — a bare failing command does stop the step. It is only when you pipe into tail, tee, grep, jq or head — exactly what you do to make CI logs readable — that the failure disappears. A green pipeline whose tests are failing is worse than a red one.

The same trap, three more disguises

run: cmd || true and continue-on-error: true both discard the failure deliberately, which is fine when you mean it and a disaster when it was pasted in to silence a flaky step and never removed. if: always() on a later step does not mask the earlier failure — the job still fails, which is what you want for “always upload the report”. And a backgrounded command (cmd &) has no exit status the step will ever see.

7.2 Running the job inside a container

What a container job costs you

You give up the runner’s preinstalled software. A hosted runner ships Node, Python, Go, Docker, the AWS CLI and much more; python:3.13-alpine ships Python and almost nothing else — not even bash, which is why a run: block using bashisms fails there with not found. You also give up some actions: anything invoking docker or expecting sudo will not work, and Node-based actions need a Node the image may not have. Alpine in particular uses musl rather than glibc, so a prebuilt binary that runs everywhere else can fail with a cryptic loader error.

When it is the right call

Use container: when the job needs a toolchain the runner does not have and a setup-* action does not offer — an old compiler, a scientific stack, a vendor SDK — or when you want CI to run in exactly the image production runs, which is the strongest argument for it. Pin the image by digest rather than tag for the same reason you pin actions by SHA: python:3.13-alpine is a moving target, and a silent base-image update is a build failure with no commit behind it.

7.3 Building and pushing an image

7.4 Making the second build fast

Why a build cache needs somewhere to live

7.5 Tags a human can read

The tag you must not rely on

latest means “whatever was pushed last”, which is not a version, and on a busy repository it is a race. Use it for convenience if you like, but deploy from an immutable reference: a semver tag you never move, or better, the digest from Listing 7.3. The failure this prevents is the one where a rollback to latest rolls you forward.

Small images are a security posture, not just a download saving

The multi-stage build in Listing 7.2 exists mostly so the final image contains no compiler, no package manager cache, and no build-time secrets in an intermediate layer. Every binary you ship is attack surface someone has to patch. node:22-alpine over node:22 is roughly 150 MB against 1.1 GB, and the difference is almost entirely software you did not intend to ship.

Checkpoint

A workflow declares a service and expects it to be built from the repository’s Dockerfile. What happens?

It is pulled from a registry, not built — services: takes an image reference only. Build the image in an earlier step (or job), push it, and reference the pushed tag; or run it with docker compose up -d as an ordinary step. There is no form of services: that builds.

Why does a container job sometimes break actions that work everywhere else?

Because the job no longer has the runner’s preinstalled software. Node-based actions need a Node runtime the image may lack; anything calling docker or sudo will not find them; and on Alpine, musl rather than glibc breaks prebuilt binaries. container: replaces the environment, it does not extend it.

An image build takes six minutes on every push although dependencies never change. Two causes?

No layer cache — the runner is new each time, so cache-from/cache-to (type=gha or type=registry) is required for anything to persist. And a Dockerfile that copies source before installing, so any edit invalidates the install layer. Fix the Dockerfile first; caching a badly ordered build caches very little. For a multi-stage build, add mode=max.

Why deploy by digest rather than by tag?

A tag is a mutable pointer — it can be moved to different content at any time, so “we deployed 1.4.0” does not identify what ran. A digest is the content hash and cannot be repointed. Capture steps.build.outputs.digest at build time and pass that through to the deploy.

8.2 A deploy that actually runs

Never echo a secret, even to check it

Chapter 3 showed masking being defeated by trivial transformations; the lesson here is narrower and simpler. A private key should go from the secret straight into a file with printf '%s\n' and never through anything that prints. ssh-keygen -lf gives you a fingerprint — enough to confirm which key was installed without revealing it. And prefer ssh-keyscan into known_hosts over StrictHostKeyChecking=no: the latter turns off the one check that would notice you are talking to the wrong machine.

The deploy key should be able to do exactly one thing

On the server, restrict the key in authorized_keys: command="/usr/local/bin/deploy",no-pty,no-agent-forwarding,no-port-forwarding ssh-ed25519 AAAA…. Then a leaked CI key runs your deploy script and nothing else — no shell, no tunnel into the private network. This costs ten minutes and removes the worst consequence of the most likely breach.

8.3 The switch that silently deploys nothing

The release is uploaded, the job is green, and production is running the previous version. This is not a hypothetical; it is a one-character difference.

Verify the switch, not the upload

Every failure in this section produces a successful upload. That is why Listing 8.1 ends by reading readlink and VERSION back over SSH: it asserts the thing you actually care about. Better still, curl the running application’s health endpoint and fail on anything but the expected version — then a green deploy means the new code is serving traffic, which is the only claim worth making.

8.4 Rolling back

Keep releases, but not all of them

A deploy that never prunes fills the disk, and a full disk during a deploy is a memorable evening. Add ls -1dt /srv/app/releases/* | tail -n +6 | xargs rm -rf after a successful switch to keep the last five. Prune after the switch and never the release current points at.

Why prefer OIDC over storing a cloud access key?

A stored key is long-lived, works from anywhere, and stays valid until someone notices. OIDC issues a token per run, scoped to the repository and often the branch or environment, valid for minutes. There is nothing in the repository to leak, and nothing to rotate.

Start with a composite action

It is the smaller commitment. A composite action is a directory you can delete, it shows up as ordinary steps in the log, and debugging it is debugging your own job. Promote it to a reusable workflow at the moment you need a different runner, a matrix, a service container, or a job boundary — and not before. The reverse migration, reusable workflow back to composite, is much more disruptive because every caller changes shape.

Checkpoint

When must it be a reusable workflow rather than a composite action?

When it needs its own runner (runs-on), a matrix, service containers, or its own job boundary in the UI. A composite action packages steps and runs inside the caller’s job, so it inherits the runner and cannot fan out. If none of those apply, a composite action is the smaller and more debuggable choice.

A caller reads an empty string from a reusable workflow’s output. Why?

Almost always a missing forwarding level. The value has to travel three times: step writes $GITHUB_OUTPUT → job republishes it under outputs: → workflow republishes that under on.workflow_call.outputs with value:. Missing the middle level is the usual cause. Also check the caller reads it via needs.<job>.outputs and declares that job in needs.

What is wrong with secrets: inherit?

It passes every secret the caller can see, not the one the callee needs — so a workflow you may not maintain gains your signing key and cloud credentials. Name the secrets explicitly; the extra lines double as the audit trail of what the callee could reach.

A reusable workflow cannot see an env: value set by its caller. Bug or design?

Design. It is a separate execution context, not a textual include — no caller env, no caller step outputs. Everything it needs arrives through with: or secrets:. Wanting to reach back into the caller is the signal that you wanted a composite action instead.

Chapter Ten · Part IV

Permissions and Security

A workflow is code with credentials, triggered by strangers, running third-party software you have never read. This chapter is about reducing what any one of those can cost you — starting with a demonstration of the most-ignored risk in the whole system.

By the end of this chapter you will be able to
  • Restrict what GITHUB_TOKEN is allowed to do
  • Understand why a version tag is not a version
  • Handle pull requests from forks without giving them your secrets
  • Replace stored cloud keys with OIDC
  • Apply a hardening checklist that fits on one page

10.1 The token every job already has

The default is a repository setting, not a workflow setting

A repository created before 2023 may still default to read and write all scopes, meaning every workflow in it can push commits, publish packages, and edit issues unless told otherwise. Newer repositories default to read-only. You cannot tell which you have by reading the YAML — it is under Settings → Actions → Workflow permissions. Setting permissions: explicitly at the top of every workflow removes the question entirely, which is why it is worth doing even when the default is already correct.

10.2 A version tag is not a version

Nothing in this section requires a compromised maintainer or a clever exploit. It requires only that a tag is a mutable pointer, which it is.

The same reference, different code

This applies to the actions you trust most

actions/checkout@v4 is a moving reference maintained by GitHub, and the risk there is low. The risk is in the long tail: the marketplace action with 300 stars and one maintainer, added two years ago, which now runs in a job that has your deploy key. Pin everything you do not control, and prefer inlining five lines of shell over adding a dependency for something you could write yourself — Chapter 2 made that argument on maintenance grounds, and this is the security half of it.

10.3 Pull requests from forks

What is actually wrong here

One: pull_request_target runs in the context of the base repository — with a writable token and access to repository secrets — while pull_request runs with a read-only token and no secrets. Two: checking out head.sha pulls the fork’s code into that privileged context, and npm install then executes the fork’s postinstall script. Anyone who can open a pull request now runs arbitrary code with your secrets. Three: the PR title is interpolated straight into a shell command, so a title containing $(…) executes — that one actionlint catches.

The thing that will actually get you

It is not a novel exploit. It is an action added in 2023 by someone who has left, referenced by a floating tag, running in a job that has a deploy key in its environment because that was convenient at the time. Checkpoint

Adding permissions: packages: write broke actions/checkout. Why?

The permissions: block is a whitelist, not a patch — naming any scope sets every unnamed scope to none, so contents: read was removed. List every scope the job needs, contents: read included.

Your workflow file has not changed in a year. Can the code it runs have changed?

Yes, if it references actions by tag or branch. A tag is a mutable pointer; repointing it makes the same uses: line run different code, with access to everything in the job — as §10.2 demonstrated, including reading a secret past masking while the job stays green. Pin to a commit SHA.

Why is pull_request_target plus checkout ref: head.sha the classic mistake?

pull_request_target grants a writable token and repository secrets; checking out the head SHA then brings the fork’s code into that privileged context, and any build step executes it. Anyone able to open a pull request runs code with your secrets. Use pull_request for contributor code, or split the work across a workflow_run boundary.

What makes an OIDC setup weak in practice?

A sub condition of repo:owner/name:*. It authenticates the repository but not which branch, workflow or environment — so any run, including one introduced by a pull request, can assume the role. Bind to ref:refs/heads/main or, better, environment:production, which composes with approvals.

Chapter Eleven · Part V

Self-Hosted Runners

A self-hosted runner is a machine you own running an agent that accepts jobs. It solves problems hosted runners cannot — and it hands you back three that GitHub was solving for you, one of which is a security hole you can open in a single click.

By the end of this chapter you will be able to
  • Decide whether you actually need one
  • Match jobs to runners with labels
  • Handle a workspace that is not clean
  • Understand why they must not run public pull requests
  • Choose between persistent and ephemeral runners

11.3 The workspace is not clean

Two failure modes, and the second is worse

A build that fails because of leftovers is annoying and obvious — a stale node_modules, a lock file from a killed process. A build that succeeds because of leftovers is the dangerous one: it passes because a dependency is still installed from three weeks ago, and it is not reproducible anywhere else. You discover this the day you add a second runner and the same commit fails on one machine and passes on the other.

Or sidestep the whole problem

Run the job in a container (container:, Chapter 7) and the filesystem it sees is fresh even though the host is not — leftovers on the runner become invisible. Better still, use ephemeral runners (§11.5), which accept exactly one job and then unregister. That restores the hosted-runner guarantee, and it is the configuration you want for anything you cannot fully trust.

11.4 Why not on a public repository

Never attach a self-hosted runner to a public repository

This is GitHub’s own guidance, and the reason is mechanical rather than theoretical. Anyone may fork a public repository and open a pull request. If your workflow runs on pull requests — the normal configuration — a stranger’s code executes on your machine, inside your network. On a persistent runner they can leave something behind for the next job, which may be a job that has your deploy key. The fork does not need write access, does not need approval on a first-run-approved repository, and the pull request can be closed afterwards.

A persistent self-hosted runner on a public repository should be treated as a machine that strangers can run code on, because it is one.

The runner registration token is a credential

It is short-lived, but the .credentials file the runner writes after registering is not — it holds a long-lived token that can register more runners. Anyone with a shell on that machine, including a job that ran on it, can read it if the runner service user owns it and the job runs as the same user. Run the agent as a dedicated unprivileged user, and never as root.

Checkpoint

A job with runs-on: [self-hosted, linux, x64] never starts and never errors. Why?

No runner carries all three labels — labels are an AND, and an unsatisfiable combination queues silently rather than failing. Compare the exact label strings on the runner (a runner labelled amd64 does not match x64). Every self-hosted runner gets self-hosted, its OS, and its architecture automatically; the rest you add.

Which is worse: a build that fails from leftover state, or one that passes?

The one that passes. A failure is visible and gets fixed; a pass that depends on something installed weeks ago is not reproducible anywhere else, and you find out when a second runner joins and the same commit behaves differently. actions/checkout cleans the workspace and nothing else — Docker images, temp files and installed packages are yours to manage.

Why must self-hosted runners not serve a public repository?

Anyone can fork it and open a pull request, and a pull-request workflow then runs a stranger’s code on your machine inside your network. On a persistent runner they can also leave something behind for a later, more privileged job. Split the repositories, or use ephemeral runners in a disposable, network-isolated VM.

What does --ephemeral buy, and what does it cost?

It buys the hosted-runner guarantee back: one job per registration, no state carried forward, and a compromise that ends with the job. It costs cache warmth, since nothing persists — which is exactly the problem actions/cache and a registry-backed layer cache already solve.

Advanced Patterns: Concurrency and Environments

The last chapter is about the shape of a pipeline rather than any single job: which jobs wait for which, what happens to the graph when one of them is skipped, and how to stop two runs of the same workflow from fighting over the same server.

By the end of this chapter you will be able to
  • Build a job graph that fans out and back in
  • Use status functions to branch on success and failure
  • Avoid the skipped-dependency trap
  • Serialise deploys and cancel superseded CI runs
  • Assemble everything into one pipeline

12.1 Conditions, and the four status functions

FunctionTrue whenTypical use
success()Every job in needs succeededThe default — you rarely write it
failure()Any job in needs failedAlerting, opening an issue
cancelled()The run was cancelledReleasing a lock, tearing down
always()Unconditionally, cancellation includedUploading logs and reports
!cancelled()Success or failure, but not cancellationUsually what always() should have been

Table 12.1 The last row deserves the emphasis. always() means always — including after somebody hits cancel, at which point your clean-up job starts on a run everyone has walked away from, and a cancelled deploy can proceed to deploy. !cancelled() covers reporting on both success and failure while still honouring a cancellation, and is the better default for almost everything except releasing a lock.

A step condition and a job condition are not the same scope

if: on a step is evaluated against the steps before it in the same job — failure() there means “an earlier step in this job failed”. if: on a job is evaluated against needs. Writing if: failure() on a job with no needs is therefore always false, which is a quiet way to build an alerting job that never alerts.

12.2 The skipped dependency

This is how a “working” pipeline quietly stops deploying

Put a paths: filter or an if: on a build job so it only runs when relevant files change, and every job downstream of it inherits the skip. The pull request is green — a skipped job is not a failed job, and the checks all pass — while the deploy has not happened. Nothing in the interface says so. The fix is to make downstream jobs state their own condition: if: always() && needs.build.result != 'failure', or better if: !cancelled() && needs.build.result == 'success', so “skipped upstream” and “successful upstream” are distinguished deliberately rather than by default.

needs.x.resultMeaning
successIt ran and passed
failureIt ran and failed
cancelledThe run was cancelled
skippedIts if: was false, or an upstream job was skipped

Table 12.2 Reading result explicitly is the only way to tell these four apart, because the default success() collapses the last three into “do not run”. When a job must run unless something genuinely broke, test result != 'failure' rather than relying on the default.

cancel-in-progress on a deploy is how you corrupt a release

Cancelling a deploy mid-flight can leave files half-uploaded, a database migration half-applied, or a symlink pointing at an incomplete release. Set it to false on anything that changes a system, pair it with the mv -T atomic switch from Chapter 8 so that even a killed job cannot leave a half-switched state, and give the job a timeout-minutes so a hung deploy does not block the queue indefinitely.

Like the environment approvals in Chapter 8, concurrency is enforced by GitHub’s scheduler rather than by the workflow file — there is no second concurrent run locally for a group to serialise. 12.5 Everything, in one pipeline

The order to adopt these in

If you take one thing from this book, take defaults: run: shell: bash — it costs two lines and stops a green pipeline lying to you about failing tests. Then permissions: contents: read, then pinned third-party actions, then concurrency on CI. Those four are cheap, apply to every repository, and between them prevent the majority of the failures this book has demonstrated.

Checkpoint

An alerting job with if: failure() never fires. Why?

Most likely it has no needs. A job-level condition is evaluated against needs, so with nothing to depend on there is no failure to observe and failure() is always false. Add every job it should watch to needs. (On a step, failure() refers to earlier steps in the same job — a different scope.)

A path filter was added to the build job and now nothing deploys, but every check is green. What happened?

A skipped job propagates skipping to everything downstream, and a skipped check reports as passing. The pull request looks fine while the deploy never ran. Give downstream jobs an explicit condition — if: !cancelled() && needs.build.result == 'success' — so “skipped” and “succeeded” are distinguished on purpose.

Why does CI want cancel-in-progress: true and a deploy want false?

A newer push makes the older CI result irrelevant, so cancelling saves minutes with nothing lost. A deploy changes a system: cancelling mid-flight can leave a half-uploaded release or a partly applied migration. Deploys must queue. Pair the queue with an atomic switch and a job timeout so a hung deploy cannot hold the lock forever.

When is !cancelled() better than always()?

Almost whenever you were about to write always(). always() keeps running after someone hits cancel — so a cancelled run can still deploy, or a clean-up job starts on a run everybody has abandoned. !cancelled() still covers both success and failure, which is what “always upload the report” actually means. Reserve always() for releasing a lock or tearing down infrastructure that must be freed even on cancellation.
