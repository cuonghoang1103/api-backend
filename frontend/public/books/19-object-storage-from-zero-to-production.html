About this book

Object storage is easy to start with and full of edges that only appear at scale, under load, or in front of a security review. It looks like a filesystem, and it is not one; it looks like it has folders, and it does not; it gives you a checksum-shaped string that is not a checksum. This book is about those edges, and it demonstrates each one rather than asserting it.

Everything here was executed. When Chapter 0 says the ETag stops being an MD5 above a certain size, the same client uploads a small file and a large one and the second ETag comes back as …-3. When Chapter 1 says a listing caps at a thousand keys, the bucket is seeded with 1,200 and the command line cheerfully reports all of them while the API underneath returns IsTruncated: true. When Chapter 5 claims a browser upload policy is enforced by the server rather than by your code, three uploads go out and come back 204, 400 EntityTooLarge and 403 AccessDenied.

The security material is demonstrated the same way. Chapter 8 makes one prefix public with a policy and shows the same missing key returning 404 where you may read and 403 where you may not — which is why an AccessDenied on a read is so often a typo rather than a permissions bug. Chapter 10 uploads a photograph carrying GPS coordinates and shows them gone from every derivative, along with the one flag that quietly puts them back.

Who should read this

Anyone storing user-uploaded files, serving assets, or inheriting a bucket somebody else designed. You need JavaScript and a terminal; no AWS account is required, because the lab is a local S3-compatible server and every listing can be reproduced offline.

How this book is organised

Chapters map one-to-one onto the twelve modules of the Object Storage & S3 track in Code Lab, each ending with that module’s graded exercises — 120 in total, all linked. Read 0 and 1 first; they establish the flat keyspace that everything later depends on. Chapters 4 and 5 are a pair, and Chapter 11 is the one to read before designing anything.

Where the lab is not AWS, the book says so

The lab is MinIO, which implements the S3 API. The data plane behaves identically and Chapters 0–4 are indistinguishable from AWS. Three differences are surfaced deliberately rather than hidden: it rejects a key containing an empty path segment where AWS accepts one (§1.4); it does not implement PutBucketCors and answers preflights for any origin, so a CORS bug cannot be reproduced locally (§5.3); and it refuses the AbortIncompleteMultipartUpload lifecycle rule, which happens to be the one rule every production bucket needs (§9.3). A permissive lab is a false-negative machine, and that is worth knowing about your own.

Four decisions that shape everything else

The key is the only index — there is no query but a prefix, so the key scheme is the schema, and it cannot be changed later without copying every object. Metadata is fixed at write time, so Content-Type and Cache-Control must be right on the way in. The database knows what the bytes are; the bucket only stores them. And anything that must survive a compromise lives in a second account, written by a credential that cannot delete.

Chapter Zero · Part I

Object Storage Fundamentals

Object storage looks like a filesystem in every user interface built on top of it, and behaves like one for about a week. This chapter is about the four places the resemblance breaks — and each break is shown happening, because reading that "the keyspace is flat" is not the same as watching a directory fail to exist.

By the end of this chapter you will be able to
  • Say precisely how object storage differs from a filesystem
  • Explain why there are no directories, only key prefixes
  • Predict what happens when you write to an existing key
  • Know why an ETag is not a checksum
  • Run the lab used for the rest of this book

Table 0.1 The last two rows are why anyone puts up with the rest. An object is reachable by HTTP from any machine on earth without a mount, a VPN, or a shared filesystem — and it is stored redundantly enough that losing one is not something you plan for. The price is every row above them, and the row that catches people first is rename: moving a million objects into a different prefix is a million copies and a million deletes, and it is billed as such.

0.2 There are no directories

Why this matters more than it sounds

Three consequences follow immediately. An empty folder cannot exist — delete the last object under photos/2026/ and the prefix vanishes, which is why console UIs create zero-byte objects with a trailing slash to fake it. Renaming a folder is not an operation; it is a list, then a copy and a delete per object. And listing is prefix-ordered, not tree-ordered — ListObjectsV2 returns keys in lexicographic order across the entire bucket, so a listing of a million keys is paginated 1,000 at a time no matter how they are “nested”.

This is also why key design is a real design decision

Because the key is the only index you get. There is no WHERE, no secondary lookup, and no way to ask “which objects were uploaded by user 42” unless the answer is a prefix. Chapter 11 designs keys properly; for now, note that user/42/avatar.jpg is queryable and avatars/42.jpg is not.

0.3 An object is replaced, never edited

Read-after-write is strongly consistent — since December 2020

Older material describes S3 as eventually consistent: you would PUT an object, immediately GET it, and sometimes get a 404. That has not been true since December 2020 — S3 now gives strong read-after-write consistency for all operations, including overwrites and deletes, at no cost. If you are carrying a retry loop that exists to work around this, you can delete it. Note the guarantee is about a single key, not about listings being instantly complete in every edge case, and not about other providers — check before assuming.

Metadata is fixed at write time

Content-Type, Cache-Control, Content-Disposition and your own x-amz-meta-* headers are set when the object is written and cannot be changed in place. Correcting a wrong Content-Type across a bucket means copying every object onto itself with --metadata-directive REPLACE. Getting it right at upload time is much cheaper than fixing it, and Chapter 3 shows how it is usually got wrong.

0.4 The ETag is not a checksum

So how do you verify an object?

Ask S3 to compute a checksum you name. Uploading with --checksum-algorithm SHA256 stores a real, additive checksum that survives multipart, and head-object --checksum-mode ENABLED returns it. That is the supported answer, and it is what Chapter 3 uses. Treat the ETag as what it is — an opaque change-detection token, useful for If-None-Match and conditional requests, and meaningless as an integrity check.

Checkpoint

Why can a folder not be empty in object storage?

Because folders do not exist. A key is one flat string, and the slashes in it are ordinary characters. What a browser shows as a folder is CommonPrefixes, computed per request from the keys that exist — so with no keys under a prefix there is no prefix. Consoles fake empty folders by writing a zero-byte object whose key ends in /.

You need to change one line in a 4 GB object. What does that cost?

Downloading 4 GB, changing it locally, and uploading 4 GB. There is no partial write and no append — a PUT replaces the whole object. If a workload needs to edit in place, object storage is the wrong store for it; keep the mutable state in a database and put the immutable artefacts in the bucket.

Your integrity check compares the ETag to a local MD5 and started failing. What changed?

The file got big enough for the client to switch to multipart — the AWS CLI does this at 8 MB. A multipart ETag is the MD5 of the concatenated part MD5s with -N appended, so it cannot equal the file’s MD5 and cannot be recomputed without knowing the part size the uploader used. Upload with --checksum-algorithm SHA256 and read it back with --checksum-mode ENABLED instead.

Is S3 eventually consistent?

Not since December 2020 — read-after-write is strongly consistent for all operations including overwrites and deletes, at no extra cost. Retry loops written to work around the old behaviour can go. This is a property of AWS S3; other S3-compatible providers make their own guarantees, so check rather than assume.

Chapter One · Part I

Buckets, Keys and the S3 API

The S3 API is a small REST API with a large amount of folklore attached. This chapter covers what the operations actually are, which characters a key may contain, and the one hard limit that the command-line tool politely hides from you until your own code trips over it.

By the end of this chapter you will be able to
  • Name buckets and design keys deliberately
  • Use prefix, delimiter and start-after to query a bucket
  • Paginate a listing correctly
  • Predict how a key is encoded into a URL
  • Recognise the S3 API as ordinary HTTP

1.1 Buckets

Table 1.1 Two of these bite in practice. Global uniqueness means images and assets were taken in 2006, so real names look like acme-prod-user-uploads-euw1 — and a name you release can be claimed by anyone, which is a genuine hijacking vector for anything still linking to it. Dots are the subtler one: my.bucket.com works over HTTP and fails TLS certificate validation on the virtual-host endpoint, because a wildcard certificate for *.s3.amazonaws.com does not match a name with extra dots in it.

A naming scheme that keeps working

<org>-<env>-<purpose>-<region>, all lower case, hyphens only: acme-prod-user-uploads-euw1. It is unique enough to survive the global namespace, it sorts usefully in a console listing, and the environment is in the name — which matters the first time somebody runs a cleanup script against the wrong bucket. Separate buckets per environment, always: a prefix is not an access-control boundary you want to rely on.

1.3 Querying a flat keyspace

The parameters that make listing useful

Prefix restricts to keys starting with a string — the only filter that exists. Delimiter collapses everything after the next occurrence of that character into CommonPrefixes, giving the folder illusion from Chapter 0. StartAfter begins the listing after a given key, which is how you resume without a token. MaxKeys lowers the page size but cannot raise it above 1,000. There is no suffix filter, no wildcard, no date filter, and no sort order other than lexicographic — if you need to query it, it has to be in the prefix.

1.4 What may go in a key

The characters that are legal and still a mistake

? and # terminate the path in a URL, so any consumer that concatenates strings instead of encoding properly will truncate your key at that point — and a browser will do exactly that. % invites double-encoding bugs, where 50%off.png becomes 50%2525off.png after one round-trip too many. Spaces work but produce %20 in every log line and every href. The safe set is a–z 0–9 - _ . /, and everything else should be transliterated at upload time — not because S3 objects, but because the six systems downstream of it will.

Where the lab and AWS genuinely disagree

path//double.txt — an empty path segment — was rejected by MinIO above with XMinioInvalidObjectName. AWS S3 accepts it, stores it, and then makes it awkward to address because many clients normalise // to / in a URL and fetch the wrong key. So the two behaviours differ, and the practical conclusion is the same either way: never construct a key by joining path fragments without collapsing the separators. This is the first place in the book where the lab is not AWS, and it will not be the last — Chapter 6 is largely about such differences.

Checkpoint

Your code lists a bucket and processes Contents. What breaks, and when?

It silently stops seeing objects once the bucket passes 1,000 keys — that is a hard cap on a single ListObjectsV2, and the SDK does not follow the continuation token for you. There is no error. Use paginateListObjectsV2, and be aware the AWS CLI hides this by paginating automatically, so testing at the command line will not reveal it.

You need “all objects uploaded by user 42”. How do you get them?

Only by making it a prefix — users/42/… — and listing with Prefix. There is no query language, no metadata search and no filter other than the key. If you need richer queries, the index belongs in a database that stores the keys; the bucket stores the bytes.

Why avoid dots in a bucket name?

Virtual-host-style addressing puts the bucket name in the hostname, and a wildcard certificate for *.s3.amazonaws.com does not match a name containing further dots — so TLS validation fails. The bucket works over plain HTTP and breaks over HTTPS, which is a memorable way to find out. Use hyphens.

A key contains a space and a #. Is that legal, and is it wise?

Legal — a key is a UTF-8 byte string. Unwise: # starts a fragment in a URL, so a client that concatenates rather than encodes truncates the key there, and a space becomes %20 everywhere it is printed. Restrict generated keys to a–z 0–9 - _ . / and transliterate user-supplied filenames on upload.

Never construct a client with a hard-coded key

Listing 2.2 reads from the environment, and even that is only because the lab has a fixed test credential with no value outside this book. In application code, pass no credentials at all: new S3Client({}) uses the chain, so the same build runs on a laptop with a profile, in CI with OIDC, and on a task with a role — with nothing to rotate and nothing to leak. A key pasted into a config file is the finding that opens a security review, and Chapter 8 covers the alternatives properly.

2.3 The body is a stream

Usually you should not read it into memory

transformToString() is fine for a small JSON document and wrong for a 2 GB video — it buffers the whole object. The reason the body is a stream is so you can avoid that: r.Body.pipe(res) in an HTTP handler, or pipeline(r.Body, createWriteStream(path)) to disk, moves bytes through with constant memory. A service that transformToStrings every download works perfectly until somebody uploads something large, and then falls over on memory rather than on anything that looks like a bug.

2.4 Two names for one missing object

The bug this produces

Somebody writes an existence check with GetObject, catches NoSuchKey, and it works. Later somebody optimises it to HeadObject — sensible, since it avoids transferring the body — and the catch no longer matches, so a missing object becomes an unhandled 500 instead of a clean false. Switch on e.$metadata.httpStatusCode === 404, which is true in both cases and stable across providers, rather than on the error name.

2.5 Retries and timeouts

What is retried, and what must not be

The SDK retries what it knows to be safe: connection errors, 5xx responses, and throttling (SlowDown, 503). It does not retry 4xx, because retrying AccessDenied just wastes time. adaptive mode adds a client-side rate limiter that backs off when throttling appears, which helps a fleet stop hammering a hot prefix — and hurts if you have one client doing bulk work, since it slows down on its own. Start with standard; move to adaptive when you see SlowDown. And note that $metadata.attempts on any response tells you how many tries it actually took, which is worth logging.

Checkpoint

You log response.Body and get [object Object]. What is wrong?

Nothing is wrong — in v3 Body is a readable stream, not a Buffer. Use await Body.transformToString() for small objects, and for anything large pipe it: await pipeline(r.Body, createWriteStream(path)). Buffering every download into memory is the failure that only appears once somebody uploads a big file.

An existence check stopped working after being switched from GetObject to HeadObject. Why?

The error name changed. GetObject raises NoSuchKey; HeadObject raises NotFound, because a HEAD response carries no body for the SDK to parse an error code from. Match on e.$metadata.httpStatusCode === 404, which is true either way.

The same code works locally and gets AccessDenied in production. Where do you look first?

The credential chain. It stops at the first source that resolves, so an AWS_ACCESS_KEY_ID in the environment silently beats the profile you meant to use — and in production a role is resolving instead. Also remember AccessDenied on a read can mean the object is missing: without s3:ListBucket, S3 returns 403 rather than 404 so as not to reveal existence.

Why does the SDK need forcePathStyle for MinIO and R2?

Because AWS defaults to virtual-host addressing (bucket.host/key) and most compatible services only implement path style (host/bucket/key). Without it the client tries to resolve a hostname that does not exist, and the failure looks like DNS rather than configuration.

Immutable keys make caching trivial

Which is exactly why content-addressed keys (assets/<sha256>.js) are worth the trouble: a new build is a new key, so the old one can be cached forever and there is no invalidation to get wrong. Table 3.2 Row five is the one that costs money quietly. An interrupted multipart upload leaves its parts in the bucket, invisible to ListObjectsV2 — they do not appear in any normal listing, and you are billed for them indefinitely. Every production bucket wants the lifecycle rule from Chapter 9 that aborts incomplete uploads after a few days; without it a bucket can hold more in abandoned parts than in objects.

Streaming an upload of unknown length

PutObject needs Content-Length up front, so it cannot take a stream whose size you do not know — piping an HTTP request body straight through is the common case. Upload handles it by buffering one part at a time, which is why it is the right default for anything user-supplied. The memory cost is partSize × queueSize, so the defaults above hold 32 MB per concurrent upload; on a small container, lower queueSize before you lower partSize, because parts below 5 MB are rejected.

3.3 Downloading part of an object

What ranges are actually for

Three things, all of them real. Reading a header — the first 512 bytes of a file tell you its true type, its image dimensions, or a ZIP’s central directory offset, without downloading gigabytes. Resuming a download — request bytes=<already-have>- and continue. Parallel fetching — split a large object into ranges and pull them concurrently, which is exactly what the SDK’s download managers and every CLI cp of a big file do internally. Video streaming is the same mechanism: a browser seeking in an MP4 issues a range request for the byte offset it computed from the index.

Ranges and caching interact badly if you are careless

A CDN caches a range response as a range response. If your origin serves bytes=0-1023 and something later caches it under the full-object key, subsequent clients get a truncated file. Chapter 7 covers the header that prevents this; for now, be aware that Accept-Ranges, Vary and Range together are a place where a misconfigured cache produces corruption rather than a miss.

Checkpoint

Your uploaded images download instead of displaying. What is wrong?

No ContentType was set, so they are stored as application/octet-stream. S3 never sniffs the bytes and never looks at the file extension in the key. A range request for the first few hundred bytes — Range: "bytes=0-511" — which returns 206 and bills you for those bytes only. The same technique resumes an interrupted download and powers video seeking.

Chapter Four · Part II

Presigned URLs

A presigned URL is an entire authenticated S3 request folded into a link. It lets a browser talk to a private bucket without ever seeing a credential, which is the mechanism behind almost every “upload your avatar” and “download your invoice” feature. It is also a bearer token pasted into a URL bar, and this chapter takes both halves seriously.

By the end of this chapter you will be able to
  • Explain what a presigned URL contains
  • Generate one for reading and for writing
  • Predict exactly what it does and does not authorise
  • Choose an expiry, and know the two ceilings on it
  • Avoid handing out more access than you meant to

4.1 What is actually in the link

Which means: no request is made when you generate one

getSignedUrl is pure local computation — it never contacts S3, which is why it is instant, why it works offline, and why it succeeds for objects that do not exist. A presigned URL for a missing key is a perfectly valid URL that returns 404 when someone follows it. It is also why you cannot revoke one: nothing was registered anywhere. The only ways to stop a presigned URL working are to let it expire, delete the object, or disable the key that signed it.

4.2 What it authorises, exactly

And here is the unreassuring half

Within that scope it is a bearer token: anyone holding the link is the customer. It carries no identity check, so it survives being forwarded, pasted into a support ticket, captured in a Referer header, stored in browser history, logged by your reverse proxy, and indexed if it ever appears on a public page. Treat the URL itself as the secret it is — keep expiries short, do not log them, and never put one in a redirect that a third-party page can observe.

It also inherits your permissions, not the recipient’s

The signature proves the request was authorised by the key in X-Amz-Credential. If your server signs with an admin key, the URL you hand a user is an admin-authorised request — narrowly scoped to that one operation, but authorised at your level. The consequence is that the authorisation decision must happen in your code, before you sign: check that this user may read this invoice, and only then generate the URL. Nothing downstream will check for you.

4.3 Presigned uploads

Signing ContentType is a constraint, not a hint

Because ContentType was in the signed request, the client must send exactly that header or the signature check fails. That is useful — it stops a client that asked to upload a JPEG from uploading an HTML file that would then be served from your domain. It is also the most common cause of “my presigned upload returns 403”: the browser sent image/jpeg; charset=utf-8, or fetch set its own type, and the strings no longer match byte for byte.

Checkpoint

Does generating a presigned URL check that the object exists?

No — signing is pure local computation and contacts S3 not at all. A presigned URL for a missing key is valid and returns 404 when followed. It is also why a presigned URL cannot be revoked: nothing was registered anywhere. Let it expire, delete the object, or disable the signing key.

A user is given a presigned URL for one object. What else can they reach?

Nothing. The method, bucket, key and any signed headers are all covered by the signature, so changing any of them yields SignatureDoesNotMatch. But within that scope it is a bearer token — whoever holds the link can use it, so forwarding, Referer leakage and proxy logs all matter, and short expiries are the mitigation.

A Lambda signs seven-day URLs and they start failing after about an hour. Why?

It is signing with temporary role credentials, and a presigned URL cannot outlive the session that signed it. expiresIn is an upper bound, not a guarantee. Sign with a long-lived credential if you truly need long links — or use the redirect pattern and sign for sixty seconds on demand.

Why can a presigned PUT not stop someone uploading a 10 GB file?

Because the signature covers the method, key and signed headers, not the body length — there is nowhere in a presigned PUT to express a maximum. A presigned POST policy (Chapter 5) has a content-length-range condition and can, which is why browser upload forms use POST rather than PUT.

Cloudflare R2 Specifics

R2 speaks the S3 API and charges nothing for egress, which is why it is the substitution people actually make. This chapter is about the gap between “S3-compatible” and “S3” — where the differences are, why the egress line changes architectures rather than just invoices, and how to find out what any given endpoint supports rather than trusting a compatibility table.

6.1 The same client, three lines different

R2 credentials are not Cloudflare API tokens

R2 issues a separate S3 access key ID and secret from the R2 dashboard, distinct from the Cloudflare API token you use for everything else in that account. They are scoped per bucket and per permission set, and they are the only credential the S3 API accepts. Trying to sign with a Cloudflare API token produces SignatureDoesNotMatch, which reads as a bug in your signing code and is not.

The decisions that change when egress is free

You stop bending the design around a CDN. Serving originals directly becomes reasonable, so the elaborate cache-warming and edge-derivative machinery of Chapter 7 becomes optional rather than mandatory. Multi-cloud stops being punitive — the reason data is sticky on AWS is that moving it out costs per gigabyte, which is exactly the charge R2 does not levy. Large-file products become possible: video, datasets, game assets and backups are workloads where egress, not storage, is the reason a small team cannot afford to offer them.

And the ones that do not

Free egress is not free bandwidth for abuse. Cloudflare’s terms still apply, the r2.dev development domain is deliberately rate-limited, and a public bucket is still a public bucket — Chapter 8’s access control matters exactly as much. Operation charges also still exist: a job that lists a million-object bucket in a loop costs money on either provider, and the Chapter 1 pagination discussion is a cost discussion as well as a correctness one.

Checkpoint

Why does zero egress change architecture rather than just cost?

Because egress is usually the dominant line for anything serving content, so designs built to minimise it — aggressive CDN layering, cache warming, keeping data on one cloud because moving it is expensive — stop being forced. Which parts of the S3 API port cleanly to another provider, and which do not?

The data plane ports well — objects, keys, uploads, ranges, signatures, presigned URLs — because that is what applications use. The control plane does not: lifecycle transitions, policies, replication, event notifications and analytics are where each provider substitutes its own model. Code that puts and gets objects moves in an afternoon; code that manages buckets does not move at all.

Your probe reports NoSuchBucketPolicy. Is the feature missing?

No — that is a successful call reporting that nothing is configured. Only NotImplemented means the operation is absent; AccessDenied means it exists but your credential cannot use it. Conflating the three produces a compatibility report that is both alarming and wrong.

The two strategies, and why only one of them scales

The second is more machinery at build time and removes an entire category of production problem, including invalidation (§7.4).

7.3 Conditional requests

Conditional requests are also how you avoid lost updates

The same headers work on writes. PutObject with IfNoneMatch: "*" succeeds only if the key does not already exist — an atomic create, which is how you claim a lock or avoid two workers overwriting each other. IfMatch: <etag> on a write succeeds only if the object is still the version you read, giving you optimistic concurrency. Both return 412 Precondition Failed instead of silently clobbering, and both are much newer than most S3 code, so they are widely unknown.

A CDN invalidation is slow (minutes, globally), often billed per path, and — crucially — does not reach browser caches at all. If you told a browser max-age=31536000, that browser will not ask again for a year no matter what you purge at the edge. This is why content-addressed keys are worth the build-time machinery: app.4f3a9c21.js is never invalidated because it is never changed, and the only short-cached document is the HTML that names it. Design so that invalidation is an emergency tool, not part of your deploy.

7.5 Serving files people uploaded

Never from your application’s domain

If app.example.com serves a user-uploaded file, that file runs in your origin: an uploaded HTML or SVG file executes JavaScript with access to your cookies, your local storage and your session. Serve uploads from a separate domain — usercontent-example.net, not a subdomain, since cookies scoped to .example.com reach subdomains. This is why every large site serves attachments from a different domain entirely, and it is the one mitigation that still works when the other two fail.

You shipped Cache-Control: max-age=31536000 on a file that then changed. What now?

Edge caches can be purged; browser caches cannot. Every client that already fetched it will not ask again for a year. Which is the argument for content-addressed keys: with them, this situation cannot arise.

Why is private in Cache-Control a security control?

Because it forbids shared caches from storing the response while still allowing the browser to. Without it, a CDN can cache a per-user response and serve it to the next person requesting that URL. Any response whose body depends on who asked needs private, or no-store if it should not persist at all.

ResponseContentDisposition on the signed request — it overrides the stored header for that request only, and being part of the signature it cannot be altered by the recipient. Note each variant is a distinct URL and therefore a distinct cache entry.

Because cookies scoped to .example.com are sent to every subdomain, so an uploaded HTML or SVG file executing on files.example.com still reaches your session. A genuinely separate registrable domain contains it. Combine with Content-Disposition: attachment, nosniff and a sandbox CSP.

Checkpoint

Where does Block Public Access sit relative to a bucket policy?

Above it. With Block Public Access on, a policy granting Principal: "*" is ignored rather than rejected — which is confusing when you meant it and is the whole point when you did not. Leave it on and serve public content through a CDN with origin access control instead.

The same missing key returns 404 in one prefix and 403 in another. Why?

Because S3 will not confirm that an object is absent to a caller who would not have been allowed to read it. Where the caller has read access, a missing key is 404; where they do not, it is 403. The practical consequence is that AccessDenied on a read may be a typo in the key rather than a policy problem — check the key with a credential that can list before editing IAM.

Why is s3:ListBucket more dangerous than it looks?

It is a permission on the bucket, not on objects, so granting it without an s3:prefix condition lets the holder enumerate every key in the bucket even if they can only read one prefix — converting a set of unguessable keys into a directory listing. Scope it with a condition, and never add it to a public policy.

Does server-side encryption protect you from a leaked access key?

No. It defends against someone obtaining the physical media; the storage layer decrypts transparently for any authorised request, and a leaked credential is authorised. It is necessary and worth having on, and it is not the control that keeps data private — least privilege, short-lived credentials and Block Public Access are.

Lifecycle, Cost and Performance

Object storage is cheap per gigabyte and expensive per habit. Cold storage classes are a bet, not a discount

Moving objects to an infrequent-access or archive class lowers the per-GB price and adds three costs: a minimum storage duration (delete before it and you are billed as though you had not), a retrieval charge per GB, and, for archive tiers, a restore delay measured in minutes to hours. 9.3 The storage you cannot see

Why the parts are invisible

A multipart upload is a three-step transaction: CreateMultipartUpload, then UploadPart repeatedly, then CompleteMultipartUpload. Only the last step creates an object. If the client dies in the middle — a closed laptop, a redeployed pod, a network drop — the parts already uploaded stay on the server, belonging to an upload that will never complete. They are not objects, so ListObjectsV2 cannot see them, the console shows nothing, and aws s3 ls --summarize reports a size that does not match the bill. They are billed as storage until something aborts them.

9.4 Versioning, and what it is for

This is the defence against your own code, and against an attacker

Versioning turns “a script deleted the wrong prefix” and “someone encrypted our bucket” from unrecoverable into an afternoon — provided the credential that did the damage could not also delete versions. That is the Chapter 8 point restated as a cost decision: grant s3:DeleteObject, withhold s3:DeleteObjectVersion, and the delete is always reversible. Grant both and versioning is a defence the attacker also holds the key to.

It cannot be turned off, and it is not free

Versioning can be suspended but never disabled — existing versions remain and are billed forever until something removes them. That something should be a NoncurrentVersionExpiration rule from the moment you enable it: thirty days of history is usually plenty, and without such a rule a bucket where objects are frequently overwritten grows without bound. Enabling versioning and forgetting the expiration rule is one of the more expensive ways to be careful.

Prefixes and throughput, and the advice that is now obsolete

S3 scales to roughly 3,500 writes and 5,500 reads per second per prefix, and it partitions automatically as load grows. Older guidance told you to put a random hash at the start of every key to spread load across partitions — that advice predates automatic partitioning and is now actively harmful, because it destroys the prefix structure that makes listing, lifecycle rules and access policies work. Design keys for how you need to query them (Chapter 11), and if you genuinely saturate a single prefix, spread across a handful of deliberate prefixes rather than randomising every key.

Where the money usually is

Before optimising anything, look at the actual breakdown. In practice it is almost always egress first — fixed with a CDN or a provider that does not charge for it — and invisible multipart parts second, fixed with one lifecycle rule. Storage class transitions are the thing people reach for first and they are usually third at best, because standard storage is already cheap and the transition has its own charges.

Your bill shows more storage than the objects in the bucket account for. Where is it?

A NoncurrentVersionExpiration rule. Versioning can be suspended but never disabled, and every overwrite keeps the old version and bills for it forever. Thirty days of history is usually enough; without the rule, a bucket with frequent overwrites grows without bound.

Is listing a cheap way to check whether an object exists?

No — LIST is a Class A request costing roughly ten times a GET, and it returns up to a thousand keys regardless. Use HeadObject and treat a 404 as “absent”. If you need existence checks at volume, keep the index in a database instead of asking the bucket.

10.3 The metadata nobody meant to publish

Re-encoding is doing two jobs at once

It strips the metadata, and it destroys polyglot files — a file crafted to be simultaneously a valid JPEG and a valid HTML document or ZIP archive. Such a file passes a magic-byte check (its header really is a JPEG) and still does something else entirely when a browser is persuaded to render it. Re-encoding produces a genuinely new file from the decoded pixels, so whatever was smuggled in the original does not survive. This is why “re-encode every uploaded image” is worth doing even when you do not need a different size.

What to keep, deliberately

Orientation is the one thing you usually must handle: phones record the picture sideways and set an EXIF orientation flag, so stripping metadata without applying it rotates every portrait photo. sharp’s .rotate() with no argument reads the flag and bakes the rotation into the pixels, which is what you want — the image is then correct with no metadata at all. Colour profile matters for anything where colour accuracy is the product; keepIccProfile() keeps that and nothing else.

10.4 Keys for derivatives

Store the mapping, do not derive it

The database row for an upload should hold the original key, the hash, the dimensions, the detected content type, and the list of derivatives that exist. Reconstructing that by listing the bucket is slow, costs Class A requests (Chapter 9), and is unreliable the moment a derivative fails to generate. The bucket stores bytes; the database knows what they are. Chapter 11 makes this the central point.

Video is a different problem, not a bigger one

The output is many small segment files plus a manifest, which makes the per-request costs of Chapter 9 and the caching of Chapter 7 matter far more than they do for images. Checkpoint

Why must you re-encode an uploaded image even when the size is already right?

Two reasons. It strips EXIF — including GPS coordinates the user did not know they were publishing — and it destroys polyglot files that are simultaneously a valid image and a valid script, which a magic-byte check cannot catch. Re-encoding builds a new file from decoded pixels, so nothing smuggled in the original survives.

You strip metadata and every portrait photo is now sideways. What happened?

Phones store the image in sensor orientation and record an EXIF orientation flag; stripping the metadata removes the flag while leaving the pixels rotated. Apply the rotation to the pixels first — sharp(...).rotate() with no argument reads the flag and bakes it in — and the result is correct with no metadata at all.

Why encode the width and quality into the derivative key?

Because then the key describes the file completely, so it can be cached with max-age=31536000, immutable and can never go stale — there is no invalidation in your deploy. Combined with a content hash of the original it also deduplicates identical uploads and makes reprocessing idempotent.

What is the risk in a resize endpoint that accepts any width?

Cache and cost amplification: an attacker requests ten thousand distinct widths, each a cache miss that costs compute, storage and requests. Accept a fixed allow-list of sizes and reject anything else, and sign or otherwise constrain the parameters so they cannot be edited freely.

11.2 The bucket is not the database

Which means there are two systems, and they drift

On deletion, reverse it: mark the row deleting, remove the object, then remove the row.

A backup you have not restored is a hypothesis

Schedule a restore. Not a listing of the backup bucket — an actual restore of a real object into a scratch environment, with the checksum from Chapter 3 compared against the source. The failure modes that matter are the boring ones: the job stopped six months ago and nobody noticed, the credential expired, the destination filled, the prefix changed when someone refactored the key scheme. All of them look fine from the outside, and all of them are caught by one restore.

The end of the book, in one sentence

Object storage gives you an unlimited, durable, HTTP-addressable place to put bytes, and takes away directories, partial writes, rename, and any way to ask a question that is not a key prefix. Almost everything in these eleven chapters follows from that trade: the keys are the design, the database is the index, the metadata is set once at write time, and anything that must not be lost lives in a second account under a credential that cannot delete.

Checkpoint

Why does the order of components in a key matter so much?

Because a prefix only helps for the components to its left, and the key cannot be changed without copying every object. Put the field you will one day need to operate on in bulk — usually the tenant — first, and a date next if you want lifecycle rules to expire by age. Decide before the first upload; it is effectively permanent.

What are the two kinds of drift between a bucket and its database, and which is worse?

Orphaned objects (bytes no row references) and missing objects (rows pointing at nothing). The missing object is worse for users — a 404 on a link they were given — but the orphan is worse for you, because it is invisible and accumulates on the bill. Reconcile on a schedule, and alert rather than auto-delete.

Versioning is enabled. Are you protected from a leaked credential?

Only if that credential cannot delete versions. Grant s3:DeleteObject and withhold s3:DeleteObjectVersion, or the attacker removes the history along with the objects. The configuration that survives a full compromise is a copy in a separate account written by an append-only credential, ideally under Object Lock.

During a migration, which metric tells you it is safe to cut over?

The read-fallback counter — how often a read missed in the new provider and had to be served from the old one. While it is above zero, something has not been backfilled and cutting over would 404 it. Wait until it has been zero for a sustained period, and keep the old bucket reachable for at least as long as the longest presigned URL you issued.
