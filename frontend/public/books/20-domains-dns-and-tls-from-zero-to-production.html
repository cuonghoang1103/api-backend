About this book

DNS and TLS are the two systems everybody depends on and nobody owns. They fail on a schedule set by caches you cannot reach, using tools that answer a slightly different question from the one you asked, and they produce error messages that are true and misleading at the same time. This book is about the gap between what these systems say and what they mean.

Everything here was executed against a real lab: an authoritative BIND server, a caching resolver in front of it, a certificate chain built with OpenSSL, and a genuine ACME exchange with Let’s Encrypt’s own test CA. When Chapter 0 says a TTL is a countdown, you watch it go 30, 28, 26 through the cache while the authority says 30 every time. When Chapter 2 says a CNAME cannot live at the apex, the server refuses the zone file with CNAME and other data. When Chapter 8 says one new record can break its neighbours, an ordinary A record is added and every name beneath it returns NXDOMAIN.

The uncomfortable findings are the point. Chapter 4 asks openssl about a host whose certificate does not cover it and gets “Verification: OK”, twice, while curl refuses the same connection. Chapter 5 asks Let’s Encrypt when to renew a revoked certificate that still has seven weeks to run, and is told to renew in a window that started half an hour ago — a signal that any countdown-to-expiry renewer will miss entirely. Chapter 7 counts the DNS lookups in a real hosting company’s SPF record and finds 14, four past the limit at which the whole record stops evaluating.

Who should read this

Anyone who has moved a domain, waited for a change that would not take effect, or been paged for a certificate. You need a terminal and no prior knowledge of either system; the lab runs entirely on your own machine, and .test is reserved by RFC 6761 so it can never collide with anything real.

How this book is organised

Chapters map one-to-one onto the ten modules of the Domains, DNS & TLS track in Code Lab, each ending with that module’s graded exercises — 100 in total, all linked. Read 0 first; the caching model in it is what every later chapter reasons about. Chapters 4 and 9 are the two to reread when something is on fire.

The one habit this book is really teaching

Ask the authority and a cache, and compare. Almost every DNS question is settled by running dig @your-nameserver name beside dig @1.1.1.1 name: if they agree, the problem is elsewhere; if they differ, the answer is the remaining TTL and you are done. Most people never make that comparison, because dig without an @ quietly asks a cache — and a cache is exactly the thing under suspicion.

Four checks that cannot pass wrongly

Read status: from a full dig, never +short, which prints nothing for both NXDOMAIN and SERVFAIL and exits 0 for all three outcomes. Require the aa flag when you mean to ask the authority. Add -verify_hostname to openssl s_client, or it will bless a certificate issued to somebody else. And alert at 21 days before expiry, so a renewal that has been failing silently for two months still leaves a working week.

Chapter Zero · Part I

How the Domain Name System Works

DNS is a distributed database with one query language, no transactions, and a cache you cannot flush. Almost every confusing thing about it — the change that has not taken effect, the answer one machine gives and another does not — comes from that last clause. This chapter builds the model, and every claim in it is a query you can run.

By the end of this chapter you will be able to
  • Trace a name from the root to an answer
  • Tell an authoritative server from a resolver by its reply
  • Read a TTL as the cache-expiry countdown it is
  • Explain delegation, referrals and glue
  • Interrogate the lab server used for the rest of this book

0.1 The path a name takes

TierKnowsDoes not know
Root (13 named servers, hundreds of anycast instances)Who serves each TLDAnything below that
TLD (com, uk, test…)Who serves each registered domainWhat records those domains hold
Authoritative (your DNS host)The actual recordsAnything outside its zones
Recursive resolver (your ISP, 1.1.1.1)Nothing — it asks, then remembers—
Stub resolver (your operating system)Almost nothing — it asks one resolver—

Table 0.1 Only the third row contains your data. The other four are a distributed index for finding it, and the fourth — the resolver — is where every “why has my change not taken effect” question actually lives, because it is the only tier that keeps a copy.

Recursive and iterative are two halves of one query

Your machine asks its resolver recursively: “give me the answer, I do not care how”. The resolver then works iteratively: it asks the root, gets a referral, asks the TLD, gets a referral, asks the authoritative server, gets an answer. It is the only participant doing real work, which is exactly why it caches — a resolver serving a million users would otherwise ask the root a million times.

0.2 Two kinds of server, and the flag that names them

FlagMeansWhere you see it
qrThis is a response, not a queryEverywhere
aaAuthoritative answerFrom the server that holds the zone
rdRecursion desired — the client askedSet by dig by default
raRecursion available — the server willFrom a resolver
tcTruncated; retry over TCPLarge answers over UDP

Table 0.2 Worth memorising the second and fourth rows. aa without ra is an authoritative server; ra without aa is a cache. Seeing aa from something that should be a resolver means it has been configured to serve that zone locally — which is a real cause of “it works everywhere except in the office”, and Chapter 9 has a demonstration of exactly that.

0.3 TTL is the only cache invalidation you get

Which is why “DNS propagation” is the wrong phrase

Nothing propagates. You change a record and it is live on your authoritative server immediately. What takes hours is thousands of independent caches around the world reaching the end of a countdown that started before you made the change. A resolver that fetched your record with a 24-hour TTL five minutes ago will serve the old value for another 23 hours and 55 minutes, and there is nothing you or your DNS provider can do about it.

TTLMeansUse for
60 – 300Change takes effect in minutesBefore a planned migration
3600An hourA sensible default
86400A dayRecords that genuinely never change
604800A weekMX and NS, when you are very sure

Table 0.3 The operational rule follows directly from Listing 0.4: lower the TTL before you change anything, not when you change it. Drop it to 300, wait for the old high TTL to expire everywhere, then make the change, then raise it again. Lowering the TTL at the same time as the change achieves nothing — caches holding the old record are also holding the old TTL.

0.4 Delegation, referrals and glue

The A record in that answer is a glue record

Notice the problem it solves. The parent says “ask ns1.eu.bookshop.test” — but to look that name up you would have to ask eu.bookshop.test, which is the zone you are trying to reach. The parent breaks the loop by including the address alongside the referral. Glue is required exactly when the nameserver’s name is inside the zone it serves, and a missing glue record is a classic cause of a domain that resolves for some people and not others.

0.5 The lab

The first thing the lab taught, before any chapter did

The resolver initially answered NXDOMAIN for every name in the zone — with the aa flag set, from a server that owns nothing. The cause is that RFC 6761 makes .test a special-use domain, and unbound ships a built-in local zone that blocks it so such names never leak to the public internet. The fix is one line, local-zone: "test." nodefault. Keep the shape of this in mind for Chapter 9: a resolver answering authoritatively for a name it does not own is a real configuration, and it produces failures that look impossible.

Checkpoint

You changed a record an hour ago. Some people see the new value, some the old. Why?

Because their resolvers cached the old record before you changed it and are still counting down its TTL. Nothing propagates — your authoritative server was correct the instant you saved. Check with dig @your-ns (expect aa and the new value) versus dig @1.1.1.1, and note the remaining TTL: that is how much longer the old answer lives.

How do you tell an authoritative answer from a cached one?

The aa flag. An authoritative server sets it and does not set ra; a resolver sets ra and not aa. Seeing aa from something that should be a cache means it is serving that zone locally — a real cause of “works everywhere except here”.

Why must you lower a TTL before a migration rather than during it?

Because caches hold the old TTL along with the old record. Lowering it at the moment of the change does nothing for anyone who already cached the previous value at 24 hours. Drop the TTL, wait out the old one, then move, then raise it again.

What is a glue record and when is one required?

An address record published by the parent zone for a nameserver whose name lives inside the child zone. Without it, finding ns1.eu.bookshop.test would require asking eu.bookshop.test, which is the zone you are trying to reach — a loop. Glue is needed whenever the nameserver is named inside the zone it serves.

Chapter One · Part I

Buying a Domain

A domain is not bought; it is leased, from a registry, through a registrar, under a contract with an expiry date and a set of status codes that decide what may be done to it. Almost every domain disaster — the expired name, the hijacked transfer, the site that vanished — is one of those codes being wrong. They are public, and you can read them right now.

By the end of this chapter you will be able to
  • Distinguish registry, registrar and reseller
  • Read a domain’s real status with RDAP
  • Recognise the EPP status codes that protect you
  • Follow a domain through its expiry lifecycle
  • Move a domain without losing it

1.1 Who actually holds your domain

PartyIsExample
ICANNThe body that accredits registrars—
RegistryOperates one TLD and its authoritative databaseVerisign for .com
RegistrarSells registrations, talks EPP to the registryCloudflare, Namecheap, Gandi
ResellerSells a registrar’s service under its own brandMost web hosts
RegistrantYou — the leaseholder—
DNS hostRuns the nameserversOften, but not necessarily, the registrar

Table 1.1 The last row is the one worth separating in your head. Your registrar and your DNS host are different jobs and can be different companies — the registry only records which nameservers to delegate to (Chapter 0), not what those servers say. Keeping them separate is normal, and it means a registrar problem does not have to be a DNS outage.

The reseller layer is where domains get lost

Buying through a host that resells somebody else’s registrar means the registrant contact, the auth code and the renewal notices may all sit with a company you have never heard of — and when you want to move, you must ask the reseller to ask the registrar. If a domain matters, hold it directly at an accredited registrar, in an account that belongs to the organisation rather than to whoever set it up.

1.2 Reading a domain’s real state

Table 1.2 The three client*Prohibited codes in Listing 1.1 are the registrar lock, and their presence is the single best indicator that a domain is being looked after. A valuable domain showing only ok is unlocked and one compromised email account away from being transferred away. The row to fear is clientHold: the registry stops publishing the delegation, so the domain stops resolving everywhere within one TTL — it is what registrars do when a renewal payment fails or a WHOIS-verification email goes unanswered.

WHOIS and RDAP are the same data, differently served

WHOIS is a 1982 protocol returning unstructured text in whatever layout each registry felt like, with no encryption and no access control. RDAP returns JSON over HTTPS, with a defined schema, internationalisation, and the ability to authenticate — which is why redacted fields can be shown to parties entitled to see them. RDAP is the answer for anything programmatic; whois remains useful because it is one command and always installed.

1.3 The lifecycle, and the two weeks that cost you

PhaseDurationWhat is true
ActiveUp to 10 yearsRenew any time

Pending Delete5 daysNothing can be done, by anyone

Table 1.3 The third row is where the damage happens. During redemption the domain has already been removed from DNS, so your site and — worse — your email are down, while recovery costs a redemption fee typically ten times the renewal price. The gap between “expired” and “gone” is around 75 days in total, and every part of it is avoidable by paying for ten years up front.

Auto-renew is not a plan

Auto-renew depends on a card that expires, at a registrar whose notices go to an address that may belong to somebody who has left. The failure mode is silent: the first sign is the site being down. Register for the maximum term, put the expiry in a shared calendar with a 60-day reminder, use a role address (domains@) that more than one person reads, and check the registrant email is one you still control — the recovery path for a lost registrar account runs through it.

1.4 Moving a domain

Copy the zone before you move anything

A registrar transfer does not move DNS records, and if the losing registrar was also your DNS host, they may delete the zone the moment the domain leaves. Export every record first (dig AXFR if allowed, or the provider’s export), stand the zone up at the new host, point the delegation there, wait out the old NS TTL, and only then transfer the registration. Doing it in that order means the transfer is a paperwork change with no user-visible effect.

SymptomCause

Checkpoint

Your registrar and your DNS host — must they be the same company?

No, and separating them is normal. The registry records only which nameservers to delegate to; what those servers answer is the DNS host’s business. Keeping them apart means a registrar account problem is not automatically a DNS outage — but it also means a transfer will not move your records, so export them first.

A domain shows status ok and nothing else. Is that good?

No — it means no locks are set. clientTransferProhibited, clientDeleteProhibited and clientUpdateProhibited are what stop a compromised registrar account from moving or deleting the domain. Their absence on anything valuable is the finding.

What is clientHold, and why is it an emergency?

The registry stops publishing the delegation, so the domain disappears from DNS within one TTL — website and, more painfully, email both stop. Registrars apply it for failed renewal payments and unanswered registrant-verification emails, so it usually means an administrative problem nobody read the notice about.

Why is transferring a domain just before expiry a bad idea?

Because a transfer takes up to five days, cannot happen within 60 days of registration or a previous transfer, and requires email approval — and if any step stalls you land in redemption, where the domain has already stopped resolving and recovery costs a penalty fee. Transfers also add and charge for a year regardless, so there is no saving in leaving it late.

Chapter Two · Part I

DNS Records

A zone is a text file of typed records, and about eight types cover almost everything you will ever need. The interesting part is the rules — the alias that is illegal at the apex, the string that cannot exceed 255 bytes, the priority that is not a percentage — because each of them produces a failure that looks like something else entirely.

By the end of this chapter you will be able to
  • Choose the right record type for a job
  • Explain why a CNAME cannot live at the apex
  • Follow a CNAME chain and count the lookups
  • Publish a TXT value longer than 255 bytes
  • Control who may issue certificates for your domain

Table 2.1 The last row catches people out: you cannot publish a PTR for your own IP address, because the reverse zone belongs to whoever owns the address block. Reverse DNS is requested from your hosting provider, and mail servers do check it (Chapter 7).

2.2 The alias that cannot live at the apex

Every hosting provider’s support queue has this question in it. The rule is not a limitation of your DNS provider; it is in the protocol, and the server will tell you so.

What you wantDo this
Apex pointing at a platformALIAS / ANAME / CNAME flattening — a provider feature, §2.3

Table 2.2 The first row is what modern DNS hosts sell. ALIAS (also ANAME, or CNAME flattening) is not a DNS record type — the provider resolves the target for you and serves the resulting A record at the apex, refreshing it as the target changes. It behaves like the CNAME you wanted, it is invisible to clients, and it only exists if your DNS host implements it. That is a genuine reason to choose one DNS host over another.

The last row is the one people get wrong

DNS cannot redirect. There is no record type that means “send browsers to another URL” — DNS resolves names to addresses and stops. Apex-to-www redirection is an HTTP response, from a web server, a CDN, or a redirect service, and it requires something listening on the apex address to issue it. If your apex “redirect” is configured in a DNS panel, your provider is running an HTTP server for you.

2.3 Chasing a CNAME costs a lookup

When the target is elsewhere, the resolver pays for it

A CNAME pointing outside the zone returns only the alias, and the resolver must start a fresh lookup for the target — root, TLD, authoritative, all of it, unless cached. A chain of three CNAMEs across three providers is three sequential resolutions before the first byte of your page is requested. Each is fast; the point is that they are serial, they happen before the connection opens, and they are invisible in every performance tool that starts measuring at the request. Keep chains to one hop.

RuleConsequence

Table 2.3 Row three is a real trap. Aliasing a whole domain to a hosting provider means that domain can never have an MX record, so mail for it stops — which is exactly why the apex rule exists, since the apex is precisely where MX lives.

2.4 MX, and what the number means

Table 2.4 The last row is underused and worth adopting: publishing a null MX on a domain that never receives mail tells senders to reject immediately rather than queue and retry for days, and it removes the domain as a target for backscatter. Every parked domain you own should have one.

The backup MX that quietly makes things worse

A secondary MX at a host that merely queues and forwards used to be standard practice and is now usually a liability: it accepts mail your primary would have rejected, has none of your spam filtering, and then delivers it to you as trusted internal traffic. Modern sending servers already retry for days if your only MX is down. Unless the backup runs the same filtering as the primary, one MX is better than two.

2.5 TXT, and the 255-byte string

A real DKIM public key does not fit in a DNS string. This is not a provider limitation either — it is in the wire format, and it is why every DKIM setup guide has a step people get wrong.

Which is also why dig +short lies to you here

+short prints the strings with the quotes still in, so copying its output into a comparison gives you a value containing " " in the middle that never matches. When checking a DKIM or SPF record programmatically, join the strings yourself rather than trusting a display format — and remember the 255-byte rule applies per string, while the whole record may still exceed 512 bytes and force the response to TCP.

2.6 CAA, and who may certify you

RecordMeans
0 issue "letsencrypt.org"Only Let’s Encrypt may issue

0 issuewild "letsencrypt.org"Rules for wildcard certificates specifically
0 iodef "mailto:…"Where to report a refused request
No CAA record at allAny CA may issue — the default

Table 2.5 The default is the permissive one, which is the point of setting it. Without a CAA record, any of the hundred-plus trusted CAs may issue a certificate for your domain to anyone who can pass their validation — and CA validation has been fooled before. Two records cost nothing and reduce that surface to one issuer. Note CAA is checked at issuance time only: it does not invalidate certificates that already exist, and browsers never look at it.

CAA is inherited down the tree

A CAA record at example.com applies to api.example.com unless that name has its own. The CA walks up from the name it is issuing for until it finds a record — so setting it once at the apex covers everything, and a subdomain can only replace the policy, not add to it. This also means a forgotten CAA record at the apex is a common cause of “the certificate order failed and nothing in the logs says why”, particularly after moving from one ACME provider to another.

Checkpoint

Why can a CNAME not exist at the zone apex?

Because a name with a CNAME may have no other records, and the apex must carry SOA and NS records or it is not a zone. The two rules contradict, so the server refuses the file with “CNAME and other data”. Use an ALIAS/ANAME/flattening feature if your DNS host offers one, or a plain A record.

You aliased your whole domain to a hosting provider and mail stopped. Why?

A name with a CNAME can have no other records — including MX. Since MX lives at the apex, aliasing the apex removes the ability to receive mail entirely, and it is one of the reasons the apex rule exists at all.

Your DKIM record was rejected by the DNS server. What is the fix?

A single TXT character-string cannot exceed 255 bytes and a 2048-bit key is around 410. Split it into several quoted strings inside one record; they are concatenated with nothing between them when read. Watch for stray spaces inside the quotes, and note dig +short shows the quotes, so joining its output naively produces a value that never matches.

What does an MX priority of 10 versus 20 actually do?

Lower is tried first: everything goes to 10, and 20 is used only when 10 cannot be reached. It is a preference, not a percentage — equal values are how you spread load. And a secondary MX that merely queues without your spam filtering usually makes things worse, since senders already retry for days.

3.3 What actually happens when you change a record

Which is why “checking propagation” on a map website is theatre

Those sites query a few dozen resolvers and colour a map. Green does not mean done and red does not mean broken. The only two questions worth asking are: does my authoritative server return the right answer (dig @my-ns, expect aa), and what is the largest TTL anyone could still be holding.

3.4 A CNAME captures the whole name

The failure this causes, weekly

A service asks you to prove you own a domain by publishing a TXT record. You add it to www, which is a CNAME to your hosting platform, and verification fails — because the TXT record you added is not what anyone asking for www receives. Domain verification records belong at the apex, or at the exact label the service names (often _something), and that label must not itself be a CNAME.

Checkpoint

You lowered every TTL in your zone to 300 and a nameserver change still took two days. Why?

Because the NS TTL that resolvers follow is the one published by the TLD registry in the delegation, not the one in your zone — 172,800 seconds for .com. You cannot lower it. Plan nameserver migrations as two-day operations and keep both sets of servers serving identical data throughout.

You changed an A record ten minutes ago. It works for you and not for a colleague. Is something broken?

No. Their resolver cached the old value before you changed it and is counting down the remaining TTL. Confirm with dig @your-ns (expect aa and the new value); their resolver’s reply shows exactly how many seconds are left. Nothing propagates — caches expire.

Which TTL governs a change to a CNAMEd hostname?

The target’s record TTL, not the CNAME’s. A 300-second alias in front of a 30-second A record cuts over in 30 seconds; a 60-second alias in front of a 24-hour A record cuts over in 24 hours. Look at the last record in the chain, which is usually not yours to control.

Domain verification keeps failing on a TXT record you definitely added to www. Why?

Because www is a CNAME, and a CNAME replaces the name for every record type — a query for TXT at that name returns the target’s TXT records, not yours. Put verification records at the apex or at the exact label the service specifies, and make sure that label is not itself an alias.

HTTPS and TLS Certificates

A certificate is a signed statement that a public key belongs to a set of names. Everything difficult about TLS comes from the two words in that sentence people skim: signed — by whom, through how many intermediaries — and names, which is not the field you think it is. This chapter shows a tool declaring a certificate valid for a host it does not cover.

By the end of this chapter you will be able to

  • Build and verify a chain, and recognise a broken one
  • Understand what SNI decides

4.1 The name in a certificate is not the CN

Which is why “add the domain to the CN” never fixes anything

The field is a single string, so it could only ever hold one name, which is why the SAN extension exists and why it is where every name lives. If a certificate is rejected for a hostname, the question is always “is that exact string in the SAN list?” — including whether it is example.com or www.example.com, because those are two different entries and having one does not imply the other.

4.2 A chain is only as complete as the server sends it

And browsers hide it from you

Most browsers cache intermediates they have seen before, and many will fetch a missing one using the CA Issuers URL in the leaf’s Authority Information Access extension. So a server with an incomplete chain works perfectly in the browser you tested with, and fails in curl, in Java, in Python’s requests, on a phone that has never visited a site using that intermediate, and in your payment provider’s webhook. “It works in Chrome” is not evidence of a complete chain — openssl verify without -untrusted is.

4.3 The tool that says OK when it is not

So a monitoring check that greps for “ok” is checking nothing

This is the practical damage. A health check built on s_client | grep "Verify return code: 0" passes for a certificate issued to somebody else entirely, and there are two strings containing reassuring words, so grepping for either is fooled. Checkpoint

A certificate’s CN is shop.example.com and browsers reject it for that name. How?

Because a certificate carrying a subjectAltName extension has its CN ignored entirely for name matching, and every modern certificate carries one. If shop.example.com is not in the SAN list it is not covered — Let’s Encrypt certificates now have no subject at all. Adding names to the CN fixes nothing.

The site works in Chrome and fails in curl and on a phone. What is wrong?

Almost certainly a missing intermediate. Trust stores hold roots, not intermediates, so the server must send the full chain; browsers hide the fault by caching intermediates or fetching them via the AIA URL. Serve fullchain.pem, not cert.pem, and test with openssl verify without -untrusted.

Your monitoring greps s_client output for “Verify return code: 0 (ok)”. What does that prove?

Only that the chain leads to a trusted root — not that the certificate covers the hostname you asked for. s_client prints that and “Verification: OK” for a certificate issued to someone else. Add -verify_hostname and -verify_return_error, or use curl, which checks the name by default.

Why does connecting to a site by its IP address always fail certificate validation?

Certificates are issued for names and an IP is not one, so there is nothing to match — and without a hostname there is no meaningful SNI, so the server presents its default certificate. Use curl --resolve name:443:ip to pin the address while keeping the name for SNI and verification.

5.4 Renew on the CA’s schedule, not the calendar’s

Every renewal script ever written counts days until notAfter. There is now a better signal, and the difference is not academic.

And the response will not tell you why

Notice other keys: [] in both listings. The ARI body is two timestamps and nothing else — no reason, no revocation flag, no explanation URL. It says “renew now” and stops. Why revocation is not the safety net you think

Chapter 4 showed that Let’s Encrypt certificates no longer carry an OCSP responder URI at all — so ssl_stapling on staples nothing, and any monitoring built on OCSP reports every certificate as fine. Revocation moved to CRLs, which browsers consume through their own aggregated push mechanisms and your server never sees. The practical consequence: you cannot check your own certificate’s revocation status from your server, and ARI is the closest thing to a signal you get.

Checkpoint

You need a wildcard certificate. Which challenge type, and why only that one?

DNS-01. Proving control of *.example.com by serving a file at some hostname has no meaning, so HTTP-01 and TLS-ALPN-01 cannot express it. DNS-01 also works for hosts with no inbound internet access, which is the other common reason to choose it.

Renewal has worked for a year and suddenly fails. What changed?

Most often port 80. HTTP-01 needs it reachable at every renewal, not just the first, so a firewall tightened months ago breaks renewal silently and surfaces ninety days later. Your renewer counts days to notAfter. What can it miss?

A revoked certificate. You run a multi-tenant product on *.yourapp.com. Which rate limit bites?

Certificates per registered domain — 50 per week for yourapp.com as a whole, shared by every customer subdomain. It refills at about one per 202 minutes rather than resetting weekly. The structural fix is getting your suffix onto the Public Suffix List’s private section, which is how each *.github.io user gets an independent bucket.

CDNs and Caching

A CDN is two mechanisms wearing one name: something that decides which server you reach, and something that decides whether that server has to ask the origin. This chapter separates them, and then shows a cache-busting query string busting nothing at all.

By the end of this chapter you will be able to

  • Explain what a cache key is, and what is in yours
  • Understand which certificate a visitor actually validates
  • Choose TTLs that the CDN and the browser both obey

6.1 Two ways to send you somewhere near

Which is why DNS steering guesses wrong for you specifically

The CDN sees the resolver’s address, not yours. Using a public resolver whose nearest node is in another country hands you a CDN edge near that node instead of near you — the classic “the site got slower after I changed my DNS”. EDNS Client Subnet exists to pass a truncated form of your address along and improve the guess, and it is a privacy trade-off some resolvers deliberately refuse to make.

The reliable way to bust a cache is to change the path

The DNS TTL and the HTTP TTL are unrelated, and both matter

They fail differently and people conflate them constantly. A long DNS TTL means visitors keep connecting to an address you have stopped using — the outage is in where they go. A long HTTP cache TTL means they reach the right server and get an old file — the outage is in what they receive. A migration needs both lowered, in that order, and only the DNS one has the Chapter 3 subtlety of not being entirely under your control.

Checkpoint

How do you tell anycast from DNS-based steering?

Ask several geographically separate resolvers for the same name. Anycast returns the same addresses to all of them and lets routing do the rest; DNS steering returns a different answer per resolver. The distinction matters because steering routes on where your resolver is, which is why a distant public resolver can make a site slower.

You appended ?v=2 to bust a cached asset and nothing changed. Why?

Because the query string may not be in the cache key — a URL with a query string nobody had ever requested still returned HIT. Cache keys are configured, not standard. Change the path instead: a content-hashed filename is a different object to every cache including the browser’s, which no invalidation can reach.

Your CDN shows a padlock. Is the connection to your origin encrypted?

Not necessarily. The browser validates the CDN’s certificate and TLS terminates at the edge; the edge-to-origin hop is a separate connection governed by your CDN settings, and “flexible” mode makes it plain HTTP. Use full/strict verification, and restrict the origin so it only accepts traffic from the CDN.

What is the difference between max-age and s-maxage?

max-age applies to every cache including the browser; s-maxage applies only to shared caches such as the CDN and overrides max-age there. High s-maxage with low max-age lets the edge absorb traffic while keeping browsers close to current.

The reporting address nobody authorised

Sending rua reports to an address at a different domain requires that domain to publish an authorisation record at <your-domain>._report._dmarc.<their-domain>. Plenty of large domains ask for reports at an address they have not been authorised to receive at — a strictly conforming receiver drops those reports, and you conclude nobody is forging you when in fact nobody is telling you. Worth checking that your own reporting destination is authorised, especially if you use a third-party DMARC vendor.

Checkpoint

Your SPF record needs 12 lookups. What happens?

PERMERROR — receivers must fail the entire record, not just the terms past ten, so every listed sender becomes unauthenticated. Reduce the count with literal ip4:/ip6: ranges and by removing services you no longer use. It also degrades on its own as third parties grow their include trees, so check it periodically.

SPF passes but DMARC fails. How?

SPF authenticated the envelope sender, which is a different domain from the one in the From: header. DMARC requires alignment — that the SPF or DKIM domain matches the visible From: domain. A bulk sender passing its own SPF authenticates itself, not you; it has to sign as your domain, which is what those onboarding CNAMEs arrange.

Mail works normally but fails through a mailing list. Why, and what fixes it?

SPF authenticates the connecting IP, and a forwarder connects from its own address, so SPF legitimately fails. DKIM signs the message itself and survives forwarding — which is why DMARC accepts either mechanism aligning, and why SPF alone is not enough.

Why publish sp= before touching p=?

Because subdomains inherit p= and usually send no legitimate mail, so sp=reject protects the easiest attack surface immediately while the parent domain stays at p=none and you are still discovering which systems send as you.

Chapter Eight · Part IV

Subdomains and Wildcards

A wildcard record looks like a convenience and behaves like a rule with three exceptions, one of which turns a working hostname into NXDOMAIN because you added an unrelated record somewhere else. And the * in DNS and the * in a TLS certificate do not mean the same thing, which produces names that resolve perfectly and cannot be served over HTTPS.

By the end of this chapter you will be able to
  • Predict exactly which names a DNS wildcard covers
  • Explain why adding a record can break a sibling
  • Distinguish a DNS wildcard from a TLS wildcard
  • Delegate a subdomain with NS records
  • Recognise a subdomain takeover

8.1 What a wildcard actually matches

Which means adding a record can break names that worked yesterday

Read the sequence again as a change log. *.dev is published and every <anything>.dev and <anything>.<anything>.dev resolves. Somebody then adds one ordinary record, preview.dev, for an unrelated reason. At that moment every name under preview.dev stops resolving — api.preview.dev, db.preview.dev, all of it — with no error, no warning and nothing in the zone that looks wrong. This is RFC 4592 behaving exactly as specified, and it is the single least intuitive rule in DNS.

8.2 A wildcard makes every name exist

The tooling this breaks

A great deal of software treats NXDOMAIN as “this is not a real host” — spam filters checking sender domains, monitoring that alerts on typo’d hostnames, subdomain-takeover scanners, and the browser heuristic that offers a search instead of an error. Under a wildcard, every one of them sees a name that exists. Publish a wildcard and you have opted out of ever saying “no”, which is a bigger decision than it appears.

Table 8.2 Row two is the practical trap: a wildcard DNS record happily resolves a.b.example.com, so the name works, the server answers, and the browser rejects the certificate. Covering two levels needs either a second wildcard certificate for *.b.example.com or the exact name in the SAN list. Row three is why every wildcard certificate you buy also lists the bare domain explicitly — the wildcard alone does not cover it.

And CAA has its own wildcard rule that overrides the obvious one

If any issuewild property is present in your CAA records, it governs wildcard issuance entirely and the issue property is ignored for wildcards. So adding a CA to issue to let it issue your wildcard does nothing if an issuewild exists naming somebody else — and the failure appears as an ACME order rejected for reasons the client cannot explain. If you publish issuewild at all, publish it for every CA you intend to use.

Anything you still hold below a delegation becomes unreachable

Including a wildcard. If *.bookshop.test existed and eu were delegated, queries for anything.eu.bookshop.test would go to the child’s servers and the parent’s wildcard would never be consulted. Records left behind under a delegated name are invisible, and they are a common source of “but I can see the record in the zone file”.

8.5 Subdomain takeover

StepWhat happens

Table 8.4 The damage is larger than a defaced page: the attacker can obtain a valid certificate for the name (HTTP-01 will validate — they control the content), read cookies scoped to .example.com, and pass any “verify you own this domain” check that accepts a subdomain. Step 3 is the only mistake, and it is an omission rather than an action, which is why it survives reviews.

Scanning for NXDOMAIN finds the wrong thing

The intuitive check — look for CNAMEs whose target does not resolve — misses most real cases, because large platforms answer NOERROR for names nobody has claimed rather than NXDOMAIN. The reliable signal is the HTTP response body: a platform-specific “there is no site here” page reached through one of your names. And if your zone has a wildcard (§8.2), NXDOMAIN never happens at all, so the scan finds nothing by construction.

Checkpoint

You have *.dev.example.com and everything works. You add preview.dev.example.com. What breaks?

Every name below preview.dev — api.preview.dev.example.com and friends — starts returning NXDOMAIN. The existence of a name switches the wildcard off for that whole branch (RFC 4592). Nothing in the zone looks wrong, and the failure appears only for names nobody thought were related.

A DNS wildcard resolves a.b.example.com. Will a *.example.com certificate serve it?

No. A TLS wildcard matches exactly one label, so it covers b.example.com and not a.b.example.com — the name resolves, the server answers, and the browser rejects the certificate. You need *.b.example.com as well, or the exact name in the SAN list. A wildcard certificate also does not cover the bare domain, which is why they always list it separately.

Why does publishing a wildcard break monitoring and spam filtering?

Because it makes every name under it exist: queries return NOERROR with no data instead of NXDOMAIN. Anything that treats NXDOMAIN as “not a real host” — sender-domain checks, typo alerts, takeover scanners — now sees a valid name everywhere.

What is the single change that prevents subdomain takeover?

Delete the DNS record before tearing down the resource it points at. The dangling CNAME is what makes the abandoned resource reachable under your name. Scanning for NXDOMAIN is unreliable — most platforms answer NOERROR for unclaimed names — so inventory external CNAMEs on a schedule and watch Certificate Transparency for certificates you did not request.

And the string tells you nothing about which one it is

There is no way to distinguish “this certificate expired” from “your clock is ahead” by reading the error. The discriminator is scope: if every site fails on one machine, the machine is wrong; if one site fails from every machine, the certificate is. Check the certificate’s notAfter against a clock you trust — curl -sI https://example.com | grep -i ^date reads one off a server rather than off the broken host.

9.4 Checks that cannot pass wrongly

What to alert on, and what to merely record

Page for: the authority returning the wrong value, a certificate under 21 days, a chain that no longer verifies, and an ARI window that has moved into the past (Chapter 5). Record without paging for: a resolver disagreeing with the authority while a TTL is still counting down — that is the system working. The distinction matters because a monitor that pages during every normal DNS change is a monitor people learn to ignore.

Checkpoint

A name gives SERVFAIL everywhere, but dig +trace returns an address. What is happening?

Almost certainly a DNSSEC validation failure. +trace walks the delegation itself and does not validate signatures, so it happily shows you an answer that every validating resolver refuses. It also bypasses your resolver’s cache and any local override — which is why it is the wrong first tool for “this name will not resolve”.

Why should a monitoring script never use dig +short?

Because it prints nothing for both NXDOMAIN and SERVFAIL and exits 0 in every case, including success — so it cannot distinguish “no such record” from “resolution collapsed” from “fine”. Parse status: from a full dig instead, and require the aa flag when you mean to ask the authority.

One laptop reports every HTTPS site as having an expired certificate. What is wrong?

Its clock. Validity is checked against the client’s time, and the error string is identical to a genuinely expired certificate. The discriminator is scope: every site failing on one machine means the machine; one site failing everywhere means the certificate.

A site works for you and not a colleague, ten minutes after a change. First two commands?

dig @your-authoritative-ns name — expect aa and the new value — then dig @their-resolver name and read the remaining TTL. If the authority is right and the resolver is stale, the answer is a number of seconds and nothing is broken. If the authority is wrong, no amount of waiting helps.
