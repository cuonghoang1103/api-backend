About this book

ffmpeg and its relatives are superb tools built for a person watching output scroll past a terminal. Put them in a pipeline, where nobody is watching, and their defining habit becomes a liability: faced with a request they cannot satisfy, they do something reasonable instead, write the file, and exit zero. This book is a catalogue of those moments, each one measured.

Everything here was executed. When Chapter 3 says option position changes meaning, one flag moves four characters to the left and the command runs twenty times faster with a byte-identical result. When Chapter 4 says an encoder can ignore a flag, -crf 18 and -crf 40 produce files with the same md5. When Chapter 8 says a default is wrong for you, the obvious HLS command writes eight segments, lists five, marks the playlist complete, and describes 18 seconds of a 30-second video.

Some of it is uncomfortable. Chapter 7 uploads thirty-six bytes of text named evil2.mp4; ffmpeg identifies it as a playlist from its content, follows the reference, and renders a thumbnail of a different file in the same directory — exit 0, no warning. Chapter 6 extracts “the frame at 0 seconds” and proves, by byte-identical comparison, that it is the frame at 4.96 seconds while every tool reports 0. Chapter 11 re-encodes one clip five times and watches the quality fall monotonically while the files get smaller.

Who should read this

Anyone who processes media they did not create — user uploads, a catalogue, an archive. You need a terminal and some JavaScript. Every clip in the book is generated synthetically from ffmpeg’s own sources, so there is nothing to download and every measurement can be reproduced.

How this book is organised

Chapters map one-to-one onto the twelve modules of the Media Processing track in Code Lab, each ending with that module’s graded exercises — 120 in total, all linked. Read 0 and 3 first; they establish the container/codec split and the command grammar that everything else assumes. Chapter 7 is the one to read before accepting an upload from anybody.

One note on the H.264 encoder

This book uses libopenh264 where most guides use libx264. Both produce standards-compliant H.264; libx264 is GPL-licensed and absent from some distributions’ builds, including the one these pages were written on. The commands are the same shape apart from rate control — and that difference turns out to be Chapter 4’s opening demonstration, so the substitution earned its place.

The habit the whole book argues for

Assert what you expected, on the artefact, every time. Not the exit code — the file. Does it have a video stream? Is the duration what you asked for? Are the dimensions the ones you requested, rather than one pixel less? Is the pixel format the one you specified? Each check is a line of code, and each corresponds to a failure in these pages that produced a file and exited zero. A pipeline that verifies its own output is not being paranoid; it is the only thing in the stack that checks.

Chapter Zero · Part I

Media Formats and Codecs

Almost every media bug starts with two words being used interchangeably that mean completely different things. A file has a container and its streams have codecs, and knowing which one you are looking at decides whether a fix takes one second or ten minutes of CPU. This chapter proves they are independent by moving one video between three files without re-encoding a single frame.

By the end of this chapter you will be able to
  • Separate a container from the codecs inside it
  • Read what a file really contains with ffprobe
  • Explain why remuxing is instant and transcoding is not
  • Choose a pixel format that plays everywhere
  • Pick a format for a given job

0.1 The container is not the codec

ContainerCodec

Table 0.1 The last two rows are the practical payoff. “This video will not play” has two completely different causes with completely different costs, and the filename tells you nothing about which — an .mp4 can contain H.264 that plays everywhere or AV1 that does not.

So the first question about any media problem is: which one is it?

If the codec is right and only the container is wrong — a phone that will not open .mkv but plays H.264 happily — the fix is -c copy and it is instant and lossless. If the codec itself is unsupported, you must re-encode, which costs CPU and quality. ffprobe answers the question in one command, and running it before reaching for a solution saves a great deal of time.

Table 0.2 The last three are why “how long is this video” is a harder question than it looks: the container stores a duration, each stream stores its own, and a file assembled by concatenation may have a container duration that is simply wrong. Chapter 9 takes this apart properly.

0.3 Pixel formats, and an encoder quietly overruling you

The general shape of this, which recurs all through ffmpeg

ffmpeg overwhelmingly prefers to produce a file rather than fail. Unsupported pixel format, mismatched sample rate, a filter that cannot apply — the usual response is to insert a conversion or pick something else and mention it in passing. That is excellent for interactive use and dangerous in a pipeline, because the failure mode is a file that is subtly not what you specified. Check the output with ffprobe rather than trusting the exit code, and think carefully before setting -v error on anything whose warnings you have not read at least once.

Use yuv420p for delivery unless you have a specific reason not to

It is a compatibility decision, not a quality one. Hardware decoders in phones, TVs and browsers overwhelmingly support 4:2:0 8-bit and will refuse, or fall back to slow software decoding, for anything else. Always pass -pix_fmt yuv420p when encoding for delivery — ffmpeg otherwise preserves whatever the source had, and screen recordings, ProRes masters and phone captures frequently carry something else. A file that looks perfect on the workstation that made it and shows a black screen on an iPhone is almost always this.

Chapter 4 covers what that difference actually means, and it is more consequential than it sounds.

Checkpoint

A file will not play on a phone. What is the first command to run, and why?

ffprobe. The filename tells you the container and nothing about the codecs, and the two failures have completely different costs: a wrong container is fixed with -c copy in about a second with no quality loss, while an unsupported codec requires a full re-encode. Find out which one it is before choosing a fix.

How can the same video stream exist in an MP4, an MKV and a MOV?

Because the container only files the stream away — it does not touch the compressed data. Remuxing with -c copy produces byte-identical video streams in all three, as the md5 comparison shows; only a few hundred bytes of container bookkeeping differ.

Why pass -pix_fmt yuv420p even though it discards the most colour?

Compatibility, not quality. Hardware decoders in phones, TVs and browsers overwhelmingly support 4:2:0 8-bit and will refuse or fall back to slow software decoding for anything else. ffmpeg preserves whatever the source had, and screen recordings and editing masters often carry 4:2:2 or 4:4:4 — so a file that looks perfect where it was made shows a black screen elsewhere.

AV1 compresses ~50% better than H.264. Why is H.264 still the delivery default?

Because the constraint is the hardware decoder already present in the device, not the compression ratio. Software AV1 decoding on a phone drains battery and drops frames, while hardware H.264 decoding is nearly free. Serve newer codecs where support is detectable and keep H.264 as the fallback.

Chapter One · Part I

Image Processing with Sharp

sharp is a thin binding over libvips, and libvips is built on an idea that sounds like a detail and turns out to decide everything: it never holds the whole image. This chapter measures the consequences — including a resize that makes decoding faster, and a quality setting that means something different in every codec.

By the end of this chapter you will be able to
  • Explain why libvips is fast and flat in memory
  • Use shrink-on-load rather than fighting it
  • Choose a format and quality with measurements, not habit
  • Handle EXIF orientation before it handles you
  • Know when sharp is the wrong tool

1.1 A resize that makes decoding faster

Which inverts the intuition you brought with you

The instinct from most imaging libraries is that resizing is extra work to be avoided. Here it is a hint that lets the decoder skip work. Two practical consequences: never decode at full size and then resize in a second step — pass the target to the same pipeline so libvips can plan for it — and note the effect is strongest for JPEG. PNG has no equivalent trick, so a PNG pipeline gains almost nothing and behaves the way you expected in the first place.

1.2 Memory that does not grow with the image

libvips (sharp)Full-raster (ImageMagick)
ModelStreams in tiles, demand-drivenDecodes the whole image into RAM

Table 1.1 Row three is the number that decides your architecture. A full-raster library processing a 96-megapixel upload needs more than a gigabyte of RAM per concurrent request, so a container sized for the common case dies on the uncommon one — and an attacker who knows this can knock over a service by uploading one very large image. Flat memory is the reason sharp can sit in a request path at all.

But it is not faster for one image, and that surprises people

libvips has to start its pipeline machinery, so for a single thumbnail an ImageMagick invocation can finish first — measurements put the crossover at about four images per process. sharp wins decisively once you are doing many in one process, which is exactly the shape of a server and exactly not the shape of a shell script. If your workload really is one image per process, a well-tuned magick command with -define jpeg:size (which is ImageMagick’s own shrink-on-load) is a legitimate choice.

Metadata is discarded by default, and that is the right default

Chapter 10 of the object-storage volume made the security case: EXIF carries GPS coordinates users do not expect you to publish, and re-encoding destroys polyglot files. sharp strips everything unless you ask. If you need the colour profile — and for anything where colour accuracy is the product, you do — use keepIccProfile() rather than withMetadata(), which brings the GPS back with it.

Checkpoint

Why can adding .resize(400) make a JPEG pipeline faster than not resizing?

Shrink-on-load. JPEG is built from 8×8 DCT blocks and the decoder can reconstruct them at 1/2, 1/4 or 1/8 scale, so libvips decodes far less data when it knows the target is small. It measured about 2.3× faster than decoding at full size. The corollary is to pass the target into the same pipeline rather than resizing in a second step — and to expect no such gain from PNG.

Why does full-raster image processing fall over on large uploads?

Its memory is linear in pixel count: going from 24 to 96 megapixels raised ImageMagick’s footprint by about 274% against sharp’s 8%. A container sized for typical images dies on one large one, per concurrent request — which is also a denial-of-service vector for anyone who can upload.

Is JPEG quality 100 lossless?

No. It quantises gently rather than not at all, and costs roughly three times the bytes of quality 90 for a difference no viewer will see. Quality numbers are also not comparable across codecs — WebP at 80 typically beats JPEG at 90 on both size and fidelity.

Every portrait photo comes out sideways after processing. Why?

The source was stored in sensor orientation with an EXIF flag, sharp ignored the flag, and then stripped the metadata — so the rotation was never applied and the instruction is gone. Call .rotate() with no argument before resizing, which bakes the orientation into the pixels.

Chapter Two · Part I

Resizing, Cropping and Watermarks

Resizing looks like the simplest operation in media processing and is where the most silent corruption happens. A dimension you asked for that you did not get; an aspect ratio preserved in metadata rather than in pixels; a logo whose invisible background bleeds into its visible edge. Each of these produces a file, an exit code of zero, and a wrong result.

By the end of this chapter you will be able to
  • Scale without getting a dimension you did not ask for
  • Tell a real aspect-ratio change from a stored one
  • Crop and letterbox deliberately
  • Composite a watermark without edge artefacts
  • Choose a resampling filter on purpose

2.1 The dimension you asked for, and the one you got

Why the silent version is worse than an error

One pixel does not matter. What matters is that you now have a file whose dimensions are not the ones your code believes it produced — so a manifest, a database row, or a CSS layout computed from the requested size is wrong by one pixel, and the tiling or letterboxing built on it is subtly off. Use -2, always, and read the dimensions back from the output rather than assuming them. The general rule from Chapter 0 applies again: ffmpeg would rather produce a file than fail.

2.2 An aspect ratio can be a lie in the metadata

TermMeans
width × heightThe stored pixel grid
sample_aspect_ratio (SAR)How non-square each stored pixel is
display_aspect_ratio (DAR)What the viewer should see — width×SAR : height
SAR 1:1Square pixels; stored and displayed agree
SAR anything elseThe stored frame is not what is displayed

Table 2.1 Non-square pixels are a legacy of broadcast video and they are still everywhere. The practical rule: if you extract frames, check the SAR, and normalise with -vf scale=iw*sar:ih,setsar=1 so the stored pixels become square. Otherwise your thumbnails are distorted in exactly the way the video is not.

2.3 Watermarks, and the edge nobody looks at

The transparent pixels in your logo are not transparent to the scaler

A PNG logo stores colour and alpha separately, and the colour of a fully transparent pixel is arbitrary — many exporters leave it white or black. When ffmpeg scales that image it averages the colour channels without weighting by alpha, so the invisible white bleeds into the visible edge and a red logo acquires a pale fringe. The fix is to premultiply alpha before scaling (scale=...:premultiplied=1, or -vf premultiply=inplace=1), or to scale the logo in a tool that premultiplies by default — sharp and ImageMagick both do.

2.4 Resampling, and averaging the wrong numbers

Table 2.3 For the common case — making something smaller for the web — -vf scale=1200:-2:flags=lanczos is a free improvement over the default, and the cost is invisible next to the encode that follows it.

And all of them average the wrong numbers by default

sRGB values are not proportional to light: the number 128 is roughly 22% of the brightness of 255, not 50%. So averaging two pixels by averaging their stored numbers is arithmetic on the wrong scale, and a fine black-and-white checkerboard downscaled to one pixel comes out around 128 when the physically correct answer is about 188. The result is that detailed areas get darker as they shrink, which is why some thumbnails look muddier than the image they came from. Correct handling means converting to linear light, resampling, and converting back — -colorspace RGB in ImageMagick, a zscale detour in ffmpeg. It costs time, and for most web thumbnails everyone accepts the error, but it is worth knowing that the default is an approximation rather than the truth.

Checkpoint

You asked for scale=500:-1 and the file is 500×624 when the arithmetic says 625. Why?

H.264 in 4:2:0 requires even dimensions, so the encoder rounded and continued — with no warning at any log level. Use -2, which makes the scaler produce an even number and report the aspect-ratio change, and read the dimensions back from the output rather than trusting the request.

A video plays correctly but extracted frames are distorted. What is going on?

Non-square pixels. The stored frame has been squashed and a sample_aspect_ratio other than 1:1 tells players to stretch it back — so playback looks right while anything reading the stored grid sees the distortion. Normalise with scale=iw*sar:ih,setsar=1 before extracting.

Your red PNG watermark has a pale fringe after scaling. Why?

The colour of fully transparent pixels is arbitrary and often white, and ffmpeg’s scaler averages colour channels without weighting by alpha — so the invisible white bleeds into the visible edge. Premultiply alpha before scaling, or scale the logo in sharp or ImageMagick, which premultiply by default.

Why do detailed areas darken when an image is downscaled?

Because resampling averages sRGB numbers, which are not proportional to light — 128 is about 22% of the brightness of 255, not 50%. A fine checkerboard averages to roughly 128 instead of the physically correct 188. Correct handling resamples in linear light; most web pipelines accept the error, but it should be a choice rather than a surprise.

Chapter Three · Part II

FFmpeg Basics

ffmpeg’s command line is not a list of options — it is a description of a pipeline, and where an option sits decides what it applies to. Two commands that differ only in the position of one flag can be twenty times apart in speed. And the default behaviour, when you do not say what you want, throws things away without asking.

By the end of this chapter you will be able to
  • Read an ffmpeg command as a pipeline, not a flag list
  • Place options so they apply to what you meant
  • Choose between copying and re-encoding deliberately
  • Keep every stream you meant to keep
  • Know when a filter forces a re-encode

3.1 The shape of every command

The historical warning you can now ignore

Older advice says input seeking is inaccurate — that it lands on the nearest keyframe rather than the frame you asked for. That was true for many years and is why so much code still puts -ss after -i. Modern ffmpeg seeks to the keyframe and then decodes forward to the exact frame, which is why the two files above hash identically. Test it on your own build rather than trusting either the old advice or this paragraph.

3.2 What ffmpeg keeps when you do not say

Table 3.1 The silent drop in row one is one of the most expensive defaults in ffmpeg: a pipeline that “just remuxes” user uploads quietly discards alternate language tracks, commentary, subtitles and chapter data, and nobody notices until a customer asks where the Spanish audio went. If you are processing files you did not create, start from -map 0.

Table 3.2 The line between the halves is simply whether the compressed data itself has to change. Everything above it is file bookkeeping and takes seconds regardless of length; everything below decodes and re-compresses every frame. Designing a pipeline so the common path stays in the top half is the single largest performance decision in media processing.

3.4 Reading the pipeline out loud

Three flags worth putting in every command you write

-y so it does not stop waiting for a confirmation nobody will type in a script. -hide_banner so the output is the information rather than forty lines of build configuration. And -nostdin if ffmpeg is running in the background, because it reads stdin for keyboard commands and will happily consume input meant for something else — which is the cause of the classic “my shell script stops after the first file in the loop”.

Checkpoint

Why is -ss 290 -i in.mp4 so much faster than -i in.mp4 -ss 290?

Position decides what the option applies to. Before -i it is an input option and ffmpeg uses the container index to start reading near that point; after -i it is an output option and ffmpeg decodes the whole file up to there and discards it. On a five-minute file that measured about twenty times faster, with byte-identical output.

Your remux pipeline loses alternate audio tracks. Why?

Because with no -map, ffmpeg selects one stream of each type by heuristic and silently drops everything else — no warning, exit 0. Use -map 0 to keep every stream from the input, which is what you want for any file you did not create yourself.

Why can you not combine -vf scale=... with -c copy?

A filter operates on decoded frames and -c copy means the data is never decoded. The requests contradict, and ffmpeg refuses rather than silently ignoring one. It is the clean statement of the boundary: changing the picture costs a re-encode; changing the container does not.

Why scale=1280:-2 rather than scale=1280:-1?

Both compute the height from the aspect ratio, but -2 rounds to an even number. H.264 in 4:2:0 cannot encode odd dimensions, so -1 produces an encoder error on any source whose scaled height happens to be odd — an intermittent failure that depends on the input.

Transcoding is choosing what to throw away. The controls for that choice are named inconsistently across encoders, and at least one of them will accept a setting it does not implement and produce a file anyway. 4.1 A flag that does nothing

The general defence, which applies to every option in this chapter

Verify the output, not the exit code. Encode two short clips at settings that should differ visibly, and compare their sizes; if they match, the control is not connected. It takes ten seconds and it is the only way to know that a rate-control flag reached the encoder — because unknown and unsupported options are warnings in ffmpeg, not errors.

Checkpoint

-crf 18 and -crf 40 produce identical files. What happened?

The encoder has no constant-quality mode and ignored the flag — libopenh264 does exactly this. ffmpeg warns that the option “has not been used for any stream”, but at info level, so -v error hides it. Verify rate-control flags by encoding at two settings that should differ and comparing sizes.

When is constant bitrate the right choice over constant quality?

When the size or the pipe is fixed: live streaming, a contractual rung in an adaptive ladder, a hard upload limit. Everywhere else constant quality gives a better result per byte, because it spends bits where the picture needs them instead of wasting them on easy scenes and starving hard ones.

Does a slower preset produce better quality?

At a fixed quality setting, no — it produces a smaller file at about the same quality, having spent CPU finding a better encoding. It is a bytes-for-seconds dial. The curve is also not always monotonic: some fast presets are dominated on both size and quality, and adjacent ones can be byte-identical, so measure the ones you are choosing between.

Because HLS segments can only begin at a keyframe, so the segment length you want dictates the GOP. A 10-second GOP makes 4-second segments impossible regardless of what you request — and every rung of the ladder must use the same GOP, or the segment boundaries will not align and players cannot switch cleanly between them.

Chapter Five · Part II

Audio Processing

Audio has fewer knobs than video and more ways to be quietly wrong. A normaliser that changes your sample rate without saying so, a downmix that turns a stereo track into silence, and a loudness measurement that disagrees with the other loudness measurement by eight decibels — all of them produce a file, and none of them produce a warning.

By the end of this chapter you will be able to

  • Normalise without changing things you did not intend to
  • Downmix safely
  • Detect and trim silence

5.1 Two measurements that disagree by eight decibels

Which is why every platform specifies LUFS, not dB

If loudness were measured as a simple average, the way to be loudest would be to have no quiet parts — which is exactly the loudness war that gating was invented to end. A podcast with long pauses and a dense music track can share an integrated loudness and sound equally loud, which is the entire point. Targets worth knowing: streaming platforms normalise to roughly −14 LUFS, broadcast to −23 (EBU) or −24 (ATSC), and podcasts conventionally to −16 mono / −19 stereo.

5.2 A normaliser that changes your sample rate

The pattern, again

This is Chapter 0’s lesson in a different filter: ffmpeg made a reasonable internal decision, produced a valid file, and did not consider the side effect worth mentioning at the default log level. A pipeline that normalises a podcast archive quadruples its storage and nobody notices until the bill. Always pin the output format you want — sample rate, channel layout and sample format — rather than assuming it survives the filter chain.

linear=true is a request, not a promise

loudnorm has two modes. Linear applies one constant gain to the whole file and preserves the dynamics exactly. Dynamic compresses to hit the loudness range you asked for. Asking for linear=true when your target LRA is smaller than the material’s measured range makes linear mode impossible, so it silently falls back to dynamic — and the only evidence is the normalization_type field in the JSON that print_format=json emits. If preserving dynamics matters, run the two-pass form and read that field.

5.3 The downmix that produces silence

This is not a contrived case

Out-of-phase stereo happens for real: a miswired cable, a plugin left in a “wide” setting, a stem bounced with a polarity flip, an old vinyl transfer. It sounds perfectly normal in stereo and disappears in mono — which is exactly what happens on a phone speaker, a smart speaker, or any Bluetooth device that downmixes. Check phase correlation before downmixing (astats reports it), and prefer pan with an explicit recipe over -ac 1 when you cannot inspect the source.

Encoder delay: the same audio, decoded 21 milliseconds late

AAC encoders prepend padding samples the decoder must discard. An MP4 records how many in an edit list, so the container tells the decoder to trim them and the audio lands exactly where it should. A raw ADTS stream has nowhere to store that number, so the same encode in a .aac file decodes about 21 ms (1,024 samples) later than the MP4 does. That is inaudible on its own and fatal when you are cutting audio against video, or concatenating segments, or comparing two renders sample by sample. MP3, Opus and FLAC round-trip exactly; if you are doing sample-accurate work, do not use raw ADTS.

Checkpoint

Appending silence changed your loudness measurement by 8 dB. Which measurement, and why?

The ungated RMS one (volumedetect mean_volume), which averages everything including silence. EBU R128 integrated loudness is gated — blocks below a relative threshold are discarded — so it moved by 0.1 LU for the same file. Platforms specify LUFS precisely because an ungated average rewards having no quiet parts.

Your normalised audio archive quadrupled in size. What happened?

loudnorm oversamples to 192 kHz to measure true peak and leaves the output there unless told otherwise — a 44.1 kHz input comes out at 192 kHz with no warning. Append aresample=44100, or pin the output rate with -ar. Pin sample rate, channel layout and sample format explicitly rather than assuming they survive a filter chain.

A stereo file becomes silent when converted to mono. Is that a bug?

Not in ffmpeg — the channels are out of phase and -ac 1 sums them, so they cancel exactly. It happens with miswired cables, polarity-flipped stems and some stereo-widening plugins, and it also happens on any phone or smart speaker that downmixes. Check phase correlation before downmixing, or use pan with explicit coefficients.

Why does the same AAC encode play 21 ms late as .aac but on time as .m4a?

AAC prepends encoder priming samples. MP4 stores the count in an edit list so the decoder trims them; a raw ADTS stream has nowhere to record it, so those 1,024 samples are decoded as audio. It is inaudible alone and breaks sample-accurate work — A/V sync, segment concatenation, render comparison. Use MP4, or a codec that round-trips exactly.

6.2 The timestamp it reports is not the frame you got

When this matters, and when it does not

For a poster frame, five seconds of drift is invisible and nobody cares. It matters when the thumbnail is a claim about a moment: a scrub-bar preview that must line up with the position under the cursor, a frame extracted for analysis at a known timecode, a contact sheet whose captions state times. 6.3 A frame worth showing

Why the first frame is so often useless

Video rarely starts on the interesting bit. It starts on black, on a logo, on a fade, or on the first frame of a slow push. The file size in Listing 6.4 is itself a signal — a nearly-flat frame compresses to almost nothing, so an anomalously small thumbnail is usually a blank one, and that is a cheap automated check for “did we pick a black frame?” worth running over a whole library.

6.4 The filter that writes two hundred files

The rule that prevents it

Any time you use select, thumbnail, or anything else that passes frames through irregularly, add -fps_mode vfr (older ffmpeg spells it -vsync vfr). The default is cfr, which pads. This is the same shape as everything else in this book — a reasonable default for one use case, silently expensive in another, and visible only if you count the output.

Checkpoint

Why can the frame you extract not be the one at the timestamp reported?

Because the fps filter reports the ideal grid it targets, not the source frame it chose. With the default round=near a “frame at 0 s” can genuinely be the frame at 4.96 s, and ffprobe on the output still says 0. Verify against the picture, not the metadata — and use round=up, or seek per timestamp, when the frame is a claim about a moment.

Your thumbnails are frequently black. What should you use instead of -ss 0?

The thumbnail filter, which buffers frames and picks the one least like the average of the batch. Video rarely starts on the interesting bit. A very small output file is also a useful automated signal that you picked a nearly-flat frame.

A scene-detection job produced 6,000 JPEGs instead of 6. Why?

The image muxer defaulted to constant frame rate and padded every empty slot by repeating the last selected frame. Add -fps_mode vfr whenever frames pass through irregularly — with select, thumbnail, or scene detection. There is no warning; the only symptom is the file count.

Why build a sprite sheet rather than individual preview thumbnails?

One request and one cache entry instead of twenty-five, which is the difference between a scrub bar that feels instant and one that fetches over the network as the cursor moves. Order the filters fps,scale,tile so the scaler works on small frames rather than on one large mosaic.

Chapter Eight · Part IV

Streaming and Adaptive Bitrate

Adaptive streaming is a video cut into segments, several times over at different qualities, plus text files listing them. The mechanism is simple and the defaults are not for you — this chapter starts with a command that ships two thirds of a video and marks it complete.

By the end of this chapter you will be able to
  • Package a video as HLS correctly
  • Recognise a playlist that is missing most of the film
  • Control segment length, which you do not do with the segment-length flag
  • Align a ladder so players can switch between rungs
  • Choose between MPEG-TS and fMP4

8.1 A playlist that omits most of the video

The default is for live, and you are almost certainly not doing live

-hls_list_size defaults to 5 because the HLS muxer is built for live streaming, where the playlist is a sliding window over the last few segments and old ones are dropped as they age out. For video on demand you want every segment listed, forever: -hls_list_size 0. It is one flag, the failure is silent, and the symptom — “the video stops early” — sounds like a player bug rather than a packaging one.

8.2 Segment length is set by the keyframes, not by the flag

Which means the GOP is decided before the packaging, in the encode

If you want four-second segments, encode with -g set to four seconds’ worth of frames — 100 at 25 fps — and add -force_key_frames "expr:gte(t,n_forced*4)" so keyframes land on exact multiples regardless of scene detection. Packaging cannot fix a GOP after the fact; remuxing with -c copy can only cut where keyframes already are, and re-encoding to fix it throws away a generation of quality.

8.3 A ladder players can actually switch between

Matching -g is not enough once the frame rate differs

-g counts frames, not seconds. A ladder whose low rung drops to 15 fps to save bitrate gets a keyframe every g/15 seconds while the 30 fps rungs get one every g/30 — so the boundaries line up only half the time, and a player switching down lands mid-segment. If any rung changes frame rate, express keyframes in time with -force_key_frames rather than in frames with -g.

8.4 The atom that decides whether playback can start

It costs one extra pass and it is not optional for the web

+faststart makes ffmpeg write the file, then rewrite it with the index moved — so it roughly doubles the file I/O and cannot be done when writing to a pipe (Chapter 7, where the same constraint appears from the other side). Put it on every MP4 you intend to serve over HTTP. A 500 MB video without it is a 500 MB download before the first frame appears, and the symptom users report is “the video does not work” rather than “the video is slow to start”.

And check where the timeline starts

MPEG-TS timestamps conventionally begin at 1.4 seconds rather than zero — a legacy of broadcast, where a small offset avoided wraparound edge cases. fMP4 starts at zero. Checkpoint

Your HLS video stops two thirds of the way through, but the file is fine. Why?

-hls_list_size defaults to 5 — a sliding window for live — so the playlist lists only the last five segments while the rest sit unreferenced on disk. EXT-X-ENDLIST is still written, so the player believes it reached the end. Use -hls_list_size 0 for video on demand.

You asked for 4-second segments and got 10-second ones. What decides segment length?

The keyframes. A segment must start with one so a player can decode from its first frame, so the GOP is the floor — -hls_time is a lower bound that is silently ignored when it is unreachable. Fix it in the encode with -g and -force_key_frames, not in the packaging.

Every rung uses the same -g 60 but players stutter when switching. Why?

Because -g counts frames, not seconds. If one rung runs at 15 fps and the others at 30, its keyframes fall every 4 seconds against their 2 — boundaries coincide only half the time and a switch lands mid-segment. Pin keyframes in time with -force_key_frames whenever frame rates differ across the ladder.

MPEG-TS or fMP4?

fMP4, unless you must support pre-2016 devices. It has lower overhead, and the same segments serve both HLS and DASH — so you package, store and serve one set instead of two. Note the timelines differ: TS conventionally starts at 1.4 s, fMP4 at 0.

Chapter Nine · Part IV

Metadata and Probing

ffprobe is how a pipeline learns what it is holding, and almost every field it returns has a caveat. Numbers arrive as strings, durations disagree with each other, dimensions are not the dimensions, and one common way of setting rotation does nothing at all. This chapter is about reading a file correctly before acting on it.

By the end of this chapter you will be able to
  • Parse ffprobe output without type bugs
  • Choose between the container duration and the stream duration
  • Read dimensions that match what a viewer sees
  • Detect a truncated or malformed file
  • Validate an upload before processing it

9.1 Every number is a string

And some of them are absent rather than zero

bit_rate is missing from some containers, nb_frames is often absent because counting requires decoding the whole file, and duration can be absent on a stream even when the container has one. So the parse has to handle three states per field — a number, a string that is a number, and nothing at all — and Number(undefined) is NaN, which then propagates silently through every arithmetic operation downstream.

9.2 Which duration?

So pick the duration that matches the question

Seeking to a percentage, or extracting frames? Use the video stream’s duration. Showing a length to a user, or billing by minutes? The container duration is the honest answer. Comparing two renders? Compare both, and treat a difference larger than one frame as a defect. And whichever you use, check the output exists afterwards — nothing in the exit status will tell you.

9.3 Dimensions are not what is displayed

Rotation, and a way of setting it that does nothing

A phone stores video in sensor orientation and records a display matrix in the container saying how to turn it. ffprobe exposes it in the stream’s side-data list, not as a simple field — and the legacy tags.rotate key that most older code looks for no longer exists. Worse, the corresponding way of setting it, -metadata:s:v:0 rotate=90, is now a silent no-op: the MP4 muxer drops it, ffmpeg exits 0, prints no warning, and the output has neither the tag nor a matrix. Use the transpose filter to bake the rotation into the pixels, which is what you almost always wanted, or -display_rotation to set the matrix properly.

Checkpoint

Your “pick the longest clip” query returns a 9-second file over a 30-second one. Why?

ffprobe returns durations as JSON strings, so the comparison is lexical and "9.000000" sorts after "30.000000". The same bug hits jq max_by, template sorts and untyped database columns. Coerce every numeric field at the parse boundary — and handle the fields that are absent entirely, since Number(undefined) is NaN.

Seeking to 95% of the duration produced no thumbnail and exit code 0. What went wrong?

You used the container duration, which is the longest of all streams — commonly the audio, which runs past the video because of encoder padding. 95% of it landed after the last frame, so ffmpeg wrote nothing and exited 0. Seek relative to the video stream’s duration.

Why do thumbnails come out distorted even though you scaled to the reported dimensions?

Because width and height are storage dimensions, and the display size is that grid multiplied by the sample aspect ratio. Derive the display width from the SAR — remembering it arrives as a string and can be "0:1" for unknown, which means 1:1 rather than zero.

A truncated Matroska file probes cleanly and reports its full duration. How do you catch it?

Only by decoding it. Matroska stores the duration in its header, so the metadata describes the original file; MP4 loses its index and fails loudly instead. Run ffmpeg -xerror -i file -f null - in the worker — it decodes everything and writes nothing, and it is the only check that tests the bytes rather than the file’s claims about itself.

Chapter Ten · Part V

Performance and Queues

Media work is the most expensive thing most applications do, and it is expensive in a specific way: CPU-bound, long-running, and unbounded in the size of what a user can hand you. That combination breaks the request/response model, so this chapter is about the queue you will end up building either deliberately or by accident.

By the end of this chapter you will be able to
  • Explain why media work cannot live in a request
  • Measure the concurrency that actually helps
  • Bound every job so one input cannot hold a worker forever
  • Apply back-pressure instead of collapsing
  • Make jobs safe to retry

10.1 Why this cannot go in a request handler

PropertyConsequence
CPU-boundA worker is blocked, not idle — no async trick helps
Seconds to hoursLonger than any sensible HTTP timeout
Unbounded inputA user decides how much work you do
Memory-hungryChapter 1: full-raster tools scale with pixel count

Fails oftenMalformed uploads are normal traffic

Table 10.1 The third row is the one that decides the architecture: a user uploading a two-hour 4K file has, without asking, committed you to an hour of CPU. In a request handler that is an occupied worker, a client timing out and retrying — creating a second hour of work — and a queue of real users waiting behind it. The job has to be accepted, acknowledged, and done elsewhere.

10.2 How much concurrency actually helps

And ffmpeg is already using your cores

This is the part people miss. A single ffmpeg process multi-threads its own encoding, so running eight of them on eight cores does not give you eight times the throughput — it gives you eight processes each fighting for threads. For throughput across many files, run a few processes and cap each with -threads. For latency on one file, run one process and let it have everything. Those are different goals and they want opposite configurations, which is why a single “correct” setting does not exist.

GoalConfiguration

Fair sharing between tenantsOne job per tenant in flight, then round-robin
A machine that stays responsiveLeave a core free; nice the workers
Predictable costCap concurrency, and queue the rest

Table 10.2 The last row is the one that keeps a service up. A queue with a bounded pool degrades gracefully — jobs wait longer — while unbounded concurrency degrades catastrophically, because memory and disk run out at the same moment for every job at once.

Retries need idempotence, and media jobs get retried a lot

A worker killed by a timeout, an OOM, or a deploy will have its job redelivered. If the job appends to something, or increments a counter, or writes to a name derived from “now”, the retry produces a second artefact and the first becomes an orphan. Derive the output key from the input — a content hash plus the transform parameters, exactly as Chapter 10 of the object-storage volume does — so re-running is a no-op that overwrites itself, and a duplicate delivery costs CPU rather than correctness.

A bounded queue with a visible depth lets you decide; an unbounded one converts a traffic spike into memory exhaustion, and the first symptom is the whole machine dying rather than jobs taking longer.

Measure the queue, not the workers

Worker CPU tells you they are busy, which you already knew. The numbers that predict an incident are queue depth and oldest job age: depth rising steadily means arrival rate exceeds service rate and no amount of waiting will fix it, and an oldest-job age far above the median means something is stuck rather than slow. Alert on those two, and on the job failure rate — a slow rise in failures is usually a change in what people are uploading, which is worth knowing before it becomes an outage.

Checkpoint

Why can a transcode not run in a request handler, even asynchronously?

Because it is CPU-bound: the work occupies a core, so async only frees the event loop, not the machine. Add that a user chooses the input size, and one upload can commit you to an hour of CPU while the client times out and retries, creating a second hour. Accept, acknowledge, and do it in a worker.

You doubled worker concurrency and throughput barely moved. Why?

You ran out of cores, and ffmpeg was already multi-threading inside each process — so more processes means more competition for the same threads, not more work done. Listing 10.1 shows the curve flattening. For throughput, run a few processes with -threads capped; for latency on one file, run one and give it everything.

A file-size limit does not stop a decompression bomb. What does?

A pixel-count limit, checked from ffprobe before decoding. A 40,000×40,000 image is a few kilobytes compressed and gigabytes in memory. Probe first, assert dimensions and duration, and only then commit to the work.

Which metrics predict a media-pipeline incident?

Queue depth and oldest-job age, not worker CPU. Depth rising steadily means arrivals exceed service rate and waiting will not help; an oldest job far above the median means something is stuck rather than slow. Watch the failure rate too — it usually moves before anything else does.

Chapter Eleven · Part V

Production Media Pipelines

Everything so far has been one operation on one file. A pipeline is the arrangement that survives ten thousand of them, run by people who did not write it, on files nobody inspected — and its defining property is that every mistake it makes is permanent, because the original is usually gone by the time anyone notices.

By the end of this chapter you will be able to
  • Lay out storage so reprocessing is possible
  • Keep a master, and know what it costs not to
  • Order a pipeline so failures are cheap
  • Handle the failures that are normal traffic
  • Reason about what the pipeline costs

11.1 Every re-encode costs something, forever

Which is the whole argument for keeping the original

Store what the user uploaded, untouched, and derive everything from it. Then a new preset, a new resolution, a new codec, or a bug fix in your pipeline is a reprocessing job rather than a permanent degradation — and the fifth generation above becomes the first. Storage is cheap and monotone; quality is expensive and irreversible. The one caveat is Chapter 7: the original is untrusted input, so it must be validated and never served directly.

Recording each rendition as it lands turns that into “this asset has 2 of 4”, which a retry can act on.

And keep the failure, not just the fact of it

When a job fails, store the last few kilobytes of ffmpeg’s stderr against the asset (Chapter 7 keeps the tail, because the useful error is at the end). Six months later, “why did these 400 assets fail in March” is answerable in a query rather than unanswerable. Without it, a failed asset is a boolean and the only recourse is to re-run everything and hope it fails the same way.

Derive on demand where the long tail is long

Most catalogues are enormously skewed: a small fraction of assets receive nearly all the views. Pre-generating every rendition for every asset spends CPU and storage on files nobody will ever request. Generating the popular rungs on ingest and the rest on first request — behind a CDN, so the second viewer gets a cache hit — usually costs far less in total, at the price of one slow first view. The object-storage volume’s Chapter 10 makes the same argument for images, and the arithmetic is the same here with larger numbers.

So the one habit worth taking away

Assert what you expected, on the artefact, every time. Not the exit code — the file. Does it have a video stream? Is the duration what you asked for? Checkpoint

Why keep the original upload rather than only the transcoded version?

Because every re-encode is a permanent, measurable loss — Listing 11.1 shows quality falling monotonically across five generations while the files get smaller, since the encoder is compressing the previous encoder’s artefacts. Keeping the original turns a new preset or a pipeline bug fix into a reprocessing job instead of another generation of damage.

Why put a pipeline version in the derived path?

So a pipeline change is additive. You write v3 beside v2, migrate readers when the backfill finishes, and delete the old one — instead of overwriting in place and ending up with a library where nobody can tell which files received the fix.

Why probe and assert before writing the database row?

So rejecting a bad upload costs one ffprobe rather than a row, a queue entry, a worker and a timeout. Bad uploads are constant traffic, not an edge case. And marking the asset ready last means any failure leaves it pending, which is a state a retry can act on.

What is the single habit this book is arguing for?

Assert what you expected on the artefact rather than trusting the exit code. Nine of the twelve chapters end in a case where a tool made a reasonable decision on your behalf, produced a file, exited zero, and did not mention it — a flag ignored, a stream dropped, a dimension rounded, a playlist truncated. Checking the output is the only thing that catches them.
