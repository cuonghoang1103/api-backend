About this book

Observability is sold as three tools you install. It is really a set of trades — between detail and cost, between noise and coverage, between how much you can afford to record and how much you will wish you had recorded. This book is about making those trades deliberately, and it measures what each one costs.

Everything here ran. When Chapter 0 says a label can destroy a metrics system, five hundred users make one request each and the counter goes from zero to five hundred time series while the well-behaved one goes from one to three. When Chapter 1 says a suppressed log line is not free, twenty thousand of them cost 289 ms against 1 ms guarded. When Chapter 5 says liveness and readiness are different questions, the same process answers 200 and 503 in the same second.

The alerting chapter is the one to read twice. It watches a real rule move from inactive to pending to firing against a real Prometheus, and the interesting state is the middle one: the condition is true, the threshold is crossed, and nobody has been woken — because the for window has not elapsed and the problem may still resolve itself. Almost every complaint about alert fatigue is that clause being missing.

Who should read this

Anyone who runs something and has been surprised by it. You need a terminal and some JavaScript; the lab is one small service and one Prometheus, both on your own machine, and every query in the book can be re-run against it.

How this book is organised

Chapters map one-to-one onto the ten modules of the Observability & Monitoring track in Code Lab, each ending with that module’s graded exercises — 100 in total, all linked. Read 0 first; the cost model in it is what every later chapter is reasoning about.

The cheapest thing in this book, and the one worth doing first

Put one correlation identifier — a trace ID or a request ID — on every log line, every error event, and the response header. It needs no tracing backend and takes an afternoon. During an incident it turns three disconnected searches into one string that finds the trace, the logs and the exception for that specific request, which is the difference between investigating a class of failures and investigating the one a user is complaining about.

A word on what alerting is for

An alert is a request to wake a human, and that framing decides the rest. Alert on symptoms — requests failing, requests slow, traffic vanishing, saturation with a trend — never on causes like CPU or memory, which are usually harmless and change with every architecture. Then review every page the next morning and ask whether a human should have been woken. An alerting configuration decays exactly like code, and one that is never pruned converges on a state where everything pages and nobody reads any of it.

Chapter Zero · Part I

The Three Pillars

Logs, metrics and traces are not three views of the same data — they are three different trades between detail and cost, and each answers a question the others cannot. Choosing wrongly is expensive in a way that only becomes visible on the invoice, so this chapter starts by measuring what makes a metric cheap and what destroys that in one line of code.

By the end of this chapter you will be able to
  • Say what each pillar answers, and what it costs
  • Explain cardinality, and why it decides your bill
  • Recognise the label that must never be a label
  • Choose the right pillar for a given question
  • Run the lab used for the rest of this book

0.1 Three questions, three costs

MetricsLogsTraces
AnswersIs something wrong?What exactly happened?Where did the time go?
ShapeNumbers over timeEvents, one per lineA tree of spans per request
Cost grows withLabel combinationsVolume × retentionRequests × sample rate
Cost per request~zeroLinearLinear
RetentionMonths, cheaplyDays, expensivelyDays, sampled
Good atAlerting, trends, SLOsForensics on one requestLatency across services
Bad atAnything per-userAggregationBeing complete

Table 0.1 Read the fourth row and the division of labour falls out. A metric costs nothing per request — a counter is incremented in memory and scraped every fifteen seconds regardless of whether you served ten requests or ten million. A log line costs money per request, forever. So metrics tell you something is wrong and logs tell you what, and the mistake that follows is trying to make metrics answer the second question.

0.2 What makes a metric cheap, and the line that ruins it

The rule, and the three labels that break it

A label value must come from a set you can write down. Routes, methods, status classes, regions, versions — all bounded. User ID, request ID, session ID, email address, full URL path, error message — all unbounded, all fatal. The last two are the ones people do not see coming: an error message often contains an ID or a timestamp, and a raw URL path contains whatever the client sent. Normalise the path to a route template (/u/:user, not /u/user_417) before it becomes a label.

And when you genuinely need per-user data, that is what logs are for

The question “what happened to user 417’s checkout” is a logs question, and logs are built for exactly this: high cardinality, short retention, queried by filter rather than aggregated. Put the user ID in the log line, keep it out of the metric, and the two systems each do what they are good at. Chapter 1 is about making those log lines queryable.

0.3 What a trace adds that neither has

You knowFromYou still do not know
p95 latency is 1.2 sMetricsWhich part is slow
This request took 1.2 sLogsWhat it was waiting on
It spent 900 ms in the payment callTraces—
The payment service is fineIts own metricsWhy your call to it was slow

Table 0.2 The last row is the case traces exist for. Two services can each report healthy metrics while the path between them is slow — a connection pool exhausted on your side, a retry loop, a DNS lookup, a queue. Metrics are per-service and traces are per-request, following it across every hop, which is the only way to see time spent between services rather than inside one.

The thing that makes a trace a trace

Context propagation. Every service passes a traceparent header onward, so the spans emitted by five different services can be assembled into one tree afterwards. If any service in the chain drops that header, the trace breaks there — you get two unrelated traces and no visible link, which is the single most common reason traces are useless in practice. Chapter 4 covers this properly; the important thing to know now is that tracing is a whole-system commitment in a way that metrics and logs are not.

0.4 Which pillar answers which question

QuestionReach for
Are we serving errors right now?Metrics
Is it worse than an hour ago?Metrics
Are we meeting the SLO this month?Metrics
What happened to order ord_9f3a?Logs
Why did this request take 4 seconds?Traces
Which dependency got slower?Traces, then its metrics
How many users hit the bug?Logs, aggregated after the fact
Should someone be woken up?Metrics only — Chapter 7

Table 0.3 The last row is a rule worth holding to. Alerts fire on metrics because metrics are cheap to evaluate continuously and are the same shape every time; alerting on log content means running a query over a large corpus every minute and getting paged when a log format changes. Detect with metrics, diagnose with logs and traces.

And there is a fourth thing, which is not a pillar

Events — deploys, config changes, feature-flag flips, scaling actions. They are neither a measurement nor a request, and they are the single highest-value annotation you can put on a dashboard, because the first question about any graph that changed shape is “what did we do at that moment?”. Chapter 9 wires deploys into the pipeline; for now, note that most incidents are caused by a change, and the change is usually yours.

Checkpoint

Why is a metric with a user_id label a serious problem?

Because a time series is created per distinct label combination and never expires, so the count grows with your user base — 500 users produced 500 series in Listing 0.2, and the scrape payload grows with it, forever. Metrics are cheap precisely because their label values come from a set you can enumerate. Per-user questions belong in logs.

Which labels look safe and are not?

Raw URL paths (they contain whatever the client sent — normalise to a route template), error messages (they usually embed an ID or timestamp), and anything derived from user input. Request IDs, session IDs and email addresses are obviously unbounded; those three are the ones that get through review.

Two services both report healthy metrics but the request is slow. What do you need?

A trace. Metrics are per-service and cannot show time spent between services — a slow DNS lookup, an exhausted connection pool, a retry loop. Tracing requires every hop to propagate the context header; if one service drops it, the trace breaks there and you get two unrelated fragments.

Why alert on metrics rather than on log content?

Because metrics are cheap to evaluate continuously and have a stable shape, while alerting on logs means running a query over a large corpus repeatedly and being paged when someone changes a log format. Detect with metrics; diagnose with logs and traces.

Chapter One · Part I

Structured Logging

A log line exists to be found later, by someone who does not know what they are looking for. That is the whole design brief, and it rules out the format almost everyone starts with — a sentence with values interpolated into it, which is readable by a human reading one line and useless to anything trying to read a million.

By the end of this chapter you will be able to
  • Write logs a machine can query
  • Choose levels that mean something operationally
  • Correlate every line belonging to one request
  • Keep secrets out of your log store
  • Control what logging costs

1.1 The same event, two ways

Put in a fieldNot in the message
Identifiers — order, user, request, traceSo you can filter by them
Amounts, counts, durationsSo you can sum and sort them
Error type and codeSo you can group by them
Outcome — status, resultSo you can count them
Service, version, environmentSo you can narrow to one deploy
The message itselfA short, constant string

Table 1.1 The last row is the one that gets violated first. Keep msg constant — "order failed", never "order ord_9f3a failed" — because a constant message is a group key: it lets you count occurrences, alert on a rate, and see that this happened 4,000 times rather than 4,000 distinct once-only messages. Everything variable belongs in a field. This is the same cardinality argument as Chapter 0, applied to a different store.

1.2 Levels that mean something

LevelMeansWho reads it
fatalThe process is about to stopWhoever is paged
errorA request failed and a human may need to actOn-call, next morning
warnDegraded, handled, worth noticingWeekly review
infoA business event happenedAuditing, support
debugInternal detailYou, during an incident
traceEverythingNobody, in production

Table 1.2 The useful discipline is the second column: a level is a statement about who should care, not about how interesting you found it while writing the code. The common failure is error for things nobody will ever act on — a validation failure on user input is info at most, and logging it as an error trains everyone to ignore errors.

Which is an argument for fewer, better log lines

The instinct during an incident is to add logging everywhere, and the instinct afterwards is to leave it in. Both are understandable and the result is a log store where the signal is 0.1% of the volume and the bill is real. A useful test: if this line fired ten thousand times, would anyone read even one of them? If not, it is a metric (a counter) or it is nothing.

1.3 Correlating one request

And accept the ID from upstream, do not always mint one

If a caller sends x-request-id, use it and pass it onward; only generate one when there is none. That single rule is what turns per-service logs into a system-wide trail: the same identifier appears in the load balancer, in your service, in the service you called, and in the response header the user can quote in a support ticket. Chapter 4 does the same thing with a formal trace context; a request ID is the poor version that works everywhere and costs nothing.

1.4 Keeping secrets out of the log store

A log store is a copy of your data with weaker access controls

That is the honest way to think about it. Logs are typically readable by everyone in engineering, retained for weeks, shipped to a third party, and indexed for full-text search — every one of which is a weaker control than the database the data came from. So anything that would require a permission check to read in the application should not be in a log line at all. Redact at the logger, not at the shipper: once it has been written to stdout it has already left your control.

Never logEvenLog instead
Card numbersThe first six digitslast4, brand
CVC / CVVEver, anywhereNothing — it may not be stored at all
PasswordsHashedNothing
Session tokens, API keysTruncatedA key id
Full request bodies“Just for debugging”Named fields you chose
Personal dataBecause it is convenientAn identifier you can join on

Table 1.3 Row two is a legal requirement rather than a preference: the card security code must not be stored after authorisation under PCI DSS, and a log line is storage. Row five is the one that quietly does the most damage — log.info({ body: req.body }) logs whatever the client sent, which over time is everything.

1.5 What it costs, and the shape that keeps it down

DecisionEffect
JSON to stdout, shipped by the platformSimplest thing that works
One line per request, not per stepVolume falls by an order of magnitude
debug off in productionMost of the volume, gone
Sample high-volume success pathsKeep all errors, 1% of successes
Short retention, with archiveHot search is expensive; cold storage is not
Counters instead of repeated linesChapter 0’s division of labour

Table 1.4 The second row is the biggest single lever. A request that logs at entry, at each of four steps, and at exit produces six lines where one would do — and that one, written at the end with the outcome and the duration in fields, is more useful because it can be counted and aggregated. Log the transaction, not the trajectory.

Write to stdout and stop there

Not to a file you rotate, not to a network socket, not to a third-party SDK inside the process. The container platform captures stdout, and every one of the alternatives introduces a way for logging to break the application it is meant to observe — a full disk, a blocked socket, an SDK that buffers unboundedly when its endpoint is down. A logger that can take down the service during an incident is worse than no logger, because incidents are exactly when it will happen.

Checkpoint

Why keep msg constant and put the identifiers in fields?

Because a constant message is a group key: it lets you count occurrences, alert on a rate, and see “this happened 4,000 times” instead of 4,000 unique messages. Interpolating an ID into the message makes every line distinct — the same cardinality mistake as Chapter 0, in a different store — and forces a regex to get the value back out.

Debug logging is disabled. Is log.debug({...heavy}, "x") free?

No. The line is not written, but the arguments are still evaluated — the object is allocated and any string building runs. Listing 1.2 measures it. In a hot path, guard with isLevelEnabled; better still, ask whether the line would ever be read and make it a counter instead.

Where should redaction happen, and why there?

In the logger, before serialisation. Redacting at the shipper is too late — the secret has already been written to stdout and left your control. Treat the log store as a copy of your data with weaker access controls: broad read access, long retention, third-party indexing.

Why log one line per request rather than one per step?

Volume, and usefulness. Six lines per request cost six times as much and are harder to work with than one line written at the end carrying the outcome, the duration and the identifiers in fields — which can also be counted and aggregated. Log the transaction, not the trajectory.

Chapter Two · Part I

Error Tracking

An error tracker is not a log store with a nicer interface. It is a database of problems rather than of events — it groups thousands of occurrences into one thing that can be assigned, resolved, and regressed. Everything useful about it follows from that grouping, and everything frustrating about it follows from the grouping being wrong.

By the end of this chapter you will be able to
  • Say what an error tracker does that logs cannot
  • Read what an error event actually contains
  • Control how errors are grouped
  • Detect a regression against a release
  • Keep personal data out of a third-party service

2.1 What it does that a log line cannot

LogsError tracker
UnitAn eventA problem, with many occurrences
Duplicate errorsA million linesOne issue, count = 1,000,000
StateNoneUnresolved / resolved / ignored
RegressionYou would have to noticeDetected — resolved, then seen again
Stack traceA stringFrames, with source context and variables
NotifiesNoOn first occurrence, and on regression
RetentionWeeks of everythingA long time, deduplicated

Table 2.1 Rows two and four are the whole product. A log store answers “show me the errors” and returns a million lines that are the same error; a tracker answers “what is broken” and returns a list of forty problems with counts. And the fourth row is the one that pays for itself — an issue you marked resolved that appears again in a later release is a regression, and being told about it automatically is something no amount of log searching will do for you.

2.2 What is actually in an event

flush() is not optional in a serverless function

The SDK batches and sends asynchronously, which is correct for a long-running server and fatal in a Lambda or an edge function: the runtime freezes or destroys the process the moment your handler returns, and the queued event is lost. await Sentry.flush(2000) before returning is the fix, and “errors only appear sometimes” in a serverless deployment is almost always this.

2.3 Grouping, which is the whole product

How two occurrences become one issue

By default the tracker computes a fingerprint from the exception type, the message, and the top in-app stack frames. Two occurrences with the same fingerprint are the same issue. This works well until the message contains something variable — "order ord_9f3a2c1d failed" — at which point every occurrence is a new issue, the list becomes thousands of items long, counts are all 1, and notifications fire constantly. It is Chapter 1’s constant-message rule again, and here it decides whether the product works at all.

Grouping problemCauseFix
Thousands of issues, count 1 eachVariable text in the messageConstant message; §2.3
Everything in one giant issueA shared wrapper at the top of every stackCustom fingerprint
One issue splits after a deployLine numbers movedUpload source maps; group on function names
Framework noise groups your bugs togetherNo in_app markingConfigure which paths are yours
Same bug, two issuesTwo call pathsMerge them, or set an explicit fingerprint

Table 2.2 The second row is the mirror image of the first and just as common: wrap every error in new AppError(...) thrown from one central place, and every distinct bug in the system shares a top frame and collapses into one unusable issue. When the default grouping is wrong in either direction, set fingerprint explicitly — it accepts an array of strings and "{{ default }}" to extend rather than replace.

2.4 Releases, and how a regression is detected

Set thisAnd you get
releaseFirst-seen and last-seen release per issue
release + resolved stateRegression detection
release + source mapsReadable stacks from minified code
environmentStaging noise separated from production
A deploy notification“Issues introduced in this deploy”
NothingA list of errors with no idea when they started

Table 2.3 The mechanism is simple and worth stating precisely: mark an issue resolved, and if an occurrence arrives tagged with a release later than the one it was resolved in, it is reopened as a regression and announced. That is only possible because the release is on every event — which is why a deployment that does not set it loses the single most valuable feature of the tool.

Use the commit SHA, and set it in one place

release: "checkout@1.4.0" is fine for a versioned product; for a service deployed continuously, the commit SHA is better, because it is unambiguous and maps to a diff. Set it from the same variable your build already has — GITHUB_SHA in the CI of Volume 18 — and pass it to both the SDK and the source-map upload, since they must agree exactly or the maps will not be found.

2.5 What not to send

You are shipping your exceptions to a third party

Which is fine, and worth being deliberate about. An exception carries a message, a stack, local context the SDK may have collected, request headers, and whatever you attached. Several of those routinely contain personal data or credentials: an Authorization header, a request body echoed into an error message, an email address used as a user identifier, a database error quoting the row that failed. The beforeSend hook is the one place you can guarantee it is removed, because it runs on every event including the ones the SDK captured automatically.

ControlEffect
sendDefaultPii: falseNo IP addresses, cookies or headers by default
beforeSendThe final, guaranteed scrub
ignoreErrorsDrop known noise (browser extensions, bots)
sampleRateSend a fraction of errors — quota control
denyUrls / allowUrlsBrowser SDK: ignore third-party scripts
Server-side data scrubbingA backstop, applied after receipt

Table 2.4 The last row is a backstop rather than a control: it runs on the vendor’s side, after the data has crossed the network and been received. If something must never leave your infrastructure, it has to be removed in beforeSend. And note the fourth row applies to errors, not to how many occurrences of one issue are counted — sampling errors means your counts become estimates, which is usually an acceptable trade and should be a conscious one.

Checkpoint

Why does an error tracker exist when you already have logs?

Because it stores problems rather than events: a million identical failures become one issue with a count, which can be assigned, resolved, and — the valuable part — automatically reopened as a regression when it recurs in a later release. Logs can show you the errors; they cannot tell you that there are forty distinct ones and that number seven came back.

Your tracker shows 4,000 issues each with a count of 1. What is wrong?

Variable text in the exception message, so every occurrence fingerprints differently. Use a constant message and put the order ID and gateway text in extra, with low-cardinality values in tags. The opposite failure — everything collapsing into one issue — comes from a shared wrapper at the top of every stack, and is fixed with an explicit fingerprint.

Errors from your Lambda appear only sometimes. Why?

The SDK sends asynchronously and the runtime freezes the process when the handler returns, discarding the queued event. await Sentry.flush(2000) before returning. The same applies to any short-lived process — a CLI, a cron job, a worker that exits.

Where must scrubbing happen, and what does the SDK attach that you did not ask for?

In beforeSend, because that is the last point inside your process; server-side scrubbing runs after the data has already been transmitted. The SDK attaches server_name — the machine hostname — by default, and console breadcrumbs capture whatever your code logged, which can reintroduce secrets you carefully redacted.

Chapter Three · Part II

Capturing Context and Breadcrumbs

A stack trace tells you where a program stopped. It almost never tells you why, because the cause is usually something that happened earlier and elsewhere — a value that was already wrong, a call that already failed, a branch nobody expected to be taken. Context is the machinery for reconstructing that, and it has to be collected before you know you will need it.

By the end of this chapter you will be able to
  • Choose between tags, extra, context and breadcrumbs
  • Leave a trail that explains a failure
  • Attach context without threading it through every function
  • Keep breadcrumbs from becoming a leak
  • Decide what is worth capturing

3.1 Four places to put context, and they are not interchangeable

IsSearchableCardinalityUse for
tagsKey/value stringsYes, indexedMust be lowGateway, region, plan, feature flag
extraArbitrary JSONNoAnyOrder ID, request payload, computed state
contextsStructured blocksPartlyAnyDevice, OS, runtime, your own domain block
userWhoYes—An id; see §3.4
breadcrumbsA time-ordered trailNo—What happened before the failure

Table 3.1 The mistake that costs the most is putting a high-cardinality value in tags — an order ID, a URL, a message. Tags are indexed for filtering, so unbounded values bloat the index and, on most plans, are silently dropped past a limit. The rule is Chapter 0’s again: if you cannot write down the set of possible values, it is not a tag.

3.2 The trail that explains the failure

Breadcrumbs are a ring buffer, and the default is not large

Typically the last hundred are kept, oldest discarded. So a request that emits a breadcrumb per database query will have flushed out the interesting one before it fails, and you will be left with a hundred identical SELECT lines and nothing else. Breadcrumbs are curated, not automatic — the SDK will happily add one for every console call and every fetch, and the useful configuration is usually to turn those integrations down rather than up.

3.3 Attaching context without threading it everywhere

Custom contexts are underused and cost nothing

setContext("order", {...}) creates a labelled block in the issue rather than a flat blob of extra. When someone opens the issue at three in the morning, an Order panel with the amount, currency and state is worth more than the same fields scattered among forty other keys. Name the blocks after the domain objects your team already talks about.

3.4 Context is data leaving your building

TemptingSend instead
setUser({ email })setUser({ id }) — join in your own database
The full request bodyThe three fields that matter
The database row that failedIts primary key
The whole config objectThe two flags relevant to this path
Console breadcrumbsCurated breadcrumbs you wrote
Everything, “in case we need it”What you would actually read

Table 3.2 The last row is the honest test and it is worth applying literally: open a recent issue and ask which of the attached fields anybody looked at. On most projects the answer is three or four, and the rest is a liability — data in a third-party system, indexed, readable by everyone with a login, retained for months.

And the identifiers you send should be joinable

The point of user.id rather than user.email is not only privacy — it is that an internal ID is stable, unique, and can be looked up in your own database by someone with the right permissions. An email address is a copy of personal data in a place with weaker controls, and it is also a worse key, because people change them. The same argument applies to order references, tenant names, and anything else: send the key, keep the data.

Checkpoint

What must never go in tags?

Anything whose set of values you cannot write down — order IDs, URLs, messages, timestamps. Tags are indexed for filtering, so unbounded values bloat the index and are commonly dropped past a limit. Those values belong in extra or a named context block, which are attached to the occurrence but not indexed.

An exception says “gateway timeout” and nothing else. What would have made it diagnosable?

Breadcrumbs — particularly for outbound calls. “POST /api/pay → 502, attempt 2, 1,840 ms” turns an unhelpful message into a specific question about a specific dependency. Feature-flag breadcrumbs are the other high-value category, because they explain why a failure affects only some users.

Why is setting tags on the global scope inside a request handler a bug?

Concurrency. Requests share the global scope, so one request’s user ID and tags end up attached to another request’s exception — wrong data, and a privacy problem. Use an isolation scope per request, and withScope for a single capture.

Why send a user ID rather than an email address?

Privacy and correctness. The ID is stable, unique and looked up in your own database under your own access controls; an email is a copy of personal data in a third-party system with broader read access and longer retention, and it changes. Send keys, keep the data.

Chapter Four · Part II

Performance Monitoring and Tracing

Metrics can tell you that the 95th percentile is 1.2 seconds. They cannot tell you which 1.2 seconds — which call, in which service, waiting on what. A trace follows one request across every hop and records where the time went, and the whole technique rests on one fragile thing: every service passing a header onward.

By the end of this chapter you will be able to
  • Read a trace as a tree of spans
  • Instrument the boundaries that matter
  • Propagate trace context across services
  • Choose a sampling strategy that keeps the interesting traces
  • Connect a trace to the logs and errors from the same request

Table 4.1 The trace_id is the field to care about most, and not only within tracing — putting it on every log line and every error event is what lets you move between the three pillars for one specific request instead of guessing. That is §4.5.

4.2 What to instrument, and what not to

Table 4.2 Note what is absent: individual functions. A span per function call produces traces with thousands of spans that are expensive to store, slow to render, and no easier to read than a profiler’s output. Instrument boundaries — the places where your process waits on something else — because that is where wall-clock time goes in almost every service that is not doing heavy computation.

Auto-instrumentation is the right starting point, and not the end

The OpenTelemetry auto-instrumentations wrap HTTP, common database drivers and popular frameworks, and they will give you a useful trace on day one with no code changes. What they cannot know is your domain: that these three queries are “load the cart”, that this HTTP call is “authorize payment”, that this span should carry the order ID. Start with auto-instrumentation, then add a handful of named spans and attributes at the points your team actually talks about.

4.3 Context propagation, and the one way it breaks

And it breaks in exactly one way: something in the middle drops the header

A proxy that strips unknown headers. A queue whose message format has no room for metadata. An HTTP client constructed without the instrumentation. A serverless platform that rebuilds the request. When that happens you do not get an error — you get two traces, each internally consistent, with no visible relationship, and the gap where the time went is invisible. The symptom is a trace that ends abruptly at a service boundary, and the fix is always to find where the header stopped being forwarded.

BoundaryCarry the context in

A cron job and an inbound webhook have no caller to inherit from, and trying to link them to an earlier trace produces something misleading. Give them a fresh trace and, if a causal link exists, record it as a span link rather than a parent.

4.4 Sampling: keeping the traces worth keeping

StrategyDecidesKeeps the interesting ones?
Head sampling, fixed rateAt the root, before anything happensNo — it is a coin flip

Table 4.4 Head sampling at 1% is what most people start with and it has an obvious flaw: the decision is made before the request has done anything, so 99% of your errors and 99% of your slow requests are discarded along with everything else. Tail sampling buffers the whole trace and decides afterwards — keep every trace with an error or above a latency threshold, plus a small percentage of the rest — which is what makes a sampled system still useful during an incident. It costs a collector that can hold traces in flight.

And the sampling decision has to be consistent across services

The traceparent flags carry it, which is why it is in the header: if service A decides to sample a trace and service B independently decides not to, you get a trace with holes in it — which is worse than either keeping or dropping it whole. Downstream services must respect the incoming decision rather than making their own, and a service that ignores the flag is a common cause of mysteriously incomplete traces.

4.5 Joining the three pillars

If you do only one thing from this chapter

Do that. Full distributed tracing is a real investment — a collector, a backend, instrumentation in every service, sampling decisions, cost. Putting a single correlation ID on logs, errors and responses is an afternoon, works with no backend at all, and recovers most of the practical value during an incident. Chapter 8 is about incidents, and it assumes you have this.

Checkpoint

Metrics say p95 is 1.2 s. What can a trace tell you that they cannot?

Which part of the request that time was spent in — and in particular, time spent between services, which no per-service metric can see. Listing 4.2 shows 180 ms of a 194.5 ms request inside one call to a payment provider whose own metrics may look perfectly healthy.

Your trace ends abruptly at a service boundary. What happened?

Something dropped the traceparent header — a proxy stripping unknown headers, an HTTP client built without instrumentation, a queue with nowhere to put metadata. There is no error; you simply get two unrelated traces, and the gap you were looking for is invisible.

Why is 1% head sampling a poor default?

Because the decision is made at the root, before the request has done anything, so it discards 99% of errors and 99% of slow requests along with everything else. Tail sampling decides after the trace completes — keep everything that errored or was slow, plus a small share of the rest — which is what keeps a sampled system useful during an incident.

What is the cheapest thing in this chapter with the highest return?

Putting one correlation ID on every log line, every error event, and the response header. It needs no tracing backend, takes an afternoon, and turns an incident from three disconnected searches into one string that finds everything about a specific request.

Chapter Five · Part III

Health Checks and Uptime

A health check is a contract with an orchestrator: answer this, and I will decide whether to send you traffic or restart you. Almost every outage caused by health checking comes from the same mistake — using one endpoint to answer two different questions, so a slow dependency causes the orchestrator to kill every healthy instance you have.

By the end of this chapter you will be able to
  • Separate liveness from readiness, and say why
  • Decide what a health check should and should not test
  • Avoid the check that turns a degradation into an outage
  • Drain connections during a deploy
  • Measure uptime in a way that means something

5.1 Two questions, two endpoints

LivenessReadiness
AsksIs this process broken beyond recovery?Can it serve a request right now?
Failure meansRestart meStop sending traffic
During warm-upPassFail
Dependency is downPass — see §5.2Arguably fail
During shutdownPassFail first — §5.3
Should checkAlmost nothingA little more

Table 5.1 Row four is where the reasoning gets subtle and the consequences are large. If the database is down, restarting your process does not help — so liveness must pass. Whether readiness should fail is a real judgement call: failing it removes the instance from the load balancer, which is right if another instance can serve, and catastrophic if the dependency is shared and every instance fails at once, because then you have zero instances instead of some that could at least serve cached responses.

5.2 The check that turns a degradation into an outage

CheckLivenessReadiness
The process responds at allYesYes
Event loop is not blockedYesYes
Warm-up finishedNoYes
Database reachableNoMaybe — §5.1
Cache reachableNoNo — degrade instead

Table 5.2 The sixth row is absolute. Putting somebody else’s availability into your health check means their outage restarts your fleet, and you have handed a stranger the ability to take you down. If a dependency is genuinely required, fail the individual requests that need it with a clear error — that is a degradation your users can understand and your dashboards can measure, rather than a restart loop.

A liveness check should be nearly impossible to fail

Its only job is to detect a process that is alive but permanently broken — a deadlock, an exhausted event loop, a leaked-memory death spiral. That is rare. If your liveness check fails more often than genuinely wedged processes occur, it is a source of outages rather than a defence against them, and the right response is usually to make it check less.

5.3 Shutting down without dropping requests

And the orchestrator’s patience is finite

Kubernetes sends SIGTERM, waits terminationGracePeriodSeconds (30 by default), then sends SIGKILL. Every number in Listing 5.3 must fit inside that window with room to spare, including the longest request you are willing to wait for. If your slowest request takes 60 seconds and your grace period is 30, you will drop it on every single deploy — and the fix is to raise the grace period, not to shorten the wait.

5.4 Measuring uptime honestly

Table 5.3 The gap between rows one and three is where “99.99% uptime” claims live. A service can answer health checks perfectly while returning 500 to every real request — the process is up, the product is down. Measure the ratio of good requests to total requests, from the metrics of Chapter 6, and treat the ping as a liveness signal rather than a promise to users.

An SLO is a decision, not a measurement

“99.9% of checkout requests succeed within 500 ms, measured over 30 days” is a sentence somebody has to choose, and the useful part is its arithmetic consequence: 99.9% over 30 days is 43 minutes of failure allowed. That is the error budget, it is a real quantity, and it converts arguments about whether to ship into arithmetic about how much budget is left. Chapter 7 alerts on the rate at which it is being consumed — which is a far better trigger than any absolute threshold.

Checkpoint

Why are liveness and readiness separate endpoints?

Because they answer different questions with opposite consequences: failing liveness means “restart me”, failing readiness means “stop sending traffic”. During warm-up a process must pass one and fail the other, as Listing 5.1 shows — 200 and 503 at the same instant. One endpoint cannot express both.

Why must a liveness check not test the database?

Because restarting your process does not fix a database, and a shared dependency fails for every instance at once — so the orchestrator restarts your entire fleet simultaneously, they all start cold, and they all hammer the recovering dependency. A brief degradation becomes a long outage, caused by the mechanism meant to protect you.

Your deploys drop a few requests every time. What step is missing?

Failing readiness and then waiting before closing the server. Load balancers discover unreadiness by polling every few seconds, so a process that stops accepting connections the moment it gets SIGTERM is still receiving traffic. Fail readiness, wait longer than the polling interval, then close and drain — all within the orchestrator’s grace period.

Your monitor says 99.99% uptime and users are complaining. How?

The monitor measures whether a port answers or a health endpoint returns 200 — both of which your own code controls. A service can pass every check while returning 500 to real requests. Measure good requests over total requests, and define an SLO whose error budget converts availability from an adjective into a number of minutes.

Chapter Six · Part III

Metrics and Dashboards

Four metric types, one query language, and a great many dashboards nobody looks at. This chapter is about picking the right instrument for a measurement, writing queries that mean what you think, and building a dashboard that answers a question rather than displaying everything that was easy to graph.

By the end of this chapter you will be able to
  • Choose between counter, gauge, histogram and summary
  • Write queries that survive restarts and gaps
  • Compute a percentile correctly, and know what it costs
  • Use recording rules for the expensive parts
  • Build a dashboard someone will actually use

6.1 Four instruments

TypeRepresentsQuery it withExample
CounterA total that only goes uprate(), increase()Requests, errors, bytes
GaugeA value that moves either wayDirectly, avg, maxIn-flight, queue depth, temperature
HistogramA distribution, in bucketshistogram_quantile()Latency, payload size
SummaryQuantiles computed in the processDirectlyRarely the right answer

Table 6.1 The first row carries a rule that is easy to violate: never graph a counter directly. A counter is a monotonically increasing total, so its graph is a line going up and to the right forever, which tells you nothing. You always want its rate. And the last row is a genuine recommendation — a summary computes quantiles inside each process, and quantiles from separate processes cannot be averaged, so a summary across three replicas cannot produce a fleet-wide p95. A histogram can.

Why rate() and not subtraction

rate() handles two things you would otherwise have to handle yourself. Counter resets: when a process restarts its counter goes back to zero, and rate() detects the drop and treats it as a reset rather than as a large negative number. Ragged scrapes: samples do not arrive exactly on the interval, and rate() extrapolates over the window rather than assuming they did. Any hand-rolled “current minus previous” gets both wrong, and gets them wrong exactly when a deploy is happening.

The ratio of two rates is the ratio right now, which is what anyone asking the question means.

And the answer is only as precise as your buckets

histogram_quantile interpolates within a bucket, assuming values are spread evenly across it. If your highest finite bucket is 1 and the real p95 is 4 seconds, the function cannot tell you that — every slow request lands in +Inf and the estimate is pinned near the top bucket. Choose buckets around the latencies you care about and the thresholds you alert on, and expect to change them once you have seen real traffic.

Show percentiles together, never an average

An average latency is a number that describes nobody: with a fast common path and a slow tail it sits between them, and it moves in the wrong direction when the tail gets worse and traffic simultaneously shifts to the fast path. Graph p50, p95 and p99 on one axis and the shape tells you what is happening — p50 flat with p99 rising is a tail problem affecting a subset; all three rising together is a systemic slowdown. Those need completely different investigations.

And the dashboard nobody uses is the one with forty panels

A dashboard is a question, not an inventory. “Is checkout healthy?” deserves one screen with six panels that fit without scrolling, all on the same time range. Everything else belongs on a second dashboard that is opened deliberately. During an incident, the difference between six panels and forty is whether anyone can see the anomaly at all.

Checkpoint

Why should a counter never be graphed directly?

Because it only increases — the graph is a line rising forever and carries no information. You want rate(), which additionally handles counter resets on restart and irregular scrape intervals, both of which a hand-rolled subtraction gets wrong precisely during a deploy.

What is wrong with errors_total / requests_total as an error ratio?

It divides two cumulative totals, giving the ratio since process start — a number that barely moves and that a single bad hour long ago keeps depressed indefinitely. Divide the two rates instead, which gives the ratio now.

Why can a summary not give you a fleet-wide p95?

Because it computes quantiles inside each process, and quantiles cannot be averaged across processes — the average of three p95s is not the p95 of the whole. Histograms store bucket counts, which can be summed, so histogram_quantile over sum by (le) gives a genuine fleet-wide percentile.

Why graph p50, p95 and p99 rather than an average?

Because an average describes nobody and hides the shape. Together the three tell you which problem you have: p50 flat while p99 rises is a tail affecting a subset of requests; all three rising is a systemic slowdown. They call for different investigations, and the average points at neither.

Chapter Seven · Part IV

Alerting and On-Call

An alert is a request to wake a human. That framing decides everything else: what deserves one, how long it should wait before firing, and what it must say to be worth the interruption. Most alerting systems fail not by missing incidents but by producing so many alerts that the humans stop reading them.

By the end of this chapter you will be able to
  • Alert on symptoms rather than causes
  • Use for to eliminate flapping
  • Read the states an alert passes through
  • Burn error budget as the alerting signal
  • Write an alert someone can act on at 3 a.m.

7.1 Alert on what users feel

CPU above 80%Requests failingHigh CPU may be fine

Table 7.1 The distinction is symptoms against causes. Causes are numerous, mostly harmless, and change every time the architecture changes; symptoms are few, always matter, and stay meaningful for years. A service can run at 95% CPU and serve every request perfectly — paging for that trains people to close alerts without reading them, which is the failure that matters, because it also applies to the real one.

The four symptoms almost every service should alert on

Errors — the failure ratio is above what you promised. Latency — a percentile users feel is above what you promised. Traffic disappeared — a sudden drop to zero usually means something upstream is broken and is otherwise invisible, since no errors are being generated. Saturation with a trend — not “disk is 70% full” but “disk will be full before anyone is awake”, which is what predict_linear is for. Everything else is a dashboard, not a page.

It is also how you tune — an alert that sits in pending constantly and never fires has a threshold set slightly too low.

7.3 Burn rate: the alert that scales with severity

A fixed threshold cannot express “how bad is this?”

An error ratio above 2% might be a blip or the end of the world, and one threshold cannot tell them apart. The better signal is how fast you are consuming the error budget from Chapter 5. If the SLO allows 0.1% failures over 30 days, then failing at 1% is burning budget ten times faster than sustainable — a burn rate of 10. At that rate the entire month’s budget is gone in three days.

Table 7.3 The value of this framing is that it removes the argument. “Is 3% errors bad?” has no answer without context; “we will exhaust the quarter’s budget by Thursday” has an obvious one. It also gives a principled way to say no to an alert: if a condition cannot meaningfully consume the budget, it does not deserve a page.

A runbook does not need to be long — what this alert means, the three things to check, how to mitigate, who to escalate to — and it needs to have been written on a calm afternoon.

Every page should be reviewed the next day

One question: should a human have been woken for this? If yes, was the runbook enough? If no, fix the alert — raise the threshold, lengthen for, downgrade it to a ticket, or delete it. Alerting configuration decays exactly like code, and a rotation without this review converges on a state where everything pages and nobody reads any of it. A useful health metric for the rotation itself is the ratio of pages that led to action; below about half, the system is training people to ignore it.

Checkpoint

Why not alert on CPU above 80%?

Because it is a cause, not a symptom, and a service can run hot while serving every request perfectly. Causes are numerous and mostly harmless; symptoms — errors, latency, traffic vanishing, saturation with a trend — are few and always matter. Paging for causes trains people to dismiss alerts without reading them.

Your alert fires and resolves repeatedly. What is missing?

A for clause, or a long enough one. Without it an alert fires the first evaluation the expression is true, so one slow scrape or a deploy pages somebody. With for, the condition must hold continuously and the alert waits in pending — visible to you, silent to the pager.

Why alert on burn rate rather than a fixed error threshold?

Because a fixed threshold cannot express severity. Burn rate compares the current failure rate to the rate the SLO permits, so 14.4× means “this month’s budget is gone in two days” — which decides on its own whether it is a page or a ticket. Pair a long window with a short one so the alert both confirms the problem is real and resolves when it stops.

What single addition most improves an on-call rotation?

A runbook link on every alert, written on a calm day: what it means, three things to check, how to mitigate, who to escalate to. The person paged at 3 a.m. is often not the person who wrote the service. Second is reviewing every page the next morning and deleting or downgrading the ones that did not deserve a human.

Chapter Eight · Part IV

Debugging Production Incidents

An incident is a debugging session under time pressure with an audience, on a system you cannot pause and cannot reproduce. What makes it survivable is having decided, in advance, what you will look at and in what order — because the one thing guaranteed at 3 a.m. is that you will not invent a good method on the spot.

By the end of this chapter you will be able to
  • Work an incident in a fixed order
  • Narrow from symptom to component with the tools you have
  • Recognise the failure patterns that recur
  • Mitigate before you diagnose
  • Write up an incident so it is worth having had

8.1 The order

And step 4 usually ends it

Most incidents are caused by a change, and most changes are recent and yours. Before reasoning about anything subtle, look at what was deployed, which feature flags moved, what config was edited, whether a migration ran, and whether a dependency you do not control deployed something. This is why Chapter 9 puts deploy markers on dashboards: the answer to “what changed at 14:32” should be visible on the same graph as the symptom rather than requiring a separate investigation.

8.2 Narrowing, with the three pillars

Table 8.1 The order is deliberate: metrics narrow, traces localise, logs explain. Starting in the logs is the most common mistake — it means reading individual events looking for a pattern that a single aggregate query would have shown in a second. Narrow first, then read.

Widen the time range before concluding anything

A graph over fifteen minutes makes everything look like an emergency, because you cannot see what normal is. Widen to a week: the spike may be a daily pattern, the “sudden” rise may have been climbing for days, and the deploy that looks responsible may have been fine for six hours. Comparing to the same time last week is the fastest way to tell a novel problem from a familiar one.

8.3 Patterns that recur

ShapeUsually
Errors start exactly at a deployThat deploy — roll back
Latency rises steadily for hoursA leak, or a table growing without an index

Everything slow, one dependency slowerThat dependency, or the pool to it

Table 8.2 Row five is the one people miss for longest, because every dashboard looks healthy — you cannot fail requests that never arrive. It is why “traffic dropped to zero” belongs in the four alerts of Chapter 7. Row six is the one that makes an incident recur: the fix that “worked” was a restart, which freed the resource, and it will fill again.

Correlation with a deploy is strong evidence and not proof

Deploys are frequent, so something is nearly always deployed near the start of an incident. Before committing, check whether the metric moved at the deploy or merely after it, and whether the same deploy is running in a healthy environment. That said: when the timing is exact and the change is yours, roll back first and confirm afterwards. Being wrong about the cause costs a rollback; being slow costs the users.

8.4 Mitigations worth having ready

Table 8.3 Feature flags are the strongest entry because they are the only mitigation that is both instant and precise — one code path disabled without a deploy, without a rollback, without touching anything else. That is worth building before an incident makes you wish you had. And the last row carries a warning: a restart usually works and destroys the evidence, so take a heap snapshot, capture the goroutine or event-loop state, and save the logs before you do it, or you will be here again next week with nothing new to go on.

Write it up, and make the write-up about the system

A useful incident review answers four questions: what users experienced, when we knew, what we did, and what made this possible. The last one is where the value is, and it is a question about the system rather than about a person — a config with no validation, a dependency with no timeout, an alert that did not exist, a runbook nobody had written. Actions from a review should be changes to the system; “be more careful” is not an action, and a review that produces one has failed.

Checkpoint

Why does mitigation come before diagnosis?

Because every minute spent understanding is a minute of continued impact, and mitigation is usually cheap and reversible while diagnosis is neither. Roll back or disable the flag first; the bug will still be there afterwards, in a system nobody is shouting about.

Why is starting in the logs usually the wrong move?

Because you are reading individual events looking for a pattern that one aggregate query would show instantly. Metrics narrow — everything or one endpoint, everyone or some users, since when. Traces localise it to a component. Logs explain the specific case, filtered by the trace ID you now have.

Every dashboard is green and users say the site is down. What shape is that?

Traffic dropped to zero. You cannot fail requests that never arrive, so error and latency panels look perfect — the problem is upstream: DNS, the load balancer, a CDN, a firewall rule. It is why “traffic vanished” must be one of the alerts you actually have.

A restart fixed it. Why is that a warning sign?

Because it freed a resource that will fill again — a leak, a pool, a lock, a descriptor. The restart also destroyed the evidence needed to find out which. Capture a heap snapshot and the process state before restarting, or you will be back with nothing new.

Chapter Nine · Part IV

Observability in CI/CD

The pipeline is where observability stops being a monitoring concern and becomes a delivery one. A deploy that cannot be attributed, a release that cannot be identified, and a rollback that has to be improvised are the three things that turn a small incident into a long one — and all three are fixed in the build rather than in the dashboard.

By the end of this chapter you will be able to
  • Stamp every artefact with an identity that survives to production
  • Put deploy markers where the graphs are
  • Verify a release automatically after it ships
  • Roll back on a signal rather than on a hunch
  • Observe the pipeline itself

9.1 One identifier, everywhere

Put the release inSo that
The image tagYou can identify and re-deploy it
A metric labelYou can compare error rates between versions
Every log lineYou can filter to one release
The error trackerRegressions are detected — Chapter 2
Trace resource attributesSpans are attributable

Table 9.1 The last row is worth having for one reason: during an incident, “what is deployed” is answered by asking the process rather than by trusting the pipeline. Those two disagree more often than anyone expects — a failed rollout, a stuck pod, a cached image, a canary nobody remembered.

One caution about version as a metric label

It is a label whose value changes on every deploy, so each release creates a new set of series. That is acceptable — deploys are not unbounded and old series age out — but it is the one legitimate exception to Chapter 0’s rule, and it stops being acceptable if you also add build number, branch and timestamp. One version label, on a small number of metrics.

9.2 Deploy markers, which cost nothing

The set-commits step is the one worth the extra minute

It uploads the commit range in the release, which lets the error tracker say which commit likely introduced a new issue rather than only which release. On a deploy containing thirty commits from six people, that is the difference between a useful notification and a group message asking whether anyone recognises a stack trace.

9.3 Verify the release, do not just deploy it

StrategyBlast radiusNeeds

Table 9.2 The last row is the one that changes how incidents feel, and it does so by separating deploying from releasing: the code ships dark, is enabled for 1% of users, and can be turned off in seconds without a rollback, a rebuild, or a deploy queue. The cost is real — every flag is a branch that must eventually be deleted — and it is a much smaller cost than the alternative.

Compare versions rather than comparing to yesterday

With a version label on your metrics, a canary is a single query: the error ratio for the new version beside the error ratio for the old one, at the same moment, under the same traffic. That removes the two things that make deploy-time comparisons unreliable — daily patterns and changes in load — and turns “does this look worse?” into a number.

9.4 Observing the pipeline itself

MeasureTells you
Deploy frequencyHow small your changes are
Lead timeCommit to production
Change failure rateHow often a deploy causes an incident
Time to restoreHow fast you recover
Build durationWhat developers are waiting for
Flaky test rateHow much people trust the pipeline

Table 9.3 The first four are the DORA metrics, and they interact in a way worth internalising: teams that deploy more often usually have a lower change failure rate, because each deploy is smaller and easier to attribute. “Deploy less often to be safer” is intuitive and backwards — large batched releases fail more, and fail in ways nobody can localise.

And a flaky test is an observability problem

It is a monitor that fires without a real fault, which is Chapter 7’s alert-fatigue problem in a different system: people learn to re-run the pipeline without reading the failure, and then do the same thing when the failure is real. Track flake rate per test, quarantine the worst offenders, and fix them — the cost is not the minutes spent re-running, it is the credibility of every future red build.

Checkpoint

Why put the release identifier on metrics, logs, traces and errors?

So every signal can be attributed to a commit. “Errors started at 14:32” becomes “errors come only from a3f9c21” — which identifies the change, enables regression detection in the error tracker, and makes canary comparison a single query.

Your pipeline reports a successful deploy. Why also check /version?

Because the deploy command exiting zero says the instruction was accepted, not that the new version is serving traffic. Failed rollouts, stuck pods, cached images and half-finished canaries all produce a green pipeline and old code in production. Ask the running process what it is.

What makes feature flags a better mitigation than a rollback?

They separate deploying from releasing: the change can be disabled in seconds, for a chosen subset of users, without a rebuild, a rollback, or a deploy queue. The cost is that every flag is a branch someone must eventually delete — real, and much smaller than the alternative during an incident.

Is deploying less often safer?

No — it is usually the opposite. Larger, less frequent releases bundle more changes, so failures are more likely and much harder to attribute. Teams with high deploy frequency generally have lower change failure rates, because each deploy is small enough to reason about and roll back.
