About this book

A black window with a blinking cursor is the oldest surviving interface in computing, and almost nothing about it is arbitrary. This book is the reasons.

It is written for someone who can use a computer and cannot yet use a terminal — or who has memorised twenty commands and would like to stop guessing about the rest. It goes from pwd to writing a script that fails loudly, and it covers the three systems people actually work on rather than assuming everyone is on Linux.

The rule this book is built on

Every Linux listing was executed before it was printed. The output is pasted, not written. Where a command produced something other than what the text expected — and that happened repeatedly — the text was changed, not the output. Several of the most useful passages in this book exist because a command did something surprising: awk comparing a header row as a string, bash re-checking its command cache after PATH changes, a set -e script exiting silently mid-loop.

What this book will not do

Two substitutions, stated plainly. The account this book was built under is shown as deploy, and its home directory as /home/deploy — a real absolute path is printed wherever the command prints one, so pwd, readlink -f and hash look exactly as they will on your machine. Nothing else in any Linux listing is altered.

It will not print invented output. This book was built on Linux, so macOS and Windows commands are given with their documented behaviour and no fabricated terminal output — they are marked as shown rather than run. The same applies to anything that would describe the author’s own machine: network paths, running services, installed packages and open ports are explained, and the listing that would reveal them is not printed. Where a demonstration genuinely needed a network or a server, one was built in isolation: chapter 12 runs inside a private network namespace on documentation-range addresses, and chapter 14 talks to a real OpenSSH server started for the build on 127.0.0.1.

How it is organised

Chapter 0 is the history — teletypes, why the commands have two-letter names, and the three separate things people call “the terminal”. Supplement A draws the map across Linux, macOS and Windows once, so every later chapter can name a system and be understood. Then seven parts, from moving around to diagnosing a production failure, and a reference appendix.

Chapter 5 is the hinge. Everything before it is vocabulary; it is the grammar — three streams, a handful of operators, one number — and after it a command you have never seen becomes something you can immediately use.

Every chapter ends the same way

A checkpoint of questions with real answers, and practice tasks to type. Reading a command and running it are different skills, and only one of them is the one you need at 2am.

If you read one thing

Chapter 7, on quoting. It is the shortest chapter in the book and it prevents the most damage — four habits, each costing two characters, that remove the largest single class of shell bug there is.

Chapter Zero · Orientation

What a Terminal Actually Is

A black window with a blinking cursor is the oldest surviving user interface in computing, and almost nothing about it is arbitrary. The two-letter command names, the rectangle that opens at 80 columns wide, the key combination that appears to freeze your screen — each is a fossil of a specific machine that existed before the screen did. This chapter is that history, because knowing it turns a pile of trivia into a system you can reason about.

By the end of this chapter you will be able to
  • Explain what the word terminal originally referred to, and what it means now
  • Separate the three things people call “the terminal”: emulator, TTY layer, shell
  • Say why cp is not called copy
  • Recognise the teletype heritage still visible in stty -a today
  • Place Linux, macOS and Windows on two different family trees
  • Give an honest answer to “why not just use the GUI?”

0.1 The terminal was a machine, and it printed on paper

In 1970 a terminal was a physical object you could stub your toe on. The one that matters most is the Teletype Model 33, a 34-kilogram electromechanical typewriter that could send and receive characters over a wire at ten characters per second. It had no screen. Output was printed onto a roll of paper, permanently, one character at a time, with a noise contemporaries compared to a machine gun.

Unix was written for that machine. Not adapted to it — written for it, in 1969, on a PDP-7 at Bell Labs, by people whose only window onto the computer was a device that typed on paper at the speed of a slow human. Every design decision in the next few pages follows from that one fact.

Open a terminal on any of the three operating systems in this book and run echo $TERM; the answer will almost certainly contain the string xterm, and xterm is a program written in 1984 to imitate a VT100. You are using a 1978 device through a 1984 imitation of it.

Why “TTY” is still everywhere

TTY is the abbreviation of teletype. It survives in the command tty, in the device files under /dev/pts, in stty (“set tty”), in the getty process that offers you a login prompt, and in the Unix permission group named tty. Nobody has attached a teletype to a computer in decades, and the name has never been worth changing.

0.2 The evidence is still on your screen

This is not an analogy. The teletype is still there, in the settings of the terminal you are using right now.

start = ^Q; stop = ^S — the line that still catches people

Look for stop = ^S in the output above. That is XON/XOFF flow control, and it exists because a computer could produce characters faster than a mechanical printer could print them. Ctrl+S told the computer to stop sending; Ctrl+Q told it to resume.

Both keys still work. If you ever press Ctrl+S in a terminal — easy to do by reflex, since it means save in every other program on the computer — the terminal appears to freeze completely. It has not crashed. It is waiting, exactly as designed, for a mechanical printer that stopped existing in the 1980s to catch up. Press Ctrl+Q and everything you typed in the meantime arrives at once.

0.3 Why the commands have such short names

At ten characters per second, typing copy instead of cp costs you two-tenths of a second, every time, plus the paper. Multiply by a working day. The short names were not a stylistic preference; they were the interface being designed around its bottleneck.

The bottleneck vanished around 1975. The names did not, because by then the cost of changing them exceeded the cost of learning them — and that trade has held for fifty years.

0.4 The shell is not the terminal

This confusion costs beginners more time than any other, because the two words are used interchangeably by people who know the difference and are being casual. They are three distinct programs.

The trailing ; : in that command is not decoration

Write it as bash -c 'ps -p $$ -o comm=' — a single command and nothing else — and it answers ps, which is wrong and briefly baffling. The shell has an optimisation: when the last thing it has to do is run one command, it does not fork, it execs, replacing itself with that program. The process id is unchanged, so $$ is still correct — but the process wearing that id is now ps looking at itself.

Adding any second statement — ; : will do, where : is the shell’s do-nothing builtin — gives the shell something to do afterwards, so it forks instead and the answer is bash. This is worth meeting early: it is the first of many places where a tool reports something true about a situation you did not realise you had created.

Why this matters practically

Three real consequences. One: if you add a line to ~/.bashrc and you are actually running zsh, nothing happens, and the internet will tell you to try harder. Two: colours, fonts and how Ctrl+Arrow behaves are the emulator’s business, so no amount of shell configuration fixes them. Three: when you ssh to a server, layers 2 and 3 are on the server and layer 1 stays on your laptop — which is exactly why a remote session can look wrong if the two disagree about $TERM.

Table 0.4 The CRLF row is the funniest and the most expensive. Windows still ends a text line with two bytes because a Teletype Model 33 needed two separate physical motions: return the carriage to the left, then advance the paper by one line. Unix decided one byte was enough and the driver could do the rest. That disagreement is still generating merge conflicts in 2026.

macOS is Unix — more literally than people assume

macOS is not merely “Unix-like”. It is certified UNIX, registered against the Single UNIX Specification, descended from NeXTSTEP and thence from BSD. Linux, by contrast, is not certified UNIX; it is an independent implementation of the same interfaces. The practical upshot is exactly backwards from what the branding suggests: your Linux commands and your macOS commands are close cousins, and the differences you will actually trip over are small ones between GNU tools (Linux) and BSD tools (macOS) — sed -i being the classic. Chapter A is that list.

Windows is now two worlds, and you should pick deliberately

A modern Windows machine can give you PowerShell (a genuinely different design — it pipes objects, not text) or WSL, a real Linux kernel running real Linux binaries. They are both correct answers to different questions. This book teaches both, marks every listing with which one it belongs to, and says plainly when the honest advice is “install WSL and use the Linux column”.

The one thing that makes it click

Beginners try to memorise commands. That does not work, and it is not what fluent people are doing. What they have internalised is much smaller: every command reads text, writes text, and returns a number saying whether it worked. Once that is genuinely automatic, new commands stop being things to memorise and start being things you can slot into sentences you already know how to build. Chapter 5 is where that happens; everything before it is vocabulary.

Checkpoint

You press Ctrl+S by accident and the terminal stops responding. What happened, and what do you press?

Nothing crashed. Ctrl+S is stop in the terminal driver — XON/XOFF flow control, from the era when the computer could outrun the printer. Output is being held, not lost. Press Ctrl+Q (start) and all of it arrives at once. Nothing you typed in between was discarded either.

A tutorial says “check which shell you are using with echo $SHELL”. Why is that not quite right?

$SHELL is your configured login shell from the account record. It does not change when you start a different shell. Run zsh from inside bash and $SHELL still reports bash. The question “what am I typing into right now” is answered by ps -p $$ -o comm=, where $$ is the current shell’s own process id.

Why is rm called rm and not remove?

Because it was named for a Teletype Model 33 running at ten characters per second, where every character cost a tenth of a second and a piece of paper. The bottleneck disappeared by about 1975; the name stayed because renaming it would have broken every script and every pair of hands already trained on it. Fifty-five years on from the first edition of Unix, that trade still looks worth taking — which is why the names look the way they do.

Your colleague says “my terminal is slow”. What are the three different things that could mean?

One: the emulator is slow at drawing — usually a font, a huge scrollback, or a GPU problem, and no shell setting will fix it. Two: the shell is slow to give you a prompt — usually something expensive in a startup file, like a git status in the prompt inside a huge repository. Three: the command is slow, and the terminal is innocent. Figure 0.1 is why the sentence is ambiguous; asking “slow to draw, slow to prompt, or slow to finish?” resolves it immediately.

Why does a text file written on Windows sometimes show ^M at the end of every line on Linux?

Because Windows ends a line with two bytes, CR LF, and Unix ends it with one, LF. The Unix tool prints the leftover carriage return as ^M. Both conventions are inherited directly from the teletype, where returning the carriage and advancing the paper were two separate physical movements; Unix decided the driver could supply the first one. Chapter A has the fix.

Supplement A · Orientation

Three Systems, One Skill

Linux, macOS and Windows are not three separate things to learn. Two of them are close cousins that disagree about a handful of flags, and the third offers you a choice between a genuinely different design and a real Linux running inside it. This chapter draws the map once, so that every later chapter can just say Linux, macOS or Windows and you already know what that implies.

By the end of this chapter you will be able to
  • Name the commands that behave identically on all three systems
  • Predict which flags will fail when you move a script from Linux to macOS
  • Choose deliberately between PowerShell and WSL on Windows
  • Explain why PowerShell pipes objects rather than text
  • Handle paths, case sensitivity and line endings across systems
  • Write a command today that will still work on the other two

A.1 The large part that is genuinely the same

Start with the good news, because it is most of the news. There is a written standard — POSIX, IEEE Std 1003.1 — that specifies a shell language and about 160 utilities. Linux implements it. macOS is certified against it. Windows does not, but WSL runs a real Linux and therefore does.

The single most useful sentence in this book

Learn the POSIX core first, and learn it well. The differences below are real and will cost you an afternoon each, but they are a footnote against the shared 90%. Beginners who try to learn “the Linux way and the Mac way and the Windows way” as three parallel vocabularies are making the subject three times harder than it is.

If you develop on a Mac and deploy to Linux

This is the common case and the dangerous direction, because the machine you test on is the more restrictive one — a script that works on your Mac will usually work on the server. The reverse bites: a script written on Linux, using sed -i and date -d, fails on a colleague’s Mac. The cheap fix, if you are on a Mac and tired of it, is brew install coreutils gnu-sed, which installs the GNU versions prefixed with g (gsed, gstat) — deliberately not shadowing the system ones.

“Terminal” versus “shell”, on Windows specifically

Windows Terminal is the emulator — layer 1 in figure 0.1. It is not a shell. Installing Windows Terminal does not give you new commands; choosing what runs inside it does.

The single recommendation, stated plainly

If you are on Windows and your goal is to learn the terminal as a developer — which is why you are reading this — install WSL and follow the Linux column of this book. You get the real thing: the same binaries, the same flags, the same manual pages, and the same behaviour as the server you will eventually deploy to. Learn PowerShell in addition, when you have a Windows machine to administer. Learning PowerShell instead, in the hope that it transfers, is the expensive mistake.

A.4 PowerShell is different in kind, not in vocabulary

It is tempting to read PowerShell as “Unix with longer command names”. It is not, and the difference is worth understanding even if you never use it, because it is the most interesting alternative design anyone has shipped.

A Unix pipe carries bytes. ls produces text; grep reads text. Every stage parses what the previous stage formatted, which is why awk exists and why parsing ls output is a known way to get hurt.

A PowerShell pipe carries objects. Get-ChildItem produces file objects with typed properties; the next stage receives those objects, not a rendering of them. Nothing is parsed because nothing was ever flattened.

A Unix pipe is a universal joint: any program in any language that reads standard input and writes standard output plugs into it, with no shared type system and no agreement beyond “bytes, and a newline usually means a record”. That is a weaker contract, and it is why it fits everything.

Checkpoint

A script with sed -i 's/old/new/' config.yml works on your Linux box and errors on a colleague’s Mac. Why?

GNU sed -i takes an optional suffix attached to the flag; BSD sed -i requires a suffix as a separate argument. On macOS the shell hands sed the string s/old/new/ as the backup suffix, leaving no script, and it fails. sed -i '' 's/old/new/' f works on macOS; sed 's/old/new/' f > t && mv t f works on both, which is the habit to form.

Your React build works locally on a Mac and fails on the CI server with “module not found”. What should you check first?

The case of the filename against the case in the import. macOS is case-insensitive by default, so import Header from './header' happily finds Header.jsx. Linux — the CI server — is case-sensitive and will not. Check with git ls-files, which shows the case actually committed, and rename with git mv; a plain rename on a case-insensitive filesystem may not register as a change at all.

What does bash: ./deploy.sh: /bin/bash^M: bad interpreter mean?

The file has Windows line endings. The shebang line reads #!/bin/bash\r, and the kernel takes the whole thing literally, looking for an interpreter whose filename ends in a carriage return. Fix the file with sed -i 's/\r$//' deploy.sh, then fix the cause with .gitattributes so it does not come back.

You are on Windows and want to learn the terminal for backend development. PowerShell or WSL?

WSL. Your server will be Linux, so WSL is the same binaries, the same flags, the same manual pages and the same behaviour — everything you learn transfers directly. PowerShell is an excellent tool for administering Windows itself, and worth learning as well if you have Windows machines to manage; it is a poor substitute for learning Unix, because the object model that makes it good does not exist on the server.

Why is rm $f dangerous when rm "$f" is not?

Because the shell expands and word-splits the variable before rm is invoked. If f is my report.txt, rm receives two arguments. If it is * , it receives every file in the directory. The quotes make it exactly one argument, whatever it contains. This is not a style preference — it is the difference between a command that does what you said and one that does what your data said.

Chapter One · Part I

Where You Are, and How to Move

Every command you will ever type is interpreted relative to one invisible piece of state: the directory the shell is currently sitting in. Almost every early mistake at the command line — the file that is not there, the command that affects the wrong thing — is really a mistake about that one number. This chapter makes it visible and then makes it effortless.

1.1 The invisible number

A shell has a current working directory. It is a property of the process, it changes only when you change it, and every relative path you type is resolved against it. Nothing else about the command line matters as much.

Your prompt is probably already telling you

Most default prompts include some form of the current directory — often abbreviated, often just the last component. That is convenient and it is also the reason people stop reading it. When a command surprises you, the first diagnostic is always pwd, typed deliberately. Chapter 19 shows how to make the prompt show the full path if you would rather never be surprised.

What is the difference between ls -l ~/lab and ls -ld ~/lab?

The first lists what is inside the directory. The second describes the directory itself — its permissions, owner and modification time. When you are diagnosing a permission problem on a directory, -ld is the one you want; without it ls answers a different question and you conclude the wrong thing.

Why does echo ~ print your home directory but echo '~' print a tilde?

Because tilde expansion is done by the shell, before echo is invoked. Unquoted, echo receives /home/deploy and prints it. Single-quoted, the shell is told to leave the text alone, so echo receives a literal ~. No program on the system understands ~; the shell has always already handled it. Chapter 7 is this idea in full.

A directory shows 4096 in the size column of ls -l. Does it contain 4096 bytes of files?

No. That is the size of the directory entry itself — the index of names it contains — not the total size of those files. A directory holding one enormous video and a directory holding twelve small text files can report the same number. For the real total, use du -sh dirname.

2.1 cat, and the moment it is the wrong answer

When cat is the wrong tool

A large file. cat dumps all of it; you get the last screenful and a scrollback you must fight. Use less.

A binary file. The bytes are sent to the terminal as if they were control codes, and some of them are. Your prompt turns into mojibake and your keyboard stops echoing. If you do this, reset will repair the terminal — and it is worth doing once, deliberately, so that it is never frightening.

Feeding one file to a command. cat f | grep x works, but grep x f is shorter, faster, and lets grep report the filename. This is common enough to have a name — the useless use of cat — and it is a harmless habit rather than a sin.

3.1 Making things

touch is really about timestamps

3.4 What rm actually does

This is the section to read slowly. rm has no undo, no trash, and no confirmation by default. It is not being reckless — it is being a tool designed for people who meant it — but the consequence is real.

“Deleted” means the name is gone, not the data

rm unlinks a name from the data. The blocks are freed only when the last name is gone and no process still has the file open. Three consequences:

One: deleting a huge log file while a program is writing to it frees no space at all — the process holds it open, and the space returns when the process closes it or restarts. This is a classic full-disk mystery, and chapter 21 shows how to find it with lsof.

Two: a file with a second hard link (section 3.6) is not gone when you remove one name.

Three: the freed blocks still contain your data until something overwrites them, which is why forensic recovery works and why “I deleted it” is not a security measure.

The three rm commands that end afternoons

rm -rf ~ — your entire home directory, silently.

rm -rf $DIR/* where DIR is unset. The shell expands it to rm -rf /*. This has taken out production systems; it is why set -u exists, and why chapter 17 puts it in every script.

rm -rf ./ folder — one stray space, and you have asked it to delete the current directory and something called folder.

None of these is exotic. All three are one character away from something you would type on purpose.

Why does moving a 40 GB file within your home directory finish instantly, while moving it to a USB stick takes minutes?

Because within one filesystem mv only rewrites a directory entry — the data does not move at all. Across filesystems there is no shared index to update, so mv falls back to copying every byte and then deleting the original. It is the same command doing two very different amounts of work, which is also why an interrupted cross-device mv can leave a partial file behind.

You deleted a 20 GB log file and df shows no space was freed. What is happening?

A process still has the file open. rm removed the name; the data is freed only when the last name is gone and the last file handle is closed. The application is still writing to a file that no longer has a path. Restarting it releases the space, and lsof +L1 lists exactly these files. The right fix is to truncate rather than delete — : > app.log — or to configure rotation properly.

rm -rf $BUILD_DIR/* is in a deploy script. What happens if BUILD_DIR is unset, and how do you prevent it?

The shell expands the unset variable to nothing, so the command becomes rm -rf /* — everything the user can reach. Prevent it with set -u at the top of the script, which makes an unset variable a fatal error instead of an empty string. ${BUILD_DIR:?BUILD_DIR is required} does the same for one variable with a message. Chapter 17 puts set -euo pipefail in every script for exactly this reason.

What is the difference between a dangling symlink and a broken hard link?

There is no such thing as a broken hard link. A hard link is a name for the data, so as long as one hard link exists, the data exists. A symlink stores a path as text and has no idea whether anything is there; delete the target and the symlink remains, pointing at nothing. ls -l usually shows dangling symlinks in red, and find . -xtype l lists them all.

Your colleague aliases rm to rm -i and says it makes them careless. Are they right?

Partly, and it is worth taking seriously. A prompt you answer y to reflexively provides no protection and trains the reflex. The habits that survive that critique are the other two: run ls with the pattern before rm with the pattern, and prefer a trash command that is genuinely recoverable. The alias is a cheap extra layer, not the plan — and note that it does not apply in scripts at all.

Why must the pattern in find . -name '*.log' be quoted?

Because otherwise the shell expands *.log first, against the current directory. If there is one .log file here, find is asked to search for that exact name everywhere — so it misses every other log in the tree. If there are several, find gets a syntax error. If there are none, the shell passes the pattern through unchanged and it works by luck, which is why the bug is intermittent and confusing.

What is the difference between -exec cmd {} \; and -exec cmd {} +?

\; runs the command once per file. + collects filenames and runs it once with all of them, in batches if there are very many. For ten thousand files that is ten thousand processes against one, so + is dramatically faster. Use \; only when the command genuinely takes one file at a time, or when you need {} to appear somewhere other than at the end.

Your search results are full of node_modules. Give two fixes.

One: exclude it explicitly — find . -not -path '*/node_modules/*', or grep -r --exclude-dir=node_modules. Two: use rg, which reads your .gitignore and skips it without being told. The second is why ripgrep feels faster than it strictly is: a good part of the speed is not searching things you never wanted.

find . -name '*.txt' | xargs rm deleted the wrong files. What went wrong?

A filename contained a space, and xargs splits on whitespace. my report.txt became two arguments, so rm was asked to delete my and report.txt — and if files by those names existed, they are gone. Use find . -name '*.txt' -delete, or -print0 | xargs -0 rm. The null separator is safe because it is the one byte a filename cannot contain.

You installed a newer node but node --version still shows the old one. Two possible causes?

One: the old copy is earlier in PATH. type -a node lists every copy in the order the shell tries them; the first is the one that runs. Two: the shell cached the old location when you first ran it and has not looked again. hash -r clears the cache, and a new terminal has no cache. Check the first cause before assuming the second — it is much the more common.

5.1 Every program has three streams

A process starts with three file descriptors already open. This is a contract the kernel provides, not a convention programs opt into, which is why it works across every language and every tool.

NumberNameDefaultCarries

Table 5.1 The separation of 1 and 2 is the design decision that makes everything else work. Progress messages go to stderr, and that is correct

curl’s progress bar, wget’s download meter and docker build’s step output all go to stderr even though nothing is wrong. That is deliberate: it means curl -o - url | tar xz works, because the progress bar is not being fed into tar. “stderr” means not the data, not an error.

> truncates before the command runs

sort f > f produces an empty file. The shell opens f for writing — truncating it to zero — before sort starts reading. There is nothing left to sort. Use a temporary file, or sponge from moreutils: sort f | sponge f. This is one of the few genuinely destructive things the shell will do without warning.

5.3 The pipe, and why it is the whole point

a | b connects a’s stdout to b’s stdin. Both run at the same time, and data flows through as it is produced — which is why you can pipe a file larger than your memory, and why tail -f app.log | grep ERROR prints matches as they happen rather than when the log ends.

sort before uniq, always

uniq only removes adjacent duplicates — it never looks further than the previous line, which is what makes it able to process a stream of any size. Unsorted input therefore gives you nonsense that looks plausible. sort | uniq -c is the idiom; if you forget the sort, the counts will simply be wrong and nothing will tell you.

Only stdout goes through a pipe

a | b sends a’s stdout to b. Errors from a go straight to your screen, bypassing b entirely — which is usually what you want, and occasionally not. To pipe errors too: a 2>&1 | b, or a |& b in bash 4+.

Why does cmd 2>&1 > file not put errors in the file?

Because redirections are applied left to right, and 2>&1 means “point stream 2 wherever stream 1 points right now” — a copy, not a link. At that moment stream 1 is still the terminal, so stream 2 is aimed at the terminal. Then > file moves stream 1 to the file, and stream 2 stays where it was pointed. Write cmd > file 2>&1, or cmd &> file.

sort data.txt > data.txt emptied the file. Why, and what should you have written?

The shell sets up redirections before running the command, and > truncates the target to zero bytes. By the time sort opened data.txt to read it, it was already empty. Write to a temporary file and move it — sort data.txt > tmp && mv tmp data.txt — or use sponge from moreutils, which reads all its input before opening the output.

A container exits with code 137. What most likely happened?

It was killed by SIGKILL: 137 is 128 + 9. In a container that overwhelmingly means the out-of-memory killer, because the process exceeded its memory limit. The important consequence is that SIGKILL cannot be caught, so the application had no opportunity to log anything — which is why the application logs look like it simply stopped mid-sentence. Look at the memory limit, not at your code, first.

sudo echo "nameserver 1.1.1.1" > /etc/resolv.conf says permission denied. Why does sudo not help?

Because sudo elevates echo, and echo is not the thing writing the file. The redirection is performed by your shell, which is still unprivileged, and it happens before sudo even runs. Use echo "nameserver 1.1.1.1" | sudo tee /etc/resolv.conf > /dev/null, where the privileged process is tee — the one actually opening the file.

uniq -c gave counts that were obviously wrong. What did you forget?

sort. uniq compares each line only against the one before it, which is what lets it handle input of any size in constant memory. Without sorting, identical lines that are not adjacent are counted as separate groups. It does not warn, and the output looks entirely plausible — which is what makes it worth committing sort | uniq -c to memory as a single unit.

Checkpoint

grep 'config.yml' list.txt matched a line containing configXyml. Why?

Because . in a regular expression means any character, and X is a character. Escape it — config\.yml — or, better, tell grep that the pattern is a literal string with -F, which removes the whole class of problem. This matters most with filenames and IP addresses, where dots are everywhere and the accidental matches look plausible.

What is the difference between sed '5p' and sed -n '5p'?

sed prints every line by default. sed '5p' therefore prints the whole file, with line 5 appearing twice — once automatically and once because you asked. -n turns off the automatic printing, so sed -n '5p' prints only line 5. Any time you are using p, you almost certainly want -n with it.

You need the total of column 4 in a CSV, grouped by column 3. Which tool?

awk: awk -F, 'NR>1 {sum[$3] += $4} END {for (k in sum) print sum[k], k}'. It has fields, arithmetic and associative arrays, which is exactly the three things this needs. grep cannot do arithmetic and sed cannot do fields. The caveat is real, though: if any field can contain a quoted comma, -F, is wrong and you need a real CSV parser.

Why is grep a bad way to read a JSON API response?

Because JSON is not line-oriented and its whitespace is not significant, so any pattern you write is really a bet about formatting. The same document pretty-printed, or with keys in a different order, or with a value that contains a brace, breaks the pattern — and it breaks by matching nothing, silently, rather than erroring. jq parses the document, so it answers correctly regardless of layout.

A colleague’s sed -i 's/a/b/' f works for them and errors for you. What is different?

One of you is on macOS and the other on Linux. GNU sed takes an optional backup suffix attached to -i; BSD sed requires the suffix as a separate argument, so on macOS the substitution expression is consumed as the suffix. sed -i.bak works on both; sed 's/a/b/' f > t && mv t f works on both and leaves no backup file behind.

The shell rewrites your command before any program sees it. Checkpoint

In what order does the shell perform word splitting and globbing, relative to variable substitution?

Variable substitution happens first, then word splitting, then globbing. That order is the whole problem: the shell substitutes the variable’s value into the command line and then splits that value on spaces and expands any wildcards it contains. A variable holding my report.txt becomes two arguments; one holding * becomes every file in the directory. Double quotes suppress steps 6 and 7 while keeping step 3.

Why must awk '{print $1}' use single quotes?

Because $1 means “the first field” to awk and “the first positional parameter” to the shell. In double quotes the shell substitutes its own $1 — normally empty — and awk receives {print }, which prints the entire line. It does not error; it quietly does something else. Single quotes stop the shell touching the program at all.

for f in *.log; do ...; done ran once with f set to *.log. What happened?

There were no .log files. By default bash leaves an unmatched glob as the literal pattern, so the loop ran once with the pattern itself as the value. shopt -s nullglob makes an unmatched glob expand to nothing, so the loop body does not run at all — which is almost always what was intended. The alternative is to test inside the loop: [ -e "$f" ] || continue.

How do you delete a file named -rf?

rm ./-rf or rm -- -rf. Without one of those, rm parses the name as flags. -- is the POSIX end-of-options marker and works with almost every command; ./ works because a path that starts with a dot is unambiguous. This is not a curiosity — it is what happens when filenames come from user input, and it is why programs that accept untrusted names should use -- as a matter of course.

A command is not doing what you expect and the quoting looks fine. What do you run?

set -x. The shell then prints every command, after all expansions, prefixed with +, so you can see exactly what was executed rather than what you believe you typed. set +x turns it off. For a script, bash -x script.sh does the same without editing the file. Nothing else in this chapter saves as much time.

If word splitting causes so many bugs, why does the shell do it?

Chapter Eight · Part III

Users, Permissions, and Elevation

Unix was designed in 1969 for a machine shared by many people, and that assumption is still in every file on your laptop. Nine bits per file decide who may do what. Once you can read them you can read every “permission denied” you will ever get, and — more usefully — predict them before they happen.

By the end of this chapter you will be able to
  • Read and write permissions in both symbolic and octal form
  • Explain what the execute bit means on a directory
  • Predict the permissions a newly created file will have
  • Use sudo deliberately, and know what it does not cover
  • Recognise setuid and the sticky bit when you meet them

8.1 Three identities, three permissions

Every file has an owner and a group. Every process runs as some user, who belongs to some groups. When a process touches a file, the kernel asks one question in order: are you the owner? no — are you in the group? no — then you are “other”. The first matching category decides, and the others are not consulted.

Table 8.1 The directory column is the one that causes real confusion, and rows two and three are the reason. Deleting a file is a write to its directory, not to the file. You can delete a file you cannot read, if you can write the directory it sits in — and you cannot delete a file you own if you lack write permission on its parent. This surprises everyone once.

Where the umask should be set

In your shell startup file (chapter 10) for interactive use, or in the service definition for a daemon. Do not set it inside a script to fix one file — set the permissions on that file explicitly with chmod, which is visible to the next reader. A umask buried in a script changes the behaviour of everything after it, including things you did not write.

8.4 The execute bit on a directory, properly

“Permission denied” on a path is about the whole path

To reach /a/b/c/file you need x on /, on a, on b and on c, and then r on file. One missing traverse bit anywhere along the way produces exactly the same error as if the file itself were unreadable. When a permission error makes no sense, walk the path: namei -l /a/b/c/file prints the permissions of every component at once and finds it in one command.

8.5 sudo, and what it is not

root — user id 0 — bypasses the permission checks entirely. sudo runs one command as root, after checking that you are allowed to and logging that you did.

The three things sudo does not do

1. It does not apply to redirection. sudo echo x > /etc/f fails, because your unprivileged shell performs the >. Use echo x | sudo tee /etc/f, as chapter 5 showed.

2. It does not apply to the rest of a pipeline. In sudo cmd1 | cmd2, only cmd1 is elevated.

3. It does not carry your environment by default. Your http_proxy and PYTHONPATH are dropped, and PATH is replaced by sudoers’ secure_path — which is why sudo mytool can report “command not found” for something that works fine without it.

Checkpoint

You own a file, its permissions are r--rw-r--, and you are in its group. Can you write it?

No. The kernel checks the categories in order and stops at the first match. You are the owner, so the owner bits — r-- — are the answer, and the more generous group bits are never consulted. Owner permissions can be less than group permissions, and when they are, the owner has less access than everyone else. Fix it with chmod u+w.

Why can you delete a file you have no write permission on?

Because deleting is a modification of the directory, not of the file. If you have w and x on the containing directory, you may remove entries from it regardless of the permissions on what those entries point at. rm normally prompts before removing a write-protected file, but that is rm being polite, not the kernel objecting. The sticky bit exists to restrict exactly this in shared directories like /tmp.

A file is 644 and readable, yet cat says permission denied. What should you check?

The directories above it. You need the execute — traverse — bit on every component of the path to reach the file at all, and a missing one produces the same message as an unreadable file. namei -l /full/path/to/file prints the permissions of each component in order and shows you exactly which one blocks you.

Why does sudo echo "x" > /etc/file still fail?

Because the shell performs the redirection, and the shell is still you. sudo elevates echo, which never touches the file — it writes to a stream that your unprivileged shell already opened, or failed to. Use echo "x" | sudo tee /etc/file > /dev/null, where the elevated process is the one opening the file, or wrap the whole thing: sudo sh -c 'echo x > /etc/file'.

Your teammate’s fix for everything is chmod 777. What is wrong with it?

It grants write access to every process on the machine, including anything an attacker manages to run as any user — so a web server compromise becomes the ability to rewrite your files. It also usually treats the wrong cause: the real problem is normally ownership, or a missing traverse bit on a parent directory, and 777 masks that rather than fixing it. The right answers are chown, the correct one of 644/755/600, and g+s with a shared group when several people genuinely need to write.

It is common because it makes the immediate symptom go away — the upload works, the cache writes. If root ignores permissions, why do permissions protect anything?

Because almost nothing runs as root. Permissions are not a defence against someone who is already root — they are what makes becoming root the hard part, which is why setuid binaries are audited so carefully and why running daemons as root is now considered a design fault rather than a convenience.

Checkpoint

Why is kill -9 a last resort rather than the normal way to stop something?

Because SIGKILL cannot be caught, so the process gets no chance to run cleanup: buffers are not flushed, lock files are not removed, in-flight requests are not finished, children are not told to stop. SIGTERM — plain kill — is a request the program can handle properly. Escalate only if it does not respond, and if -9 also fails the process is in state D and the problem is the disk or the network, not the process.

You closed a terminal and the build you started died. How should you have run it?

The shell sent SIGHUP to its jobs when it exited. nohup cmd & would have made it immune, and cmd & disown detaches it from the shell’s job table. But the better answer for anything you might want to watch again is tmux: run it inside a session, detach with Ctrl+b d, and reattach later from anywhere — including from a different machine.

Load average is 40 but top shows the CPUs nearly idle. What is happening?

On Linux, load counts processes in uninterruptible sleep — state D, blocked on I/O — as well as those wanting CPU. A load of 40 with idle processors means about forty processes are waiting on storage or a network filesystem. Look at iostat -x 1, at disk health, and at any NFS or network mounts. Nothing in your application code will explain it.

npm start fails with “address already in use”. How do you find the culprit?

lsof -i :3000 — or ss -tlnp 'sport = :3000' — names the process holding the port, with its pid. Then kill it, politely first. The common cause is a previous run that was detached or backgrounded and never stopped, which is also a reason to prefer tmux over stray background jobs: you can go and look at what is still running.

What is a zombie process, and is it a problem?

A process that has finished but whose exit status has not been collected by its parent, so its entry stays in the table — shown as Z. A zombie uses no memory and no CPU; it holds a process-table slot and nothing else. One or two are harmless and transient. Thousands mean the parent is not reaping its children, which is a bug in the parent — and killing the zombie does nothing, because it is already dead. Kill or fix the parent, and init adopts and reaps the orphans.

Checkpoint

Why does a script fail to change your current directory, no matter what it does?

Because a script runs in a child process, and the environment — including the working directory — flows one way only. The child changes its own directory and then exits; the parent shell is untouched. To change the calling shell’s state you must run the file in that shell: source script.sh or . script.sh. This is the same reason cd has to be a builtin, from chapter 1.

Your cron job says “node: command not found” but node works fine in your terminal. Why?

Cron runs a non-login, non-interactive shell, which reads no startup files — not .bashrc, not .bash_profile. Your node is almost certainly installed by nvm, which puts it on PATH from .bashrc. Cron’s PATH is a short default. Fix it with an absolute path, a PATH= line at the top of the crontab, or a wrapper script — and test it with env -i, which reproduces the stripped environment.

What is the difference between VAR=x and export VAR=x?

VAR=x creates a shell variable, visible only to that shell. export puts it in the environment, which is copied into every child process the shell starts. If a program you run cannot see a variable you set, the missing word is almost always export. env lists the exported ones; set lists everything.

You installed a newer tool but the old one still runs, and type -a shows the new one first. What now?

hash -r. The shell caches the location of each command it has run. Assigning to PATH flushes that cache, so a reordering takes effect at once — but the cache does survive the binary itself moving or being replaced while PATH stays the same, and then the shell keeps trying the remembered path. hash -r clears the cache, and a new terminal never had one. type -a reflects the current PATH, which is why it can disagree with what actually runs.

Why is mytool --password=secret worse than PASSWORD=secret mytool?

Because command-line arguments are readable by any user on the machine through ps or /proc/PID/cmdline, for as long as the process runs. The environment of a process, by contrast, is readable only by its owner and root. Neither keeps the secret out of your shell history — for that you need a file, or HISTCONTROL=ignorespace and a leading space — but the argument form is public to everyone on the box, which is a different order of problem.

Checkpoint

Why does tar need gzip at all?

Because they do different jobs. tar turns many files into one stream while preserving names, permissions and timestamps; it has no compression. gzip compresses one stream and has no concept of files or directories. The Unix answer to “compress a directory” is to compose them, which is why the format is .tar.gz and why -z is a separate flag. zip takes the other approach and does both, which is why it can extract a single member quickly and .tar.gz cannot.

Someone sends an archive and extracting it scatters forty files into your current directory. What happened, and how do you avoid it next time?

It is a tarbomb — made from inside the directory with tar -czf x.tar.gz ., so the members have no common parent. Avoid it by running tar -tzf x.tar.gz | head before extracting, and by extracting into an empty directory with -C out/ regardless. When creating archives, stand outside and name the folder: tar -czf notes.tar.gz notes/.

tar printed “Removing leading / from member names”. Is something wrong?

No — that is a safety feature. tar converts absolute paths to relative ones so that extracting the archive cannot overwrite /etc or /usr on the receiving machine. The files land under wherever you extract instead. If you genuinely need absolute paths restored you can pass -P, and you should think carefully before doing so.

When is xz the right choice over gzip?

When the archive is compressed once and downloaded many times, and the extra minutes of compression buy bandwidth for everyone else — release tarballs, distribution packages, container base layers. It is the wrong choice for a nightly backup, where the compression time is paid every night and the archive may never be read. For anything where both ends are yours, zstd gets most of xz’s ratio at a small fraction of the cost.

You need to send a folder to a colleague on Windows who is not technical. What format?

.zip. It opens by double-clicking with nothing installed, on Windows and macOS both. .tar.gz is technically better — it preserves Unix permissions and symlinks — and none of that matters if the recipient cannot open it. Choose the format for the receiver, not for the sender.

A service bound to 127.0.0.1:3000 is reachable only from the same machine; one bound to 0.0.0.0:3000 is reachable from anywhere that can route to you. Checkpoint

ip addr shows 192.168.1.42 but a colleague on the internet cannot reach you there. Why?

Because that is a private address — RFC 1918 — valid only on your local network. Your router performs NAT, so the internet sees the router’s public address instead. curl ifconfig.me reports that one. For a colleague to reach a service on your machine you need a port forward on the router, a tunnel such as ngrok or Tailscale, or to put the service somewhere with a public address.

A host does not respond to ping. Is it down?

Not necessarily, and usually not. ICMP is blocked by default at most cloud providers and many corporate firewalls, so a machine serving millions of HTTPS requests may never answer a ping. Test the port that matters instead: nc -z host 443, or curl -v https://host/. ping succeeding is strong evidence the path works; ping failing is weak evidence of anything.

A name resolves for your colleague and not for you. What is the first command?

dig +short name @1.1.1.1 — ask a public resolver directly. If it answers, the record exists and your resolver is the problem: check /etc/resolv.conf, your VPN, or a stale cache. If it also returns nothing, the record genuinely does not exist or has not propagated. Then compare with getent hosts name, which goes through the system resolver and honours /etc/hosts — an entry there is a classic cause of “works on my machine”.

Your dev server works locally and a colleague on the same wifi cannot open it. Most likely cause?

It is bound to 127.0.0.1 rather than 0.0.0.0. Most development servers default to loopback deliberately, so that a work-in-progress is not exposed to the network. ss -tlnp shows it: 127.0.0.1:3000 means local only, *:3000 or 0.0.0.0:3000 means anywhere. Most frameworks accept --host 0.0.0.0. Check the firewall second, and think about whether you want it exposed at all.

A traceroute ends in three rows of asterisks. What does that tell you?

Very little on its own. Many routers are configured not to reply to the probes while still forwarding traffic normally, and the final destination often does not reply either. Asterisks at the end are the normal case, not a fault. What is meaningful: a large latency jump between consecutive hops, or the trace consistently stopping at the same hop from several different starting points. For anything serious, use mtr, which distinguishes occasional non-replies from real loss.

13.4 Moving files to and from a server

The trailing slash is not cosmetic

rsync -a src/ dst/ copies the contents of src into dst. rsync -a src dst/ copies the directory itself, producing dst/src/. Getting this backwards creates a nested duplicate, and with --delete it can empty the destination and then fill it with a subdirectory. Run it with -n first, every time --delete is involved.

13.5 Did the right thing arrive?

A checksum and a signature are different promises

A checksum tells you the file is not corrupted — it survived the network intact. It does not tell you the file is genuine, because whoever replaced the file could replace the checksum on the same page. A signature — gpg --verify, or a signed release — tells you it came from someone holding a specific private key. Use the checksum for “did the download work” and the signature for “is this really from them”.

On curl … | bash

You will meet installation instructions of the form curl -fsSL https://x/install.sh | bash. The honest position: you are executing whatever that URL returns, at that moment, with your privileges, without reading it — and a compromised host or a redirect can change what that is. It is not different in kind from running any installer you did not read, and it is more exposed, because there is no package signature and no cached copy. The cheap improvement costs one extra step: curl -fsSL URL -o install.sh, read it, then bash install.sh. Chapter 15 is about the alternative — a package manager, where signing and provenance are built in.

Checkpoint

Why does curl -fsSL appear in so many installation instructions?

Four separate fixes. -f fails on an HTTP error instead of saving the error page and exiting 0. -s silences the progress meter. -S puts errors back, which -s would otherwise suppress. -L follows redirects, which release URLs and CDNs use constantly. Each letter exists because its absence produced a confusing bug — most often a script that downloaded a 404 page and then failed at the next step with a message about a corrupt archive.

Your script downloads a tarball and tar says it is corrupt. What is the likely cause?

The download succeeded in HTTP terms but returned something that is not a tarball — a 404 page, a login redirect, or a “click to continue” interstitial. Without -f and -L, curl saved it and reported success. Check with file downloaded.tar.gz, which reads the magic bytes rather than the name, or head -c 200 — you will usually find HTML. Then add -fL.

What is the difference between rsync -a src/ dst/ and rsync -a src dst/?

The trailing slash on the source. With it, the contents of src go into dst. Without it, the directory goes into dst, giving you dst/src/. This is the most common rsync mistake and it is genuinely dangerous alongside --delete, which would then remove everything already in dst that is not inside the newly nested copy. Always -n first.

A checksum matches. Does that mean the file is safe?

No. It means the file is intact — the bytes you have are the bytes the checksum was computed from. If an attacker replaced the file on the server, they replaced the checksum on the same page, and it matches perfectly. A checksum defends against corruption, not against substitution. For provenance you need a signature verified against a key you obtained independently, which is what package managers do for you automatically.

Why is -H "Authorization: Bearer $TOKEN" better than pasting the token inline?

Because the expanded command line is visible to every user on the machine through ps, and it lands in your shell history. Using a variable keeps the literal out of your history file, and reading it from a chmod 600 file or a secret manager keeps it out of the environment of unrelated processes too. curl also supports --config file and -K -, which read options — including headers — from a file or standard input, so the token never appears as an argument at all.

14.2 Connecting, and the host key question

What host key verification actually protects

The first connection is the vulnerable one: you have no prior knowledge, so ssh asks you to accept a fingerprint that you cannot really check. Every connection after that is protected — if something intercepts the connection, it cannot present the same key, and ssh refuses loudly.

That loud refusal is REMOTE HOST IDENTIFICATION HAS CHANGED, and the honest advice is: it is usually a rebuilt server, and it is occasionally an interception, and the two look identical. Do not blindly run the ssh-keygen -R the message suggests. Confirm out of band that the machine was rebuilt, then remove the old entry.

What is the difference between “connection refused” and “connection timed out”?

Refused means your packet arrived and the host actively rejected it — the machine is up and reachable, and nothing is listening on that port. Check that sshd is running and on the port you think. You get REMOTE HOST IDENTIFICATION HAS CHANGED. What should you do?

Stop and find out why before removing anything. A rebuilt server and an interception produce identical messages. Confirm out of band — the provider console, a colleague, the machine’s new fingerprint from a trusted channel — and only then run ssh-keygen -R hostname. Reflexively deleting the entry because the error message suggests it is exactly the behaviour the check exists to prevent.

Why does Host * belong at the bottom of ~/.ssh/config?

Because ssh applies the first value it finds for each option, reading top to bottom — the opposite of most configuration formats. A Host * block at the top wins for every option it sets, silently overriding every specific host defined below it. At the bottom it does what you intend: supplies defaults for anything not already decided.

What does ssh -L 5433:127.0.0.1:5432 server actually do?

It listens on your port 5433 and forwards anything arriving there to 127.0.0.1:5432 as seen from the server — that is, the server’s own PostgreSQL. So a client on your laptop connecting to localhost:5433 reaches the database, over the encrypted ssh connection, without the database ever being exposed to the network. The middle address is resolved on the far side, which is the part people get wrong.

Why is ForwardAgent yes risky, and what should you use instead?

Because it lets processes on the remote host use your agent to authenticate as you, to anything your keys open. Root on that machine — or anyone who compromises it — can use your keys for as long as you are connected. ProxyJump (-J) solves the usual reason people reach for forwarding: it routes the connection through the intermediate host, with authentication happening locally, so the bastion never sees your agent at all.

15.7 And when there is no package

On curl … | bash, honestly

Half the tools you will want are installed this way, and the position worth holding is neither “never” nor “fine”.

What you are actually doing: executing whatever that URL returns at that moment, with your privileges, unread. A compromised host, a hijacked domain or a malicious redirect all become code execution. There is no signature and no cached copy to audit afterwards.

Why it is not unique: running any installer you did not read is the same trust, and a package from a third-party repository can also run scripts as root. The difference is degree — no signature, no provenance, no record.

The cheap improvement: curl -fsSL URL -o install.sh, read it, bash install.sh. Thirty seconds, and you would notice something obviously wrong.

The real answer: prefer the package manager where the tool is in it. That is the whole point of this chapter.

Checkpoint

Why is a package manager’s signature check stronger than a checksum on a download page?

Because the checksum and the file come from the same place. Anyone who can replace the download can replace the checksum next to it, and it will match perfectly. A package manager verifies a signature against a public key installed with your operating system, obtained through a different channel than the package — so forging it requires the vendor’s private key, not merely write access to a web server. A checksum defends against corruption; a signature defends against substitution.

apt install says a package does not exist, but you can see it on the project’s site. What did you forget?

sudo apt update. apt installs from a local index that is only as fresh as the last refresh, and on a machine that has been off for a while the index can be months old. This is the standing difference from dnf, which refreshes automatically. The pairing to remember: apt update refreshes the list, apt upgrade installs the updates — two commands whose names suggest the opposite division of labour.

Your cron job cannot find node, but it works in your terminal. What is the cause and what is the fix?

nvm. Version managers work by modifying PATH from your shell startup file, and cron reads no startup files — chapter 10. The fix is not to make nvm work under cron; it is to reference the version directly: /home/deploy/.nvm/versions/node/v22.x/bin/node, or a wrapper script that sets up the environment explicitly. A systemd unit with Environment= lines is the tidier version on a modern server.

Why does signed-by= matter when adding an apt repository?

Because without it the key is added to the global keyring, where it can sign packages for any repository — not just the one you added it for. Trusting a vendor for one tool would then let them replace anything on your system on the next update. signed-by= binds the key to that one source, which is why apt-key add was deprecated. It is the difference between “I trust this vendor for this software” and “I trust this vendor for everything”.

Is curl … | bash acceptable?

It is what many reputable projects instruct, and the honest analysis is about degree. You are executing unread code from a server, with no signature and no cached copy — worse than a signed package, comparable to any installer you did not read. Two improvements cost almost nothing: download it, read it, then run it; and prefer the package manager whenever the tool is available there. The position to avoid is treating it as either unthinkable or unremarkable.

In one sentence, how does every version manager work?

It puts a directory at the front of your PATH and changes what that directory contains or points at. nvm edits PATH from a shell function; pyenv and rbenv install shims that dispatch to the chosen version; sdkman repoints a current symlink. Why can cron not find a tool installed by nvm?

Because nvm modifies PATH from your shell startup file, and cron runs a non-login, non-interactive shell that reads no startup files at all. The tool is installed and executable; it is simply not on the PATH cron uses. Do not try to source nvm from the crontab — reference the absolute path to the version you want, or use a wrapper script, or a systemd unit with explicit Environment= lines.

You installed a new version and the old one still runs. What do you check?

type -a, which lists every copy on PATH in the order the shell tries them — the first wins, and it is very often a system package shadowing the managed one, or the reverse. If type -a shows the new one first and the old one still runs, the shell has cached the old location: hash -r, or a new terminal. Both diagnoses are chapter 10.

Why does your editor use a different Python than your terminal?

Because a graphical editor launched from a desktop icon inherits the desktop session’s environment, which was built at login and never saw the PATH your version manager sets in ~/.bashrc. Launch the editor from a terminal, or set the interpreter path explicitly in its settings.

Why do modern Linux distributions refuse pip install outside a virtualenv?

Because the system Python is a dependency of the operating system — package managers, system utilities and desktop components are written in it — and installing or upgrading a library underneath them has broken real systems. The refusal (externally-managed-environment) is deliberate. Use a virtualenv for a project, and pipx for a command-line tool, which creates an isolated environment per tool automatically and still puts the command on your PATH.

What does each part of set -euo pipefail do?

-e exits on a failing command instead of carrying on. -u makes an unset variable a fatal error, which is what stops rm -rf $DIR/* becoming rm -rf /*. -o pipefail makes a pipeline fail if any stage failed, not just the last — without it, curl bad-url | tar xz reports whatever tar said. Together they turn a script that continues wrongly into one that stops where the problem is.

Why #!/usr/bin/env bash rather than #!/bin/bash?

Because env searches PATH, so it finds bash wherever it is installed — which on some BSDs and on macOS with Homebrew is not /bin/bash. The related and more damaging mistake is writing #!/bin/sh and then using bash features: on Debian and Ubuntu /bin/sh is dash, which has no arrays, no [[ ]] and no local, so the script works on your machine and fails on the server with a syntax error.

When you forward arguments to another command, why "$@" and never "$*"?

Because "$@" expands to one properly quoted word per argument, preserving the boundaries — so my report.txt stays a single argument. "$*" joins them all into one string, merging that argument with whatever followed it. In practice "$*" is only right when you genuinely want one string, such as building a log message.

Why mktemp -d rather than /tmp/mybuild?

Because /tmp is world-writable and the name is predictable, so another user can create that path first — as a symlink to somewhere else — and your script will then write through it. mktemp -d creates a uniquely named directory with 700 permissions, atomically, and prints the name. Pair it with trap cleanup EXIT so it is removed however the script ends.

Your script works but shellcheck reports SC2086 twenty times. Does it matter?

Yes, and it is the highest-value warning it produces. SC2086 is an unquoted expansion, which means the value is word-split and glob-expanded before the command runs — so the script is correct only as long as no path contains a space and no value contains an asterisk. It works until the day someone names a folder “Q3 reports”. Quoting costs two characters per site and removes the whole class.

Checkpoint

What does */5 * * * * mean, and what does 0 0 13 * 5 mean?

The first is every five minutes, every hour, every day. The second is the trap: the 13th of the month, or any Friday — not Friday the 13th. When both day-of-month and day-of-week are restricted, cron ORs them; every other combination of fields is ANDed. If you want Friday the 13th you have to test the date inside the job.

Your cron job never runs and there is nothing in any log. Where do you start?

With output, before anything else: change the entry to >> /tmp/job.log 2>&1 so that both streams are captured — most “nothing in the log” reports are really “the errors went to mail that nobody reads”. Then reproduce the environment with env -i HOME="$HOME" PATH=/usr/bin:/bin /bin/sh -c 'yourcommand', which will usually fail the same way at your own prompt. After that, check the script is executable and that the command has no unescaped %.

Why does a systemd timer usually beat cron on a server?

Because it answers the questions cron leaves to you. The environment is stated explicitly with Environment=, output goes to the journal automatically and is retrievable with journalctl -u, systemctl status shows the last run and its exit code, Persistent=true catches up a run missed while the machine was off, overlapping runs are prevented by construction, and systemctl start tests the job exactly as the timer would run it. Cron gives you none of that and asks you to build each one.

A five-minute job sometimes takes seven minutes. What happens, and what do you add?

Runs pile up: at minute 10 a second copy starts while the first is still going, then a third, and the machine slowly buries itself. It usually presents as a load or memory problem rather than a scheduling one. Add a lock — flock -n /tmp/job.lock /srv/app/job.sh in the crontab, so a second run exits immediately — or use a systemd oneshot service, which will not start a second instance while the first is active.

Why is date +%F broken inside a crontab?

Because % has a special meaning there: it marks a newline, and everything after the first one becomes standard input to the command. So date +%F is silently truncated to date +. Escape it as date +\%F, or — better — put the command in a script and call the script, which removes the whole class of crontab quoting problems at once.

Why alert on absence rather than on failure?

Because a failure alert requires the job to run far enough to notice it failed. If the machine is off, the disk is full, cron is not running, or the script died before its error handling, nothing sends anything — and silence is indistinguishable from success. 19.6 Keeping it, and moving it

The if in that script is not a style choice

The obvious way to write that loop is [[ -f "$f" ]] && ln ... && echo ..., and it has a subtle bug that this book hit while writing the listing — though not the one you might expect. When the file is absent the whole && chain returns non-zero. set -e does not abort the script: every command of an AND-list except the last is exempt, and the loop runs to completion.

What happens instead is quieter. The loop is the script’s last statement, so the script exits with the status of its final iteration — 1, because the last file was missing. Everything worked, and the script reports failure. That fails a CI step, breaks an && chain, and sends you looking for a problem that is not there. An if makes the intent explicit and returns 0, which is why the version above uses one.

Keep server configuration minimal, and separate

Resist installing your full local setup on every server. A server you visit occasionally wants a small .bashrc — history settings, a hostname in the prompt, perhaps three aliases — and nothing that needs a font, a framework or a network fetch at startup. Two files in your dotfiles repository, bashrc.local and bashrc.server, with the install script choosing between them, keeps both honest.

Checkpoint

What is the single highest-value keystroke in this chapter?

Ctrl+R. It searches your history backwards as you type, so a command you ran last week is three characters away instead of being retyped from memory. Press it again to step to the next older match. The runner-up is Alt+., which inserts the last argument of the previous command — mkdir -p a/b/c then cd Alt+..

Why can mkcd not be an alias?

Because an alias substitutes text at the front of the line, so whatever you type ends up at the end. mkcd needs its argument twice — once for mkdir and once for cd — which requires a function. The general rule: alias when the argument can only go last, function when it goes anywhere else, when there are several commands, or when you need a conditional.

Your script relies on your rm -i alias for safety. What happens when it runs?

Nothing safe: the real rm runs. Scripts are non-interactive shells and do not read ~/.bashrc, so your aliases do not exist there — which is correct, because a script that behaved differently depending on who ran it would be far worse. Safety in a script comes from set -u, from checking before deleting, and from printing what will be removed first.

Your coloured prompt garbles when you recall a long command. What is missing?

The \[ and \] markers around the escape sequences. They tell readline that those bytes take up no screen width; without them the shell miscounts the cursor position, so a recalled line that wraps overwrites the prompt or leaves fragments behind. Every colour code in PS1 must be wrapped, including the reset.

Why run tmux the moment you ssh to a server?

Because your connection becomes irrelevant to whether the work survives. The session runs on the server; if your laptop sleeps or the wifi drops, the shell keeps its terminal and the job continues, and tmux attach puts you back exactly where you were. It costs nothing when nothing goes wrong, and it also lets a colleague attach to the same session and see your screen — the fastest form of pair debugging on a production box.

strace is the tool for “it is doing nothing and I do not know why”

strace -p PID attaches to a running process and prints every system call it makes. A process that appears hung will show you exactly what it is blocked on — a read on a socket, a flock that never returns, a connect to an address that is not answering. strace -c summarises instead, counting calls and time, which finds the program opening the same file forty thousand times.

It is slow (every call is intercepted), it needs privileges for other users’ processes, and on macOS the equivalent is dtruss, which System Integrity Protection restricts. But when the question is “what is it doing”, nothing else answers it as directly.

Checkpoint

A container exits with 137 and the application log ends mid-sentence. What happened?

It was killed with SIGKILL — 137 is 128 + 9 — and in a container that overwhelmingly means the out-of-memory killer. SIGKILL cannot be caught, so the process had no chance to flush its log or write a shutdown message, which is exactly why the log stops mid-sentence and explains nothing. The evidence is in the kernel, not the application: dmesg -T | grep -i "killed process", or OOMKilled: true in docker inspect. Look at the memory limit.

df says the disk is full but the files you can find add up to far less. Two explanations?

Deleted but still open: a process holds a descriptor on a file whose name is gone, so the space is not freed. lsof +L1 lists them; restarting the process releases the space, and truncating with : > file instead of deleting avoids the problem entirely. Out of inodes: a filesystem has a fixed number of them, one per file, and millions of tiny files can exhaust them while gigabytes remain free. df -i shows it, and the message is identical.

Load average is 40 and the CPUs are idle. Where do you look?

At storage, not at code. Linux counts processes in uninterruptible sleep — blocked on I/O — toward the load average, so a slow disk or a stuck network mount produces a very high load with no CPU use. vmstat 1 and iostat -x 1 confirm it, and processes in state D in ps are the ones waiting. Nothing in your application will explain it.

rm *.log fails with “Argument list too long”. Why, and what works?

Because the shell expands the glob into every matching filename and hands them to rm as one argument list, and the kernel caps the size of that list for a single exec. With enough files it simply will not fit. find . -maxdepth 1 -name '*.log' -delete never builds one, and find ... -exec rm {} + batches into as many invocations as it needs. Note that the limit depends on total size, so long filenames hit it sooner.

What is the first question of the method, and why does it matter most?

What changed? Because almost everything that is broken now was working recently, so the cause is usually in the difference rather than in the system as a whole. “Nothing changed” is nearly always false — a package updated, a certificate expired, a disk filled, a token rotated, someone merged something. ls -lt on the relevant directory, the package manager’s history, and your own shell history with timestamps will usually find it faster than reasoning from first principles.

When should you stop debugging and restart the thing?

A restart is a legitimate move when you need service back now and understanding can wait — but it destroys the evidence, so gather what you can first: the exit code, the last hundred log lines, ps state, and a dmesg tail take about twenty seconds together. The failure mode to avoid is restarting reflexively, because the problem recurs at 3am and you have no more information than you did the first time. If you restart, write down what you saw beforehand.

Is it worth learning strace properly?

Worth knowing it exists, worth using strace -c and strace -p, and rarely worth going deeper. The two invocations that pay for themselves are attaching to a process that appears hung — which shows you precisely what it is blocked on — and the summary, which finds the program opening the same file forty thousand times. Beyond that you are usually better served by the application’s own instrumentation. On macOS the equivalent, dtruss, is restricted by System Integrity Protection and is much less practical.
