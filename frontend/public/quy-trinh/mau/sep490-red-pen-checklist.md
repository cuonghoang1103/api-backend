# Pre-submission Checklist – 10 Red-Pen Errors

> **Purpose:** the ten mistakes lecturers circle in red most often, checked before every report submission. Tick each line with evidence (where you checked).
> **Guide:** in CT Work, School › Submission check runs most of these automatically (use case names vs issues vs WBS, codes that do not exist, template text left over). Do the rest by hand.

## 1. The ten checks

| # | Check | How to verify | Done | Evidence |
|---|---|---|---|---|
| 1 | Use case names are identical in the SRS, the issues and the WBS | School › Submission check | ☐ | |
| 2 | Every UC/BR/SM code used in the text exists in the registers (no BR-17 when there are 12 rules) | Requirements › Six links + Submission check | ☐ | |
| 3 | No template text left: "<…>", "Feature name", "TBD", "Member 1", "TABLE_NAME" | Submission check | ☐ | |
| 4 | Use case flows use the system's name, never the word "System" | Six links › UC lint | ☐ | |
| 5 | Alternative/Exception step codes (4A, 8E1) point to real Normal Flow steps | Six links › UC lint | ☐ | |
| 6 | Postconditions describe data state only — no BR-xx or SM-xx inside | Six links › UC lint | ☐ | |
| 7 | One system message per case (SM-xx), each used by a use case | Requirements › System messages | ☐ | |
| 8 | Every NFR has a scale, a meter and a Must value | Requirements › Quality (NFR) | ☐ | |
| 9 | Test totals and pass rates in the report equal the test data (5.1/5.2/5.3) | Report 7 › Assemble (cross-checks) | ☐ | |
| 10 | Record of Changes lists every implemented change request | Docs › Fill from project data | ☐ | |
